# The family rule and the audit loop were bounded (7.0)

Two rules, each sound alone, multiplied. *The ask names a site; the design
answers the family* required every member of a family — about seven edges,
several backends, a dozen decorator pairs — to be built, refused with a compile
error and a snapshot, or raised as an owner question, and a defect found at one
member to be fixed at all of them. *Run /audit again after fixing what it found*
had no severity bar and no stop: an adversarial audit never returns zero, and
each fix is new code. A third rule closed every finding with a new rule sentence
and, where mechanical, a new conformance join.

The result during 7.0: the rules corpus grew from about 4,400 to 6,200 lines,
the scanner from 7.2k to 17.9k, and three audit rounds produced 79 findings in
the last, about a quarter of them against the scanner itself. The owner
memory recording an admin port and gauges built because rules "widen every need
to its whole family", then removed, is the same mechanism.

Now: decide for the family, build for the caller, list the other members in the
commit body; security and data-integrity fixes stay family-wide. An audit runs
once, on risk, with impact severity and a written threat model; only P0/P1 fixes
are re-audited, once. A finding is fixed with its regression test, and a rule
changes only on contradiction or recurrence.
