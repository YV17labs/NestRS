# Docs site — STYLE.md is the law

`docs/STYLE.md` is the single source of truth for docs prose and
structure — **read it before writing or editing any page**, then start
from the matching skeleton in `docs/templates/` (T-CONCEPT, T-INDEX,
T-TUTORIAL, T-RECIPE, T-SINGLE). This file carries only the traps a
session hits before it thinks to look.

On conflict about prose, `STYLE.md` wins; about code or naming,
`CLAUDE.md` wins.

## The caps the linter greps (CI-enforced)

- **≤ 3 Asides per page.** Reference page ≤ ~250–300 lines answering
  ONE question; tutorial ≤ ~250 lines ending on a runnable checkpoint.
- First screen: one working snippet ≤ ~15 lines, **no Aside above it**.
- Verbatim outputs real (run once, paste), trimmed to ≤ ~8 lines.
- Controlled H2 vocabulary in canonical order (`Install` → `Run it` →
  `Wire it in` → … → `Configuration` → `Limits` → `What fails if you
  get it wrong` → `Reference` → `Going further`); the closing block is
  `## Going further` (utility pages exempt).
- Banned words: *blazing(ly), powerful, seamless(ly), simply,
  effortless(ly), easy, magic(al)*. No exclamation marks in prose.
- **Example canon = the Publish universe only** (hello, blog/posts,
  users/orgs, chat/notify, audio, weather, media). The ban list
  (`items`, `products`, `artworks`, `file_assets`, `Ledger`, …) must
  stay at zero — never invent a feature.
- **Code-truth checks** — twenty of them, each a shipped defect on a
  released page. **The list is not restated here**: it lived in three
  places (the linter, STYLE.md § F, and this file), nobody kept the three
  in step, and seven rules ended up in only the first. The population is
  `RULES` in `lint-docs.mjs`; STYLE.md § F documents it and
  `scripts/lint.test.mjs` fails when the two disagree. Read § F.

## `docs/canon.json` — the facts, derived once, in Rust

**Every code-truth check reads it, and the linter derives nothing.** The
file is generated by `nest-rs-conformance`'s `canon` join and committed:
capabilities, decorators, `pub trait _: Layer`, the trait surface, the
test count, the version requirement, the OTel binding, the queue
envelope keys, every `#[config]` struct's fields, the architecture
rules' two restated regions, and every demo file with the port it pins.

Seven checks used to open `crates/**` and `demo/**` and re-derive those
in JavaScript with regexes. That is two implementations of one
definition, and it shipped: the linter counted 27 capabilities against a
landing that correctly said 28, while its own comment claimed the two
derivations could not disagree.

Three consequences bind how you work here:

- **Never re-derive in the linter.** A check needing a new fact adds a
  field to the `canon` join; a `readFileSync` outside `docs/` is the
  defect this seam removes. The linter's input set is `docs/**` exactly,
  which is what makes the workflow's `paths:` filter a true declaration.
- **Touching `crates/` can fail `docs/`.** The join rewrites the file and
  fails until it is committed, so a framework change that moves a
  documented fact carries a `docs/` diff — deliberately, since that diff
  is what makes the docs job fire on the commit that caused it instead of
  on the next unrelated docs edit.
- **Never hand-edit it.** The join asserts it equals the tree; an edit is
  overwritten on the next run.

**Two shapes travel, and the rule picking between them is the shared
grammar.** A fact whose comparison needs no grammar travels *extracted*
(a decorator list, checked with `includes`). A fact whose comparison runs
the *same* extractor over both sides travels *raw* — `architecture` is
the only one: the join slices the rules file into the role-table rows and
the reserved-vocabulary block and tokenizes neither, because what a role
token *is* has one definition and it lives on the page side.

- **`landing-claim`** — the one written before its defect rather than
  after it. The landing argues the framework with four figures, so all
  four are derived: capabilities and tests from the canon, decorators
  from the decorator index, pages from the content tree. Exact counts
  must agree; a `+` floor may lag inside a band and no further. Deleting
  a figure is deleting its gate, and the rule reports that too.
  **A capability is a feature a developer can type after `--features`** —
  not a crate. The two number the same today by coincidence and did not
  before; `sources::UmbrellaMatrix` holds both and names each.

## Gotchas no page shows

- **Snippets are hand-written.** There is no `<Code file=…>` /
  `examples/` extraction. (This used to cite the docs README as
  describing one aspirationally; `39ae06f0` removed that passage, so the
  citation was stale while the substance stayed true.) A fence `title=`
  naming a real repo path must match
  the file **byte-for-byte** or say "(abridged)"; fictional snippets
  get generic `src/…` titles, never a real-looking path. Titles cite
  the user's workspace shape (`crates/features/…`); GitHub URLs use
  real repo paths (`demo/crates/features/…`).
- **The linter is baseline-gated**, and the contract is now enforced
  rather than promised: `npm run lint:docs` fails on a violation not in
  `docs/scripts/lint-baseline.json` **and** on a baseline line naming a
  violation since fixed. **`--update-baseline` is gone** — it
  re-snapshotted every violation, code-truth ones included, so the remedy
  the failure message printed turned a proven-false public claim into a
  permanent exemption. Fix the page; if a line genuinely belongs in the
  baseline, add it by hand where a reviewer sees it.

## The linter is joined against itself

Its rules are a family and `scripts/lint.test.mjs` is their join. Every
member of `RULES` owes three cells: **a fixture that makes it fire**, a
**STYLE.md § F entry**, and no violation naming anything outside the set.
Adding a rule without a fixture fails; weakening one until it matches
nothing fails; documenting one that does not exist fails.

That join is the reason the rest is trustworthy. Before it, thirty rules
had no proof they still fired — neutralise any regex and the gate went
*greener*, which is the state `.claude/rules/testing.md` calls worse than
an empty cell.

**A fixture proves the rule triggers, never that its judgement is right.**
That is `/audit`'s question and the two do not substitute.

## Definition of done here

`cd docs && npm run lint:docs && npm test` — plus `npm run build` if you
touched config, components or styles. Deploy is `docs-pages.yml` on push; there
is no other docs CI.

**And it runs the other way too.** A change under `crates/` that moves a
documented fact fails `cargo nextest run -p nest-rs-conformance` until
`docs/canon.json` is regenerated and committed — the framework's own
*Definition of done* is what keeps the docs' facts current, so no CI has
to watch `crates/` on the docs' behalf.
