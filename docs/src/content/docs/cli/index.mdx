import { Aside, FileTree } from '@astrojs/starlight/components';

The **`nestrs`** CLI scaffolds one layout: a workspace — `crates/features/` for
your domain, `apps/*` for the binaries that serve it. **`nestrs new` reads the
directory tree** to know whether it is creating that workspace or adding an app
to one you already have; there are no mode flags and no config file. Generated
code follows the same decorators as the framework repo (`users/` for features,
`api/` for composition apps).

<Aside type="caution">
  The CLI ships on crates.io as **`nest-rs-cli`** (binary name **`nestrs`**),
  lockstep with the other `nest-rs-*` crates.
</Aside>

## Install

```bash
cargo install --locked nest-rs-cli
nestrs version
```

A binary, so it is the one thing that does not come through the `nest-rs`
umbrella — there is no `--features cli`.

Requires **Rust 1.97+** (edition 2024). That single install is all you need: the
first time you call [`nestrs run`](#running-tasks), the CLI installs the dev
toolchain it drives — `just`, `bacon`, `cargo-nextest`, `cargo-llvm-cov` — once.
Run **`nestrs doctor`** after install to check the Rust toolchain and list
optional `<PREFIX>_*` environment variables.

## Layout detection

`nestrs new` infers where you are and what to create. There is **no**
`nestrs-cli.yaml` — the workspace shape is already declared in the root
`Cargo.toml` (`members = ["crates/*", "apps/*"]`). The CLI walks up from the
current directory (or `-o` path) and reads that manifest.

| Where you run | Command | Result |
|---|---|---|
| Outside a nestrs workspace | `nestrs new hello` | Monorepo at `./hello/` + `apps/hello/` on port **3000** |
| Inside a nestrs workspace | `nestrs new blog` | Thin app at `apps/blog/` — **next free port** in `apps/blog/.env` |

If `apps/blog/` already exists, the CLI stops with ``app `blog` already exists at
<path>``: it does not overwrite.

<Aside type="note">
  No extra config file to maintain. Cargo's workspace manifest is the single
  source of truth; the generators use the same discovery as `nestrs new`. If you
  ever need to tune defaults, an **optional** `[workspace.metadata.nestrs]` table
  in the root `Cargo.toml` accepts `port-base` — never required, every key has a
  default.
</Aside>

## Create a project

```bash
nestrs new hello
cd hello
nestrs run dev hello
```

Open **http://localhost:3000/** — `Hello World`. Logic in
`crates/features/src/hello/`; `apps/hello/` composes modules only.

<FileTree>
- hello/
  - Cargo.toml
  - Justfile
  - test.just
  - db.just
  - compose.yml
  - .env
  - .env.development
  - .env.test
  - .env.example
  - .gitignore
  - rust-toolchain.toml
  - README.md
  - AGENTS.md the conventions every coding agent reads
  - CLAUDE.md imports AGENTS.md
  - crates/
    - features/
      - Cargo.toml
      - src/
        - hello/
          - http/…
          - service.rs
        - lib.rs
    - migrations/ SeaORM migrations + the `migrate` binary
    - seed/ the `seed` binary
  - apps/
    - hello/
      - .env the port
      - src/
        - lib.rs
        - main.rs
        - module.rs
      - tests/
        - integration/main.rs
        - e2e/main.rs
</FileTree>

The `e2e` suite is scaffolded **empty**. It has to exist: `nestrs run test integration`
filters on `not binary(e2e)` and `nestrs run test e2e` on `binary(e2e)`, and
nextest rejects a filterset naming a binary the workspace does not have.

**Grow the workspace** (from the workspace root or any sub-folder):

```bash
nestrs new blog
nestrs g resource posts title:string body:text --app blog
```


**`rust-toolchain.toml`** is what makes every recipe run on a project minutes
old. It pins Rust 1.97 as the toolchain `channel`, plus three components, each
because a recipe shells out to it:

- **`clippy` and `rustfmt`** are what `nestrs run lint` runs. Undeclared, they
  are present only because rustup's *default* profile happens to install them —
  so the recipe works on your machine and fails on a `minimal` one.
- **`llvm-tools-preview`** carries the `llvm-cov` and `llvm-profdata` behind
  `nestrs run test cov`. Those two read a `.profraw` only when they come from
  the same LLVM as the rustc that wrote it, so they are pinned here, beside
  `channel`, rather than installed once per machine: following the channel is
  what keeps the two versions married.

Rustup is what reads that file. On a toolchain installed any other way it is
inert — point `LLVM_COV` and `LLVM_PROFDATA` at your own binaries instead.

### One starter, no template flag

There is nothing to choose. Every path out of `nestrs new` writes the same
**`hello` module** — a service with a greeting and one `#[public] GET /` that
returns it:

| What you run | What you get | `GET /` |
|---|---|---|
| `nestrs new acme` | monorepo + `hello` feature + `apps/hello/` on 3000 | `200 Hello World` |
| `nestrs new blog` (inside one) | `blog` feature + `apps/blog/` on the next free port | `200 Hello World` |

A freshly created project has to prove it started, and a `404` proves nothing to
someone looking at a browser — so there is no routeless variant to pick. Delete
the feature once you have a real one; `nestrs new blog` refuses if a `blog`
feature already exists, rather than overwriting it.

Ports: the CLI reads the port each existing app listens on and writes the next
free one into the new app's own `.env` (same pattern as `auth` → 3001, `api` →
3002, …). The workspace's root `.env` files do **not** set
`<PREFIX>_HTTP__PORT`, and no `module.rs` pins it — a pin would take the app's
whole HTTP namespace off the `.env` cascade:

```bash title="apps/api/.env" frame="terminal"
NESTRS_HTTP__PORT=3002
```

An app's own files are read over the root's under the `development` and `test`
profiles ([an app's own files](/configuration/env-cascade/#an-apps-own-files));
a deployment sets the port on the process.

Optional: **`--check`** runs `cargo check` after generation.

### Add an app to an existing workspace

From the workspace root (or `apps/`, `crates/features/`, …):

```bash
nestrs new blog
nestrs run dev blog
```

Creates a **thin** app under `apps/blog/` — composition root only, no
`service.rs` / `controller.rs` in the app crate — plus the `blog` feature it
serves under `crates/features/src/blog/`. That split is why the greeting is a
feature rather than a controller in the app: the layout keeps no business logic
in an app crate, so the same rule that governs your code governs the starter.

## Running tasks

Every project task runs through **`nestrs run <recipe>`** — the single front
door. It forwards the recipe and its arguments verbatim to
[`just`](https://github.com/casey/just), which reads the `Justfile` the
scaffolder wrote:

```bash
nestrs run dev               # watch mode (rebuild + restart on save)
nestrs run test integration  # in process, no database
nestrs run db up             # apply migrations
nestrs run                   # list the available recipes
```

The recipes are yours to edit. Add your own to the `Justfile` and they run the
same way — `nestrs run deploy`, `nestrs run docker-up`, whatever you write. The
framework owns the recipes it ships; you own the rest.

The **first** `nestrs run` installs the toolchain it drives (`just`, `bacon`,
`cargo-nextest`, `cargo-llvm-cov`) once — all of it, whichever recipe you asked
for, so no recipe is ever a step behind. On CI, where you provision tools
yourself, set `NESTRS_NO_BOOTSTRAP=1` or pass `--no-bootstrap` — a missing tool
then fails with the manual install command instead of fetching anything.

## Build

Release binaries land in `target/release/`. **`nestrs run start`** compiles and
starts the server under the production profile, so it reads no
`.env.development`: the database and queue URLs are the deployment's to set.
Use **`nestrs run build`** when you only need the artifact (Docker, CI, or
copying the binary elsewhere).

```bash
nestrs run build              # default app (hello)
nestrs run build blog         # after nestrs new blog
nestrs run build --all          # every app in the workspace
nestrs run start hello        # build + run in release
```

## Generate features and adapters

Generators scaffold under `crates/features/src/<name>/`, register
`pub mod …` in `crates/features/src/lib.rs`, and wire what they wrote into the
app that serves it, from wherever in the workspace you run them. That app is
the one **`--app <name>`** names, else the one your directory is in, else the
workspace's only app; with several apps and none named, the generator writes
the feature, wires nothing, and lists the apps and the imports to write. Every
command takes **`--dry-run`** (print what would change, write nothing) and a
**`-p`** path override (default: auto-discover from the current directory).
Re-running a generator is safe: it refuses to overwrite an existing feature or
adapter, and the wiring edits are idempotent.

A **port** is the transport-agnostic core (service + module). An **adapter**
bolts one transport onto a port. A **resource** is a DB-backed CRUD port plus its
HTTP adapter in one shot.

```bash
# Port only (service + module, no transport)
nestrs g feature posts

# DB-backed CRUD: #[expose] entity + CrudService + guarded #[crud] controller,
# its table's migration and, in the app serving it, its round trip — all from
# the one column list. Bootstraps the auth adapter below when the workspace has
# none — its routes name AuthnGuard/AuthzGuard, so they would not compile
# without it.
nestrs g resource posts title:string body:text published_at:datetime:nullable

# One #[expose] entity in an existing feature — no controller, no auth
# bootstrap. The name after the slash is the entity's own when the feature's
# singular is not it.
nestrs g entity posts             # → Post, in posts/entity.rs
nestrs g entity posts/comment     # → Comment

# The app's authn/authz adapter — Claims, AuthnGuard, AuthzAbility, AuthzGuard.
# Run it *before* the first `g resource`, or not at all: it refuses when
# `crates/features/src/authz/` already exists. It draws a random HS256 secret
# into the git-ignored `.env.local` and another into `.env.test`, read only by
# the test suites; the committed `.env` gets no secret. Neither is written where
# a file of the same runs, `.env` included, already sets a `<PREFIX>_AUTHN__`
# variable: a secret beside your own key would fail the boot.
nestrs g auth

# A SeaORM migration, registered in lib.rs and migrator.rs. `create_<table>`
# over a table an entity declares creates the columns its Model does, and its
# key's default; any other name writes the create-table skeleton to fill. A
# name registered already, or a table a registered `create_` migration creates
# (`create_post` after `create_posts`), is refused: the next change to a table
# takes a name of its own.
nestrs g migration create_comments
nestrs g migration add_status_to_posts

# The framework's own migration, the outbox's table: one migrator.rs entry, no
# file. The `nestrs_` prefix is the framework's: any other `nestrs_` name, and a
# resource or an entity whose table would take it, is refused.
nestrs g migration nestrs_outbox

# Bolt a transport onto an existing port
nestrs g http posts        # controller
nestrs g graphql posts     # resolver
nestrs g ws posts          # gateway
nestrs g queue posts       # processor, and the outbox's migration
nestrs g schedule posts    # scheduled tasks
nestrs g mcp posts         # MCP tool
nestrs g events posts      # event listener, with its event at the port
```

`g graphql` and `g mcp` also write that transport's **authz module** under
`crates/features/src/authz/` when the workspace has a policy to enforce, and the
adapter imports it. It is not optional wiring: `/graphql` and `/mcp` run the guards
a module declares at their request, so without it `/mcp` denies every call and
`/graphql` runs operations with no ability attached. `g ws` writes none: a
gateway's module imports `AuthzModule`, which `g auth` wrote, and that brings the
guards whose ability crosses the connection and scopes its rows.

`g queue` also registers the framework's outbox migration in
`crates/migrations`, when the workspace keeps that crate. The queue it enables
keeps a job pushed inside a transaction in the outbox's table until the commit,
and an app binding SeaORM beside a queue refuses to boot without the table:
`nestrs run db up` creates it.

<Aside type="note">
Generated entities default to wire-only `#[expose]` (no GraphQL tokens) — see
[HTTP-only resources](/database/#http-only-resources). `nestrs g graphql` on a
resource port adds the `graphql` flag and the crate features that flag needs, so
the entity becomes a GraphQL object at the moment something asks for one.
</Aside>

Each adapter delegates to the port's service, so a freshly-generated port plus
any adapter compiles immediately — the handler is the seam you fill in. Its
`module.rs` imports the port and the module providing its guards, and the
handler's decorator brings what serves its edge (`HttpModule`, `GraphqlModule`,
`WsModule`, `McpModule`, `QueueModule`, `ScheduleModule`), so an app importing
the adapter serves it, reads its edge's configuration and imports nothing
more; `g events` imports `EventsModule` into the
port that emits. The app's root keeps only the bindings it chooses, and the
generator writes them there, in the same edit as the adapter, when the root has
none. The queue's backend is one: `g queue` writes `RedisQueueModule`, which
imports the Redis connection it runs on. The data layer is the other: a `#[crud]`
handler — `g resource`'s controller, `g http` or `g graphql` over a resource
port — runs each call in the unit of work `SeaOrmDatabaseModule` binds, so the
generator writes it, and it imports the pool. A root already naming a binding —
bare, pinned with `for_root`, or a named instance — keeps its own line, as one
pinning a resource does. And the auth adapter's token route: a generator that wrote the adapter on the way
writes `AuthnHttpModule`.

```text frame="terminal"
$ nestrs g resource posts --app blog
…
  3. PostsHttpModule is wired into `blog`, beside SeaOrmDatabaseModule and AuthnHttpModule.
```

### The columns `g resource` takes

Each column after the name is `<name>:<type>`, the field grammar Rails' and
Phoenix's generators share, or `<name>:<type>:nullable` for one a row may leave
empty; with none, a resource gets one `name:string` column. The key and the
three timestamps come with every table, so no list names `id`, `created_at`,
`updated_at` or `deleted_at`.

| Type | Field | Column | The round trip posts |
|------|-------|--------|----------------------|
| `string` | `String`, at least one character | `varchar` | `"Title 1"` |
| `text` | `String`, `column_type = "Text"`, at least one character | `text` | `"Body 1"` |
| `integer` | `i32` | `integer` | `1` |
| `bigint` | `i64` | `bigint` | `1` |
| `float` | `f64` | `double precision` | `1.5` |
| `boolean` | `bool` | `boolean` | `true` |
| `uuid` | `Uuid` | `uuid` | a UUID |
| `date` | `Date` | `date` | `"2026-01-01"` |
| `datetime` | `DateTimeWithTimeZone` | `timestamptz` | an instant |

One list writes three files that must agree, and a column typed four times by
hand is four chances to disagree: the entity's field, exposed as an input of
both writes; the migration's `ColumnDef` and `DeriveIden` variant; and the
round trip's body, which writes a value of each column and reads each back. A
name the grammar does not read, a type it does not know, a column named twice
or a house column is refused before anything is written. A column added later
goes into the entity, and into a migration of its own — `nestrs g migration
add_<column>_to_<table>` writes the file to fill.

### Why `g resource` is guarded

`g resource` emits the `#[crud]` + `#[use_guards(AuthnGuard, AuthzGuard)]` form,
and scaffolds the `g auth` adapter when the workspace has none. That is not
hardening you can defer: `Repo` filters every read by the caller's ambient
[`Ability`](/security/authorization/), which only the ability guard installs, so
an unguarded DB-backed controller mounts its routes and then serves nothing.

A generated resource therefore answers **401** without a token and **403** until
[`AuthzAbility`](/security/authorization/) grants a rule for its entity — the line
the generator prints. A resource meant to be readable without a login is
the same slice with one route marked `#[public(Read, Entity)]` and a rule in
`define_visitor`; see [Public reads](/security/authorization/public-reads/).
Before inventing a second layout, open
[`crates/features/src/orgs/`](https://github.com/YV17labs/NestRS/tree/main/demo/crates/features/src/orgs)
side by side with what the generator emitted.

### Where `g entity` puts the file

A module keeps its entities in one of two shapes, and the generator reads
which one you are in rather than asking. A feature with no entity yet gets
the lone `posts/entity.rs`. A feature already keeping several in
`posts/entities/` gets one more file there, named for the singular —
`comment.rs` beside `post.rs`.

Growing from the first shape into the second, it moves `entity.rs` to
`entities/post.rs` (named for its table) in the same run: the moved file's
`super::` paths gain the level it gains — those SeaORM spells inside string
literals included — `mod.rs` declares `entities` and keeps re-exporting the
first entity flat, so `crate::posts::Entity` still names it, and every path in
the feature that named `entity` names `entities::post`. A reference it cannot
rewrite with certainty — the module imported by name, a `super::` count that
does not reach the feature, an inline module in the moved file — refuses the
run before anything is written, naming its file and line.

The entity it writes names **no service**. `#[expose(service = …)]` points at the
one [`CrudService`](/database/crud/) whose `Entity` is this entity, `g entity`
writes no service, and a plain `g feature` port's service is not one — so the
link is yours to add, and the printed next steps spell the line. Reach for
`g resource` instead when you want the entity, the service and the guarded
controller together.

### `g graphql` over a resource carries the same guarantee

The GraphQL adapter for a resource port is the `#[crud]` resolver behind the
ability guard — `#[use_guards(AuthzGuard)]` alone, since `AuthnGuard` checks
HTTP requests only and a resolver refuses it at compile time — and it comes with
the endpoint guards that authenticate the `/graphql` request:
`crates/features/src/authz/graphql/` plus the `AuthzGraphqlModule` import in the
adapter's `module.rs`. That folder is not optional decoration — no controller
owns `/graphql`, so the guards its module declares are the only thing that
authenticates the caller and attaches the ability the resolvers read.

### A generated operation is never open

Over a port with no entity, `g graphql` and `g mcp` still write a gated
operation: they declare the port's capability with
[`#[subject]`](/security/authorization/policies/#subjects-no-table-holds) beside
its service — `crates/features/src/posts/subject.rs`, `pub struct Post;`,
written once by whichever adapter comes first — and gate the query or the tool
on it with `#[authorize(Read, Post)]`, behind the same guards and authz module
as the resource form. It answers `FORBIDDEN` until your policy grants it,
`ab.can(nest_rs::authz::Action::Read, crate::posts::Post)`, which the printed
next step spells.
A port with an entity but no service gates on that entity instead. The file is
`subject.rs` whatever the port's name, so `subject` is one of the words
[no module takes](/architecture/#what-a-folder-may-not-be-called).

A subject masks nothing, so an operation that starts answering with rows is
re-gated on their entity, `#[authorize(Read, PostEntity)]`. `g entity posts`
does it: the entity's wire type takes the subject's name, so the run retires
`subject.rs` and its two lines in `mod.rs`, and gates on `crate::posts::Entity`
each operation `g graphql` and `g mcp` gated on `Post`, in the same
transaction. The grant stays yours — the run prints the line to write in
`authz/ability.rs` where you granted `crate::posts::Post`, and until you do the
operations answer `FORBIDDEN`. A subject or an operation you edited beyond what
the generator wrote is yours too: the run refuses, naming the file.

### A generated route or socket is never open

`g http` and `g ws` bind `#[use_guards(AuthnGuard, AuthzGuard)]` on the
controller or gateway over a plain `g feature` port too, import the transport's
authz module, and scaffold the `g auth` adapter when the workspace has none, as
`g resource` does. A route those guards cover needs no posture of its own, and
the boot refuses one no guard covers, so an opening is always a line you write:
`#[public]` on the route that is open on purpose. A gateway's guards run at the
upgrade and cover its messages the same way.

## Doctor

```bash
nestrs doctor
```

Checks:

- `rustc` ≥ 1.97 and `cargo` on `PATH`
- whether the current directory sits inside a nestrs workspace
- optional env vars (`<PREFIX>_SEAORM__URL`, `<PREFIX>_REDIS__URL`, …), read as an
  app started in the same shell and directory would read them — the real
  environment over the `.env` cascade, inline or through `<NAME>_FILE`. A value
  the app would refuse at boot — a `_FILE` naming a file it cannot read, a
  variable given both ways — is a blocking issue, and a `_FILE` naming a file
  that holds nothing is `not set`.

`nestrs doctor -p apps/<app>` reads one app as `nestrs run` starts it: from the
workspace's root, its own `apps/<app>/.env*` over the root's files under the
`development` and `test` profiles
([an app's own files](/configuration/env-cascade/#an-apps-own-files)).

Use it after install and before running DB- or Redis-backed apps.

## Lint

```bash
nestrs lint
```

Doctor asks whether the machine is right; lint asks whether the code is. It
runs the one naming rule of your project's `AGENTS.md` that a path cannot
derive: **a file's stem against the types it declares**.

One shape is refused, and only one — a stem that reaches *nothing* the file
declares:

```
nestrs lint

  crates/features/src/principal.rs
    `principal` reaches none of `DeskOperator`
    name the file from the type, or split it — a stem that reaches nothing
    is a slot, and a slot fills
```

That file was named for a *slot* — "who acts", "what we pass around" — rather
than for a subject. A slot has no admission test, so the next type about that
slot lands there too; it is a `shared/` folder at the scale of a file. And it
is invisible from outside, because both names read perfectly well alone and
only the pair is wrong.

Everything short of that passes. The word may come from the folder rather than the file —
`throttler/store.rs` holding `RedisThrottler` — or from the folder's singular,
read the way `nestrs g` reads it: `cities/subject.rs` holding `City`. An inflection is the same
word (`scope.rs` holding `Scoped`), and so is an abbreviation (`context.rs`
holding `Ctx`). And a file whose principal export is a function is a
namespace that owes no pairing at all: `queue/consume.rs` exporting
`consume::attempt`.
Files a table already names — `service.rs`, `controller.rs`, `registry.rs` —
are named by that table and are not this rule's business.

It exits non-zero on a finding, so it belongs in CI: the scaffolded `lint`
recipe already runs it, and `nestrs run lint` is the front door.

The demo holds itself to it through the same code: its `lint` recipe runs the tree's
`nestrs lint` in CI.

## Version, about, info, and update

```bash
nestrs version
# → NestRS x.y.z

nestrs about
# → version, tagline, docs, repository, license, author

nestrs info
# → layout, name, root, framework pin, apps, features, env prefix, toolchain

nestrs update
# → checks crates.io; skips when already on the latest version

nestrs update --force
# → cargo install --force --locked nest-rs-cli (reinstall even at the same version)
```

`about` is the framework — the same lines on every machine. `info` is the tree in
front of you: which layout you are standing in, the apps and features it holds,
the `nest-rs` version its manifests pin, and which app a generator would wire
into. It reports the root relative to where you ran it, and outside a project it
says so rather than failing.

Contributors inside the monorepo clone install the tree's CLI directly:

```bash
cargo install --locked --path crates/nest-rs-cli --force
```

## Command reference

| Command | Description |
|---------|-------------|
| `nestrs new <name>` | Monorepo at `./<name>/`, or app at `apps/<name>/` when already inside one |
| `nestrs new <name> --check` | Run `cargo check` after scaffolding |
| `nestrs doctor` | Toolchain and env sanity check |
| `nestrs lint` | Every file named for what it declares |
| `nestrs version` | Print the CLI version |
| `nestrs about` | Print NestRS metadata (tagline, docs, license, author) |
| `nestrs info` | Report the project the current directory sits in |
| `nestrs update` | Install latest CLI from crates.io when a newer version exists |
| `nestrs update --force` | Reinstall from crates.io even when already on the latest version |
| `nestrs g feature <name>` | Transport-agnostic port in `crates/features/src/` |
| `nestrs g resource <name> [<column>:<type>[:nullable]…]` | DB-backed CRUD port + guarded HTTP adapter, its table's migration and round trip (deps auto-added) |
| `nestrs g entity <feature>[/<name>]` | One `#[expose]` entity in an existing feature |
| `nestrs g auth` | The app's authn/authz adapter — one per workspace |
| `nestrs g migration <name>` | SeaORM migration, registered in `lib.rs` and `migrator.rs`, its columns an entity's for `create_<table>`; `nestrs_outbox` registers the framework's own |
| `nestrs run [<recipe> [args…]]` | Run a project task through `just`; bare, list the recipes |
| `nestrs g http\|graphql\|ws\|queue\|schedule\|mcp\|events <name>` | Add one transport adapter to a port |

Every generator accepts **`--dry-run`** and **`-p <path>`**; the ones that wire
an app (`resource`, `auth` and the adapters) also take **`--app <name>`**.
Aliases: **`nestrs g`** = **`nestrs generate`**.
**All of them require a workspace**, which is what `nestrs new` writes.

## Move an existing crate into a workspace

Bringing a crate you already have — a small service, a prototype — under
`crates/features/` is a handful of file relocations. There is no `nestrs
migrate` for it: doing it by hand keeps you in control of the app boundary you
are introducing.

The one thing to know before you start: **`nestrs new <workspace>` already
writes a `hello` feature and a `hello` app** — the starter that proves the
workspace runs. Move the incoming crate in under its **own** name. `mv` does
not warn about overwriting, and `nestrs new` initialises no git repository, so
a collision has nothing to recover from.

```bash frame="terminal"
# 1. Scaffold the workspace beside the crate you are moving.
nestrs new acme && cd acme

# 2. Give the incoming crate its own feature folder, with the adapter
#    sub-folder the workspace layout uses.
mkdir -p crates/features/src/posts/http

# 3. Move the port and the adapter into their conventional homes. `main.rs`
#    stays behind: apps/hello/src/main.rs already exists and does the same job.
mv ../posts/src/service.rs    crates/features/src/posts/
mv ../posts/src/module.rs     crates/features/src/posts/
mv ../posts/src/controller.rs crates/features/src/posts/http/
```

Then the edits a move cannot do:

1. **`crates/features/src/lib.rs`** — add `pub mod posts;`.
2. **`crates/features/src/posts/mod.rs`** (new) — the folder index:
   `mod service; mod module; pub mod http;` plus the `pub use` lines.
   A single crate needs none, because `main.rs` declares its modules.
3. **`crates/features/src/posts/http/mod.rs`** (new) — `mod controller; mod
   module;` plus its `pub use` lines, and a `http/module.rs` holding
   `#[module(imports = [PostsModule], providers = [PostsController])]`.
4. **`crates/features/src/posts/module.rs`** — drop `HttpModule::for_root(…)`
   and the controller from `providers`. In a workspace the transport comes with
   the **adapter's** controller, and the port module provides only the service:
   `#[module(providers = [PostsService])]`.
5. **Imports** — `crate::service::PostsService` becomes
   `crate::posts::PostsService`; the app's `module.rs` adds
   `features::posts::PostsHttpModule` to its imports.

Both halves of step 4 matter. Leaving `HttpModule` in the port would open an
HTTP server in every binary reaching `PostsService` — a worker included — and a
config pinned there contests the app's own at boot. And a moved controller
still declaring `#[controller(path = "/")]` collides with the starter one:

```text frame="terminal"
Error: duplicate controller prefix "/": HelloController and PostsController
both mount there — a controller prefix is its exclusive namespace; give each
one a distinct path
```

Give the moved controller its own prefix, or delete the starter `hello` feature
and app once yours is serving.

`crates/migrations/` and `crates/seed/` come from `nestrs new`, so the database
verbs and `g migration` work from the first `nestrs run db up`. From here
every generator is available: `nestrs g http <feature>` and its siblings wire
themselves into the app whose directory you are standing in, or the one
`--app` names.
