Tests bypass the environment in two ways depending on the layer. End-to-end
tests use `TestApp` and seed pinned config values directly — the seed
wins over `ConfigModule::for_feature::<C>()`. Unit tests for a `Config`
impl read a map of variables through `ConfigService::with_vars`, and never
touch `std::env`.

Both rely on a single guarantee: under `<PREFIX>_ENV=test`, the
[`.env.local`](/configuration/env-cascade/#test-mode-is-hermetic) file is
skipped, so a developer's personal secrets cannot leak in.

## Seeding a pinned value (e2e)

`TestApp::builder()` exposes `.provide(value)` — when the value's type
matches a config registered via `ConfigModule::for_feature::<C>()`, the
seed wins and the factory never runs.

```rust title="apps/api/tests/e2e/token.rs"
use nest_rs::testing::TestApp;
use uuid::Uuid;

#[tokio::test]
async fn issues_a_token_for_a_registered_client() {
    let app = TestApp::builder()
        .module::<AuthModule>()
        .provide(OAuthConfig {
            clients: vec![RegisteredClient {
                client_id: "test-client".into(),
                client_secret: "secret".into(),
                scopes: vec!["read".into()],
                payload: Uuid::nil(),
            }],
            default_org_id: Uuid::nil(),
        })
        .build()
        .await
        .unwrap();

    let response = app.http().post("/oauth/token")
        .body(r#"{"client_id":"test-client","client_secret":"secret"}"#)
        .send()
        .await;
    response.assert_status_is_ok();
}
```

The test never sets a `<PREFIX>_OAUTH__*` variable, doesn't depend on a
committed `.env.test`, and produces the same result on any machine.

## Pinning through `for_root`

Every configurable module's `for_root` accepts a `pinned: Option<C>`: `None`
loads from the environment over the config's defaults, `Some(cfg)` makes `cfg`
the **base** the environment overlays.

<Aside type="caution">
`for_root` is not a hermetic pin. A `<PREFIX>_<NS>__<KEY>` set in the ambient
environment still wins, per field — that is [the dual-path
rule](/configuration/#the-dual-path-rule), and it applies to test runs too. When
a test must not read the environment at all, seed the value with `.provide()`
(above): a seed short-circuits the resolving factory outright.
</Aside>

```rust title="apps/api/tests/e2e/http.rs"
use nest_rs::http::{HttpConfig, HttpModule};

let app = TestApp::builder()
    .module::<ApiModule>()
    // ...
    .build()
    .await?;
```

```rust title="apps/api/src/module.rs"
#[module(
    imports = [
        HttpModule::for_root(HttpConfig {
            host: "127.0.0.1".into(),
            port: 0,
            ..Default::default()
        }),
    ],
)]
pub struct ApiModule;
```

`HttpModule::for_root(opts)` routes its `Option<HttpConfig>` through
`ConfigModule::provide_feature`, which queues one resolving factory either way
— the `Option` only decides what the environment overlays. Use this when the
test module **owns** the binding (it composes the app) and an ambient
`<PREFIX>_HTTP__*` overriding it is *welcome*; use `.provide()` when the value
must hold regardless of the environment.

## A test-specific source

`ConfigModule::for_root()` always uses the default `EnvSource`. To
isolate config loading from `std::env` entirely, build the
`ConfigService` yourself with a [custom source](/configuration/sources/)
and seed the loaded `Config`:

```rust title="crates/features/tests/integration/config.rs"
use std::sync::Arc;
use nest_rs::config::{Config, ConfigService, MapSource, var_name};

let source = Arc::new(MapSource::from_iter([
    (var_name("seaorm", "URL"), "postgres://test/app"),
    (var_name("seaorm", "MAX_CONNECTIONS"), "5"),
]));
let env = ConfigService::with_source("seaorm", source);
let cfg = SeaOrmConfig::from_env(&env, SeaOrmConfig::defaults()).unwrap();

let app = TestApp::builder()
    .module::<AppModule>()
    .provide(cfg)
    .build()
    .await?;
```

A custom source also decides *where* the values come from, so the test cannot
pick up a stray `<PREFIX>_*` from the ambient environment — that is the whole
point of reaching for one.

It is **not** the case that a test leaves `std::env` untouched. No config *read*
writes there, but `TestApp::builder()` calls `load_project_env`, which publishes
the nearest project `.env` cascade set-if-absent — the harness needs backend
URLs before any `ConfigService` exists. The merge is bounded (once per process,
real env still wins, and `.env.local` is skipped under `<PREFIX>_ENV=test`), and a
`for_root` pin still outranks every cascade value, but a test asserting on a
variable a committed `.env` happens to define will read the file. Use
`with_source` — or `.provide(cfg)` — when the test must not. See
[hermeticity and the cascade](/configuration/sources/#what-fails-if-you-get-it-wrong--hermeticity-and-the-cascade).

## Unit-testing a `Config` impl

When the unit under test is the `from_env` mapping itself, read it from a
map of variables. `ConfigService::with_vars` answers for one namespace,
by key, from the pairs you give it, and reads neither `std::env` nor the
`.env` cascade. Validation is the struct's own `validate()`, which
`load()` runs after the mapping.

```rust title="crates/features/src/oauth/config.rs (from the demo, abridged)"
#[cfg(test)]
mod tests {
    use super::*;

    // …

    #[test]
    fn empty_clients_fails_validation() {
        let cfg = OAuthConfig {
            clients: vec![],
            default_org_id: Uuid::nil(),
        };
        let err = cfg.validate().unwrap_err();
        assert!(err.field_errors().contains_key("clients"));
    }

    // …

    #[test]
    fn clients_are_read_from_their_variable() {
        let env = ConfigService::with_vars(
            "oauth",
            [(
                "CLIENTS",
                r#"[{"client_id":"web","client_secret":"s3cr3t","scopes":["user"],"payload":"00000000-0000-0000-0000-000000000000"}]"#,
            )],
        );
        let cfg = OAuthConfig::from_env(&env, OAuthConfig::defaults()).expect("the clients parse");
        assert_eq!(cfg.clients.len(), 1);
        assert_eq!(cfg.clients[0].client_id, "web");
        cfg.validate().expect("valid");
    }
}
```

Nothing in it touches the process, so these tests run in parallel under
any runner.

## Default `<PREFIX>_ENV` in tests

`TestApp::builder()` sets `<PREFIX>_ENV=test` if nothing else has set it.
Two consequences:

- The `.env` cascade skips `.env.local` (per-machine secrets stay out of
  the test).
- Env-aware framework defaults stay off: the GraphQL playground doesn't
  mount, SDL emission doesn't fire, dev-only middleware unloads.

A test that wants to assert prod behavior overrides this explicitly
before building the app — `unsafe { std::env::set_var("<PREFIX>_ENV",
"production") }`. Set it before `TestApp::builder()` so the cascade
loads the right files.

## What not to do

- **Don't mutate `std::env` to feed a config.** `std::env::set_var` is
  `unsafe` since Rust 2024: in a process another test shares, it races
  that test's reads. `with_vars` answers from a map, and `.provide()`
  skips the read altogether.
- **Don't pin config in a `setup` shared between tests.** Each test
  should declare its inputs explicitly — that's what makes a failure
  reproducible from the test code alone.
- **Don't ship `.env.test` with secrets.** The file is committed by
  convention; treat it as documentation of test defaults, not as a
  vault.
