The readiness probe should fail when the database is unreachable. NestRS
ships a [SeaORM](https://www.sea-ql.org/SeaORM/)-backed indicator that runs
`DatabaseConnection::ping` and plugs straight into
[`nest-rs-health`](/health/)'s indicator registry — no glue code, no probe
handler to write.

## Wire it in

Import `SeaOrmHealthModule` alongside `HealthModule`:

```rust title="apps/api/src/module.rs"
use nest_rs::core::module;
use nest_rs::health::HealthModule;
use nest_rs::seaorm::{SeaOrmDatabaseModule, SeaOrmHealthModule, SeaOrmModule};

#[module(
    imports = [
        SeaOrmModule::for_root(None),
        SeaOrmDatabaseModule,
        SeaOrmHealthModule,
        HealthModule,
    ],
)]
pub struct AppModule;
```

That's it. Importing the module attaches the pool's indicator, `seaorm`, to
both the **readiness** and the **startup** probe — `HealthModule` runs it beside
every other indicator the app imports, and refuses the boot when a second one
claims the name. Without `SeaOrmModule::for_root`, the import fails the boot
naming it: there is no pool to ping.

## What gets probed

Two endpoints exit the box with the database wired in:

| Endpoint              | Key      | Failure                         |
|-----------------------|----------|---------------------------------|
| `GET /health/ready`   | `seaorm` | `503` while unreachable         |
| `GET /health/startup` | `seaorm` | `503` until first ping succeeds |

One key on both probes: the probe is the route, so the name says which
resource answered — the crate that owns the pool — never which probe asked.

The liveness probe (`GET /health/live`) deliberately does not depend on the
database — a brief DB outage should not kill the pod.

## A passing probe

```bash frame="terminal"
$ curl -s http://localhost:3000/health/ready
{"status":"up","info":{"seaorm":{"name":"seaorm","status":"up"}},"error":{},
 "details":{"seaorm":{"name":"seaorm","status":"up"}}}
```

When the ping fails the indicator moves from `info` to `error`, the overall
`status` switches to `down`, and the response is a `503`. The body carries
the **fixed** reason `"check failed"` — never the `DbErr`, which would put a
DSN or an internal hostname on a routinely unauthenticated endpoint. The
real error goes to the log instead: `warn` on `nest_rs::health`, with
`indicator`, `kind` and `error` as fields. [Indicators](/health/indicators/)
is the reference for that split; the shape itself is on
[Health](/health/).
