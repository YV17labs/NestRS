A mutating request runs inside a transaction with no boilerplate. The
`DbContext` interceptor — auto-installed by `SeaOrmDatabaseModule` — opens it on
the way in, hands the handler the transactional executor, and decides
commit or rollback based on the response. The hard cases — serialization
conflicts, deadlocks — get their own primitive, with a defined boundary
between what the interceptor handles and what the service owns.

The conflict classifier matches against
[sqlx](https://github.com/launchbadge/sqlx)'s typed `DatabaseError::code()`
(SQLSTATE) — never a formatted error string — so a digit substring in a
message can't trigger a false retry. [SeaORM](https://www.sea-ql.org/SeaORM/)
provides the `TransactionTrait` the programmatic boundary builds on.

## How the auto-commit works

`DbContext` classifies the HTTP method and branches:

```text
GET / HEAD / OPTIONS / TRACE   → Executor::Pool,  no transaction
POST / PUT / PATCH / DELETE    → Executor::Lazy, BEGIN on the first
                                                 data-layer touch;
                                                 commit on 2xx/3xx,
                                                 rollback otherwise
```

Inside the handler, `Repo::<E>::conn()` returns whichever variant the
interceptor installed — same code, different mode. The decision matrix:

| Outcome                  | Decision  |
|--------------------------|-----------|
| `Ok(2xx)` or `Ok(3xx)`   | commit    |
| `Ok(4xx)` or `Ok(5xx)`   | rollback  |
| `Err(_)` from the handler| rollback  |
| Commit error             | response becomes `500`, rollback is implicit |

A failed mutation never half-persists, even when the failure surfaces as
a typed 4xx body from a `thiserror`-derived error. See
[Repo and executor](/database/repo-and-executor/) for the full sequence,
including the escape-on-spawn case.

## What waits for the commit

An [event](/events/) emitted inside the transaction is dispatched **after**
the commit, and dropped when the transaction rolls back or fails to commit, or
the request fails — an event announces a fact, and a write that did not land is
not one. The same holds at every boundary that settles a transaction: a
WebSocket message, an MCP operation, a queue attempt, a scheduled tick. The
listeners run outside the transaction they waited for, on the pool, with the
caller's scope, ability and every value the emitter carries; the response
leaves once they have.

A `push`, a WebSocket broadcast and a storage write do **not** wait, and
cannot: each answers its caller — a receipt, `UniqueKeyHeld`, a send failure,
an object key — and that answer only exists once the backend has been asked.
Inside a transaction they happen where they are written. A push that fails
fails the request, so its writes roll back and nothing is lost; the price is
a job a later rollback leaves behind. When the work must follow the commit,
emit an event and push from its listener — the demo's publish does exactly
that.

An [atomic block](#atomic-blocks) holds what is emitted inside it: when it
keeps its writes, the events join the request's and wait for the request's
commit; when it rolls back, they are dropped with its writes.

The primitive underneath is `nest_rs::database::after_commit`, which the bus
calls; a [database driver](/database/writing-a-driver/) implements it for its
own transactions.

## Atomic blocks

A statement that fails inside a transaction aborts the whole transaction, so a
service that expects a failure — a unique key a concurrent request may have
just taken — runs that statement in `nest_rs::database::atomic`. The block is a
savepoint inside the request's transaction: an error rolls back the block
alone, and the request carries on and commits.

```rust title="crates/features/src/users/service.rs (from the demo, abridged)"
let linked = atomic(async {
    let conn = Repo::<UserIdentities>::conn()?;
    Ok::<_, ServiceError>(
        Repo::<UserIdentities>::insert_unscoped(
            new_identity_active(user_id, identity),
            &conn,
        )
        .await?,
    )
})
.await;
match linked {
    Ok(_) => {
        // …
        Ok(())
    }
    Err(ServiceError::Conflict(_)) => Ok(()),
    Err(e) => Err(e),
}
```

- **`Ok` keeps the block's writes** in the request's transaction, which still
  commits or rolls back as a whole.
- **`Err`, a panic, or a failure the block swallowed** rolls the block back
  and nothing else. A block that returns `Ok` over a failed statement answers
  `AtomicError::Poisoned`, since nothing it wrote stands.
- **On a safe route**, where the request runs on the pool, the block is a
  transaction of its own, committed when it returns `Ok`. A block in a block
  is a savepoint of its own and rolls back alone.
- **Nothing is sent until the block's first statement**: a block that never
  queries costs no round trip.

The block's error type takes an `AtomicError` — `ServiceError` does, by the
class of the database's refusal — so `?` works inside it. Read the block's
executor through `Repo::conn()` inside it: the request waits while a block is
open, since a statement of its own would land inside the savepoint, and a
statement issued from inside the block on an executor taken before it is
refused, whether or not the block has opened yet, rather than left to wait for
the block that holds it.

A transaction you opened and installed yourself (`Executor::Txn`) is not held
back that way: a statement you issue on it beside an open block lands inside
the block and rolls back with it. Await the block before writing on.

<Aside type="caution">
A block dropped before it settles — cancelled by a timeout or a `select!` —
leaves its savepoint open, so the request can no longer commit: it answers
`500`. Keep a deadline outside the block, around the work that may cancel it.
</Aside>

## Why retrying belongs to the service, not the interceptor

A poem `Request` is consumed by `next.run` — the body bytes are gone past
the handler call. The interceptor cannot replay the same handler on a
fresh transaction; the `DatabaseTransaction` handle is already aborted by
the time a conflict surfaces. Two consequences:

1. **The interceptor observes the conflict, it does not retry it.** The
   failed commit has already consumed its handle, and the handler's
   non-transactional side effects — a queued job, an object written to
   storage — would replay with it. (An emitted event is not among them: it
   waits for the commit, and a failed one drops it.)
2. **Retrying is the service's job.** Only the service knows which
   boundary is replayable, so the replayable closure owns that boundary
   itself.

The framework exposes two pieces, deliberately split:

## The observability flag

```bash frame="terminal"
NESTRS_SEAORM__OBSERVE_SERIALIZATION_CONFLICTS=true
```

```rust title="apps/api/src/module.rs"
SeaOrmModule::for_root(SeaOrmConfig {
    observe_serialization_conflicts: true,
    ..Default::default()
})
```

With the flag on, the `DbContext` interceptor matches a commit-time
conflict against the SQLSTATE markers below and logs it at `warn` with
the conflict tag (target `nest_rs::orm`) so ops sees the failure mode
distinctly from a generic commit error.

<Aside type="note">
**The flag observes; it never retries** — which is why it is named for what
it does. Replaying a commit-time conflict means re-running the whole handler,
and a handler may already have pushed a job or written an object. Neither
rolls back with the transaction, so a transparent retry would duplicate them
silently. The framework will not make that call on your
behalf; the response fails closed with a `500` after the `warn` line, and
retrying is the service's decision at a boundary it knows is replayable.
</Aside>

## The working retry primitive

For an actually-retried operation, wrap a replayable closure in
`retry_on_conflict` inside a service method that owns its programmatic
transaction boundary:

```rust title="crates/features/src/posts/service.rs"
use std::sync::Arc;
use std::time::Duration;
use nest_rs::seaorm::retry::{
    retry_on_conflict, DEFAULT_RETRY_ATTEMPTS, DEFAULT_INITIAL_BACKOFF,
};
use sea_orm::{DatabaseConnection, TransactionTrait};

impl PostsService {
    pub async fn publish(&self, id: Uuid) -> Result<post::Model, ServiceError> {
        let db = self.db.clone();
        retry_on_conflict(DEFAULT_RETRY_ATTEMPTS, DEFAULT_INITIAL_BACKOFF, || {
            let db = db.clone();
            async move {
                let txn = db.begin().await?;
                let published = read_update_insert(&txn, id).await?;
                txn.commit().await?;
                Ok::<_, sea_orm::DbErr>(published)
            }
        })
        .await
        .map_err(ServiceError::from)
    }
}
```

The closure's transaction is yours, committed out of the framework's sight,
so an event emitted inside it would not wait for it: emit once
`retry_on_conflict` has returned `Ok`, after the commit that stood.

`retry_on_conflict` runs the closure up to `attempts` times, sleeping
`initial_backoff << attempt` between tries (5 ms → 10 ms → 20 ms with the
defaults), each sleep scaled by a jitter between 0.8 and 1.2 drawn per call —
two transactions that conflicted with each other retry apart, not at one
instant into the same conflict. A non-retryable error returns immediately; a
retryable one is logged at `warn` and the closure re-runs from scratch —
that's what makes the retry honest, the body re-opens a fresh transaction
against a fresh snapshot.

The defaults are conservative on purpose:

| Constant                  | Value                  |
|---------------------------|------------------------|
| `DEFAULT_RETRY_ATTEMPTS`  | 3                      |
| `DEFAULT_INITIAL_BACKOFF` | 5 ms                   |
| `MAX_RETRY_ATTEMPTS`      | 32 (hard ceiling)      |
| Per-sleep cap             | 30 s, before jitter    |

The two limits bound what a caller can ask for: no sleep goes past 30 s
before jitter, however many attempts have failed, and no call makes more than
32 attempts, so a call passing `usize::MAX` still ends in bounded time.

<Aside type="caution">
**This is a service primitive.** It lives in `nest_rs::seaorm::retry` and
takes an `Arc<DatabaseConnection>` because the closure re-opens the
transaction from scratch. A handler can't use it against the ambient
transaction — that handle is already aborted past the first attempt's
failure.
</Aside>

## What `is_retryable_conflict` catches

| SQLSTATE | Backend(s)             | What it means                  |
|----------|------------------------|--------------------------------|
| `40001`  | Postgres, MySQL        | Serialization failure          |
| `40P01`  | Postgres               | Deadlock detected              |
| `1213`   | MySQL                  | Deadlock found                 |
| `1205`   | SQL Server             | Transaction was deadlock victim |

Anything else — `23505` (unique violation), `RecordNotFound`, a generic
`Internal` error whose message *contains* "40001" — returns immediately.
A unique-violation retry would loop forever; a substring match on the
message would falsely retry a connection log mentioning port `40001`. The
classifier reads the typed code only, never the display string.

## When retries don't help

The failure modes a retry cannot fix:

- **A unique constraint violation.** Retrying inserts the same row again,
  same failure. The classifier rejects these.
- **A row that doesn't exist.** `RecordNotFound` is terminal — no amount
  of retries materialize the row.
- **Application-side validation.** `ServiceError::Validation` is not a
  conflict; the closure re-runs from scratch but the input is the same.
- **A handler-time conflict on the auto-commit transaction.** The
  interceptor cannot retry the body; the conflict surfaces as a
  `DbErr` from the service, which gets mapped to the appropriate HTTP
  status. Use `retry_on_conflict` at the service level instead.

The split is deliberate. The interceptor handles the common case
transparently (open / commit / rollback); the service handles the hard case
explicitly (replay the work against a fresh snapshot). One way to do each.
