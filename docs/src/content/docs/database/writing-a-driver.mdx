The [`nest-rs-database`](https://github.com/YV17labs/NestRS/tree/main/crates/nest-rs-database)
crate is a port: one `UnitOfWork` every edge runs its units of work through —
an HTTP request, a WebSocket message, an MCP operation, a queue attempt, a
scheduled tick, a lifecycle hook — and an object-safe `Executor`, the handle
each unit's body reads from the ambient context. It names no store and no
query API, so the same contract fits a SQL pool, a document store, a
key-value session. This page and
[Binding a database driver](/database/binding-a-driver/) walk
[`nest-rs-seaorm`](https://github.com/YV17labs/NestRS/tree/main/crates/nest-rs-seaorm),
the reference driver, in the order every driver page follows: each excerpt is
its code, compiled and tested in its suite.

## Install

```bash frame="terminal"
cargo add nest-rs --no-default-features --features database,config
cargo add nest-rs --dev --no-default-features --features database,config,http,testing
```

A driver implements the port rather than consuming it, so it takes `database`
without `seaorm` — the first-party integration is what you are replacing. It
needs no edge feature: every edge, HTTP included, opens its units through the
binding on its own — its tests take `http` to drive one. Your crate is
`nestrs-<technology>`, depending on the umbrella alone beside what your store
needs; the [naming rule](/semver/#naming-a-package) roots every name it owns
at that crate, its span target included. The app picks a driver by importing
its binding instead of `SeaOrmDatabaseModule`.

## The contract

### The executor

The executor is what a unit's body reads: an enum of your store's handles, so
one query helper returns one type whichever mode the unit is in. SeaORM's,
`SeaOrmExecutor` in `crates/nest-rs-seaorm/src/executor.rs`, has a variant for
the pool, a transaction opened on the unit's first statement, and an atomic
block's savepoint. It is no part of that crate's API: an app has nothing to do
with it, so nothing about it freezes with a release.

What the port asks of a handle is what it holds: the pool, or a transaction.
It reads every other decision off that answer — whether `after_commit` waits,
the block `atomic` opens, the savepoint a resilience policy runs an attempt in,
where a pushed job is kept — and each answer is a trait whose methods have no
default, so a handle that leaves one out does not compile. SeaORM installs one
crate-private type per answer:

```rust title="from nest-rs-seaorm's executor"
impl nest_rs_database::Executor for InstalledPool {
    fn holds(&self) -> Holds<'_> {
        Holds::Pool(self)
    }
}

// …
impl nest_rs_database::Executor for InstalledTransaction {
    fn holds(&self) -> Holds<'_> {
        Holds::Transaction(self)
    }
}
```

What it holds is private to your crate. `current_executor` is public, and
`Holds::downcast_ref` hands out what a handle holds as any type its caller can
name: a public type there is a connection a service could run a query on that
your row filter never saw. A wrapper — SeaORM's atomic block — answers what it
wraps, so your query API reaches through it; and SeaORM's `Repo` hands out no
connection, so every statement that reaches the database is one `Repo` built,
and its select hands out no statement to rewrite. A transaction keeps the work
an emitted event holds for the commit:

```rust title="from nest-rs-seaorm's executor"
impl HeldTransaction for InstalledTransaction {
    fn after_commit(&self, work: Deferred) {
        match self {
            Self::Lazy(lazy) => lazy.hold(work),
            Self::Savepoint(block) => block.hold(work),
        }
    }
    // …
}
```

On the pool the port runs the work at once; handed to a transaction, it is
yours to run after the commit and drop on every other outcome. It runs where
the unit settles, so take what it needs where it is registered: what the unit
carries into its commit (`RequestContinuation::capture(Continuation::Commit)`)
and the scope it ran under (`current_executor_scope()`), inside which your pool
is installed when the work runs. Contain a panic in it: the commit already
stood.

### The unit of work

An edge declares each unit as a `UnitSpec` — its operation-log unit, its
scope, its `TransactionPolicy`, its deadline — and asks your binding to `open`
it, runs the body with your executor installed, then calls `settle` with the
edge's own verdict:

```rust title="from nest-rs-seaorm's unit of work, abridged"
impl UnitOfWork for SeaOrmUnitOfWork {
    fn open(&self, spec: &UnitSpec) -> Result<Box<dyn OpenUnit>, Unhonoured> {
        // …
        match spec.policy {
            TransactionPolicy::Pool => Ok(Box::new(OnPool {
                // …
            })),
            TransactionPolicy::PerUnit => Ok(Box::new(InTransaction {
                lazy: Arc::new(self.lazy(transport)),
                // …
            })),
            // A policy this driver does not know is refused before the body runs.
            _ => Err(Unhonoured::deterministic(UNSUPPORTED_POLICY)),
        }
    }

    fn settle_net(&self) -> Duration {
        self.settle_net
    }
}
```

Opening sends nothing: the transaction begins on the unit's first statement,
so a unit a guard denies costs no round trip. The settle runs on a task the
binding tracks, so an edge that drops its future — a client gone, an
operation stopped — never cuts a `COMMIT`:

```rust title="from nest-rs-seaorm's unit of work, abridged"
let task = TaskContext::capture(Continuation::Commit).carry(async move {
    let settled = nest_rs_core::panic::contain(async move {
        let (outcome, held) = lazy.answer(ok).await;
        // The edge may have stopped listening; the settle goes on regardless.
        let _unheard = answer.send(classify(outcome, ok, transport, observe_conflicts));
        held.run().await;
    })
    .await;
    // …
});
let finished = settles.spawn(task);
Box::pin(told(ok, transport, net, deadline, answered, async move {
    drop(finished.await);
}))
```

What your binding owes:

- **Settle on the outcome you are handed.** `ok` is the edge's verdict — a
  2xx or 3xx, a reply that is not an error frame, a tool answer without
  `isError`, a job's `Ok`. `Settlement::Unhonoured` turns a success you could
  not keep into the edge's failure; a failure stands unless you answer it `Unhonoured::IN_DOUBT`.
- **Answer within your settle net.** Past `settle_net` without your store's
  answer to a commit, answer `Unhonoured::IN_DOUBT`: the commit may have
  landed, so the unit is never retried. Wait for the held work until the
  unit's deadline, then answer and let it run on: a slow listener never fails
  a committed unit.
- **Fail closed on an escaped handle.** `settle` is called once the body and
  the executor it ran with are dropped, so a handle still alive was carried
  off by a spawned task: answer `Unhonoured` on a success.
- **Honour `TransactionPolicy::Pool`.** It is the developer's
  `transactional = false`, and a safe HTTP method's. A pool unit may be
  dropped unsettled: a streaming body or a DataLoader batch runs on one.
- **Settle what `after_commit` held** once the commit landed; drop it when the
  unit failed. A retry then announces only the attempt that stood.

### What the edges ask of it

You write nothing per edge: each resolves your binding once, when it mounts
or boots, and runs every unit through it, around its guards — so a guard that
denies has run before anything opens. Which policy each edge's units ask for,
and which outcome commits, is the app's side of this contract, on
[Transactions](/database/transactions/#how-the-auto-commit-works). The request
timeout cuts the body, never the commit: the edge waits your `settle_net` past
the unit's deadline before it answers `500` for a commit that never answered.
What the router answers itself — a `404`, a `405` — opens no unit.

### Atomic blocks

`nest_rs::database::atomic(work)` opens a block off what the ambient handle
holds: a savepoint of a transaction (`HeldTransaction::savepoint`), a
transaction of its own on the pool (`HeldPool::transaction`); outside any unit
it refuses with `AtomicError::Unsupported` without running the work. Every
GraphQL mutation runs each root field in one, and a resilience policy runs each
attempt of an idempotent call, or of a method naming a `fallback`, in the
transaction's savepoint, so a failed attempt's writes never stay in the unit; on
the pool an attempt runs as it would with no policy. SeaORM sends its savepoint
on the connection of the transaction, or the block, it opens in:

```rust title="from nest-rs-seaorm's executor"
fn savepoint(&self) -> Arc<dyn AtomicBlock> {
    let savepoint = match self {
        Self::Lazy(lazy) => Savepoint::in_boundary(Arc::clone(lazy)),
        Self::Savepoint(block) => Savepoint::in_block(Arc::clone(block)),
    };
    Arc::new(AtomicExecutor::savepoint(Arc::new(savepoint)))
}
```

A block owes, in order of how badly it goes wrong without it: the enclosing
unit waits for it, so none of its statements lands inside the block's
savepoint; a failure inside poisons the block, not the unit; a refused
`RELEASE` or `ROLLBACK TO`, or a block dropped once its `SAVEPOINT` was
answered and before it settled, leaves what holds it unable to commit — the
unit, for a block sitting directly in it, and for a block nested in another
block or attempt's savepoint that one alone, the unit going on to commit what it
wrote beside it — while one dropped before that answer leaves what it sat in as
it was; nothing is sent before the block's first statement;
and a block of its own on a pool unit commits on your settle task, its pool
unit answering `Unhonoured::IN_DOUBT` when the body was cut before it saw
that commit's answer. `crates/nest-rs-seaorm/src/savepoint.rs` and `turn.rs`
are the reference shape.

### The outbox

A job pushed inside a unit is filed after its commit only where the driver
keeps an outbox: the queue port writes the sealed jobs into the `Outbox` a
transaction answers (`HeldTransaction::outbox`), and a cancel removes a record
through it, or through the `OutboxKept` the pool answers (`HeldPool::outbox`).
A handle answering `None` says it keeps none: its jobs are filed at once, and a
rollback leaves them behind. To keep one, bind a
`nest_rs::database::OutboxStore` over a table of your own beside your unit of
work — `arm` proves the table, `written` wakes once a unit that wrote records
committed, `claim` locks due records no other relay holds, oldest first — and
import `nest_rs::queue::OutboxModule`, which attaches the relay that drains
it. Then answer an outbox once the store is armed: `write` the records on the
transaction, in its turn, and wake the relay after its commit; `remove` and
`remove_unique` delete a record no relay has filed, and wait for one a relay
holds rather than skip it. The records are opaque: write them as you receive
them, and never log the sealed text, which carries the job's payload.
`crates/nest-rs-seaorm/src/queue/outbox.rs` is the reference shape.
