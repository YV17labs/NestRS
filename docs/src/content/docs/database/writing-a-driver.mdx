The [`nest-rs-database`](https://github.com/YV17labs/NestRS/tree/main/crates/nest-rs-database)
crate is a port: one `UnitOfWork` every edge runs its units of work through —
an HTTP request, a WebSocket message, an MCP operation, a queue attempt, a
scheduled tick, a lifecycle hook — and an object-safe `Executor`, the handle
each unit's body reads from the ambient context. It names no store and no
query API, so the same contract fits a SQL pool, a document store, a
key-value session. This page walks
[`nest-rs-seaorm`](https://github.com/YV17labs/NestRS/tree/main/crates/nest-rs-seaorm)'s
binding, the reference driver, in the order every driver page follows: each
excerpt is its code, compiled and tested in its suite.

## Install

```bash frame="terminal"
cargo add nest-rs --no-default-features --features database
cargo add nest-rs --dev --no-default-features --features database,http,testing
```

A driver implements the port rather than consuming it, so it takes `database`
without `seaorm` — the first-party integration is what you are replacing. It
needs no edge feature: every edge, HTTP included, opens its units through the
binding on its own — its tests take `http` to drive one. Your crate is `nestrs-<technology>`, depending on the
umbrella alone beside what your store needs; the
[naming rule](/semver/#naming-a-package) roots every name it owns at that
crate, its span target included. The app picks a driver by importing its
binding instead of `SeaOrmDatabaseModule`.

## The contract

### The executor

The executor is what a unit's body reads: an enum of your store's handles, so
one query helper returns one type whichever mode the unit is in. SeaORM's has
a variant for the pool, a transaction opened on the unit's first statement,
and an atomic block's savepoint. Its one obligation beside `as_any` is to keep
the work an emitted event holds for the commit:

```rust title="from nest-rs-seaorm's executor"
/// A lazy transaction or a block's savepoint holds the work for its
/// settling; a pool and a caller's [`Txn`](Executor::Txn) hand it back to
/// run at once.
fn after_commit(&self, work: Deferred) -> Option<Deferred> {
    match self {
        Executor::Lazy(lazy) => {
            lazy.hold(work);
            None
        }
        Executor::Savepoint(block) => {
            block.hold(work);
            None
        }
        Executor::Pool(_) | Executor::Txn(_) => Some(work),
    }
}
```

The trait's default hands the work back to run at once — right for a handle
with no transaction, and wrong for one with: a driver that leaves it out
dispatches every event emitted inside a transaction before that transaction
landed, and announces writes a rollback then undoes. The held work runs where
the unit settles, so take what it needs where it is registered: what the unit
carries into its commit (`RequestContinuation::capture(Continuation::Commit)`)
and the scope it ran under (`current_executor_scope()`), inside which your
handle outside the transaction is installed when the work runs. Contain a
panic in it: the commit already stood.

### The unit of work

An edge declares each unit as a `UnitSpec` — its operation-log unit, its
scope, its `TransactionPolicy`, its deadline — and asks your binding to `open`
it, runs the body with your executor installed, then calls `settle` with the
edge's own verdict:

```rust title="from nest-rs-seaorm's unit of work, abridged"
impl UnitOfWork for SeaOrmUnitOfWork {
    fn open(&self, spec: &UnitSpec) -> Result<Box<dyn OpenUnit>, Unhonoured> {
        // …
        match spec.policy {
            TransactionPolicy::Pool => Ok(Box::new(OnPool {
                // …
            })),
            TransactionPolicy::PerUnit => Ok(Box::new(InTransaction {
                lazy: Arc::new(self.lazy(transport)),
                // …
            })),
            // A policy this driver does not know is refused before the body runs.
            _ => Err(Unhonoured::deterministic(UNSUPPORTED_POLICY)),
        }
    }

    fn settle_net(&self) -> Duration {
        self.settle_net
    }
}
```

Opening sends nothing: the transaction begins on the unit's first statement,
so a unit a guard denies costs no round trip. The settle runs on a task the
binding tracks, so an edge that drops its future — a client gone, an
operation stopped — never cuts a `COMMIT`:

```rust title="from nest-rs-seaorm's unit of work, abridged"
let task = TaskContext::capture(Continuation::Commit).carry(async move {
    let settled = nest_rs_core::panic::contain(async move {
        let (outcome, held) = lazy.answer(ok).await;
        // The edge may have stopped listening; the settle goes on regardless.
        let _unheard = answer.send(classify(outcome, ok, transport, observe_conflicts));
        held.run().await;
    })
    .await;
    // …
});
let finished = settles.spawn(task);
Box::pin(told(ok, transport, net, deadline, answered, async move {
    drop(finished.await);
}))
```

What your binding owes:

- **Settle on the outcome you are handed.** `ok` is the edge's verdict — a
  2xx, a reply that is not an error frame, a tool answer without `isError`, a
  job's `Ok`. `Settlement::Unhonoured` turns a success you could not keep into
  the edge's failure; a failure stands whatever you answer.
- **Answer within your settle net.** Past `settle_net` without your store's
  answer to a commit, answer `Unhonoured::IN_DOUBT`: the commit may have
  landed, so the unit is never retried. Wait for the held work until the
  unit's deadline, then answer and let it run on: a slow listener never fails
  a committed unit.
- **Fail closed on an escaped handle.** `settle` is called once the body and
  the executor it ran with are dropped, so a handle still alive was carried
  off by a spawned task: answer `Unhonoured` on a success.
- **Honour `TransactionPolicy::Pool`.** It is the developer's
  `transactional = false`, and a safe HTTP method's. A pool unit may be
  dropped unsettled: a streaming body or a DataLoader batch runs on one.
- **Settle what `after_commit` held** once the commit landed; drop it when the
  unit failed. A retry then announces only the attempt that stood.

### What the edges ask of it

You write nothing per edge: each resolves your binding once, when it mounts
or boots, and runs every unit through it, around its guards — so a guard that
denies has run before anything opens. On HTTP, a safe method (`GET`, `HEAD`,
`OPTIONS`, `TRACE`) opens a `Pool` unit and a mutating one a `PerUnit` unit,
committed on a success and rolled back on a handler error or any `4xx`/`5xx`,
whatever an exception filter answered. `/graphql` and `/mcp` open a `Pool`
unit for the request, and each operation opens its own. The request timeout
cuts the body, never the commit: the edge waits your `settle_net` past the
unit's deadline before it answers `500` for a commit that never answered. What
the router answers itself — a `404`, a `405` — opens no unit.

### Atomic blocks (optional)

`nest_rs::database::atomic(work)` asks the ambient executor for a block
through `Executor::atomic`. The default answers `None`, and `atomic` then
refuses with `AtomicError::Unsupported` without running the work —
fail-closed, so a driver that offers no block loses the feature, and every
GraphQL mutation with it: each root field runs in a block. SeaORM's nests one
in whatever the handle holds:

```rust title="from nest-rs-seaorm's executor"
fn atomic(&self) -> Option<Arc<dyn AtomicBlock>> {
    let block = match self {
        Executor::Pool(pool) => {
            AtomicExecutor::own(Arc::new(LazyTransaction::new(pool.clone(), ATOMIC)))
        }
        Executor::Txn(caller) => AtomicExecutor::own(Arc::new(LazyTransaction::nested_in(
            Arc::clone(caller),
            ATOMIC,
        ))),
        Executor::Lazy(lazy) => {
            AtomicExecutor::savepoint(Arc::new(Savepoint::in_boundary(Arc::clone(lazy))))
        }
        Executor::Savepoint(block) => {
            AtomicExecutor::savepoint(Arc::new(Savepoint::in_block(Arc::clone(block))))
        }
    };
    Some(Arc::new(block))
}
```

A block owes, in order of how badly it goes wrong without it: the enclosing
unit waits for it, so none of its statements lands inside the block's
savepoint; a failure inside poisons the block, not the unit; a refused
`RELEASE` or `ROLLBACK TO`, or a block dropped before it settled, leaves the
unit unable to commit; nothing is sent before the block's first statement;
and a block of its own on a pool unit commits on your settle task, its pool
unit answering `Unhonoured::IN_DOUBT` when the body was cut before it saw
that commit's answer. `crates/nest-rs-seaorm/src/savepoint.rs` and `turn.rs`
are the reference shape.

### The outbox (optional)

A job pushed inside a unit is filed after its commit only where the driver
keeps an outbox: the queue port hands the sealed jobs to
`Executor::write_outbox`, whose default answers `None` — the job is filed at
once, and a rollback leaves it behind. To keep one, bind a
`nest_rs::database::OutboxStore` over a table of your own beside your unit of
work — `arm` proves the table, `written` wakes once a unit that wrote records
committed, `claim` locks due records no other relay holds, oldest first — and
import `nest_rs::queue::OutboxModule`, which attaches the relay that drains
it. Then write the records `write_outbox` hands you on each transaction a unit
settles, in its turn, and wake the relay after its commit; `remove_outbox` and
`remove_outbox_unique` delete a record no relay has filed, and wait for one a
relay holds rather than skip it. The records are opaque: write them as you
receive them, and never log the sealed text, which carries the job's payload.
`crates/nest-rs-seaorm/src/queue/outbox.rs` is the reference shape.

## The binding

The binding is the module an app imports. It binds your unit of work through
`provide_unit_of_work`, as `Arc<dyn UnitOfWork>` — a **declaration** carrying
the port's `BACKEND_REMEDY`, so a second database driver imported beside
yours fails the boot naming both — and as the unit every lifecycle hook runs
in. A binding that declares `Arc<dyn UnitOfWork>` by hand still serves every
edge but leaves every lifecycle hook bare:

```rust title="from nest-rs-seaorm's database binding, abridged"
impl Module for SeaOrmDatabaseModule {
    fn collect(builder: ContainerBuilder, _: Collecting<Self>) -> ContainerBuilder {
        let builder = budgets(BudgetReach::Ambient)
            .into_iter()
            .fold(builder, ContainerBuilder::provide_meta);
        // …
        let builder = provide_unit_of_work::<UnitInputs, _, _>(builder, |container| async move {
            Ok(Arc::new(unit_of_work(&container)?) as Arc<dyn UnitOfWork>)
        })
        // Installed after the pool, so its close drains every settle still
        // running before the pool's closes.
        .provide_factory_after::<Settles, (DatabaseConnection,), _, _>(|_| async {
            Ok(Settles::default())
        })
        .provide_close::<Settles, _, _>(|settles| async move {
            settles.drain().await;
            Ok(())
        });
        // …
        builder
    }
    // …
}
```

`UnitInputs` names the pool and its config, so the boot builds the unit of
work once both exist, wherever the imports fall. The pool itself is opened by
the substrate, `SeaOrmModule::for_root`, which every SeaORM binding shares:
its config is settable from `<PREFIX>_SEAORM__*` and from the struct the app
pins, as every module's is.

### Close what it opened

What the substrate opens, it closes with `provide_close`, attached in
`collect` beside its factory, so a boot whose later factory fails still
closes the pool. Closes run after every shutdown hook, the value installed
last closing first — which is why the binding installs its `Settles` after
the pool: every unit's settle is drained before the pool says goodbye. The
pool's close then waits `SHUTDOWN_SETTLE_TIMEOUT`, half a second, for what
the settled units hand back, and says what it leaves at `warn`. A pool the
app seeded instead — a test's database — is the app's to close.

## Budget and net

Two budgets bound what the pool waits: a connection from the pool, and a
statement on the server. The binding declares both as **ambient**, since
every unit reaches the pool through its context rather than by injection —
so every net around developer code holds them, an authentication guard's
among them:

```rust title="from nest-rs-seaorm's substrate"
pub(crate) fn budgets(reach: BudgetReach) -> [Budget; 2] {
    let declare = |resource, bounds: &DurationBounds, read| {
        let setting = format!(
            "{}, or `{}` in code",
            nest_rs_config::var_name(NAMESPACE, bounds.key()),
            bounds.field(),
        );
        match reach {
            BudgetReach::Injected => Budget::of::<DatabaseConnection>(resource, setting, read),
            BudgetReach::Ambient => Budget::ambient::<DatabaseConnection>(resource, setting, read),
        }
    };
    [
        declare("the SeaORM pool", &CONNECT_TIMEOUT, acquire_budget),
        declare("the SeaORM statements", &STATEMENT_TIMEOUT, statement_bound),
    ]
}
```

The port's own net is your `settle_net`: SeaORM's is its statement timeout
plus a second, above every bound the server holds a `COMMIT` to, so it fires
only on a database that stopped bounding itself.

## When the backend fails

A failure is classified from what the database said, never guessed, because
a retry replays the whole job body, side effects included:

- **`Unhonoured::retryable`** is for a failure that could end differently —
  a serialization conflict, a deadlock.
- **`Unhonoured::deterministic`** is for a constraint violation, or a commit
  whose outcome you do not know.
- **A failed statement and a failed commit are not one question.** Inside an
  open transaction nothing is durable yet, so a connection lost mid-attempt
  left nothing behind: retryable. At commit the same error means the commit
  may have landed: deterministic. SeaORM splits them as
  `retry::is_transient_failure` against `CommitError::is_retryable_conflict`.

**Say your errors without their values.** A database server words its
refusal around the input it refused, and every framework log line, a dead
letter's reason and a client's error frame read an error chain through
`nest_rs::core::error_message`, which asks each `SafeLink` about a link before
its `Display`. Submit one:

```rust title="from nest-rs-seaorm's errors, abridged"
nest_rs_core::inventory::submit! { nest_rs_core::SafeLink::new(say) }

/// What a sea-orm or sqlx error means, said without a value: a server error by
/// its SQLSTATE and the names it reported; a variant whose text can hold a value
/// by its kind alone; every other by its own sentence, which holds none.
fn say(link: &(dyn std::error::Error + 'static)) -> Option<String> {
    if let Some(err) = link.downcast_ref::<DbErr>() {
        return Some(said_db(err));
    }
    // …
}
```

A link your sayer claims is said by its sentence alone, and nothing below it
is read. Keep identifiers — a code, a constraint, a table — and drop every
message: SeaORM says a unique violation as `database error 23505 on
constraint "users_email_key", table "users"`.

## TLS

Your store's connections verify the server, with no way to turn it off but an
explicit plaintext setting. Follow the store's own standard where it has one:
Postgres's is libpq's URL parameters, so SeaORM reads `sslmode` and
`sslrootcert` off `<PREFIX>_SEAORM__URL`, verifies by default, and refuses
every mode that encrypts without verifying:

```rust title="from nest-rs-seaorm's config, abridged"
match parsed.get_ssl_mode() {
    PgSslMode::Prefer if !named => Ok(PgSslMode::VerifyFull),
    mode @ (PgSslMode::Disable | PgSslMode::VerifyFull) => Ok(mode),
    unverified => Err(Self::refuse_url(format!(
        "asks Postgres for TLS without verifying its certificate (sslmode={}): write \
         sslmode=verify-full, with sslrootcert naming the authority that signed the \
         server's certificate, or sslmode=disable for a server without TLS",
        // …
    ))),
}
```

A store with no such standard reads `nest_rs::config::ClientTls` under its
own namespace, as the [queue driver page](/queue/writing-a-driver/#tls) shows.

## Proof at boot

The boot proves the pool before the app serves: `nest_rs::core::prove` runs
one attempt after another within the connect budget, on the reconnect curve,
until one opens and proves the resource, one meets what every attempt would,
or the budget is spent:

```rust title="from nest-rs-seaorm's substrate, abridged"
prove(
    budget,
    Backoff::RECONNECT,
    process_seed(),
    said(&endpoint, budget),
    |_| {
        // …
        async move {
            // …
            PgConnection::connect_with(probe)
                .await
                .map_err(met)?
                .close()
                .await
                .map_err(met)?;
            Database::connect(options)
                .await
                .map_err(|error| classify(error, endpoint))
        }
    },
)
.await
```

`classify` sorts each failure into `Attempt::Refused` — credentials or a
database the server refuses, TLS that fails — which ends the boot at once,
and `Attempt::Failed` — a refused connection, a server starting up — which
the next attempt follows. `said` reports each retry on the driver's own
target, since a span target is a callsite constant the kernel cannot borrow,
and names the server by its host and port, never by a URL carrying a
password.

## Health

A driver ships its readiness check behind its crate's `health` feature, a
binding module attaching an `IndicatorEntry` under the crate's name:

```rust title="from nest-rs-seaorm's health binding"
impl Module for SeaOrmHealthModule {
    fn register(builder: ContainerBuilder, _: Registering<Self>) -> ContainerBuilder {
        if let Err(missing) = present(&builder.snapshot()) {
            return builder.refuse(missing);
        }
        builder
            .provide_meta(IndicatorEntry::new::<Self>(
                NAME,
                ProbeKind::Readiness,
                ping,
            ))
            .provide_meta(IndicatorEntry::new::<Self>(NAME, ProbeKind::Startup, ping))
    }
}
```

Yours is keyed `nestrs_<technology>` and runs on the readiness and startup
probes, never on liveness — see
[an indicator a module attaches](/health/indicators/#an-indicator-a-module-attaches).

## Test it

Your suite boots apps over your binding and proves each obligation above
against a live server. SeaORM's holds them in `nest-rs-seaorm`'s suites:
`tests/e2e/unit.rs` for the commit, the rollback, the escaped handle, the
conflict and the held work under the HTTP edge;
`tests/integration/database/module.rs` for the request timeout that cuts the
body and never the commit, and a GraphQL request whose operations each open
their own unit; and the unit tests of `src/database/module.rs`, among them
`a_second_unit_of_work_binding_fails_the_boot_in_the_ports_words`, for the
contest. Each test writes only in what its suite creates: SeaORM's write in
probe tables of their own, or in a whole database through `EphemeralDatabase`
— a SeaORM fixture, which `testing` carries only beside the `seaorm`
capability. Yours creates its own the same way, in your store's terms — a
database per test, dropped after it, is the plainest — and never writes in the
database a deployment's URL names.

## What the seam carries, and what stays store-native

The SeaORM-typed primitives — `Repo<E>`'s row-level filter through
`Ability::condition_for`, the `#[expose]` response mask, `Bind<A, S>`,
`CrudService` — read SeaORM's typed `Column` and `EntityTrait`, so a driver
ships their equivalents in its store's terms: Postgres RLS, an
ability-derived filter document, a per-collection helper. What every driver
keeps is the seam's: a transaction per unit of work on every edge, the
ambient executor across HTTP and the workers, the access graph and the
module wiring. Its events go on its own target, `nestrs_<technology>`, as
SeaORM's go on `nest_rs::orm`.
