The [`nest-rs-database`](https://github.com/YV17labs/NestRS/tree/main/crates/nest-rs-database)
crate is a port: one `UnitOfWork` trait every edge runs its units of work
through — an HTTP request, a WebSocket message, an MCP operation, a queue
attempt, a scheduled tick — and an object-safe `Executor` trait for the handle
each unit's body reads from the request's ambient context, which carries it
across every layer. The seam names no store and no
query API — a handle is a handle. The same scaffold fits a SQL pool, a
document-store client, a key-value session, a graph driver, an in-memory
map. This page gives you the **shape** of a driver, not its implementation:
the trait you implement, the methods you wire, with `// your code here`
markers where the store-specific work lands. The reference impl is
[`nest-rs-seaorm`](https://github.com/YV17labs/NestRS/tree/main/crates/nest-rs-seaorm) —
read it once when a placeholder is unclear.

## Install

```bash frame="terminal"
cargo add nest-rs --features database,http,interceptors
```

A driver implements the port rather than consuming it, so it takes `database` without `seaorm` — the first-party integration is what you are replacing. `http` and `interceptors` carry the request interceptor of Step 3.

## What you'll implement

- An `Executor` enum holding your store's handles, with the trait impl.
- A `UnitOfWork` that opens each unit an edge declares and settles it on the
  edge's own outcome — one transaction per unit by default, the pool on
  `transactional = false` and on a safe HTTP method.
- A request interceptor that runs each HTTP request through it.
- Optionally, the atomic block `nest_rs::database::atomic` runs on.
- A `SafeLink` that says your store's errors without the values its server
  quotes.

A driver lives in a crate of your own, `nestrs-<technology>`, depending on
`nest-rs` with `default-features = false` and the features it binds —
`database`, `http`, `interceptors` — plus whatever your store needs.
The [naming rule](/semver/#naming-a-package) roots every name your driver owns
at that crate. The app picks a driver by importing its module instead of
`nest-rs-seaorm`'s.

## Step 1 — The Executor enum

An enum is the right shape because your unit of work branches on it to
decide commit vs rollback, and a single query helper returns one type
whichever mode the unit is in. Two variants: one for ordinary work,
one carrying a transaction. A store with no transaction primitive
collapses to a single variant — the seam absorbs that too.

```rust title="crates/yourdb/src/executor.rs"
use std::any::Any;

/// Your driver's handle, carried in the request's ambient context.
/// The framework only reaches it via the trait; the variants are yours.
#[derive(Clone)]
pub enum Executor {
    /// Non-transactional handle — pool, client, connection.
    /// Used on safe routes (GET/HEAD/OPTIONS) and on a job that opted out
    /// with `transactional = false`.
    Default(/* your handle, e.g. YourPool */),
    /// Transactional handle — your store's unit of work.
    /// Used on mutating routes and on a job attempt by default; committed
    /// or rolled back at the boundary.
    Transactional(/* your tx/session type, wrapped in Arc<Mutex<_>> */),
}

impl nest_rs::database::Executor for Executor {
    fn as_any(&self) -> &dyn Any { self }

    /// Work that must wait for the commit — every event emitted inside the
    /// transaction. Keep it beside the transaction; the boundary that
    /// settles it runs it after a commit and drops it otherwise.
    fn after_commit(
        &self,
        work: nest_rs::database::Deferred,
    ) -> Option<nest_rs::database::Deferred> {
        match self {
            Executor::Transactional(/* … */) => {
                // Your code: push `work` onto a list your boundary drains.
                None
            }
            // Nothing to wait for: hand it back, it runs at once.
            Executor::Default(/* … */) => Some(work),
        }
    }
}
```

The `Arc<Mutex<_>>` around the transactional variant is the common pattern
because most stores' transaction handles take `&mut` on their query
methods, and the unit needs to keep one reference while the body holds
another.

`after_commit` is what makes an event wait for the write it announces. The
trait's default hands the work back to run at once — right for a handle with
no transaction, and wrong for one with: a driver that leaves it out dispatches
every event emitted inside a transaction before that transaction has landed,
and announces writes a rollback then undoes.

Your boundary runs the held work where it settles, so take what the work
needs where it is registered, inside `after_commit`: what the unit carries
into its commit, `nest_rs::core::RequestContinuation::capture(Continuation::Commit)`
— the ability, the trace, every value that crosses — and the scope it runs
under, `nest_rs::database::current_executor_scope()`. The capture carries no
executor of yours, and its scope goes with it, so re-install your
non-transactional handle inside the capture under the scope you read:
`with_request_executor`, `with_job_executor`, or `with_executor` when none was
tagged — and for any other: `ExecutorScope` can grow within 7.x, so your `match`
keeps a `_` arm, and `with_executor` is the one that fails closed. A job's held
work installed untagged would fail closed like a request. Contain a panic in
it: the commit already stood.

The other continuations — a streaming body, a DataLoader batch — run on a
`TransactionPolicy::Pool` unit your binding opens on their first read: they
never borrow a transaction that has settled.

## Step 2 — The unit of work

This is the centerpiece. An edge declares each unit it runs as a `UnitSpec` —
its operation-log unit (`ws.message`, `queue.job`, …), its scope, its
`TransactionPolicy` — and hands it to `run_unit`, which asks your binding to
`open` it, runs the body with your executor installed, and calls `settle` on
the edge's own outcome. The framework owns the install and what each edge
counts as a success; the numbered comments mark the places you write
store-specific code.

```rust title="crates/yourdb/src/unit.rs"
use std::future::Future;
use std::pin::Pin;
use std::sync::Arc;
use nest_rs::database::{
    OpenUnit, Settlement, TransactionPolicy, Unhonoured, UnitOfWork, UnitSpec,
};

pub struct YourUnitOfWork {
    // your pool / client here
}

impl UnitOfWork for YourUnitOfWork {
    fn open(&self, spec: &UnitSpec) -> Result<Box<dyn OpenUnit>, Unhonoured> {
        match spec.policy {
            // (1) The pool: every statement stands alone, nothing to settle.
            TransactionPolicy::Pool => Ok(Box::new(OnPool(/* your handle clone */))),
            // (2) A unit of its own: a transaction opened on its first touch.
            //     Opening sends nothing, so a unit a guard denies costs nothing.
            TransactionPolicy::PerUnit => Ok(Box::new(InTransaction::new(/* … */))),
            // A policy this driver does not know: refuse the unit unrun.
            _ => Err(Unhonoured::deterministic(
                "this driver does not support the unit's transaction policy",
            )),
        }
    }
}

impl OpenUnit for InTransaction {
    fn executor(&self) -> Arc<dyn nest_rs::database::Executor> {
        // (3) The handle the body reads: your transactional variant.
        Arc::new(Executor::Transactional(/* a clone of the unit's handle */))
    }

    fn settle(self: Box<Self>, ok: bool) -> Pin<Box<dyn Future<Output = Settlement> + Send>> {
        Box::pin(async move {
            // (4) Reclaim sole ownership. A handle still held escaped into a
            //     spawned task: nothing it wrote can be vouched for.
            // (5) Commit on `ok`, roll back otherwise — then run the work
            //     `after_commit` held, or drop it.
            match /* commit using your store's API, when `ok` */ {
                Ok(()) => Settlement::Settled,
                // A serialization conflict or a deadlock is the one shape
                // another attempt could win.
                Err(err) if err.is_conflict() => Settlement::Unhonoured(Unhonoured::retryable(
                    "the unit's transaction could not be committed",
                )),
                Err(_) => Settlement::Unhonoured(Unhonoured::deterministic(
                    "the unit's transaction could not be committed",
                )),
            }
        })
    }
}
```

`OnPool`'s `settle` answers `Settlement::Settled` at once: there is nothing to
commit, and a pool unit may be dropped unsettled — it is what a streaming body
or a DataLoader batch runs on.

What your binding owes:

- **Settle on the outcome you are handed.** `ok` is the edge's own verdict —
  a 2xx, a reply that is not an error frame, a tool answer without `isError`,
  a job's `Ok`. A failure stands whatever you answer; `Settlement::Unhonoured`
  turns a *success* you could not keep into the edge's failure.
- **Fail closed on an escaped handle.** `settle` is called once the body and
  the executor `run_unit` installed are dropped, so a handle still alive was
  carried off by a spawned task: answer `Unhonoured` on a success.
- **Honour `TransactionPolicy::Pool`.** It is the developer's
  `transactional = false`, and ignoring it silently gives up the
  atomicity the default promises.
- **Settle what `after_commit` held.** Run it once the unit's commit landed;
  drop it when the unit failed or could not be committed. A retry then
  announces only the attempt that stood.
- **Classify an `Unhonoured` from what your backend said, not from a
  guess.** A retry replays the whole job body, side effects included, so
  `Unhonoured::retryable` is for a failure that could genuinely end
  differently — a serialization conflict, a deadlock. A constraint
  violation, or a commit whose outcome you do not know, is
  `Unhonoured::deterministic`.
- **A failed *statement* and a failed *commit* are not the same
  question**, and answering them alike dead-letters a job over an outage.
  Inside an open transaction nothing is durable yet, so a connection your
  store could not acquire, or lost mid-attempt, left nothing behind:
  **retryable**. At commit the same error means the commit may already
  have landed: **deterministic**. `nest-rs-seaorm` splits them as
  `retry::is_transient_failure` (statements) against
  `CommitError::is_retryable_conflict` (the commit), and yours should
  split them too.

No caller means no ambient ability: a unit declared `ExecutorScope::Job` — a
queue attempt, a tick — runs unscoped, which is correct for system work.

## Step 3 — The request interceptor

Every edge but HTTP opens its units through your binding on its own. Until the
HTTP edge runs its request unit itself, your driver registers the interceptor
that does, in the innermost band, so a guard that denies a request has run
before anything opens:

```rust title="crates/yourdb/src/interceptor.rs"
use std::sync::Arc;
use nest_rs::core::async_trait;
use nest_rs::core::{Layer, injectable};
use nest_rs::database::{ExecutorScope, TransactionPolicy, UnitOfWork, UnitSpec, run_unit};
use nest_rs::http::poem::http::{Method, StatusCode};
use nest_rs::http::poem::{Error, Request, Response, Result};
use nest_rs::interceptors::{Interceptor, Next};

#[injectable]
pub struct YourDbContext {
    #[inject]
    unit: Arc<dyn UnitOfWork>,
}

// `Interceptor` has `Layer` as a supertrait — an empty impl is enough
// unless the layer needs a `priority`.
impl Layer for YourDbContext {}

#[async_trait]
impl Interceptor for YourDbContext {
    async fn intercept(&self, req: Request, next: Next<'_>) -> Result<Response> {
        let policy = match *req.method() {
            Method::GET | Method::HEAD | Method::OPTIONS | Method::TRACE => TransactionPolicy::Pool,
            _ => TransactionPolicy::PerUnit,
        };
        let spec = UnitSpec::new(nest_rs::http::unit::REQUEST, ExecutorScope::Request, policy);
        run_unit(
            Some(&self.unit),
            spec,
            next.run(req),
            |result| matches!(result, Ok(resp) if resp.status().is_success() || resp.status().is_redirection()),
            |_| Err(Error::from_status(StatusCode::INTERNAL_SERVER_ERROR)),
        )
        .await
    }
}
```

## Step 4 — The Module

The activation seam an app imports. A `DynamicModule` that seeds the
connection at the factory phase, registers the interceptor, and binds your
unit of work as `Arc<dyn UnitOfWork>` — a **declaration** carrying the port's
`BACKEND_REMEDY`, so a second database driver imported beside yours fails the
boot naming both. Every edge resolves that binding once, when it mounts or
boots. Every field of the config is settable
from both the environment (`<PREFIX>_<NAMESPACE>__<KEY>`) and a pinned
struct — the framework-wide dual-path rule.

A factory names the outputs it reads as its inputs, a tuple — the pool's is
`(YourConfig,)` — so the boot runs it once they exist, wherever the imports
fall. It reads the config with `ConfigModule::resolved`, whose refusal names
the config when nothing resolved it: a factory returns it with `?`, a
`register` files it with `builder.refuse(..)`.

```rust title="crates/yourdb/src/module.rs"
use std::any::TypeId;
use std::sync::Arc;
use nest_rs::config::ConfigModule;
use nest_rs::core::{Collecting, ContainerBuilder, DynamicModule, Registering};
use nest_rs::database::{BACKEND_REMEDY, UnitOfWork};

pub struct YourDbModule;

impl YourDbModule {
    pub fn for_root(config: impl Into<Option<YourConfig>>) -> YourDbSetup {
        YourDbSetup { pinned: config.into() }
    }
}

pub struct YourDbSetup {
    pinned: Option<YourConfig>,
}

impl DynamicModule for YourDbSetup {
    fn module() -> TypeId {
        TypeId::of::<YourDbModule>()
    }

    fn register(self, builder: ContainerBuilder, _: Registering<Self>) -> ContainerBuilder {
        <YourDbContext as nest_rs::core::Discoverable>::register(builder)
    }

    fn collect(&self, builder: ContainerBuilder, _: Collecting<Self>) -> ContainerBuilder {
        let builder = ConfigModule::provide_feature(self.pinned.clone(), builder);
        builder
            .provide_factory_after::</* YourHandle */, (YourConfig,), _, _>(|container| async move {
                let config = ConfigModule::resolved::<YourConfig>(&container)?;
                // Your code: build your pool / client from `config`.
            })
            .provide_declared_factory_after::<Arc<dyn UnitOfWork>, (/* YourHandle */,), _, _>(
                BACKEND_REMEDY,
                |container| async move {
                    let unit = YourUnitOfWork::new(/* the handle from `container` */);
                    Ok(Arc::new(unit) as Arc<dyn UnitOfWork>)
                },
            )
    }
}
```

## Step 5 — Say your errors without their values

A database server words its refusal around the input it refused —
`invalid input syntax for type uuid: "…"` — and a driver's error repeats that
sentence in its own `Display` and in its causes. Every framework log line, a
dead letter's reason and a client's error frame read an error chain through
`nest_rs::core::error_message`, which asks each `SafeLink` about a link before
its `Display`: submit one, and your errors are said your way everywhere.

```rust title="crates/yourdb/src/error.rs"
use std::error::Error;

use nest_rs::core::SafeLink;

nest_rs::core::inventory::submit! { SafeLink::new(say) }

fn say(link: &(dyn Error + 'static)) -> Option<String> {
    let err = link.downcast_ref::<YourDbError>()?;
    // Your code: the error's kind and server code, the schema names it carries.
    Some(format!("yourdb error {}", err.code()))
}
```

A link your sayer claims is said by its sentence alone, and nothing below it
is read, so a cause repeating the server's message never reaches a line.
Keep identifiers — a code, a constraint, a table, a column — which are schema
an operator searches for, and drop every message. `nest-rs-seaorm` says a
`DbErr` as `database error 23505 on constraint "users_email_key", table
"users"`.

## Step 6 — Atomic blocks (optional)

`nest_rs::database::atomic(work)` asks the ambient executor for a block through
`Executor::atomic`. The default answers `None`, and `atomic` then refuses with
`AtomicError::Unsupported` without running the work — fail-closed, so a driver
that offers no block loses nothing but the feature. To offer one, return an
`AtomicBlock`: an executor of yours that the block runs on, settled once.

```rust title="crates/yourdb/src/executor.rs"
use std::future::Future;
use std::pin::Pin;
use std::sync::Arc;
use nest_rs::database::{AtomicBlock, AtomicError};

impl nest_rs::database::Executor for Executor {
    // … as_any, after_commit …

    fn atomic(&self) -> Option<Arc<dyn AtomicBlock>> {
        // Your code: a block nested in this handle's transaction — or a
        // transaction of its own when this handle holds none.
        Some(Arc::new(YourBlock::nested_in(self.clone())))
    }
}

impl AtomicBlock for YourBlock {
    fn settle(
        self: Arc<Self>,
        ok: bool,
    ) -> Pin<Box<dyn Future<Output = Result<(), AtomicError>> + Send>> {
        Box::pin(async move {
            // Your code: release the savepoint and hand the held after-commit
            // work to the enclosing handle when `ok`; roll it back and drop
            // that work otherwise.
            Ok(())
        })
    }
}
```

What a block owes, in order of how badly it goes wrong without it:

- **The enclosing unit waits for it.** A statement the unit issues while the
  block is open must not land inside the block's savepoint, or it rolls back
  with the block.
- **A failure inside poisons the block, not the unit.** Work that returns `Ok`
  over a failed statement settles as `AtomicError::Poisoned`.
- **A refused `RELEASE` or `ROLLBACK TO`, or a block dropped before it
  settled, leaves the unit unable to commit.** Nothing can vouch for what it
  writes next.
- **Nothing is sent before the first statement**, so a block that never
  queries costs no round trip.

`crates/nest-rs-seaorm/src/savepoint.rs` and `crates/nest-rs-seaorm/src/turn.rs`
are the reference shape.

## A query helper (sketch)

Services don't read the ambient context directly — they call a small helper
your driver ships. The helper reads the current executor, downcasts to
your enum, and hands the caller a store-native handle.

```rust title="crates/yourdb/src/executor.rs"
pub fn current_executor() -> Option<Executor> {
    nest_rs::database::current_executor()?
        .as_any()
        .downcast_ref::<Executor>()
        .cloned()
}
```

A service then writes `let exec = current_executor().ok_or(...)?;` and
issues queries against whichever variant came back — your problem from
here, against types your users already recognise.

## What the seam carries, and what stays store-native

The SeaORM-typed primitives — `Repo<E>`'s ambient
row-level filter via `Ability::condition_for`, the `#[expose]` response
mask, `Bind<A, S>`, `CrudService` — all read SeaORM's typed `Column` /
`EntityTrait` model layer, so a driver ships their equivalents in
store-native terms
(e.g. Postgres RLS, an ability-derived filter document, a per-collection
helper). What every driver does keep: transparent transactions on
every edge's units of work, the ambient executor across HTTP and workers, the
access graph and module wiring, structured observability under
`nest_rs::orm`.
