Two seams turn a handler's error into a response, in the order the
framework tries them:

1. **An exception filter** — a layer that catches one error type, or every
   error, at the route, the controller or the whole app, closest first.
2. **`ResponseError`** on a feature's error type — the default mapping the
   framework answers with when no filter answered. Lives next to the error in
   the crate that owns it.

`ExceptionFilter` is a [`Layer`](/fundamentals/request-lifecycle/) sub-trait in
`nest_rs::core`, edge-neutral like [interceptors](/fundamentals/interceptors/),
and dedups by [`TypeId`](https://doc.rust-lang.org/std/any/struct.TypeId.html)
across the global, controller and method scopes.

```rust title="nest_rs::core::ExceptionFilter"
#[async_trait]
pub trait ExceptionFilter: Layer {
    /// The error it catches, found anywhere in the failure's source chain —
    /// `dyn Error + Send + Sync` for every one.
    type Exception: Catch + ?Sized;

    async fn catch(&self, exception: &Self::Exception, cx: &mut UnitContext<'_>) -> Caught;
}
```

<Aside type="caution">
**HTTP runs them today**, on a route, a self-mount's request (`/graphql`,
`/mcp`, a WS upgrade) and what the router answers itself, and so do
[GraphQL fields](#on-a-graphql-field),
[WebSocket messages](/websockets/messages/#interceptors-filters-and-pipes),
[MCP tool calls and prompt fetches](/mcp/#layers-around-an-operation),
[jobs](/queue/#layers-around-a-job), [ticks](/schedule/#layers-around-a-tick)
and [listener calls](/events/dispatch/#layers-around-a-listener-call). A
WebSocket `#[on_connect]` / `#[on_disconnect]` hook runs none yet:
`#[use_exception_filters]` on one is a compile error.
</Aside>

## Install

```bash frame="terminal"
cargo add nest-rs
```

The trait, its specs and `Caught` live in `nest_rs::core`, which every build
has: no feature turns them on.

## The default: framework error types, already mapped

The plumbing failures every service runs into — database errors,
input validation, authentication, OAuth wire codes — ship as framework
types with their HTTP mapping already wired:

| Error | Source | Maps to |
|-------|--------|---------|
| `DbErr`, through `?` into `ServiceError` | `nest_rs::seaorm` | `409` for a unique violation, `404` for a row a write found gone, `503` for a statement cancelled at its bound, else `500` (`code: INTERNAL`, no `detail`) |
| `ServiceError::Validation(ValidationErrors)` | `nest_rs::seaorm` | `422` |
| `AuthError::*` | `nest_rs::authn` | `401` + `WWW-Authenticate: Bearer` |
| `AuthError::Unavailable` | `nest_rs::authn` | `503`, a `Retry-After` when the failing party gave one — an outage is not a credential signal |
| `CredentialError` | `nest_rs::authn` | `401` (opaque `"invalid credentials"`) |
| `TokenError::*` | `nest_rs::oauth::server` | RFC 6749 wire codes (`400` / `401`, the `401` with the `Basic` challenge of a client refused over HTTP Basic); `server_error` at `500`, or `503` for a dependency that did not answer |

A service returns the framework type directly; `?` flows it to the
boundary; the impl decides status and body. What a `5xx` among them keeps
from the client — the database's error, the store that did not answer — is
filed by the edge, never by the type as it renders: once the answer is
final, at `error`, at `warn` behind a `503`, on `nest_rs::http`. Every row
above implements `nest_rs::http::ResponseError`, which is what makes the `?`
legal — a
handler returning `Result<Json<T>>` propagates any of them with no
`map_err`. No per-feature `error.rs` for these — the framework owns them
once, every feature reuses them.

```rust title="crates/features/src/users/service.rs"
use nest_rs::seaorm::ServiceError;

impl UsersService {
    pub async fn create(&self, input: CreateUser) -> Result<User, ServiceError> {
        input.validate()?;                              // → ServiceError::Validation
        let row = active_for_new_user(input).insert(&Repo::<Users>::conn()?).await?;  // → ServiceError::Conflict on a taken email
        Ok(User::from(&row))
    }
}

#[post("/")]
async fn create(&self, Valid(input): Valid<Json<CreateUser>>)
    -> Result<Json<User>, ServiceError>
{
    Ok(Json(self.svc.create(input).await?))
}
```

<Aside type="note">
The data-layer HTTP mapping lives behind the `http` feature of
`nest-rs-seaorm`, which only the umbrella's `http` turns on: a worker built
with `queue,seaorm` and no `http` links no HTTP stack.
</Aside>

### When a feature defines its own error type

Write a per-feature error **only** when the failure is genuinely
domain-specific — a wire contract a consumer reads, a security-critical
opaque variant. In that case the type lives in `<feature>/error.rs`
and its `nest_rs::http::ResponseError` impl sits next to it, with nothing
beyond the `http` feature its controllers already need. Most features never
need this — they compose the framework's types.

`ResponseError` is HTTP's seam. An error that also crosses GraphQL,
WebSockets or MCP implements `nest_rs::core::ToProblem` once: the `Problem`
it says — a status, a `Code`, a detail — is what those edges answer, each in
its own form (see [GraphQL errors](/graphql/errors/)). A resolver, a
gateway handler or an MCP tool returning the error is read by its type; an MCP
tool answering `McpError` converts it with `nest_rs::mcp::problem_error`. HTTP
reads `ResponseError`,
not `ToProblem`: a route answers a `Problem` only when the error is one or
carries one in its chain. What no seam answers — no `ResponseError`, no
`ToProblem` where the edge reads it, no framework type in its chain — is
answered opaquely on every edge, and its whole chain is filed once at
`error`, as is the chain behind a `5xx` problem or a `5xx` a `ResponseError`
answers: a failed handler is never logged nowhere.

## Exception filters

When the answer should depend on the concrete error type — `DomainError`
becomes `422`, every other failure keeps its own answer — write an exception
filter. It names the type it claims in `Exception`; a failure whose chain does
not carry that type never reaches it, and one that does gets the filter's
`catch`:

```rust title="apps/api/src/exception_filter.rs"
use nest_rs::core::{Caught, ExceptionFilter, Layer, UnitContext, async_trait, injectable};
use nest_rs::http::{HttpView, IntoResponse, ProblemDetails, ResponseError, StatusCode};

#[derive(Debug, thiserror::Error)]
#[error("domain failure: {0}")]
pub struct DomainError(pub String);

impl ResponseError for DomainError {
    fn status(&self) -> StatusCode {
        StatusCode::INTERNAL_SERVER_ERROR
    }
}

#[injectable]
#[derive(Default)]
pub struct DomainErrorFilter;

impl Layer for DomainErrorFilter {}

#[async_trait]
impl ExceptionFilter for DomainErrorFilter {
    type Exception = DomainError;

    async fn catch(&self, err: &DomainError, cx: &mut UnitContext<'_>) -> Caught {
        let problem = ProblemDetails::unprocessable().with_detail(format!("caught: {err}"));
        match HttpView::of(cx) {
            Ok(view) => Caught::Answered(view.respond(problem.into_response())),
            Err(_) => Caught::Declined,
        }
    }
}
```

`catch` answers one of three ways:

| `Caught` | What the client reads |
|---|---|
| `Answered(settled)` | the reply the filter wrote through the edge's view |
| `Problem(problem)` | a `nest_rs::core::Problem`, which every edge renders in its own form — the problem document on HTTP |
| `Declined` | whatever the next filter answers, else the default |

The `ResponseError` impl is what lets a handler's `?` carry `DomainError`; its
status is the **default** the filter replaces. Drop the filter and the same
handler answers the opaque `500` from that status — `code: INTERNAL`, no
`detail`.

A filter reads the request it answers as a guard does, through
`HttpView::of(cx)?.request()` — its method, its headers, its extensions — so it
can answer in the media type the client accepts; only the body is gone once
the handler read it. What the client is finally sent decides what is filed,
whatever the failure's type: a failure a filter answers with a `4xx` files
nothing, and one it answers with a `5xx`, its own reply or a `Problem`, files
the chain the client is not told once, at `error`, at `warn` behind a `503`.
Drop the filter above, and `DomainError`'s default `500` files
`domain failure: boom` the same way.

Bind it like any other layer: for the whole app with
`App::builder().use_exception_filters_global([exception_filter::<DomainErrorFilter>()])`,
on a controller with `#[use_exception_filters(DomainErrorFilter)]`, or beside a
verb:

```rust title="crates/features/src/users/http/controller.rs"
#[get("/domain")]
#[use_exception_filters(DomainErrorFilter)]
async fn domain(&self) -> Result<&'static str, DomainError> {
    Err(DomainError("boom".into()))
}
```

That answers `422` with `caught: domain failure: boom`.

### On a GraphQL field

A resolver binds filters as a controller does — `#[use_exception_filters]` on
the `#[resolver]` struct or beside a root field — and the app's run there too.
A field has no reply a filter writes through a view, so a filter answers with
a `Problem`: the field's error then carries its message and its code under
`extensions.code`, while the operation's other fields resolve as they would:

```rust title="crates/features/src/orders/graphql/exception_filter.rs"
#[async_trait]
impl ExceptionFilter for LedgerConflict {
    type Exception = LedgerRefused;

    async fn catch(&self, _: &LedgerRefused, _: &mut UnitContext<'_>) -> Caught {
        Caught::Problem(Problem::new(409, code::CONFLICT).with_detail("the ledger is busy"))
    }
}
```

A `#[field_resolver]` runs only the filters declared on it. What no filter
answers keeps [GraphQL's own rule](/graphql/errors/).

### Every error: the catch-all

`type Exception = dyn Error + Send + Sync` claims every failure — the
envelope a product answers every error in. Bound globally, it also shapes
what no route answers: a `404` for a path nothing serves, a `405` for a
method a path does not take, an API version the header or media-type
strategy refuses, and a self-mount's own error, such as `/graphql` refusing
an oversized batch.

```rust
#[async_trait]
impl ExceptionFilter for Envelope {
    type Exception = dyn std::error::Error + Send + Sync;

    async fn catch(&self, _: &Self::Exception, cx: &mut UnitContext<'_>) -> Caught {
        /* answer every failure in the product's own envelope */
        Caught::Declined
    }
}
```

### Closest first

The method's filters are tried first, then the controller's — or the
resolver's — then the app's; the first that answers wins. A typed filter on a route therefore answers
before a catch-all on its controller, and a `Declined` hands the failure on.

### A failed unit stays failed

A filter changes what the client reads, never whether the unit failed: a
mutating request whose handler failed rolls its writes back, whatever status
the filter answered — a `200` included. A guard's refusal never reaches a
filter: it is answered by the guard stage, before the filters run.

## TypeId dedup — redeclaration is free

An exception filter declared globally and redeclared on a controller or a
method runs once, at the broadest scope that declares it — the same
[defense-in-depth rationale as guards](/fundamentals/guards/#declare-on-the-provider):
a portable controller that needs a domain filter redeclares it, and the dedup
keeps the cost at zero.

## Where filters sit in the chain

Exception filters run around the handler stage, after the guards and the
posture's class gate, so a failure of the handler or of any handler-stage
interceptor reaches them. The full order is on
[the request lifecycle](/fundamentals/request-lifecycle/#nesting-order).

## Choosing between the seams

| Seam | Where it lives | When to reach for it |
|-------|----------------|-----------------|
| `ResponseError` on an error type | Framework crate that owns the error (`nest-rs-seaorm`, `nest-rs-authn`), or `<feature>/error.rs` for a domain-specific variant | Default. Every handler returning that error gets the same mapping |
| A typed `ExceptionFilter` | A provider | The mapping depends on the **error type** across many routes |
| A catch-all `ExceptionFilter` | A provider | One envelope for every failure, bound on a route, a controller or the app |

Reach for `ResponseError` first.

## Validation envelopes

The framework's pipe error renderer already returns an RFC 9457
`application/problem+json` body:

```json
{ "type": "…#status.400", "title": "Bad Request", "status": 400, "detail": "…", "errors": { /* ... */ } }
```

If your API uses a different envelope (`{ ok: false, error: { ... } }`), bind
one catch-all exception filter globally that re-renders it. The error itself
stays pure.
