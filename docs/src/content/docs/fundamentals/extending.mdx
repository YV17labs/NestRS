Some parts of NestRS are meant to be replaced: the ORM, the queue backend, the
rate-limit store, a social provider. This page is the contract you implement to
do that, and — just as important — how the framework decides what is swappable
in the first place.

## What a swappable concern owes you

A concern you can plug into ships an **extension contract**: the trait you
implement, the seam that makes your implementation reachable from the container,
and the sentence describing what happens when there is more than one.

If that contract cannot be written, the concern is **not** swappable, and the
crate says so in its module docs. A trait with no contract beside it would be an
extension you have to reverse-engineer; a client with no trait at all is a closed
door that looks open. Neither is left to inference.

## Two questions decide the shape

### Who owns the driver problem?

This is the question most likely to surprise you, because it explains why some
ports look thin.

**Delegated.** A third-party library is *already* the multi-driver abstraction,
and the NestRS crate is a thin adapter over it that does not let the vendor's
types leak.

| the crate that *binds* the port | delegates to | which already drives |
|---|---|---|
| `nest-rs-seaorm` | `sea-orm` | PostgreSQL, the one engine nestrs builds it for |
| `nest-rs-storage` | `object_store` | S3, GCS, Azure, local filesystem, in-memory — of which the store's URL opens `s3` and `memory` |

Note which column the crate names sit in. The question is answered by whoever
**binds** the port, never by the crate that declares it — `nest-rs-database`
depends on the kernel and `thiserror` alone, and `nest-rs-queue` names no
Redis client. A port crate depending on nothing is the normal case.

When a concern is delegated, the port exists for exactly one move — swapping the
**vendor** — so its contract is thin and it declares **no configuration of its
own**. That thinness is the correct outcome, not an unfinished one. If you want
a different object store, you do not write a NestRS driver: you point
`object_store` at it.

**Owned.** Nothing abstracts the concern, so NestRS defines the trait, the
registration seam and the arbitration sentence itself — `ThrottlerStore`,
`JobProducer`, `OccurrenceLock`, `SocialProvider`, `Strategy`. An adapter then
carries only its transport: `nest-rs-redis` drives Redis Streams itself —
handing jobs over, renewing their leases, settling each outcome — while what a
job attempt *is* — its id, its retries and their backoff, its trace, the
capabilities a backend declares — is `nest-rs-queue`'s, and so is the consume
loop its `QueueWorker` runs. A second queue backend implements the port's
`JobProducer` and `JobConsumer`, and inherits the rest.

### What selects the active implementation?

Three modes. They are not interchangeable, and which one a concern uses tells
you where your configuration goes.

**By import.** Exactly one implementation, chosen by which binding your app
imports beside the port's module. Consumers inject `dyn Port` and never name the
backend, so swapping it is a composition-root edit rather than a change to your
handlers. The port's own default is an *ordinary* factory, so a vendor binding
supersedes it wherever it sits in `imports`; two vendor bindings contest, and
the boot fails naming the port and the remedy. `ThrottlerStore`,
`dyn JobProducer` (queue), `dyn OccurrenceLock` (schedule) and `dyn UnitOfWork`
(database) each word that remedy once, as their crate's `BACKEND_REMEDY`.

```rust title="apps/api/src/module.rs"
ThrottlerModule::for_root(None),   // the port: policy, guard, counters in this process
RedisThrottlerModule,              // the binding: counters shared across instances
```

**By type parameter.** You name the implementation in an alias, and the generic
host is instantiated with it. No arbitration exists and none is owed: two
instantiations are two distinct types, so nothing can be contested.

```rust title="crates/features/src/authn/strategy.rs"
pub type AuthnStrategy = JwtStrategy<Claims>;
pub type AuthnGuard = nest_rs::authn::AuthnGuard<AuthnStrategy>;
```

The same shape carries `AbilityGuard<F: AbilityFactory>` and
`EndpointGuards<V, G>`. This is the mode NestRS uses most.

**By configuration.** The import only **opens the gate** — for a social
provider, the provider's own module beside `SocialModule`; configuration decides
which opened members are active, from zero to all of them. Registering a
provider is not activating it — that distinction is the whole mechanism.

| `<PREFIX>_SOCIAL__<KEY>__*` | outcome |
|---|---|
| complete | the provider is active |
| absent entirely | inert, with one boot `warn` — its routes 404 |
| partial, or invalid | **the boot fails**, naming the provider |

## Where your configuration lives

It follows from the contract; nothing is arbitrated.

**A port owns a config namespace if and only if its contract requires you to
honour one.** The throttler's does, so `<PREFIX>_THROTTLER__LIMIT` and
`<PREFIX>_THROTTLER__WINDOW_SECS` survive a backend swap unchanged — they are the
policy every store honours, and your store reads them through the shared seam. A
store whose counters leave the process adds the port's
`<PREFIX>_THROTTLER__PSEUDONYM_KEY`: the port, not the store, keys each bucket
under a pseudonym before any store sees it.
The queue's does too: its worker is the port's, so the drain window,
`<PREFIX>_QUEUE__SHUTDOWN_TIMEOUT_SECS`, is the same on every backend.

A delegated port's contract requires nothing of you, so it owns no
namespace. Your own settings take their namespace from where they are
declared — **read off the path, exactly as a type name is**: your crate's
word (a package's subject, `nestrs-kafka` → `<PREFIX>_KAFKA__*`, by the
[naming rule](/semver/#naming-a-package)), then the binding folder's when the
config sits in one, joined by `__`. The resource your crate opens is its own subject, so its config sits at the
crate root and wears your crate's word: `nest-rs-redis/src/config.rs` →
`RedisConfig` → `<PREFIX>_REDIS__*`, and `nest-rs-seaorm/src/config.rs` →
`SeaOrmConfig` → `<PREFIX>_SEAORM__*`. A setting one binding owns sits in that
binding's folder and wears both words — `nest-rs-redis/src/queue/config.rs`
→ `RedisQueueConfig` → `<PREFIX>_REDIS__QUEUE__*`. From the variable an operator can name your crate and
your type; from your module a developer can name the variable.

Selection by configuration is the case where the member is a folder of your
crate, hence two segments — `<PREFIX>_SOCIAL__GITHUB__*` beside
`<PREFIX>_SOCIAL__GOOGLE__*`. Selection by type parameter needs no namespace at
all. Nothing else needs either.

## Worked example — a different ORM

`nest-rs-database` ships only the seam: the `Executor` trait, the `ExecutorScope`
tag, and the installers that keep "the current handle on a unit of work" in the
request's ambient context, which carries it across the framework. Its own
module docs carry the contract:

1. Implement `Executor` on the type representing your handle — a pool, a
   transaction, or an enum forwarding to either.
2. Ship a module that wraps each HTTP request in `with_request_executor` with
   your `Arc<dyn Executor>`. Do the same with `with_job_executor` for worker
   transports.
3. Provide your own query API that calls `current_executor` and downcasts to
   your concrete type.
4. Optionally, override `Executor::atomic`, so `nest_rs::database::atomic` runs
   a block on your store; without it the block refuses, fail-closed. The
   [driver guide](/database/writing-a-driver/) shows the shape.

Step 3 is deliberate. `Repo`, `CrudService` and `Bind` couple tightly to SeaORM's
`EntityTrait` and `Model` — that coupling is where their leverage comes from, and
a generic abstraction over them would lose most of it. Your integration ships its
own row-level-filter equivalent rather than inheriting one.

## Worked example — a value every unit carries

A package that needs a per-request value — a tenant, a locale, a set of
feature flags — makes it ambient rather than asking every edge to pass it
along. Its type says how far it travels:

```rust title="crates/yourpkg/src/locale.rs"
use nest_rs::core::AmbientValue;

pub struct Locale(pub String);

impl AmbientValue for Locale {}
```

Implementing `AmbientValue` is the line that lets it travel. By default the
value crosses every place the unit continues — a streaming body, a DataLoader
batch, a task handed to `TaskContext`, work held for the commit and the
listeners of an event the unit emits, a socket's next messages — and never
into a job's envelope: a job is system work, run later and elsewhere, and
carries only the envelope's own keys — the trace, the actor, the tenant and
W3C `baggage` — so a value whose `carry` lets it into an envelope still crosses
nothing. A value that must not outlive the unit says where it stops:

```rust title="crates/yourpkg/src/budget.rs"
use std::sync::Arc;
use nest_rs::core::{AmbientValue, Continuation};

pub struct QueryBudget(pub u32);

impl AmbientValue for QueryBudget {
    fn carry(self: Arc<Self>, into: Continuation) -> Option<Arc<Self>> {
        (into == Continuation::Batch).then_some(self)
    }
}
```

Your layer adds the value around the unit:

```rust title="crates/yourpkg/src/interceptor.rs"
async fn intercept(&self, req: Request, next: Next<'_>) -> Result<Response> {
    let locale = Arc::new(Locale(negotiated(&req)));
    with_ambient(locale, next.run(req)).await
}
```

Anything the request reaches reads it back — a service, its streaming body,
the DataLoader batches its fields trigger:

```rust title="nest_rs::core::ambient"
let locale = ambient::<Locale>();
```

Reading is not deciding: a service may read who the caller is this way, as it
reads a `Ctx<T>`, but an authorization decision still belongs in a guard.

## Worked example — a transport of your own

What serves an app — the HTTP server, the queue worker, the scheduler — is a
`Transport`, and your package can ship one: a metrics scrape port, a tail of a
change feed, a consumer of a broker. Its module attaches it with
`provide_transport`, and `App::run` builds it from the assembled container,
configures it, has it listen and serves it beside the others:

```rust title="crates/yourpkg/src/module.rs"
use nest_rs::core::{ContainerBuilder, Module, Registering};

pub struct MetricsModule;

impl Module for MetricsModule {
    fn register(builder: ContainerBuilder, _: Registering<Self>) -> ContainerBuilder {
        builder.provide_transport(|container| MetricsPort::from_container(container))
    }
}
```

The boot lines name it `MetricsPort`, read off its type. The builder takes a
function, not a closure holding a value: what your transport needs comes from
the container, where the app's `for_root` value has already landed. It binds
what it serves in `listen`, never in `serve`, and states a finite
`stop_bound`, the longest it takes to stop once told to.

A transport adds no edge — the edges are the framework's — so it does one of
three things: it serves infrastructure no caller identifies, it carries system
work into an edge that exists (publishing an event, pushing a job) under the
actor `Correlation::continued` carries, or, when it is request-shaped and must
authenticate, it rides HTTP as a self-mount whose guards decide. Your
transport's own code never makes an authentication or authorization decision.

## Worked example — a social provider

`nest-rs-social` ships an open provider contract. You publish an independent
crate that depends on it, implements `SocialProvider` and `SocialProviderConfig`,
ships the module that opens your provider, and submits one `SocialProviderEntry`
naming that module — the same public seam the first-party GitHub and Google
providers use (`GithubSocialModule`, `GoogleSocialModule`), with no
crate-private shortcut.

A social provider is not a DI provider: it is never injected by type, only
reached through `SocialRegistry` as `Arc<dyn SocialProvider>`. So discovery is
gated by your module — an app that never imports it never holds your provider —
and within that gate your provider's own `#[config]` decides its fate, per the
table above. The module is not ceremony: a crate that no code names is not
linked at all, so a dependency line alone would leave your registry entry out
of the binary, and the app's import is what names your crate.

## Where each contract is written

Every port above carries its contract on the page that owns the concern, not in
the crate's module docs — so start from the page rather than from docs.rs:

| Port | Contract |
|---|---|
| `JobProducer` | [queue / writing a driver](/queue/writing-a-driver/) |
| `OccurrenceLock` | [schedule / writing an occurrence lock](/schedule/writing-a-lock/) |
| `UnitOfWork` / the database binding | [database / writing a driver](/database/writing-a-driver/) |
| `ThrottlerStore` | [rate limiting / writing a store](/rate-limiting/writing-a-store/) |
| `Strategy` | [security / authentication](/security/authentication/) |
| `SocialProvider` | [security / social login](/security/authentication/social-login/) |

**`nest-rs-storage` is the delegated case at its plainest.** There is no
driver trait to implement: the store's URL picks the `object_store` backend —
`s3://` for AWS S3 and the servers speaking its API, `memory:///` for
development and tests — as a Redis URL's scheme picks its topology. This
release opens those two. Another backend `object_store` drives (`gs://`,
`az://`, `file://`) is a scheme the crate learns, added in a minor without an
API change for the features that inject `Storage`; if you need one, say so on
the issue tracker — that is the signal that decides it.
