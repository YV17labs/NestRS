A guard is written once and bound wherever a caller reaches a unit: an HTTP
route, a GraphQL field, a WebSocket message, an MCP tool call or prompt fetch.
It writes its decision once, in `check`, which runs on every unit and, through
`check_http`, on an HTTP request too; it overrides `check_http` only where the
request differs from the unit. It declares, with one `GuardFor` line per edge,
that it checks those units. A job, a tick and a listener call have no caller,
so no guard runs there: guard where the work is produced.

```rust title="crates/features/src/posts/guard.rs (from the demo, abridged)"
#[async_trait]
impl Guard for PostAuthorGuard {
    async fn check_http(&self, cx: &mut UnitContext<'_>) -> Result<(), Denial> {
        let claims = cx.require::<Claims>()?;
        Self::attach_author(cx, &claims)
    }

    async fn check(&self, cx: &mut UnitContext<'_>) -> Result<(), Denial> {
        let claims = cx
            .ambient::<Claims>()
            .ok_or_else(|| Self::user_required("no_claims"))?;
        Self::attach_author(cx, &claims)
    }
    // …
}

impl GuardFor<HttpView> for PostAuthorGuard {}

impl GuardFor<GraphqlView> for PostAuthorGuard {}
```

Both entries attach the author the handler writes with. They differ where the
request differs from the unit: on a gated route `AuthnGuard` already refused
an anonymous caller, so missing claims there are a wiring defect — `require`
answers a `500` filed once at `error` — while a GraphQL field reads what the
`/graphql` request's guards made ambient, where an anonymous caller is
legitimate and refused with a `403`.

## Two entries, four edges

A guard writes `check`, overrides `check_http` where the request differs, and
the framework runs each at its own seam:

| Entry | Runs | Bound by |
|---|---|---|
| `check_http` (`check` unless overridden) | post-routing on the request, before the handler; on a WS upgrade; on the `/graphql` and `/mcp` requests | `#[controller]` / `#[routes]`, and the `#[gateway]` struct |
| `check` | per GraphQL field, and in front of the federation root fields | `#[resolver]` / `#[operations]` |
| `check` | once per inbound envelope, after the upgrade | beside a `#[subscribe_message]` |
| `check` | once per `#[tool]`, `#[prompt]`, `#[resource]` or `#[resources]` operation, inside rmcp's dispatch | `#[mcp]` host / `#[tools]` operation |

`use_guards_global([...])` reaches every edge at every entry it
implements. `/graphql` and `/mcp` run the pool at their request and in each
operation: `check_http` once on the request, `check` once per operation it
carries — so a global `ThrottlerGuard` rate-limits the `/mcp` request and each
tool call. A global guard writing only `check` runs it on every request too,
the route, the WS upgrade and the `/graphql` and `/mcp` requests included; one
whose decision is the unit's alone admits the request in `check_http`.

The three multiplexed edges need one thing on top: the guards that build
the caller's `Ability` at the request, because a unit below the request does
not see the request. A gateway binds them on its struct, for its upgrade; on
`/graphql` and `/mcp`, which no controller owns, a module declares them —
`EndpointGuards<GraphqlView, (AuthnGuard, AuthzGuard)>` — and the transport
runs them beside the global pool, each guard once. What they attach is ambient
for every operation the request carries; below it you bind ordinary guards as
usual, and a handler reads what they attached as a `Ctx<T>` parameter on every
edge. That wiring — `AuthzGraphqlModule`, `AuthzWsModule`, `AuthzMcpModule`,
and what each one gates — lives on
[Endpoint guards](/security/authorization/endpoint-guards/),
with the connection-vs-message split on
[WebSocket guards](/websockets/guards/).

## A guard declares the edges it checks

A guard writing neither entry admits — right as "this guard does not apply to
that edge", and the reason a guard bound where it has no check would compile
and pass everything. `GuardFor<V>`, `V` the view of the units a site
dispatches, closes that:

| Bound at | Requires | Because it runs |
|---|---|---|
| `#[controller]` / `#[routes]`, `#[gateway]` struct | `GuardFor<HttpView>` | `check_http`, `check` unless overridden |
| `#[resolver]` / `#[operations]` | `GuardFor<GraphqlView>` | `check` |
| beside a `#[subscribe_message]` | `GuardFor<WsView>` | `check` |
| `#[mcp]` host / `#[tools]` operation | `GuardFor<McpView>` | `check` |

Declare it next to the entry it covers — `impl GuardFor<GraphqlView> for
RequireAdmin {}` — and the binding compiles. Bind a guard that lacks it and it
does not, with a diagnostic naming the view and the way out. `AuthnGuard` is
the guard it catches most often: it checks HTTP requests only, which is why a
resolver binds `AuthzGuard` alone and leaves authentication to the guards
at the `/graphql` request. Bound on one anyway:

```text frame="terminal"
$ cargo check -p features
error[E0277]: `nest_rs::nest_rs_authn::AuthnGuard<JwtStrategy<Claims>>` does not declare that it checks `GraphqlView` units
   --> crates/features/src/users/graphql/resolver.rs:14:14
    |
 14 | #[use_guards(AuthnGuard, AuthzGuard)]
    |              ^^^^^^^^^^ bound at a site whose units are `GraphqlView`
    |
    = note: `check` admits by default and `check_http` runs it, so a guard bound here without its decision would pass every unit silently
    = note: write the guard's decision in `Guard::check` (overriding `Guard::check_http` only where the HTTP request differs from the unit), then declare `impl GuardFor<GraphqlView> for nest_rs::nest_rs_authn::AuthnGuard<JwtStrategy<Claims>> {}`
```

The declaration never proves the *entry* is overridden — the defaults give
every guard both. It proves you **declared** that this guard checks this
edge's units. On HTTP the gap is closed: a guard declaring `GuardFor<HttpView>`
and writing only `check` refuses requests with it. On an in-band edge it is
the line a reader sees: a guard declaring `GuardFor<GraphqlView>` and writing
only `check_http` still admits every field. An empty `impl Guard for X {}` satisfies the compiler and
passes every request; `GuardFor` is what turns that into an error at the
`#[use_guards]` line rather than a chain entry that guards nothing. A guard
whose one `check` is the same on every edge declares it once for all of them,
`impl<V: UnitView> GuardFor<V> for X {}` — `ThrottlerGuard` does.

A guard bound **globally** takes no `GuardFor`, and that is a deliberate hole
rather than an oversight. A global guard serves whichever edges it
implements — its `check_http` on the request, its `check` on every unit.
Requiring `GuardFor<HttpView>` there would refuse a GraphQL-only guard, and
the alternative is four global lists where the developer wrote one. So an
empty guard registered globally still passes everything: `GuardFor` binds
`#[use_guards]` sites, not the pool.

A guard on the `#[gateway]` **struct** declares `GuardFor<HttpView>`, not
`GuardFor<WsView>` — the upgrade is an HTTP `GET`, and `WsView` belongs to the
per-message scope.
