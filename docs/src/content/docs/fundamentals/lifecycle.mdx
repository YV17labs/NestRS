A binary has a beginning and an end. Between the container being built
and the first request served, providers may need to warm a cache, open
a long-lived connection, or check a migration ran. When the process
receives a signal, those same providers want a chance to flush, drain,
or report before the runtime tears down. The lifecycle hooks are where
that work hangs.

A provider opts in by tagging methods on an `impl` block with
`#[hooks]`. Each tagged method names exactly one phase. The framework
collects every hook at link time and drains them phase by phase — init
phases after wiring and before serving, shutdown phases after the
transports stop.

```rust title="crates/features/src/blog/service.rs"
use nest_rs::core::{hooks, injectable};

#[injectable]
#[derive(Default)]
pub struct BlogService;

#[hooks]
impl BlogService {
    #[on_application_bootstrap]
    async fn warm(&self) -> anyhow::Result<()> {
        tracing::info!(target: crate::blog::TARGET, entries = 0, "cache warmed");
        Ok(())
    }

    #[on_application_shutdown]
    async fn flush(&self) {
        tracing::info!(target: crate::blog::TARGET, pending = 0, "buffers flushed");
    }
}
```

`crate::blog::TARGET` is the log target the generated feature declares at the
top of `blog/mod.rs` — one constant the feature's files name, never a literal
each one retypes.

The `#[hooks]` block is separate from the one `#[injectable]` decorates
— a provider keeps its primary `impl` for methods, and adds a second,
hook-only `impl` the macro scans. The phase attributes
(`#[on_application_bootstrap]`, …) need no import; `#[hooks]` consumes
them.

The host **must** be a **singleton** provider — the phases resolve it
with `Container::get::<Host>()`, outside any request, which answers for
exactly one registration shape. Three hosts can never satisfy that, and
all three are compile errors naming the fix rather than a notice at boot:

| Host | Why it cannot |
|---|---|
| an edge host (`#[controller]`, `#[gateway]`, `#[resolver]`, `#[mcp]`) | registers metadata; the instance is built at mount |
| `#[injectable(scope = request)]` | the container holds a factory, not a value |
| `#[injectable(scope = transient)]` | resolution would build a throwaway, and the hook's effects would be dropped |

Each decorator **records** which of these it built, as
`ProviderResidency::SINGLETON`, and `#[hooks]` reads it. So the refusal
is not a marker you can satisfy by implementing it: contradicting what
your decorator already wrote is a coherence error. A provider you
register by hand with `ContainerBuilder::provide` is the one case nothing
has spoken for, and it says so itself:

```rust title="apps/api/src/provider.rs"
impl ProviderResidency for MyHandWrittenProvider {
    const SINGLETON: bool = true;
}
```

A fourth shape is your composition rather than a contradiction, so it warns
at boot instead. A host the container holds under some *other* key has
nothing under `Foo` itself — bound as `providers = [Foo as dyn Trait]`,
imported through a `for_root`, or registered by hand under a name. Move the methods to a provider listed under its own type.
Listing the same host twice is **not** the repair it looks like: each
binding runs the constructor, so the hooks fire on one instance while
everything injecting `Arc<dyn Trait>` holds another.

## The five phases

Two run on the way up, three on the way down. They drain in this fixed
order:

| Phase | Attribute | When |
|-------|-----------|------|
| **Module init** | `#[on_module_init]` | After the container is built and transports configured, before serving. |
| **Application bootstrap** | `#[on_application_bootstrap]` | After every module-init hook has run, still before serving. |
| **Module destroy** | `#[on_module_destroy]` | After the transports stop. |
| **Before shutdown** | `#[before_application_shutdown]` | After every module-destroy hook has run. |
| **Application shutdown** | `#[on_application_shutdown]` | Last — after every before-shutdown hook has run. |

The container is flat, so the init pair isn't about per-module
resolution order the way a tree-shaped framework would split them —
both run against the assembled container. The two names exist so you
can express "everyone's `on_module_init` finishes before anyone's
`on_application_bootstrap` starts": late hooks see the side effects of
early ones. The three shutdown phases give the same staged unwind in
reverse-intent order.

## Method shape

A hook method takes `&self`, and is an `async fn` or a plain `fn` — only
an `async fn` is awaited. Its return is either:

- **nothing** — the hook is infallible (`async fn flush(&self)`), or
- **`Result<(), E>`** where `E: Into<anyhow::Error>` — the hook can
  fail, and the framework folds the error into the phase outcome.

```rust title="fallible and infallible hooks"
#[on_module_init]
async fn check(&self) -> Result<(), MyError> { /* ... */ Ok(()) }   // fallible

#[on_module_destroy]
async fn drain(&self) { /* ... */ }                                  // infallible
```

A hook that needs another provider **injects it** — there is no
attribute to declare "run after `OtherService`'s hook." Cross-provider
init dependencies are expressed through the DI graph, not the lifecycle
registry.

## Ordering and failure

Within a phase, hooks run **sequentially** in `(provider, method)` name
order — stable across builds, never parallel. The two halves of the
lifecycle treat failure differently, and deliberately:

- **Init is strict.** `on_module_init` then `on_application_bootstrap`
  run one hook at a time; the **first error aborts boot** with a
  message naming the provider, method, and phase. Nothing is listening
  yet, so a failed warm-up never leaves a half-started server accepting
  traffic.
- **Shutdown is exhaustive.** The three teardown phases start every hook
  even if one fails or panics — either is logged at `error` on the
  `nest_rs::lifecycle` target, naming the hook, and the next hook still
  runs, so one provider's botched cleanup can't skip another's. (At init a
  panic aborts the boot like an error does, with the same sentence naming
  the hook.)
- **Shutdown is bounded — once, for all of it.** The three phases share one
  five-second budget (`SHUTDOWN_HOOKS_TIMEOUT`), not five seconds each: a
  hook still waiting when it is spent is abandoned — dropped where it waits,
  so what it had not done stays undone — and a `warn` names its phase,
  provider, method and module. Every hook after it still starts, and is
  polled once: one that finishes without waiting (a count logged, a buffer
  handed to a channel) finishes, one that waits is abandoned at once, with
  its own `warn`. The bound reaches a hook that awaits; one that blocks its
  thread is past any timer's reach.

The budget is one of the bounded steps on [the way down](#the-way-down), and it
is sized against their sum. A bound per hook could not hold a sum — four hooks
that hang would spend twenty seconds — which is why it is a budget.

```text frame="terminal"
Error: lifecycle hook MigrationGuard::check (OnModuleInit) failed: pending migrations
```

## Where it sits in the run

`App::run` walks a fixed sequence. The hooks bracket the serving window:

```
build container
→ attach + configure transports
→ on_module_init            ┐ strict — first error or panic aborts boot
→ on_application_bootstrap  ┘
→ serve (until SIGINT / SIGTERM, or a transport errors)
→ transports stop              — each within its own window
→ on_module_destroy            ┐ exhaustive — every hook starts, errors and
→ before_application_shutdown  │ panics logged; five seconds between all of
→ on_application_shutdown      ┘ them, what still waits then is abandoned
```

Shutdown is triggered by `SIGINT` / `SIGTERM` (a shared cancellation
token cancels every transport), or by the first transport that errors —
which cancels the rest, then runs the teardown phases once the last
transport has stopped.

## The way down

Kubernetes gives a pod 30 seconds between `SIGTERM` and `SIGKILL` by default,
and a process past it dies without a line, skipping every hook still to run and
the telemetry flush. So every step from the signal to the exit is bounded, and
by default they sum under the kill:

| Step | Bound | Default |
|---|---|---|
| The transports stop, together | each its own window, then half a second (`SHUTDOWN_SETTLE_TIMEOUT`) for what it stopped to unwind | 20.5 s, the longest |
| The shutdown hooks run | `SHUTDOWN_HOOKS_TIMEOUT`, across all three phases | 5 s |
| Telemetry flushes | [`FLUSH_TIMEOUT`](/opentelemetry/), every provider at once | 3 s |
| The runtime is torn down | what the hooks and the flush left of their budget | nothing past it |

28.5 seconds, one and a half under the kill. Each transport's window is its
own:

- the HTTP transport's [shutdown window](/http/configuration/#shutdown),
  `<PREFIX>_HTTP__SHUTDOWN_TIMEOUT_SECS`, 20 s, then the half second;
- the queue worker's [drain window](/queue/delivery/#shutdown),
  `<PREFIX>_QUEUE__SHUTDOWN_TIMEOUT_SECS`, 20 s, its hand-backs inside it;
- the scheduler's: a [scheduled tick](/schedule/) already running gets what a
  hook gets — five seconds, spent *before* the hooks so no tick runs through the
  cleanup it may depend on — and one still running then is stopped where it
  waits and files its `schedule.tick` line `outcome="cancelled"`, then the half
  second.

Raising a window means raising the pod's grace period with it, keeping 8.5
seconds above the longest window for the half second, the hooks and the flush.
The boot says what this deployment will spend: once every transport is
configured, `way down bounded` on `nest_rs::app` carries the longest stop among
the transports it mounted, settle included (`stop_bound_ms`), and the hooks'
budget (`hooks_budget_ms`); add the flush when OpenTelemetry is installed.

**The last step is `#[nest_rs::main]`'s**, which is why every `main` is
written with it rather than `#[tokio::main]`:

```rust title="apps/blog/src/main.rs"
#[nest_rs::main]
async fn main() -> anyhow::Result<()> {
    App::builder().module::<BlogModule>().build().await?.run().await
}
```

It builds the same runtime `#[tokio::main]` does — tokio's multi-threaded one,
sized by `TOKIO_WORKER_THREADS` — and tears it down differently. Dropping a
runtime waits for every blocking task still running, so under `#[tokio::main]`
a hook abandoned while it waited on a `spawn_blocking` (a synchronous client
wrapped the usual way, a `tokio::fs` call) held the exit for as long as that
call lasted, after the process had said its last line. `#[nest_rs::main]` gives
the teardown what the hooks and the flush left of their budget and then exits,
abandoning what still runs — said at `warn` when it waited out a bound. A
`main` that runs no app, such as a migration tool, spent none of the budget, so
work it left behind gets all five seconds. The app's manifest needs no `tokio`
line for it.

**A second signal exits at once.** One `SIGINT` or `SIGTERM` starts the way
down; another received during it — a second `Ctrl-C`, an orchestrator repeating
its `SIGTERM`, a signal after a failing transport began the way down — exits
immediately, with the code a shell gives a process that signal killed (130 for
`SIGINT`, 143 for `SIGTERM`), after one `error` on `nest_rs::app` naming what it
abandons:

```text frame="terminal"
ERROR nest_rs::app: shutdown signal received on the way down: exiting at once, abandoning what still runs signal="SIGINT" exit_code=130 step="shutdown hooks" phase=OnModuleDestroy provider="CacheService" method="flush"
```

Nothing runs after that line — no later hook, no telemetry flush — since
exiting at once is what was asked.

<Aside type="tip">
A test harness can drive the init phases without serving: `App::init()`
runs `on_module_init` then `on_application_bootstrap` against the built
container, so an e2e test exercises the same startup the server
performs.
</Aside>

## Common things a hook does

- **Init** — warm a cache, verify migrations applied, register with a
  service discovery backend, prime a connection pool, assert an
  external dependency is reachable (fail boot if not).
- **Shutdown** — flush a buffer, deregister from discovery, emit a final
  metric or report, all of it inside the five-second budget. Draining
  in-flight work belongs to a transport's own window, which a deployment
  sets.

The `UsersService` in the Publish workspace uses
`#[on_application_shutdown]` to log how many users exist at teardown —
a one-method `#[hooks]` block beside the service's main `impl`.
