Four layer families wrap every request: **guards** (gate access), **pipes**
(edge conversion), **interceptors** (cross-cutting work around the handler)
and **exception filters** (error mapping). This page is the one place that
explains how they compose — every other page links here instead of
re-explaining it.

## One pool per family

Declaring a layer at any scope — **global** (`use_*_global`), **controller**
(on the struct), or **handler** (beside the verb) — contributes to **one pool
per family**, deduplicated by `TypeId` in a single composition. The
layer executes **exactly once per request**. Broadest scope wins;
`#[force_guards]` is the opt-in to re-run.

Scope never multiplies executions — it chooses the **execution site**. The
teachable rule:

> Global = around the whole HTTP process. Scoped = around your handler. Either
> way, once.

You can watch the dedup happen. Declare `AuthnGuard` both globally
(`use_guards_global`) and on a controller (`#[use_guards(AuthnGuard, …)]`), and
boot logs the redundant declaration it dropped — the guard still runs exactly
once:

```text
DEBUG nest_rs::layers: redundant layer declaration deduped
  layer="AuthnGuard<JwtStrategy<Claims>>" kept="global" skipped="host"
  hint="broadest site wins; use `#[force_*]` to re-run"
```

## Execution sites

Each family runs at the site that matches its nature. The pool is the same; the
site differs:

| Family | Global scope | Controller / handler scope |
|---|---|---|
| Guard | the guard stage, after routing (reads `#[public]`); a self-mount's request | same site |
| Pipe | before the handler, over the body; `/graphql` POST variables and a WS message's `data`, at their endpoint — a graphql-ws operation runs none | before the handler; per argument on the other edges |
| Exception filter | around the handler stage; a self-mount's request; what the router answers itself | around the handler stage |
| Interceptor | the handler stage, after the guards | the handler stage, inside the app's |

Global guards are **pooled** globally but **execute** after routing, because a
guard reads `#[public]` route data that only exists once the route is known —
they do **not** run "before routing". Nothing the framework runs before them
reads the request body: the transport wraps it, and whatever reads it first — a
guard, the pipe pool, an extractor — reads it under
[the body cap and its gap bound](/http/configuration/#request-body-size-limit).

Two ways to be app-wide, both at the handler stage: `use_interceptors_global`
is the app's list, and `#[interceptor]` is what a module import brings. Only
an interceptor its module declares `#[interceptor(stage = unit)]` runs around
the guards — on every HTTP unit, a `404` and a refusal included — and writing
`stage = unit` is the visible line that opens it.

## Nesting order

Every HTTP unit — a route, a self-mount's request, what the router answers
itself — runs the same stages, outermost first:

1. **The edge**: the request span and its operation line, the request scope,
   the deadline, panic containment.
2. **The unit of work**, opened through the database binding when one is
   imported: a transaction on a mutating route, the pool otherwise. It
   commits on the unit's own outcome.
3. **The unit stage**: `#[interceptor(stage = unit)]` (`Server-Timing`, the
   RFC 9728 challenge).
4. **The guard stage**: the global, controller and method guards, then the
   route's `#[authorize]` class gate. A refusal is answered here.
5. **Exception filters**: the method's, the controller's, then the app's.
6. **The handler stage**: the app's global interceptors, then the modules'
   `#[interceptor]`s in import order, then the controller's, then the
   method's.
7. **The handler**: the global pipe pool over the body, the extractors and
   their pipes, the handler, the response mask.

A self-mount's request runs stages 1 to 5, its guard stage the request stage
the transport composes for it; no handler of yours runs there, so no handler
stage either. What the router answers itself — a `404`, a `405`, a module's
fallback — runs the edge, the unit stage and the exception filters alone: no
unit of work, no guard.

A GraphQL root field is a unit nested in the `/graphql` request (and in its
operation's unit of work): it runs stages 4 to 7 — its guard stage the app's
pool, the resolver's and the field's guards, each one's `check`, then the
field's class gate; the exception filters and the handler stage with the
app's own; then its argument pipes, the call and the mask. A
`#[field_resolver]` runs once per parent row, inside the root field that
produced it: its resolver's guards and its own, then only the interceptors and
exception filters declared on it — none of the app's, since the root field ran
them.

The operation span is outside all of it: the transport opens it before routing,
so every stage above logs under one `trace_id` — see
[Correlation](/fundamentals/correlation/).

The route's `#[authorize]` class gate runs with its guards, before any
interceptor or filter the route declares: a caching interceptor never answers a
caller the gate refuses, and a filter never sees the refusal. `Layer::priority`
orders entries *within* a site, never across sites: a handler-scope guard at
`-10` still runs after every global and controller guard.

A failure is sticky. A handler's error, or a `4xx`/`5xx` it answered, fails
the unit; an exception filter or an interceptor may change what the client
reads, never whether the unit failed, so a failed mutating request rolls back
whatever it answered.

## `#[public]` and `#[meta]`

`#[public]` and `#[meta(EXPR)]` are not layers — they are **declarations** a
layer reads. `#[public]` marks a route as anonymous-admissible (the guard admits
it through); `#[meta]` declares typed data on a route or its controller, which a
guard reads through `cx.reflector()`. Each route keeps one declaration for
the process, its values built once as it mounts; its layers read it through a
pointer, so nothing is copied per request. A refusal is answered by the guard
stage — exception filters never see it; a unit-stage interceptor observes it.

Every guarded site's `#[meta]` is read the same way: a resolver, a gateway, an
MCP host and each of their methods keep theirs with their site, and a guard's
`check` reads it through `cx.reflector()` as `check_http` does on a route. A
processor, scheduled tasks and listeners take `#[meta]` too, but run no guard,
so a value declared there is read by nothing yet.

## What fails at boot

Wiring mistakes fail the boot with a named error, never a silent drop.

If a provider injects a layer whose module the app never imported, the
**access graph** fails the boot naming the exact fix:

```text
module access violation: `PostsController` (in module `PostsHttpModule`)
depends on `AuthzGuard`, but `PostsHttpModule` imports no module that
provides it. `AuthzGuard` is provided by `AuthzModule` — add
`AuthzModule` to `#[module(imports = [...])]` of `PostsHttpModule`, or
route the dependency through a module `PostsHttpModule` already imports.
```

A global guard, pipe, interceptor or exception filter that cannot
resolve (its provider's module is not imported) fails the boot of every app, one
that serves no HTTP included, naming the type: the check runs at the boot's
wiring step, before any hook.

A layer a site declares — on a controller, a route, a gateway or one of its
messages, a GraphQL field — that no imported module provides fails the boot
too, naming the layer and the site; an MCP operation, which composes its chain
on its first call, refuses that call opaquely and logs one `error` naming
both. No site ever runs without a layer it declares.

A route whose guards are misordered — an authorization guard listed before the
authentication guard whose principal it reads, at any scope — fails the boot
naming both, rather than answering `500` to every request; a global pool listed
that way fails it in an app serving no route too.

<Aside type="caution">
These are boot-time failures, by design. A missing guard module is a compile-
then-boot break, not a request that silently runs unguarded. Fail-secure is the
point: forgetting to wire authz cannot ship.
</Aside>
