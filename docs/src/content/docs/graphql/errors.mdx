A resolver returns `T` or a `Result<T, E>`; an `Err` short-circuits with a
GraphQL error envelope alongside `data`. Which envelope is decided by the
error's **type**, so a client reads only what someone meant it to read:

- an `async_graphql::Error` you built is answered as built;
- an error implementing `ToProblem` answers the problem it says — its sentence
  and a stable `extensions.code`;
- the framework's own vocabulary found in the chain — a `Problem`, a pipe
  rejection, a decode failure said without its value — answers in its own form;
- **anything else answers `"internal error"` under the `INTERNAL` code**, and its
  whole chain is filed once at `error` on `nest_rs::graphql`.

A return is fallible when it is spelled the way async-graphql reads one —
`Result<T, E>` or `FieldResult<T>` — and anything else is a value: a payload
named `SearchResult` is an object. The message goes on `errors[].message`;
structured data goes on `errors[].extensions`. The framework's shared error
type, `ServiceError` from `nest-rs-seaorm`, implements `ToProblem`, so a feature
returns its service result and the wire shape just works.

## The smallest error

```rust title="crates/features/src/posts/graphql/resolver.rs"
use async_graphql::{Error, Result};
use nest_rs::graphql::{operations, resolver};

#[resolver]
pub struct PostsResolver;

#[operations]
impl PostsResolver {
    #[query]
    #[public]
    async fn post(&self, id: String) -> Result<String> {
        if id.is_empty() {
            return Err(Error::new("id must not be empty"));
        }
        Ok(format!("post {id}"))
    }
}
```

On the wire:

```json
{
    "data": null,
    "errors": [
        {
            "message": "id must not be empty",
            "path": ["post"],
            "locations": [{ "line": 1, "column": 3 }]
        }
    ]
}
```

`Error::new` is the deliberate spelling: a `?` that would turn a foreign error
into an `async_graphql::Error` does not compile, because async-graphql's
`custom-error-conversion` is on — the blanket conversion would ship the error's
`Display` before the framework could answer it opaquely. Return the error itself
(`Result<T, MyError>`) and let its type decide.

The framework rewrites every message that quotes a value the request carried.
A decode failure: serde's sentence quotes the value it refused — a resolver
returning a `serde_json` error, or an anyhow chain holding one, async-graphql's
own `Json<T>` scalar coercing an argument — so `errors[].message` says where and
what kind instead: `invalid type: a string, expected u64 at line 1 column 24`,
under the `INVALID_ARGUMENT` code. A value from `variables`, or written in the
document, that its argument's type refuses: async-graphql quotes it, and the
message says it by kind — `enumeration type "Role" does not contain the value
sent`, `an unknown field of type "PostFilter"`, `Expected input type "Int",
found a string.`, and a scalar's own refusal as `Failed to parse "UUID": a
value its type does not accept`. And an `operationName` the document holds no
operation of: the request's `operationName` is any text the client wrote, so
the message reads `Unknown operation named by operationName`. Every rewrite
holds on the socket as on `POST`. A name the document spells — a field, an
argument, a fragment, a variable — stays in the message, as the GraphQL
specification's own errors name it; it is the sender's own document, and no
log line carries it.

## Extensions and codes

`extensions.code` is the stable class a client branches on without parsing the
message. The framework's codes are constants in `nest_rs::core::problem::code`
— `UNAUTHENTICATED`, `FORBIDDEN`, `INSUFFICIENT_SCOPE`, `RATE_LIMITED`,
`UNAVAILABLE`, `INVALID_ARGUMENT`, `NOT_FOUND`, `CONFLICT`, `INTERNAL`: the HTTP
reason phrase for an HTTP class, gRPC's canonical name otherwise. Every refusal
the framework writes reads them: a guard's denial, the by-id binding (a `bind`
argument that is not a UUID v7 answers `"id must be a UUID v7"` under
`INVALID_ARGUMENT`, the twin of the HTTP path's `400`), an opaque failure.

A feature's own error says its class through `ToProblem`, once for GraphQL,
WebSockets and MCP (HTTP reads its `ResponseError`, see
[Exception filters](/fundamentals/exception-filters/)):

```rust title="crates/features/src/posts/error.rs"
use nest_rs::core::problem::code;
use nest_rs::core::{Code, Problem, ToProblem};

pub const SLUG_TAKEN: Code = Code::new("SLUG_TAKEN");

#[derive(Debug, thiserror::Error)]
pub enum PublishError {
    #[error("the slug is taken")]
    SlugTaken,
    #[error("the post is not a draft")]
    NotADraft,
    #[error("the search index refused the post")]
    Index(#[source] std::io::Error),
}

impl ToProblem for PublishError {
    fn to_problem(&self) -> Option<Problem> {
        match self {
            Self::SlugTaken => Some(Problem::new(409, SLUG_TAKEN).with_detail("the slug is taken")),
            Self::NotADraft => Some(Problem::new(409, code::CONFLICT)),
            Self::Index(_) => None,
        }
    }
}
```

```rust title="crates/features/src/posts/graphql/resolver.rs"
#[mutation]
#[authorize(Update, posts::Entity)]
async fn publish(&self, id: String) -> Result<Post, PublishError> {
    self.svc.publish(&id).await
}
```

```json
{
    "errors": [
        {
            "message": "the slug is taken",
            "extensions": { "code": "SLUG_TAKEN" },
            "path": ["publish"]
        }
    ]
}
```

A problem without a detail says its code in words (`NOT_A_DRAFT` would read
`not a draft`); a `5xx` never carries one — a `503` answers
`"service unavailable"`, any other `"internal error"`, and the chain behind
it is filed at `error` on `nest_rs::graphql`. `None` is the opaque answer:
`Index`'s chain is filed at `error`, the client reads the constant. A
`Code` declared in a `const` is checked when it compiles: `Code::new("conflict")`
is refused, and so is a `Problem` whose status is not a `4xx` or a `5xx`.

## `ServiceError`

A `CrudService` method returns `Result<T, ServiceError>`, and `ServiceError`
implements `ToProblem`: `NotFound` answers `NOT_FOUND`, `Conflict` `CONFLICT`,
`Forbidden` `FORBIDDEN`, `Invalid` and `Validation` `INVALID_ARGUMENT`, each with
its own sentence; `Db`, `Masking` and `Internal` answer opaquely, their cause
filed at `error`. A resolver returns the service's result as it is:

```rust title="crates/features/src/posts/graphql/resolver.rs"
use nest_rs::authz::Read;
use nest_rs::graphql::{operations, resolver};
use nest_rs::seaorm::ServiceError;

#[operations]
impl PostsResolver {
    #[query]
    #[authorize(Read, posts::Entity)]
    async fn post(&self, id: String) -> Result<Post, ServiceError> {
        self.svc.find_by_id(&id).await
    }
}
```

A `DbErr` turned into a `ServiceError` by `?` is classified on the way: a
unique violation becomes `Conflict`, a row a write found gone `NotFound`, any
other failure `Db`, whose chain is filed by its SQLSTATE, never by the
server's message. A `#[crud]` operation answers the same classes
([When the database refuses](/database/crud/#when-the-database-refuses)), and a
mutation field answering one rolls back its own writes — the whole operation's,
when its `null` reaches `data`
([GraphQL: one unit per operation](/database/transactions/#graphql-one-unit-per-operation)).

A body that mixes failures keeps `async_graphql::Result` and uses `?`:
`ServiceError` converts into `async_graphql::Error` through the same
`ToProblem`, the one conversion `nest-rs-seaorm` writes for it.

## An error the client is not owed

An error with no `ToProblem` is already answered opaquely. `Opaque` says so at
the call site, where a failure the client could otherwise read is one it must
not — and it reads the same on every client-facing transport, HTTP, GraphQL,
WebSockets and MCP:

```rust title="crates/features/src/posts/graphql/resolver.rs"
use nest_rs::graphql::Opaque;

#[query]
#[authorize(Read, posts::Entity)]
async fn post(&self, id: String) -> async_graphql::Result<Post> {
    Ok(self.svc.find_by_id(&id).await.opaque()?)
}
```

`.opaque()?` logs the real error at `error` on `nest_rs::graphql` and puts
a constant message on the wire, under the same `INTERNAL` code an internal
denial carries — so a client cannot tell an unexpected failure from a
refusal it was owed no explanation for.

## An exception filter answers first

Every rule above is what a field answers when nothing answered it. An
[exception filter](/fundamentals/exception-filters/#on-a-graphql-field) bound
on the resolver, the field or the app reads the failure before them: one
claiming the error's type answers with a `Problem`, which the field renders
in this page's form — its sentence on `message`, its code on
`extensions.code` — while the operation's other fields resolve as they would.
The chain behind a `5xx` the filter answers is filed as for any other; one it
answers `4xx` files nothing. A field that failed stays failed, so a mutation
field's savepoint rolls back whatever the filter answered.

## Authorization denials

A guard's denial reads the same on every edge. On GraphQL it answers its
sentence under its code — `UNAUTHENTICATED`, `FORBIDDEN`, `INSUFFICIENT_SCOPE`
with `requiredScopes`, `RATE_LIMITED` with `retryAfterSeconds` — and a server
side failure never carries the guard's text: an unavailable dependency answers
`"service unavailable"` under `UNAVAILABLE` (with `retryAfterSeconds` when
known), an internal denial `"internal error"` under `INTERNAL`.

The handler doesn't write the mapping; it just declares
`#[authorize(Action, Entity)]`. See [Security](/security/) for
the full chain.

## `Option<T>` vs error

`Option<T>` is the right return when an absent value is a *normal*
outcome (looked something up, found nothing). Reserve errors for
*abnormal* outcomes (validation failed, DB unreachable, principal
refused). On the wire:

- `Option<T>` returning `None` → `"data": { "post": null }`,
  no `errors` block.
- `Result<T>` returning `Err` → `"errors": [...]`, the field's
  value is `null`.

The bind helper follows this rule: `bind::<Read, UsersService>(ctx,
&id).await?` returns `Result<Option<User>>` — `None` means absent
(404 equivalent), `Err` means denied or broken.

```rust title="crates/features/src/users/graphql/resolver.rs"
#[query]
#[authorize(Read, UserEntity)]
async fn user(&self, ctx: &Context<'_>, id: String) -> Result<Option<User>> {
    Ok(bind::<Read, UsersService>(ctx, &id)
        .await?
        .as_ref()
        .map(User::from))
}
```

## Where a failed field's `null` lands

A field that fails answers `null`, and its error carries the `path` to it, as
the GraphQL specification handles a field error (§6.4.4). Its siblings keep
their answers:

```json
{
    "data": { "users": [{ "id": "0192…" }], "bad": null },
    "errors": [{ "message": "id must be a UUID v7", "path": ["bad"],
                 "extensions": { "code": "INVALID_ARGUMENT" } }]
}
```

That is `{ users { id } bad: user(id: "not-a-uuid") { id } }`, whose `user`
returns `Result<Option<User>>`, a nullable `User`. A Non-Null field cannot hold
the `null`: a `Result<T>` is `T!` in the schema, so its parent answers `null` in
its place, up to the nearest nullable field — and `data` itself answers `null`
when a Non-Null root field fails. Pick the return by what its failure may cost
the answer around it: `Result<Option<T>>` keeps its siblings, `Result<T>`
promises a value wherever its parent has one. The rule holds on `POST`, for each
operation of a batch, and over the socket. On a mutation, where the `null` lands
also decides which writes stand: a root field answering `null` rolls back its
own, and a `null` reaching `data` the whole operation's
([GraphQL: one unit per operation](/database/transactions/#graphql-one-unit-per-operation)).

Two selections fall outside it, both from async-graphql 7.2.1. A field selected
on an interface type reports its error without a `path`, so its key stays
absent, and under a mutation its root field's writes stand with the root
field's answer: select it inside `... on <ConcreteType>` and its error carries
the path, so its `null` lands. And an object selected twice at one place — two
fragments that each select `org` — keeps whichever copy finishes first. When
that copy's every field failed, the object answers `null`, or its nearest
nullable parent does, never an object missing what the other copy answered.

## Multiple errors in one response

GraphQL allows several errors per response. A query selecting two
fields, each failing, gets two `errors[]` entries — async-graphql
collects them automatically across resolver calls. There is no
"first error wins" semantic; clients see the full set with `path`
pointing at each failed field.

This matters most for partial-success shapes (one ok, one denied)
where the client wants the available data plus a clear refusal on the
rest — the denied field nullable, so that its `null` stands beside the
data. The framework does not need any code for this — return the
`Result` from each `#[field_resolver]` and async-graphql does the
gathering.

## A body that is not a GraphQL request

A body that is JSON but not a request — `"variables"` as a string — or not
JSON at all is refused before anything executes: `400`, and one `errors` entry
saying why, the way GraphQL-over-HTTP answers a request it cannot accept. No
`data` member, since nothing ran. The why is a decode failure, said like every
edge says one — where and of what kind, never the value sent:

```bash frame="terminal"
$ curl -s localhost:3000/graphql -H 'content-type: application/json' \
    -d '{"query":"{ tag }","variables":"sk_live_secret"}'
{"errors":[{"message":"the body is not a GraphQL request: invalid type: a string, expected a map at line 1 column 47"}]}
```
