Importing `HttpModule::for_root(...)` in `AppModule.imports` attaches the
HTTP transport at boot. Pass `None` to read every option from the
environment, or pin `HttpConfig` in code:

```rust title="apps/hello/src/module.rs"
use nest_rs::core::module;
use nest_rs::http::{HttpConfig, HttpModule};

use features::hello::HelloHttpModule;

#[module(
    imports = [
        HttpModule::for_root(HttpConfig { port: 3000, ..Default::default() }),
        HelloHttpModule,
    ],
)]
pub struct HelloModule;
```

```rust title="apps/api/src/module.rs"
use nest_rs::core::module;
use nest_rs::http::{HttpConfig, HttpModule};

#[module(imports = [
    HttpModule::for_root(HttpConfig { port: 3002, ..Default::default() }),
])]
pub struct ApiModule;
```

Default values: host `0.0.0.0`, port `3000`, no TLS (plain HTTP), no CORS,
no framework `Server` header, a `2 MiB` request-body cap, a `30`-second
request timeout, at most `10 000` open connections, a `20`-second shutdown
window, fail-secure boot on, and the default security headers on.

## `HttpConfig` fields

Every field of `HttpConfig` is settable both by env var and in the pinned
struct — the same dual-path rule every config in the framework follows.
Real env always wins over the `.env` cascade.

| Field | Env variable | Default | Pinned form |
|-------|--------------|---------|-------------|
| `host` | `<PREFIX>_HTTP__HOST` | `0.0.0.0` | `HttpConfig { host: "127.0.0.1".into(), ..Default::default() }` |
| `port` | `<PREFIX>_HTTP__PORT` | `3000` | `HttpConfig { port: 3002, ..Default::default() }` |
| `tls.cert` | `<PREFIX>_HTTP__TLS_CERT` (inline PEM) or `<PREFIX>_HTTP__TLS_CERT_FILE` (path) | unset ⇒ plain HTTP | `HttpConfig { tls: Some(HttpTls::new(cert, key)), ..Default::default() }` |
| `tls.key`  | `<PREFIX>_HTTP__TLS_KEY` or `<PREFIX>_HTTP__TLS_KEY_FILE`  | unset ⇒ plain HTTP | (set together with `tls.cert`) |
| `cors.origins` | `<PREFIX>_HTTP__CORS_ORIGINS` (comma list) | unset ⇒ CORS off | `HttpCors { origins: vec!["https://app.example.com".into()], ..Default::default() }` |
| `cors.methods` | `<PREFIX>_HTTP__CORS_METHODS` | empty | `methods: vec!["GET".into(), "POST".into()]` |
| `cors.headers` | `<PREFIX>_HTTP__CORS_HEADERS` | empty | `headers: vec!["Content-Type".into()]` |
| `cors.exposed_headers` | `<PREFIX>_HTTP__CORS_EXPOSED` | empty — `Link`, `Location` and `Retry-After`, which the framework sends, are always exposed | `exposed_headers: vec!["X-Total-Count".into()]` |
| `cors.credentials` | `<PREFIX>_HTTP__CORS_CREDENTIALS` (`true`/`false`) | `false` | `credentials: true` |
| `cors.max_age` | `<PREFIX>_HTTP__CORS_MAX_AGE` (seconds) | unset | `max_age: Some(Duration::from_secs(3600))` |
| `server_header` | `<PREFIX>_HTTP__SERVER_HEADER` (`true`/`false`) | `false` | `HttpConfig { server_header: true, ..Default::default() }` |
| `global_prefix` | `<PREFIX>_HTTP__GLOBAL_PREFIX` (one literal path: `{` `}` or `:` `*` `<` fail the boot) | unset ⇒ no prefix | `HttpConfig::default().with_global_prefix("/api")` |
| `max_body_bytes` | `<PREFIX>_HTTP__MAX_BODY_BYTES` (bytes) | `2 MiB` | `HttpConfig::default().with_max_body_bytes(4 * 1024 * 1024)` |
| `request_timeout` | `<PREFIX>_HTTP__REQUEST_TIMEOUT_SECS` (seconds, `0` ⇒ off) | `30 s` | `HttpConfig { request_timeout: Some(Duration::from_secs(15)), ..Default::default() }` |
| `max_concurrent_connections` | `<PREFIX>_HTTP__MAX_CONCURRENT_CONNECTIONS` (`1`–`1048576`) | `10 000` | `HttpConfig { max_concurrent_connections: 50_000, ..Default::default() }` |
| `shutdown_timeout` | `<PREFIX>_HTTP__SHUTDOWN_TIMEOUT_SECS` (seconds, `1`–`3600`) | `20 s` | `HttpConfig { shutdown_timeout: Duration::from_secs(55), ..Default::default() }` |
| `fail_secure_strict` | `<PREFIX>_HTTP__FAIL_SECURE_STRICT` (`true`/`false`) | `true` | `HttpConfig { fail_secure_strict: false, ..Default::default() }` |
| `security_headers` | `<PREFIX>_HTTP__SECURITY_HEADERS` (master), `__CONTENT_TYPE_OPTIONS`, `__FRAME_OPTIONS`, `__HSTS`, `__REFERRER_POLICY`, `__CROSS_ORIGIN_OPENER_POLICY`, `__CROSS_ORIGIN_RESOURCE_POLICY`, `__CROSS_ORIGIN_EMBEDDER_POLICY`, `__PERMISSIONS_POLICY`, `__CONTENT_SECURITY_POLICY` | on (safe values) | `HttpConfig { security_headers: HttpSecurityHeaders { enabled: false, ..Default::default() }, ..Default::default() }` |
| `compression` | `<PREFIX>_HTTP__COMPRESSION` (`true`/`false`) | `false` | `HttpConfig { compression: true, ..Default::default() }` |

See [Compression](/http/compression/) for what the flag negotiates and when to leave it off.

## Serve HTTPS

Setting **both** `<PREFIX>_HTTP__TLS_CERT[_FILE]` and `<PREFIX>_HTTP__TLS_KEY[_FILE]`
makes the transport serve over [rustls](https://docs.rs/rustls) instead of plain
HTTP, offering HTTP/2 then HTTP/1.1 to each client. Setting only one of the pair fails
the boot — a half-configured TLS is a deployment mistake, not a silent
fall back to plaintext. Setting both spellings of one half — `TLS_CERT` and
`TLS_CERT_FILE` — in the same tier fails the boot too, naming both, since
nothing says which was meant. Across tiers the process environment chooses,
[as it does for every variable](/configuration/#configservice-api).

```bash frame="terminal"
# Inline (suits k8s secrets, systemd EnvironmentFile, …)
NESTRS_HTTP__TLS_CERT="$(cat fullchain.pem)" \
NESTRS_HTTP__TLS_KEY="$(cat privkey.pem)" \
nestrs run dev api

# Or by path — the transport reads the pair and keeps watching it
NESTRS_HTTP__TLS_CERT_FILE=/etc/letsencrypt/.../fullchain.pem \
NESTRS_HTTP__TLS_KEY_FILE=/etc/letsencrypt/.../privkey.pem \
nestrs run dev api
```

### Renewal without a restart

The two forms differ in one way that matters in production: **material read
from files is watched.** Every `<PREFIX>_HTTP__TLS_RELOAD_SECS` seconds (60 by
default, `0` to turn it off) the pair is re-read, and a renewed pair is swapped
into the running rustls config. The listener is not rebuilt — the port stays
bound, in-flight connections finish, and certbot's `--deploy-hook` needs no
`systemctl restart`.

Two things it deliberately will not do:

- **A pair it cannot read leaves the current certificate serving**, with a
  `warn` on `nest_rs::http`. A renewal tool that unlinks before it writes would
  otherwise take the listener down between two syscalls.
- **A pair is installed only once it reads back identical twice**, so a file
  caught mid-flush is never the one that gets served.

That second rule has a limit worth knowing, because polling cannot see past it:
a renewal that writes the certificate and its key **more than one interval
apart** looks settled in between, and that pair is installed. Certbot and
cert-manager both swap atomically (a new lineage directory plus a symlink, a
remounted Secret), so this does not arise with either — but a hand-rolled hook
that writes the two files in sequence should write them together, or set
`<PREFIX>_HTTP__TLS_RELOAD_SECS` longer than the gap.

Inline PEM has no source to watch, so it is loaded once, as before.

Pinning TLS material in code uses `HttpTls::new` — rarely useful outside
tests (production deploys carry secrets in the environment):

```rust title="apps/api/src/module.rs"
use nest_rs::core::module;
use nest_rs::http::{HttpConfig, HttpModule, HttpTls};

let cert = std::fs::read("fullchain.pem")?;
let key  = std::fs::read("privkey.pem")?;

#[module(imports = [
    HttpModule::for_root(HttpConfig {
        port: 3002,
        tls: Some(HttpTls::new(cert, key)),
        ..Default::default()
    }),
])]
pub struct ApiModule;
```

## CORS

CORS uses [poem's `Cors` middleware](https://docs.rs/poem/latest/poem/middleware/struct.Cors.html)
under the hood. The transport installs it **outermost**, so a preflight
(`OPTIONS`) is answered before any guard or interceptor runs.

CORS activates only when `cors.origins` is non-empty — the default is no
CORS layer. Set the origins (and any other knob you need) via either path:

```bash title=".env.production" frame="terminal"
NESTRS_HTTP__CORS_ORIGINS=https://app.example.com,https://admin.example.com
NESTRS_HTTP__CORS_METHODS=GET,POST,PUT,DELETE
NESTRS_HTTP__CORS_HEADERS=Content-Type,Authorization
NESTRS_HTTP__CORS_CREDENTIALS=true
NESTRS_HTTP__CORS_MAX_AGE=3600
```

```rust title="apps/api/src/module.rs"
use std::time::Duration;

use nest_rs::core::module;
use nest_rs::http::{HttpCors, HttpConfig, HttpModule};

#[module(imports = [
    HttpModule::for_root(HttpConfig {
        port: 3002,
        cors: Some(HttpCors {
            origins: vec!["https://app.example.com".into()],
            methods: vec!["GET".into(), "POST".into()],
            headers: vec!["Content-Type".into(), "Authorization".into()],
            credentials: true,
            max_age: Some(Duration::from_secs(3600)),
            ..Default::default()
        }),
        ..Default::default()
    }),
])]
pub struct ApiModule;
```

`origins: vec!["*".into()]` is allowed for fully open APIs (the wildcard
is passed straight through to poem).

## Mounting under a shared prefix

Behind a reverse proxy that hands off a sub-path (`/api/*`), every
controller can be mounted under one prefix without touching `path = "…"`
on each. Like every other field it follows the dual path — set it in the
environment:

```bash title=".env.production" frame="terminal"
NESTRS_HTTP__GLOBAL_PREFIX=/api
```

or pin it in code with `with_global_prefix`:

```rust title="apps/api/src/module.rs"
use nest_rs::core::module;
use nest_rs::http::{HttpConfig, HttpModule};

#[module(imports = [
    HttpModule::for_root(HttpConfig::default().with_global_prefix("/api")),
])]
pub struct ApiModule;
```

The prefix is normalized (`"api"`, `"/api"`, `"/api/"` all yield
`Some("/api")`; empty / `"/"` collapse to no-op), then prepended to every
route at mount time — `#[get("/users")]` ends up at `GET /api/users`. The
boot log and the OpenAPI document reflect the prefix. It is one literal
path: a [route template](/http/controllers/#route-templates)'s braces, or a
`:`, `*` or `<` the router would read as a parameter, fail the boot naming
the variable.

## Framework `Server:` header

Off by default — a production-safe choice: no fingerprint of the
framework or its version is exposed. Flip on for local development to see
`Server: nestrs/<crate version>` on every response (the same shape Apache
and nginx use):

```bash title=".env.development" frame="terminal"
NESTRS_HTTP__SERVER_HEADER=true
```

```rust title="apps/api/src/module.rs"
HttpModule::for_root(HttpConfig {
    server_header: true,
    ..Default::default()
})
```

The value is sourced from the `nest-rs-http` crate's `CARGO_PKG_VERSION` at
build time — it tracks the framework, not your app version.

## Request-body size limit

`RawBody` (and every extractor built on it) accepts at most
`max_body_bytes` — `2 MiB` by default, so a runaway upload can't exhaust
memory before a handler ever sees it. Raise or lower it globally:

```bash title=".env.production" frame="terminal"
NESTRS_HTTP__MAX_BODY_BYTES=4194304   # 4 MiB
```

A single route that needs a different cap overrides it per call with
`RawBody::extract_with_limit`; the config value is the default for
everything else.

## Request timeout

`request_timeout` bounds how long one request may run, so a slow or stuck
request can't tie up a connection indefinitely. Default `30` seconds;
`<PREFIX>_HTTP__REQUEST_TIMEOUT_SECS=0` turns it off — the framework-wide
spelling every duration ceiling uses, so `0` never means "zero seconds":

```bash title=".env.production" frame="terminal"
NESTRS_HTTP__REQUEST_TIMEOUT_SECS=15
NESTRS_HTTP__REQUEST_TIMEOUT_SECS=0    # no timeout at all
```

A handler that exceeds it is aborted and the client gets **`503 Service
Unavailable`** with a `Retry-After` naming the budget — not `504`. RFC 9110
§15.6.5 scopes `504 Gateway Timeout` to a server "acting as a gateway or
proxy" whose *upstream* was slow; this transport is the origin, and the
handler that overran is its own work. The distinction is not cosmetic: a
client SDK or a load balancer that retries a `504` on another node is acting
on "that node's upstream is flaky", and re-runs a handler that will overrun
again. §15.6.4 is the origin's own sentence — explicitly temporary, and
paired with `Retry-After`.

## Connections

The transport accepts its connections itself, on [hyper](https://docs.rs/hyper),
and holds at most `max_concurrent_connections` open at once — `10 000` by
default. Past it, a new connection waits in the kernel's listen backlog until one
closes: its client sees latency, then the kernel's own refusal once the backlog
is full, never a reset of a connection it already holds. A socket upgraded to a
WebSocket counts until it closes. The first connection held back files one
`warn` on `nest_rs::http` naming the variable, and an `info` follows once a place
is free again:

```bash title=".env.production" frame="terminal"
NESTRS_HTTP__MAX_CONCURRENT_CONNECTIONS=50000
```

Whole numbers from `1` to `1048576`, Linux's default ceiling on the files one
process opens; anything outside fails the boot naming the variable, set in the
environment or pinned. A cap above the process's own file limit (`ulimit -n`) is
met by the kernel first, so raise the two together.

**Behind a proxy that caps** its connections to each upstream — nginx's
`max_conns`, Envoy's circuit breakers — keep this cap at or above the proxy's,
or the replica holds back connections the proxy believes it may open.

What one connection may do is fixed:

- an HTTP/2 connection runs at most `200` streams at once, the limit it
  advertises in `SETTINGS_MAX_CONCURRENT_STREAMS` (RFC 9113 §5.1.2), and a
  client resetting streams faster than they are answered is sent `GOAWAY`
  ([CVE-2023-44487](https://nvd.nist.gov/vuln/detail/CVE-2023-44487));
- an HTTP/1 request head larger than `64 KiB` is answered
  `431 Request Header Fields Too Large` (RFC 6585 §5) rather than buffered;
- a client speaking HTTP/2 from its first byte is served in plaintext too, and
  every socket is written without Nagle's delay (`TCP_NODELAY`).

## Shutdown

On `SIGTERM` or `SIGINT` the transport stops accepting, ends what has no end of
its own — a stream, a socket — the way its protocol ends one, and gives what is
still answering `shutdown_timeout` to finish — `20` seconds by default. It is the
first of the bounded steps on [the way down](/fundamentals/lifecycle/#the-way-down):
the window, then half a second for what the transport stopped to unwind, then
five seconds for the [shutdown hooks](/fundamentals/lifecycle/#ordering-and-failure),
then three for the [telemetry flush](/opentelemetry/) — 28.5 seconds, under the
`30` a Kubernetes pod gets between `SIGTERM` and `SIGKILL`. Raise the window
together with the pod's grace period, keeping the eight and a half seconds after
it:

```bash title=".env.production" frame="terminal"
NESTRS_HTTP__SHUTDOWN_TIMEOUT_SECS=55    # beside terminationGracePeriodSeconds: 64
```

Whole seconds from `1` to `3600`; anything outside fails the boot naming the
variable, and so does a pinned value outside the range. `0` is refused rather
than read as "off" — the spelling `REQUEST_TIMEOUT_SECS` uses — because a
shutdown that waits without a bound is what the window exists to prevent.

What the window does depends on what the connection is doing:

- **Idle** — a kept-alive connection with nothing in flight is closed at the
  signal; the window is not spent on it.
- **A request still running** — is answered, and its connection closed after
  the answer. If the window closes first, the connection is dropped, the client
  gets no answer and the handler is cancelled where it waits — over HTTP/1.1
  and over HTTP/2 alike: closing an HTTP/2 connection resets every stream on
  it, and hyper drops a reset stream's handler. Its `http.request` line is
  still filed, with `outcome="cancelled"` and the time it ran in place of a
  `status` and `bytes`, since nothing was answered. Its span exports like an
  answered one's — named `GET /reports/{id}` for the route the router matched,
  with `http.route` — and failed: `error.type` is `cancelled`, the status
  `Error`.
- **A stream with no end of its own** — an [`#[sse]` stream](/http/streaming/),
  an MCP session's standalone `GET` stream — is ended **at the signal**,
  cleanly: its last chunk is written, so the client's `EventSource` reads an end
  and reconnects, to a replica still in the load balancer. Waiting would only
  have spent the whole window on an end that is not coming. Its `http.request`
  line carries the head's `status`, the `bytes` written, and
  `outcome="cancelled"`, since the transport ended it rather than the stream.
- **A body with an end of its own** — a download — is a response still being
  answered: it gets the window, and is cut at its close, its line carrying the
  head's `status`, the `bytes` written before the cut and `outcome="cancelled"`.
- **A WebSocket** — a [gateway's socket](/websockets/) is closed **at the
  signal** with RFC 6455's `1001 Going Away`, after the message it is
  answering; a [graphql-ws socket](/graphql/subscriptions/) first completes
  each subscription still running and answers what is still answering, then
  closes the same way. A message or a
  subscription still running when the window closes is dropped with its socket,
  and files its line `cancelled`. A socket a hand-built endpoint upgraded is the
  developer's own: the transport cannot see inside it, so it neither waits for
  nor closes one — it ends when its handler ends it, or with the process.
- **An MCP operation still running** — runs on a task of rmcp's rather than on
  the connection that asked for it, so it gets the window like a request, and
  the transport stops it itself once the window has closed: it is dropped where
  it waits, files its `mcp.operation` line with `outcome="cancelled"`, and one
  `warn` names how many were stopped. A `subscriptions/listen` is answered its
  final result at the signal instead, since a subscription has no end of its
  own.

What the transport stopped at the close gets half a second to unwind, once for
every mount together, so none of it is still running when the shutdown hooks
start; what still is then — a unit blocking its thread — is named at `error`.
When the window closes on open connections, one `warn` on `nest_rs::http`
counts them: `cut`, the connections it closed, and `upgraded_open`, the sockets
a hand-built endpoint left open. The shutdown hooks run once every transport has
stopped, five seconds between all of them — see [Lifecycle](/fundamentals/lifecycle/#ordering-and-failure) —
so keep the grace period above this window plus the half second, theirs and the
flush's.

**A client that goes away mid-request is seen only if it resets.** The line of a
request whose client stopped waiting depends on how the client left:

- **An abortive close** — a reset: an HTTP/2 stream cancelled, a socket closed
  with `SO_LINGER` of zero, a process that crashed — drops the request where its
  handler waits, exactly as the window does, and it files
  `outcome="cancelled"` with no `status`.
- **An ordinary close** — `close()` after a timeout, a browser navigating away,
  `curl` giving up — is a half-close over HTTP/1.1, which is legal: a client may
  send its request, shut its writing side and still read the answer. So hyper
  does not take it for an abandonment while the handler runs; the handler runs
  to its end, the answer is written to a socket nobody reads, and the line is
  filed with that `status` and `bytes`.

hyper's reading is the specification's, so `outcome="cancelled"` counts the
requests the server could see were abandoned — never every client that stopped
waiting.

## Default security headers

On by default — a freshly-scaffolded app ships safe headers without having
to remember them:

- `X-Content-Type-Options: nosniff` — defeats MIME sniffing.
- `X-Frame-Options: DENY` — no framing (clickjacking).
- `Referrer-Policy: strict-origin-when-cross-origin` — a cross-origin
  request carries the origin, never the path or the query. It matters here
  and not only in theory: `nest-rs-social` redirects through URLs carrying
  `state`, and the Swagger UI at `GET /api` is a real page whose outbound
  links would otherwise name the API paths a reader was browsing.
- `Cross-Origin-Opener-Policy: same-origin` — a document this server serves
  keeps no `window` reference back to a cross-origin opener.
- `Cross-Origin-Resource-Policy: same-origin` — a *no-cors* cross-origin
  load of a response from this server is blocked. It does not touch CORS
  requests, which is why an API can carry it; set `cross-origin` on a server
  whose images or downloads are meant to be embedded elsewhere.
- `Strict-Transport-Security: max-age=31536000; includeSubDomains` —
  emitted **only when TLS is active** (HSTS over plain HTTP is
  meaningless and a footgun on localhost).

Three more are **settable and off by default**, each because a default would
be the framework guessing about a document it does not serve:

| Header | Field / env | Why it ships off |
|---|---|---|
| `Content-Security-Policy` | `content_security_policy` / `__CONTENT_SECURITY_POLICY` | A policy strict enough to be worth having (`default-src 'none'`) breaks the Swagger UI and every page an app serves; one loose enough to ship safely states nothing. The sources are the app's. |
| `Cross-Origin-Embedder-Policy` | `cross_origin_embedder_policy` / `__CROSS_ORIGIN_EMBEDDER_POLICY` | `require-corp` is how a *page* opts into cross-origin isolation, and it breaks every cross-origin subresource that does not carry CORP. |
| `Permissions-Policy` | `permissions_policy` / `__PERMISSIONS_POLICY` | It governs camera / geolocation / payment in a document; a restrictive guess silently disables a feature the app's own front end asked for. |

Every value is tunable through the dual path. Disable the whole set with
the master switch, or drop one header by setting its variable to `off` — in
code, by setting its field to `None`, or `content_type_options` to `false`. A
blank value is refused at boot, and an empty one counts as unset, as it does for
every variable, so that header keeps its default:

```bash title=".env" frame="terminal"
NESTRS_HTTP__SECURITY_HEADERS=false                    # all off
NESTRS_HTTP__FRAME_OPTIONS=SAMEORIGIN                  # override one value
NESTRS_HTTP__HSTS=off                                  # off ⇒ drop just HSTS
NESTRS_HTTP__CONTENT_SECURITY_POLICY="default-src 'self'"
```

```rust title="apps/api/src/module.rs"
use nest_rs::http::{HttpConfig, HttpModule, HttpSecurityHeaders};

HttpModule::for_root(HttpConfig {
    security_headers: HttpSecurityHeaders {
        frame_options: Some("SAMEORIGIN".into()),
        ..Default::default()
    },
    ..Default::default()
});
```

## Fail-secure boot

`fail_secure_strict` is `true` by default: when global guards are
registered and an endpoint the transport can't shape (an imperative
`mount(...)`) would bypass the guard pool, the boot **fails** naming the
offending mount rather than silently serving it unguarded. Setting it to
`false` downgrades that failure to a `warn` — a deliberate opt-out, not
the default:

An **imperative mount** is `HttpTransport::mount(path, |container| …)`:
a raw poem endpoint handed to the transport, which can neither shape it
(no `#[routes]` to run the guard pool through) nor introspect it (no
`EdgePosture` to read). Writing an application route is not how you get
one — `#[controller]` covers that, and a capability contributing its own
surface (GraphQL, WebSockets, MCP, OpenAPI) self-mounts *with* a posture.
It is the escape hatch for a hand-built endpoint, answering under its
`path` whole — one literal address, so a parameter or a brace fails the boot —
and the check exists because that hatch is the only hole a global guard pool
cannot reach. The boot error names the path:

```text frame="terminal"
Error: fail-secure: imperative mount(...) endpoints bypass the global guard
pool: /raw — route them through a #[controller], guard them explicitly, or
opt out with HttpTransport::fail_secure_strict(false) /
NESTRS_HTTP__FAIL_SECURE_STRICT=false
```

```bash title=".env" frame="terminal"
NESTRS_HTTP__FAIL_SECURE_STRICT=false
```
