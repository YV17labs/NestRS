An extractor pulls a typed value out of the request before the handler
runs. `Path<T>`, `Query<T>`, `Json<T>` and `Form<T>` cover the request line,
query string, JSON body and form body; beside them sit the framework-specific
extractors:
the typed header reader `Header<T>`, the
raw-body reader `RawBody`, the spoofable but observation-grade
`ClientIp`, the request-scoped DI resolver `Scoped<T>`, the
guard-attached context reader `Ambient<T>`, and the route metadata a guard reads
through `cx.reflector()`, declared with `#[meta(...)]`. A handler that needs
the request itself — its URI, a header no DTO names — takes `req: &Request`.

This page is the reference: one extractor, one example, one rule. The
[Guards](/fundamentals/guards/) for `Ambient<T>` and
[Provider scopes](/fundamentals/provider-scopes/) for `Scoped<T>` — tell the story.

## `Json<T>` — typed JSON in and out

Parses the request body into `T`; rejects a body that does not decode with
`400`, naming where — ``JSON body at `title`: missing`` — and never the value.
Works as a return type too — serializes `T`, sets
`Content-Type: application/json; charset=utf-8`, and feeds the OpenAPI document with
the same schema:

```rust title="crates/features/src/posts/http/controller.rs"
use nest_rs::core::{input, output};
use nest_rs::http::{Json, Path, Result};
use uuid::Uuid;

#[input]
struct RenamePost { title: String }

#[output]
struct Post { id: Uuid, title: String }

#[put("/posts/{id}/title")]
async fn rename(&self, id: Path<Uuid>, Json(body): Json<RenamePost>) -> Result<Json<Post>> {
    Ok(Json(self.svc.rename(*id, body.title).await?))
}
```

## Validation — the rules a type declares

Every extractor's value is held to the [validator](https://docs.rs/validator)
rules its type declares, after the guards and before the handler, with nothing
to wrap. `Json<T>` is the usual carrier, and `Query<T>`, `Form<T>`, `Path<T>`
and `Header<T>` answer the same way:

```rust title="crates/features/src/users/http/controller.rs"
use nest_rs::http::{Created, Json, Result};
use nest_rs::core::input;

#[input]
struct CreateUser {
    #[validate(length(min = 1))]
    name: String,
    #[validate(email)]
    email: String,
}
```

`#[input]` carries `Serialize`, `Deserialize`, `Validate` **and** `JsonSchema`,
so a DTO behind it needs no second derive — not for validation, not for the
OpenAPI document, and not to come back out as `Json<T>`. A DTO derived by hand
carries all four itself; adding one of them *next to* `#[input]` is a
conflicting impl (`E0119`). A reply the route only sends takes `#[output]`,
`Serialize` and `JsonSchema` alone.

```rust title="crates/features/src/users/http/controller.rs"
#[post("/users")]
async fn create(&self, Json(body): Json<CreateUser>) -> Result<Created<Json<User>>> {
    let user = self.svc.create(body).await?;
    Ok(Created::at(user.id, Json(User::from(&user))))
}
```

A validation failure returns `400` with a structured field-level error
list — no manual checks in the handler. The rest is a create's own answer, a
`201` naming what it made, which [Responses](/http/responses/) covers.

## `Piped<P, E>` — transform at the edge

`Piped<P, E>` applies any [transport-agnostic pipe](/fundamentals/pipes/) to
the value extractor `E` produced, once that value passed its rules, and binds
the pipe's output:

```rust title="crates/features/src/posts/http/controller.rs"
use nest_rs::http::Path;
use nest_rs::pipes::{ParseUuid, Piped};
use nest_rs::http::Json;

#[get("/posts/{id}")]
async fn show(&self, Piped(id): Piped<ParseUuid, Path<String>>) -> Json<Post> {
    Json(self.svc.find(id))
}
```

`Piped` is no extractor of its own: `#[routes]` reads it where the signature
spells it out, so a type alias of it is a compile error naming `FromRequest`
rather than a parameter that skips its source's rules.

## `Header<T>` — typed request headers

The header-map twin of `Query<T>`: one struct field per header,
`#[serde(rename = "…")]` spelling the wire name, and an `Option<_>`
field marking the header optional. Lookup is case-insensitive, as HTTP
header names are, and values are parsed into the field's type — a
`u32` field is an integer, not a string you parse in the handler.

```rust title="crates/features/src/notifications/http/controller.rs"
use nest_rs::http::{Header, SseStream};
use serde::Deserialize;
use schemars::JsonSchema;

#[derive(Deserialize, JsonSchema)]
struct StreamResume {
    #[serde(rename = "Last-Event-ID")]
    last_event_id: Option<u32>,
}

#[sse("/events")]
async fn events(&self, resume: Header<StreamResume>) -> SseStream {
    self.svc.stream_from(resume.into_inner().last_event_id)
}
```

A missing required header, or a value that does not parse, is rejected
with the same RFC 9457 `application/problem+json` `400` a validation
failure carries. **The rejection names the header and never quotes its
value** — a header is where credentials travel, and a `400` body is
logged, cached and proxied.

Each property becomes an `in: header` parameter in the
[OpenAPI document](/openapi/), `required` following the schema. It
composes like every other extractor: the rules its DTO declares hold,
and `Piped<P, Header<T>>` pipes it.

## `RawBody` — exact bytes, with a size cap

Some handlers need the exact byte string before any parsing — a proxied
protobuf body, a document stored as it was sent. `RawBody` reads the whole body
into [`Bytes`](https://docs.rs/bytes), capped at the transport's
`max_body_bytes` (`RawBody::DEFAULT_LIMIT`, 2 MiB, by default). Past the cap the
request is answered `413 Content Too Large` — never silently truncated, never
buffered unbounded. Like every extractor it reads after the guards, so a
refused request never had its body read.

```rust title="crates/features/src/posts/http/controller.rs"
use nest_rs::http::{Path, RawBody, Result};
use uuid::Uuid;

#[put("/{id}/source")]
async fn replace_source(&self, id: Path<Uuid>, body: RawBody) -> Result<()> {
    self.svc.replace_source(*id, body.into_inner()).await
}
```

A webhook's signature is a credential, so it is verified in a guard that reads
the same bytes and hands them on, never in the handler — see
[Read the body in a guard](/fundamentals/guard-context/#read-the-body-in-a-guard).

For a tighter cap on a specific route, take the body and read it under
your own:

```rust title="crates/features/src/posts/http/controller.rs"
use nest_rs::http::{Body, Path, Result};
use uuid::Uuid;

#[put("/{id}/summary")]
async fn replace_summary(&self, id: Path<Uuid>, body: Body) -> Result<()> {
    let summary = body.into_bytes_limit(16 * 1024).await?;
    self.svc.replace_summary(*id, summary).await
}
```

Anything that can deserialize through `Json<T>` should use that instead —
`RawBody` is for handlers that genuinely care about the bytes.

## `ClientIp` — best-effort, observation-grade

```rust title="crates/features/src/users/http/controller.rs"
use nest_rs::http::ClientIp;

#[get("/whoami")]
async fn whoami(&self, ip: ClientIp) -> String {
    format!("you look like {} (forwarded={})", ip.ip, ip.forwarded)
}
```

`ClientIp` resolves against the **transport peer**, and only believes a
forwarding header when that peer is a proxy you listed:

1. No peer address at all (a unix socket, or a proxy that hides it) ⇒
   `0.0.0.0`, `forwarded = false`. The extractor never fails.
2. The peer is **not** in `<PREFIX>_HTTP__TRUSTED_PROXIES` ⇒ that peer is the
   client, `forwarded = false`, and the headers are not read.
3. The peer **is** a trusted proxy ⇒ the client is the **rightmost** hop that
   is not itself a trusted proxy, read from `Forwarded` (RFC 7239) and
   `X-Forwarded-For`, then `X-Real-IP`; `forwarded = true`. If every hop is a trusted
   proxy, the outermost answers. If two headers name different clients none is
   believed, and if no header names a usable hop the proxy's own address answers, both
   with `forwarded = false`. Hops parse as a bare
   IP, `IP:port`, or a bracketed IPv6 (`[ip]`, `[ip]:port`); `unknown` or an
   obfuscated `_id` names no address, so where it stands for the client, the
   proxy withheld it and no client is named.

A header is read whole or not at all. One the parser cannot read — a quote no
quote closes, a pair with no `=`, a hop that is no address — names no client,
whatever the other headers say: the proxy's own address answers, and one `warn`
on `nest_rs::http`, filed inside the request, names the header, never what it
held. A quote left open is the reason: a proxy appending a quoted value to a
caller's line would close the caller's quote, and the caller's own hop would
read as the rightmost. `X-Real-IP`, one hop in no order, answers alone only
where neither chain names a client; beside a chain, it names that chain's client
or neither is believed. A proxy writing `X-Real-IP` and passing the caller's own
`X-Forwarded-For` through would otherwise let the caller choose.

With no trusted proxy configured — the default — step 2 always wins, so
`forwarded` stays `false` and a header a caller sets changes nothing.

```bash frame="terminal"
# The deployment's ingress, named once. Read by ClientIp *and* the throttler.
NESTRS_HTTP__TRUSTED_PROXIES=10.0.0.1,10.42.0.0/16
```

An entry is an address or a CIDR range, and in code a `TrustedProxy`:
`trusted_proxy!("10.42.0.0/16")` for a literal, checked as the program compiles,
so a typo in a `#[module]`'s imports fails the build rather than the boot;
`ip.into()` for an address a value holds, and `"10.42.0.0/16".parse()?` for text
read at run time. An ingress whose pods move is named by their range. Everything
inside one is believed, so it names your proxies and nothing a caller connects
from. A `/0` fails the boot, since it would believe every caller, and so do ranges
holding between them every address of a family a caller connects from
(`0.0.0.0/1,128.0.0.0/1`, or `0.0.0.0/1,128.0.0.0/2,192.0.0.0/3`, short only of
multicast and reserved space), from the environment and from code alike; so does a range with address bits set past
its prefix (`10.0.0.1/8`), which could mean the one proxy or the whole range. A listener on `[::]` reports an IPv4 peer as `::ffff:10.0.0.1`: that is
`10.0.0.1`, to this list and in the address `ClientIp` answers.

**What to list behind each proxy.** Each writes its hop as its documentation
says, and each shape below is pinned by the HTTP suite:

| In front of the app | What it writes | What to list |
|---|---|---|
| nginx, `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for` | the caller's `X-Forwarded-For` with its peer appended; `X-Real-IP $remote_addr` beside it agrees | nginx's address |
| Envoy, `use_remote_address: true` | its downstream appended to `x-forwarded-for` | every Envoy hop, the mesh's range |
| HAProxy, `option forwardfor` or `option forwarded` | an `X-Forwarded-For` line of its own after the caller's, or `forwarded: proto=http;for=…` | HAProxy's address |
| AWS Application Load Balancer, `append` mode | the client appended, `ip:port` (`[ip]:port` for IPv6) with client port preservation | the subnets its nodes take |
| Google Cloud external Application Load Balancer | the client appended, **then the forwarding rule's own address** | its front ends (`35.191.0.0/16`, `130.211.0.0/22`) **and the forwarding rule's address** |

Behind Google Cloud's balancer, leaving the forwarding rule's address off the
list answers that address for every caller: it stands right of the client, and
anything not listed is the client. A proxy writing one header passes the others
through as the caller sent them, and two headers naming different clients are
both refused; behind HAProxy's `option forwarded` alone, a caller's own
`X-Forwarded-For` leaves its request with the proxy's address, so have the proxy
delete what it does not write (`http-request del-header X-Forwarded-For`).

**Rightmost, not leftmost.** A proxy appends the address it received the request
from to the right of the chain, so the genuine client is the last hop your
infrastructure wrote; a caller can only prepend, and a prepended entry lands to
the left of it. Keying on the leftmost hop is the spoofable rule. A chain over
several field lines is one list, in order, since a proxy may add its own line
after the caller's; `X-Real-IP`, one hop, is read from its last line.

<Aside type="caution">
Treat the result as **observational** (geolocation hints, sampling keys),
never as an authn or authz input — and as personal data: the framework writes it
on no line and no span, and a line of yours holding it holds personal data. The peer is trustworthy; the hop behind
it is only as trustworthy as the proxy that wrote it — list an ingress here only
if it strips and rewrites the client's own forwarding headers.

The [throttler](/rate-limiting/) resolves the client through this same
mechanism, from this same list, so a request is never rate-limited as one
address and handed to a handler as another.
</Aside>

## `Scoped<T>` — resolve a request-scoped provider

A `#[injectable(scope = request)]` provider is built once per request —
useful for anything that should not outlive the response (a SQL
transaction handle, a per-request audit batch, a user-specific cache).
`Scoped<T>` is how a handler reads it back:

```rust title="crates/features/src/posts/http/controller.rs"
use nest_rs::core::injectable;
use nest_rs::core::Scoped;
use nest_rs::http::Json;

#[injectable(scope = request)]
pub struct PerRequestAudit { /* ... */ }

#[get("/posts")]
async fn list(&self, audit: Scoped<PerRequestAudit>) -> Json<Vec<Post>> {
    audit.note("list_posts");
    Json(self.svc.list())
}
```

Two contracts hold:

- `Scoped<T>` falls back to a singleton if no scoped factory exists for
  `T` — convenient, but a singleton should still be reached via plain
  `#[inject]` on the controller. Reserve `Scoped<T>` for genuinely
  request-scoped state.
- The framework installs the request scope as the outermost HTTP wrap
  (before guards and interceptors). A provider the request still cannot
  reach — the scope not installed, or `T` offered by no module — answers
  an opaque `500`, and the type goes to an `error` line on
  `nest_rs::http`, never to the client.

See [Provider scopes](/fundamentals/provider-scopes/) for the scope rules — a
request-scoped provider may inject singletons and other request-scoped providers,
one instance each per request; a singleton injects neither.

## `Ambient<T>` — read context a guard attached

A guard runs before the handler, can short-circuit with a response, and
can attach a typed value for the rest of the request. `Ambient<T>` is how the
handler reads that value back:

```rust title="crates/features/src/posts/http/controller.rs"
#[get("/mine")]
async fn mine(&self, caller: Ambient<Claims>) -> Result<Json<Vec<Post>>, PostError> {
    Ok(Json(self.svc.written_by(&caller.sub).await?))
}
```

`caller` is the principal the controller's `AuthnGuard` attached.

`Ambient<T>` rejects with `500` if `T` is absent — a missing context means
the guard that should have set it never ran on this route (a wiring bug,
not a client error). `T` implements `AmbientValue` and `Clone`; the value is
cloned out of the ambient context, so a large one goes in a newtype holding an
`Arc` (`struct Catalog(Arc<Entries>)`), which implements `AmbientValue` itself.

`Ambient<T>` is core's, `nest_rs::core::Ambient`, and the same parameter on every
edge: a GraphQL operation, a WebSocket message and an MCP tool read what their
guards attached the same way, and none of them lists it among the arguments
its protocol describes. A route reads the parameter by its type, so a type
alias of it (`type Me = Ambient<Claims>;`) reads as the name does; the other
three find it by its name, before any type is known, so there an alias of
`Ambient<T>` — or of `Scoped<T>` — is a compile error saying to write it out.

The canonical use is the authenticated principal: `AuthnGuard` runs the
strategy, then attaches a `Claims` (or whatever the resource server's
principal is). Every authenticated handler reads it as `auth: Ambient<Claims>`.
On a `#[public]` route, a handler reading `Ambient<Claims>`, under that name or an
alias, needs the caller the guard identifies: one it did not is refused at the guard stage, before any other
argument is read, with the `401` a rejected credential earned
(`Bearer error="invalid_token"`) or, for a caller that sent none, the plain
challenge, and the route's document lists that `401`. A handler that serves a
visitor too reads the principal with `nest_rs::core::ambient::<Claims>()`, an
`Option`.

See [Guards](/fundamentals/guards/) for how to attach a value, and for
the design rule (guards gate and attach; handlers read).

## `#[meta(EXPR)]` — typed route metadata

A route can carry typed metadata a guard reads at decision time —
the cleanest case is a rate-limit guard reading the route's quota. The
decorator declares; the reader picks it up by type.

Declare metadata on the route, or on its `#[controller]` for every route it
serves:

```rust title="crates/features/src/sign_in/http/controller.rs (from the demo, abridged)"
use nest_rs::throttler::{Throttle, ThrottlerGuard};
// …

#[post("/login")]
#[public]
#[use_guards(ThrottlerGuard)]
#[meta(Throttle::per_minute(10))]
// … #[api(…)]
async fn login(&self, Json(input): Json<LoginDto>) -> Result<AccessTokenResponse> {
    Ok(self
        .svc
        .grant_password(
            &input.email,
            input.password.expose_secret(),
            input.resource.as_deref(),
        )
        .await?)
}
```

### Advanced: reading `#[meta]` from a guard

Everything below is for the **guard author**, not the handler — a
handler only declares metadata; the guard reads it back at decision
time:

```rust title="nest_rs::throttler::ThrottlerGuard (abridged)"
async fn check_http(&self, cx: &mut UnitContext<'_>) -> Result<(), Denial> {
    let limit = cx
        .reflector()
        .get::<Throttle>()
        .copied()
        .unwrap_or(*self.default);
    // …
}
```

Three rules pin the contract:

- The value type must be `Send + Sync + 'static`. The expression is
  evaluated once, when the route mounts, and every request reads that one
  value through a pointer — never cloned, never shadowed by what a guard
  attaches. The reader resolves by `TypeId`: wrap values of one underlying
  shape in distinct newtypes when they need to coexist, and declare each
  type once per level. A second would be read by nothing, so the compiler
  refuses it when each expression names its type, and the boot when one
  hides it (`Throttle::per_minute(10)`), naming the type and where.
- The method's value of a type wins over its controller's, and a
  controller's value of another type still reads through.
- Scope does not change what a guard reads. The pool executes
  post-routing in the route's guard stage, which carries the route's
  declaration, so a guard the app's `GlobalGuards` lists reads the
  route's `#[meta]` exactly as a `#[use_guards]` one does — see
  [the request lifecycle](/fundamentals/request-lifecycle/).

`#[meta]` is declared the same way on a resolver, a gateway, an MCP host and
their operations, and on a processor's, scheduled tasks' or listeners' impl
block and its methods. Each site keeps both levels in its one declaration, and
a guard's `check` reads a resolver's, a message's or a tool's through
`cx.reflector()` exactly as `check_http` reads a route's.

## `#[public]` — the only universal marker

`#[public]` declares the route's posture, the framework's only universal
route marker. Guards read it through `cx.reflector().posture()`, which
answers `Posture::Public` for it, and decide whether to honor it. The framework itself does *not* act on the
marker — `AuthnGuard`, for example, still runs the strategy on a `#[public]`
route, but lets an anonymous request through instead of returning `401`.
It admits one on `/graphql`, `Posture::InBand`, the same way. The demo's
`POST /login` [above](#metaexpr--typed-route-metadata) is one: open to the
anonymous caller it signs in, and rate-limited all the same.
