Take a file part straight from a `multipart/form-data` request with the
`Multipart` extractor, which parses the body with
[multer](https://docs.rs/multer), and hand it to storage as it arrives. A direct
upload is the single-round-trip alternative to the
[presigned flow](/storage/): the client posts the bytes, the server stores
them. The demo reads the form in an extractor of its own, so the handler is
one delegation:

```rust title="crates/features/src/audio/http/controller.rs (from the demo, abridged)" {3, 6}
#[post("/uploads/direct")]
// … #[meta(…)], #[api(…, multipart = DirectUploadDto, …)]
async fn upload_direct(&self, upload: UploadedAudio) -> Result<Json<PresignedUrlDto>> {
    Ok(Json(
        self.svc
            .store_upload(upload.part.into_byte_stream())
            .await?,
    ))
}
```

`UploadedAudio` walks the form to its `file` part — a `FromRequest`, so
`#[routes]` passes it through like any other handler argument:

```rust title="crates/features/src/audio/http/uploaded_audio.rs (from the demo)"
pub struct UploadedAudio {
    pub part: Field,
}

impl<'a> FromRequest<'a> for UploadedAudio {
    async fn from_request(req: &'a Request, body: &mut RequestBody) -> Result<Self> {
        let mut form = Multipart::from_request(req, body).await?;
        while let Some(part) = form.next_field().await? {
            if part.name() == Some("file") {
                return Ok(Self { part });
            }
        }
        Err(HttpError::from(
            ProblemDetails::bad_request().with_detail("multipart body has no `file` part"),
        ))
    }
}
```

Two choices carry the weight: the part's filename is never read, so the
client names no object key, and `into_byte_stream()` hands the part to
storage as it arrives, so it never exists whole in memory.

## Stream the part instead of buffering it

`field.bytes()` is the buffered form: the whole part lands in memory before the
handler sees any of it. That is right for a form value and wrong for a file.
`Field::into_byte_stream()` is the other half — the part as it arrives, in the
shape [`Storage::put_stream`](/storage/) consumes:

```rust title="crates/features/src/audio/service.rs (from the demo, abridged)"
pub async fn store_upload(
    &self,
    part: impl Stream<Item = std::io::Result<Bytes>> + Send,
) -> Result<PresignedUrlDto, AudioError> {
    let key = Uuid::now_v7().to_string();
    self.storage
        .put_stream(&key, AUDIO_CONTENT_TYPE, part)
        .await?;
    // …
}
```

The service names a stream, not a transport type, so the same method serves a
multipart part, a proxied download, or a test fixture. Peak memory is one
multipart chunk plus one object-store part, whatever the file's size.

## Mint the key, never take it

A multipart part's filename is the client's choice — never let it become an
object key, or reach a log line or a reply. The service mints the key, a
UUID, and the response hands it back: every later call (`/audio/transcode`,
`/audio/results`) takes that key, parsed as a UUID at the edge, so a client
can name no path, traverse no prefix and smuggle no text into a log. The
[presigned flow](/storage/#presigned-uploads) mints its key the same way.

## Document the form

Nothing in a `Multipart` handler states what the form's parts are, so
`#[api(multipart = Type)]` declares them and the
[OpenAPI document](/openapi/) files the schema under `multipart/form-data`:

```rust title="crates/features/src/media/http/controller.rs"
#[derive(JsonSchema)]
pub struct DirectUploadDto {
    #[schemars(extend("format" = "binary"))]
    pub file: String,
}

#[post("/uploads/direct")]
#[api(multipart = DirectUploadDto)]
async fn upload_direct(&self, mut form: Multipart) -> Result<Json<PresignedUrlDto>> { /* ... */ }
```

`format: binary` is what makes Swagger UI render a file picker for the part.
Undeclared, a `Multipart` handler still documents `multipart/form-data` with a
free-form object — the media type is knowledge a client needs even when no type
states the parts.

## Presigned or direct

| | Presigned PUT | Direct multipart |
|---|---|---|
| Bytes flow | client → storage | client → server → storage |
| Server memory | none | one chunk at a time |
| Round trips | two (mint, then PUT) | one |
| Use when | large media, offload the transfer | small files, one call |

## Limits

- The [`max_body_bytes` cap](/http/configuration/#request-body-size-limit)
  gates **every** body, `Multipart` included. An upload declaring a length past
  the cap — a browser's form does — is answered `413 Payload Too Large` unread;
  one that declares none is cut at the cap as it is read, and answered `413`
  too. The default cap is **2 MiB** — so a 3 MiB upload fails out of the box.
  Raising the ceiling is `<PREFIX>_HTTP__MAX_BODY_BYTES`, not a compensating
  control in your code.
  The admin gate and rate limit the demo binds are defence in depth, not the
  size bound.
- Streaming bounds **memory**, not the request: the part is still read through
  the request body, so `max_body_bytes` is the ceiling either way. Raising it is
  what lets a large file through; streaming is what keeps the process from
  holding it. For very large media the presigned PUT still wins — it avoids
  proxying the bytes through the server at all.
- A long upload runs against the [request timeout](/http/configuration/#request-timeout),
  `20` seconds by default and counted from the request's arrival, its body's
  reading included: an upload slower than that is answered `503` part-way. A
  transport taking large files over slow links turns the budget off
  (`<PREFIX>_HTTP__REQUEST_TIMEOUT_SECS=0`) or raises it — there is no budget per
  route yet. `<PREFIX>_HTTP__BODY_READ_TIMEOUT_SECS` (`10` seconds) never cuts an
  upload that keeps sending: it counts the gap between two of its packets, and
  is the one bound left on a body once the budget is off.
