## The part you cannot forget

<div class="nestrs-reveal not-content">

Authenticated, tenant-scoped, transactional, field-masked — and the `impl`
block is empty on purpose. The two guards declare the posture, `#[crud]`
generates the five routes.

```rust title="crates/features/src/orgs/http/controller.rs (abridged)"
#[controller(path = "/orgs")]
#[use_guards(AuthnGuard, AuthzGuard)]
pub struct OrgsController {
    #[inject]
    svc: Arc<OrgsService>,
}

#[crud(service = svc, entity = OrgEntity, output = Org,
       create = CreateOrg, update = UpdateOrg)]
impl OrgsController {}
```

One ability decides the rows and the fields, in one place:

```rust title="crates/features/src/authz/ability.rs (abridged)"
ab.can(Action::Read, user::Entity)
    .when(|p| p.eq(user::Column::OrgId, actor.org_id))
    .fields([user::Column::Id, user::Column::Name]);
```

Same route, same handler — the caller's token does the rest:

Posture is mandatory, not a convention: a GraphQL operation with neither
`#[authorize]` nor `#[public]` does not compile, and an HTTP controller whose
guard wiring is missing fails at boot. Behind the guards sits the full stack — JWT on
EdDSA keys, OAuth2 with PKCE, Argon2id passwords, social login — each a module
import ([Security](/security/)).

## Everything a backend needs, in one framework

Not a router with plugins to assemble. Each concern below is a module you
import, documented on this site, and shipped as a Cargo feature you can leave
off — a headless worker compiles no HTTP stack.

| Concern | What ships | Read more |
|---|---|---|
| HTTP | Controllers, routing, versioning, extractors, uploads, streaming, compression, CORS, TLS | [HTTP](/http/) |
| API contract | OpenAPI 3 document and Swagger UI derived from the route table | [OpenAPI](/openapi/) |
| GraphQL | Resolvers, dataloaders, relations, subscriptions, federation, query limits | [GraphQL](/graphql/) |
| Realtime | WebSocket gateways, namespaces, rooms, server push | [WebSockets](/websockets/) |
| Agents | MCP server — tools, prompts, resources and tasks under the same guards | [MCP](/mcp/) |
| Database | Entities, `Repo`, ambient transactions, pagination, migrations, seeding | [Database](/database/) |
| Authentication | JWT on EdDSA keys, OAuth2 with PKCE, Argon2id passwords, social login | [Authentication](/security/authentication/) |
| Authorization | Abilities, row-level filtering, per-field masking, one policy per transport | [Authorization](/security/authorization/) |
| Background work | Redis-backed queues with retries, cron schedules, in-process events | [Queue](/queue/) · [Schedule](/schedule/) · [Events](/events/) |
| Object storage | S3-compatible client, presigned URLs, streamed read and write | [Storage](/storage/) |
| Configuration | Typed `#[config]` structs, `.env` cascade, every field reachable from the environment | [Configuration](/configuration/) |
| Operations | Liveness, readiness and startup probes, rate limiting, graceful shutdown | [Health](/health/) · [Rate limiting](/rate-limiting/) |

**31 capabilities**, one dependency to install them:
`cargo add nest-rs --features http,seaorm`. The [Packages](/packages/) page maps
every feature to the crate behind it.

## How fast, exactly

The same service written twice, each side the way its own CLI scaffolds it, on
**both Fastify and Express**. Both serve a byte-identical HTTP contract at the
same stack depth, and a conformance gate verifies the bytes before anything is
measured. One pinned core each — the regime that favours Node.

<Bench />

<details>
<summary>How these numbers were taken</summary>

The harness lives in [`bench/`](https://github.com/YV17labs/NestRS/tree/main/bench)
— provider manifests, the byte-for-byte conformance gate, and the runner.
Server and load generator ([oha](https://github.com/hatoo/oha)) are pinned to
disjoint CPU sets; each tier gets a discarded warmup, then repeated timed runs
whose medians are reported; every result embeds its machine fingerprint (CPU,
kernel, toolchains, resolved dependency versions). Node runs `NODE_ENV=production`
on Node 24; NestRS is a release build.

Per-core is the honest comparison: in production Node scales out by clustering
— one ~200 MB process per core — while one NestRS binary takes every core in a
single single-digit-MB process. The published run comes from a 4-core / 8 GB
Docker VM (Apple Silicon) — virtualized, so these figures are a floor rather
than a ceiling. One command reproduces the table on your hardware:

```bash
cd bench && just bench
```

The [benchmark page](/benchmarks/) documents the contract, the full protocol
and its limits.

</details>

## What holds it up

A backend framework is judged on what it keeps correct over years, not on what
it demonstrates in one file. Each property below is one you can check from a
clone of the repository.

- **66 decorators** — everything you write, from `#[module]` to `#[authorize]`,
  expanding to plain Rust you can print with `cargo expand`. The
  [index](/decorators/) lists every one with the position it goes in.
- **1,800+ tests** in the framework workspace, and the end-to-end suites run
  against live Postgres, Redis and S3 rather than mocks — wiring bugs are the
  ones unit tests never see.
- **Conformance joins.** The families the framework declares — its decorator
  pairs, its `for_root` seams, the `warn`-level events that record a denial —
  are derived from the source and joined against the suites that cover them, so
  a member no test names fails the suite instead of passing unnoticed.
- **Documentation gated against the code.** 120+ pages, and a linter that reads
  the framework's own source: config key tables, trait signatures, version pins,
  the imports a snippet needs to compile. A page that contradicts the code fails
  the lint.
- **A public API frozen for the major.** Every `nest-rs-*` crate publishes at
  the same version in lockstep, so one NestRS version names exactly one
  compatible resolution — down to the third-party crates that surface in your
  own signatures.
- **One artifact to operate.** `cargo build --release` produces a native binary
  for a distroless image: configuration through the environment, probes for the
  orchestrator, SIGTERM draining connections and running your shutdown hooks.

## One domain, several workloads

**Microservice scaling without the distributed-systems tax.** Entities,
services and policy are written once in a shared `features` crate; each app
under `apps/*` is a thin composition root importing only the transports it
serves, so a worker never compiles the HTTP stack. Self-contained tokens and a
shared database — no chatty RPC, no service mesh to get started.

Who runs where is a composition choice in each app's `module.rs`, not a fork of
entities and services — schematically:

## Start where you are

- **You write NestJS and want Rust's runtime cost.** The vocabulary carries
  over — module, provider, controller, guard, resolver — and
  [Coming from NestJS](/coming-from-nestjs/) maps each reflex to its
  decorator, including the four that changed on purpose.
- **You write Rust and axum is lower-level than your application.** Routing is
  the part you already have; tenancy, policy, transactions and masking are the
  parts that drift. [Why not axum](/why-not-axum/) compares the two on that
  axis, and says where a bare router is still the right call.
- **You are starting a service that has to hold its shape.** Scaffold it with
  [Getting started](/getting-started/), then build a feature end to end in the
  [tutorial](/tutorial/).
