MCP (Model Context Protocol) is the spec language models use to call tools.
In the [**Publish**](/publish/) workspace, the assistant lives in
[`assistant`](/publish/) on port **3003**.

A NestRS MCP server is a struct with a `#[mcp]` decorator: DI handles its
dependencies, `#[tool]` defines each tool, and the server self-mounts on the
HTTP transport at the path you choose. Same DI, same access graph, same
ambient ability — your tools live next to your controllers, not in a sidecar.

That ambient ability covers **every** MCP capability, not tools alone. A
prompt fetch, a resource read, a completion, a `tasks/*` call: each runs inside
the caller's request scope, with the operation's transaction around it, and a
handler writes no check on any of them. A declared operation's reads run under
the caller's ability where its posture names what it reads, and read nothing a
grant guards where it names nothing ([Authorization](/mcp/authorization/)); a
host writing rmcp's handler by hand [reads under it unmasked](/mcp/resources-and-prompts/#what-stays-hand-written).

`nest-rs-mcp` builds on [rmcp](https://docs.rs/rmcp) 3.x — the framework wraps
it so a server is an `#[injectable]` struct that self-mounts on the HTTP
transport, with [schemars](https://docs.rs/schemars) deriving the tool input
schemas the client reads.

## Install

```bash frame="terminal"
cargo add nest-rs --features mcp
```

The `mcp` feature pulls the HTTP transport the endpoint mounts on and the guard
surface that gates it: the transport runs the global pool and the endpoint's
guards at every `/mcp` request, so `/mcp` is gated by them instead of staying
deny-all.
None of that is a line you write. Add `authz` when a tool carries
`#[authorize]`, or `seaorm`, which implies it; the decorator names the feature
when it is missing.

`rmcp` is not a dependency either, and it is not an import: `#[tools]` emits
the SDK's own macros inside generated code that carries its own scope. That keeps
the SDK at the exact major `nest-rs` was built against — two majors in one graph
put two `ServerHandler` traits in scope and every generated method mismatches.
A host that needs the raw SDK reaches it through `nest_rs::mcp::rmcp`.

## The smallest possible tool

The fastest way to see the shape: one tool, one string in, one string out.

```rust title="crates/features/src/hello/mcp/tool.rs"
use nest_rs::mcp::{McpError, Parameters, mcp, tools};
use nest_rs::core::input;

#[input]
pub struct HelloParams {
    pub name: String,
}

#[mcp]
#[derive(Clone, Default)]
pub struct HelloTool;

#[tools]
impl HelloTool {
    #[tool(description = "Say hello to someone by name.")]
    #[public]
    async fn hello(&self, Parameters(params): Parameters<HelloParams>) -> Result<String, McpError> {
        Ok(format!("Hello, {}!", params.name))
    }
}
```

`#[public]` is the operation's access posture: a greeting gates nothing and reads
nothing a grant guards, so a caller with no credential is admitted. On an endpoint the app's guards
authenticate an operation needs no posture of its own, as a route needs none under
a guard, and [Authorization](/mcp/authorization/) covers the form that gates one.

That's a complete MCP server — but a bare `#[mcp]` endpoint is **closed by
default**. Its request runs the global guard pool
(the `GlobalGuards<(...)>` the module the app boots declares) and the
[endpoint guards](/security/authorization/endpoint-guards/) the app's modules
declare for it, either alone when the other is missing, and with neither it is
**deny-all** — every request answers `401`, so a schema-added tool can never
leak unauthenticated. The boot says so once, on `nest_rs::layers`:

```text frame="terminal"
WARN nest_rs::layers: no guard at the request surface="mcp" path="/mcp" then="denies every unit" hint="list `GlobalGuards<(...)>` in the providers of the module the app boots, bind `#[use_guards(...)]` on a controller or a gateway, `EndpointGuards<View, (...)>` on an endpoint carrying units, or open it on purpose: `#[public]` on a route, a message or a GraphQL operation, `McpModule::for_root(McpAccess::Public)` on an MCP endpoint. A guard that identifies no one, a rate limit or one of your own declaring no `phase()`, covers nothing: declare its `GuardPhase::Authentication` or `Authorization`, or write `#[public]`"
```

A `#[public]` operation there could open nothing, so the boot refuses it and names
the opening below, which `HelloTool` takes.

The feature's MCP adapter lists its tool like any provider. `#[mcp]` brings
`McpModule` bare, which reads the endpoint's settings from `<PREFIX>_MCP__*`
([MCP configuration](/mcp/configuration/)) and brings `HttpModule`, the server
the endpoint mounts on:

```rust title="crates/features/src/hello/mcp/module.rs"
use nest_rs::core::module;

use super::tool::HelloTool;

#[module(providers = [HelloTool])]
pub struct HelloMcpModule;
```

A *deliberately* public endpoint has to say so, where the app is composed:

```rust title="apps/assistant/src/module.rs"
use nest_rs::core::module;
use nest_rs::mcp::{McpAccess, McpModule};

use features::hello::HelloMcpModule;

#[module(imports = [
    McpModule::for_root(McpAccess::Public),
    HelloMcpModule,
])]
pub struct AssistantModule;
```

A public `/mcp` runs no guard at its request, the global pool's included, so the
opening belongs where the app is composed, never in a feature crate another app
might import — and a module declaring guards for the endpoint beside it fails
the boot rather than seeing them dropped. Every operation it serves states its
posture, `#[public]`, `#[public(Action, Subject)]` or `#[authorize(Action, Subject)]`:
no guard covers it there, and one stating none fails the boot too. The opening is made at one import: a
second `McpModule::for_root` opening the endpoint fails the boot naming both,
even when the two agree. `#[mcp]` mounts the tool on the existing HTTP transport —
same port, same CORS, no second server. An MCP client pointed at
`http://localhost:3003/mcp` sees one tool called `hello` and can invoke it. (To
authenticate instead of opening it, see [Authorization](/mcp/authorization/).)

Two decorators, one per item shape:

- **`#[mcp]` on the struct** registers it as a discoverable provider that mounts
  a streamable-HTTP endpoint on the HTTP transport, at `/mcp`. An optional
  `path` serves a different URL instead — write it whole, the way a client
  config carries it.
- **`#[tools]` on the impl** declares the operations. Every `#[tool]`,
  `#[prompt]`, `#[resource]` and `#[resources]` method is mounted, and the
  endpoint's advertised capabilities are derived from the roles present — you cannot serve a tool you forgot to
  declare. An operation declares the same request layers a route does:
  `#[use_guards(...)]`, `#[authorize(...)]` / `#[public]`,
  `#[use_exception_filters(...)]`, `#[use_interceptors(...)]`, a pipe on its
  arguments, a `Scoped<T>` parameter and an `Ambient<T>` one — see
  [Layers around an operation](#layers-around-an-operation). An operation
  answers a `Result`, known by its type: it fails with whatever error it
  holds — an `McpError`, a domain error — answered by that type, an alias
  such as `type Publishing<T> = Result<T, PublishError>` serves as well as the
  spelled one, and a `String` is refused at the return type. Two readings go
  by the spelling: a *masked* operation spells its `Result<…>`, since the mask
  reads `Json<T>` — a resource's `Option<Json<T>>` — off it, and rmcp derives a tool's output schema only from a
  return spelled `Result<Json<T>, …>`.
- **The description is `#[tool(description = "…")]`** — the sentence the model
  reads to pick this tool, so it is a value the decorator compiles in rather
  than commentary. Write a doc comment instead and it is used as a fallback, so
  the prose is never written twice; write **neither and it does not compile**.
  A blank one is none: `description = "  "`, and a doc line or a stated value
  the compiler evaluates — `include_str!` of an empty file, a `concat!` of
  spaces, a constant — fails the build with the same sentence.

The struct can take `#[inject]` fields like any other provider — `HelloTool` has
none, real servers usually do.

Note what the file does *not* name: no `rmcp`, no `ServerHandler`, no router, no
`get_info`. Those are rmcp's, and the expansion keeps them in generated code.

## Run it

```bash
$ nestrs run dev assistant
```

```text frame="terminal"
INFO nest_rs::routes: mounted endpoint surface="mcp" host="McpModule" path="/mcp"
INFO nest_rs::app: app ready transports="http" addresses="0.0.0.0:3003"
```

Point an MCP-aware client at `http://localhost:3003/mcp`. With Claude Code, add
it over the streamable-HTTP transport:

```bash frame="terminal"
$ claude mcp add --transport http hello http://localhost:3003/mcp
```

Or explore the tool surface with the MCP Inspector — no client config needed:

```bash frame="terminal"
$ npx @modelcontextprotocol/inspector
```

Now use it. Ask the model — in Claude Code, "say hello to Ada" — and it calls
the `hello` tool with `{ "name": "Ada" }`; the tool answers `Hello, Ada!`. That
round trip — client → `/mcp` → your `#[tool]` method → response — is the whole
surface. You have a running assistant, discovered and wired like any other
provider.

## Multiple tools on one server

Each `#[tool]` method becomes its own callable. Share state through `&self` —
`#[inject]` once, every tool reuses it.

```rust title="crates/features/src/posts/mcp/tool.rs"
#[mcp(path = "/mcp/posts")]
#[derive(Clone)]
pub struct PostsTool {
    #[inject]
    svc: Arc<PostsService>,
}

#[tools]
impl PostsTool {
    #[tool(description = "List the titles of the latest published posts.")]
    #[public(Read, post::Entity, unmasked)]
    async fn latest_titles(
        &self,
        Parameters(p): Parameters<LatestParams>,
    ) -> Result<String, ServiceError> {
        let titles = self.svc.latest_titles(p.limit).await?;
        Ok(titles.join("\n"))
    }

    #[tool(description = "Return a published post's summary, found by its slug.")]
    #[public(Read, post::Entity, unmasked)]
    async fn post_summary(
        &self,
        Parameters(p): Parameters<SlugParams>,
    ) -> Result<String, ServiceError> {
        let post = self.svc.by_slug(&p.slug).await?;
        Ok(post.summary())
    }
}
```

The client now sees two tools — `latest_titles` and `post_summary` — both
sharing the injected `PostsService`. The `description` is what the model
reads to decide when to call each. Each names what it reads, which
[`define_visitor`](/security/authorization/public-reads/) grants; a bare `#[public]`
would read nothing. `unmasked` leaves the field grants to the body, since each
answers a `String` it wrote rather than a row.

## A validated tool

Tool inputs are deserialized to a typed struct, so the schema the client reads
is already typed. Arguments that do not decode are refused before the body runs
as a tool error the model can correct — ``failed to deserialize parameters:
argument `limit`: invalid type: a string, expected u8`` — naming the
argument, the kind of value found and what was expected, and never the value,
which would otherwise land in the model's transcript. `Parameters` is the
framework's own for that reason, with rmcp's shape and schema. A prompt's
arguments are refused in the same words, as JSON-RPC's `invalid_params` under
`data: { "code": "INVALID_ARGUMENT" }`.

A tool error is a failed call all the same, whether rmcp answered it for
arguments that do not decode or the tool returned `CallToolResult::error`
itself: its unit of work rolls back, its `mcp.operation` line files
`outcome="error"`, and its span carries `error.type` `tool_error`, the class
OpenTelemetry's MCP conventions give a result with `isError: true`.

For extra checks beyond shape — ranges, enums, mutual exclusion — add
`validate(...)` attributes: `#[input]` already carries the `validator` derive,
so no extra import and no extra manifest line.

```rust title="crates/features/src/posts/dtos/search_posts_dto.rs"
use nest_rs::core::input;

#[derive(Debug)]
#[input]
pub struct SearchPostsDto {
    #[validate(length(min = 1, max = 100))]
    pub query: String,

    #[validate(range(min = 1, max = 50))]
    pub limit: u8,
}
```

The rules run before the body, with nothing to wrap — the same check every
edge runs on what it decodes, as [Pipes](/fundamentals/pipes/#validation-at-the-edge)
describes:

```rust title="crates/features/src/posts/mcp/tool.rs (abridged)"
#[tool(description = "Search the published posts' titles, most recent first.")]
#[public(Read, post::Entity, unmasked)]
async fn search_posts(
    &self,
    Parameters(params): Parameters<SearchPostsDto>,
) -> Result<String, ServiceError> {
    let titles = self.svc
        .search_titles(&params.query, params.limit)
        .await?;

    Ok(titles.join("\n"))
}
```

`JsonSchema` derives the schema sent to the client from `SearchPostsDto`, and a
rejection answers
`invalid_params` carrying its class and the field errors under `errors`, which
is the one MCP error a model can act on:

```json
{"code":-32602,"message":"validation failed",
 "data":{"code":"INVALID_ARGUMENT","errors":{"query":[{"code":"length"}]}}}
```

`Parameters<Piped<P>>` runs any [pipe](/fundamentals/pipes/) over the
arguments when they need transforming, once they passed their rules.

## Layers around an operation

Every request a client sends is an operation of its own — its span, its line,
its unit of work — run on the same pipeline as a route. A tool call, a prompt
fetch, a resource read and a listing run the layers their host and their
method bind, then the app's,
each family once: the guards' `check`, the posture's gate, the exception
filters, the interceptors, then the pipes, the `Scoped<T>` and `Ambient<T>`
parameters, the body and the mask. A layer reads the operation through `McpView`:

```rust title="crates/features/src/posts/mcp/tool.rs"
#[mcp(path = "/mcp/posts")]
#[use_interceptors(ToolMetrics)]
#[derive(Clone)]
pub struct PostsTool {
    #[inject]
    svc: Arc<PostsService>,
}

#[tools]
impl PostsTool {
    #[tool(description = "Publish the caller's open draft under its slug.")]
    #[authorize(Create, post::Entity, unmasked)]
    #[use_exception_filters(SlugTakenFilter)]
    async fn publish_draft(&self, draft: Scoped<Draft>) -> Result<String, PublishError> {
        self.svc.publish(&draft).await
    }
}
```

`cx.switch_to::<McpView>()` answers the JSON-RPC method (`method()`), the
router serving it (`kind()`), the tool, prompt or listing it names, or the
template a resource is read through (`name()`), and the host declaring it
(`host()`). `publish_draft` fails with the domain's own
`PublishError`: `SlugTakenFilter` reads it as that type and may answer a
problem — a `409` is `invalid_request` with `data.code: "CONFLICT"` — and an
error no filter answers is rendered by its type: a `ToProblem` error says its
problem, any other is answered opaquely, its chain filed at `error`. A filter
answers what the client reads, never whether the operation failed: its unit of
work rolls back either way.

`Scoped<T>` resolves an `#[injectable(scope = request)]` provider from the
`/mcp` request's scope, once the guards and the gate admitted the caller. It is
checked at boot like an `#[inject]` field: a provider no imported module
offers fails the boot rather than the first call. A host writing rmcp's handler
by hand reads `nest_rs::core::current_request_scope()` instead.

`Ambient<T>` reads what a guard attached — the principal the `/mcp` request's
guards verified, or what a guard bound on the operation derived from it — as a
route reads it. Neither parameter is an argument of the tool: the input schema
a client lists names neither, and an absent value answers opaquely, its type
filed at `error`.

The app's own interceptors (`GlobalInterceptors`) run around every operation
`#[tools]` declares too, outermost, after the guards. An `#[interceptor(stage = unit)]` serving MCP runs once
around every request — a listing, a handshake, a tool call alike, one naming
no declared tool included — before rmcp decodes it; `Layer::serves` reads the unit, `nest_rs::mcp::unit::OPERATION`.
Every operation's layers are composed at boot, so one that no module provides,
or two `#[meta]` values of one type on one operation, fail the boot.

`#[mcp]` and `#[tools]` sit on a concrete type: each operation's site is a
`static`, so a generic host does not compile.

## Failing without leaking

A tool body talks to a **language model**, and it would repeat whatever an error's
`Display` carries: a `DbErr` holds schema, column names and sometimes row values.
So an operation returns its error and the edge says what the model reads. A
[`ToProblem`](/http/errors/) error answers its class under `data`: a
`ServiceError` its `NOT_FOUND`, its `FORBIDDEN`, or the `UNAVAILABLE` of a statement
Postgres cancelled, which a client may retry:

```rust title="crates/features/src/users/mcp/tool.rs (from the demo, abridged)"
async fn list_people(&self) -> Result<Json<Vec<PersonDto>>, ServiceError> {
    let rows = self.svc.list().await?;
    // …
}
```

A failure that says no problem, one the model has no business reading, goes through
`opaque`, at the line where it happens:

```rust title="crates/features/src/audio/mcp/tool.rs (from the demo, abridged)"
Ok(match self.svc.presign_result(params.file).await.opaque()? {
    // …
})
```

The real error is logged at `error` on `nest_rs::mcp`, inside rmcp's own
per-operation span; the model gets the opaque answer, one JSON-RPC internal
error whoever answered it — a constant `internal error`, and the class every
edge names it by under `data`:

```json
{ "code": -32603, "message": "internal error", "data": { "code": "INTERNAL" } }
```

Returning the
error itself does the same — an operation answering a `Result<T, E>` answers
an `E` that says no problem opaquely, and files it — while keeping it typed for an
[exception filter](#layers-around-an-operation). A *deliberate* error is the
opposite case — `McpError::invalid_params(...)` exists to be read, so return it
directly and never route it through `opaque`.

A tool that **panics** is answered the same way: rmcp runs it on a task of its
own, so the panic is contained where the operation is dispatched, the client
gets that opaque answer instead of waiting out its own timeout, the
`mcp.operation` line files `outcome="panic"`, and the panic's text goes to
`nest_rs::mcp` at `error` — never to the model.

Every operation answered with a JSON-RPC error is a failed one: its unit of
work rolls back, and its `mcp.operation` line files `outcome="error"`. Its span
records the code as OpenTelemetry's
[MCP conventions](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/mcp.md)
ask. The code is always in `rpc.response.status_code` (`"-32603"`). When the
server failed, it is also the span's `error.type`, with an `Error` status.
A code the conventions read as the caller's own fails nothing on the server's
span, as an HTTP `4xx` does not: `-32700` (Parse error), `-32600` (Invalid
Request, a refusal included), `-32601` (Method not found), `-32602` (Invalid
params, a tool or prompt no host declares) and `-32002` (Resource not found).

What the client named is never handed back either. rmcp refuses a prompt no
host declares, a method no host serves, a task its `TaskManager` does not hold
and a request its transport turns away — an `MCP-Protocol-Version` it does not
know, an `Mcp-Method` or `Mcp-Name` header the body contradicts — in sentences
quoting the name, the id or the header. The endpoint answers each by kind:
`prompt not found`, still listing the prompts under `available_prompts`;
`unknown task`; JSON-RPC's own words for the error's code, such as `Method not
found`, its id and code kept; or, for a refusal that is no JSON-RPC error, the
status's problem document, under the class its status names. A refusal rmcp
words without quoting the request — `Not Acceptable: Client must accept both
application/json and text/event-stream`, `Not Found: Session not found`, the
`_meta` keys the specification requires — keeps its sentence, as the `detail`
or the message. A tool, prompt, task or method no host serves carries
`{"code":"NOT_FOUND"}` in its `data`, beside what it lists: a protocol method
rmcp refuses on a host's behalf, such as `resources/read` on a host serving no
resources, keeps its `-32601` and rmcp's message naming the method. Two
refusals carry no class: in a session negotiated before `2026-07-28`, rmcp
answers `subscriptions/listen`, and a tasks method when no host offers tasks,
inside the session's stream, before any host or the endpoint reads it.

A body typed JSON that is no JSON-RPC message is input the server cannot
accept, as MCP's Streamable HTTP transport says: it is answered `400` with a
JSON-RPC error carrying no `id`, since none could be read — `-32700` (Parse
error) for a body that is not JSON, `-32600` (Invalid Request) for JSON that is
no message — under `{"code":"INVALID_ARGUMENT"}`, never what it held. A body
typed otherwise is the `415` rmcp answers,
`Unsupported Media Type: Content-Type must be application/json`, under
`UNSUPPORTED_MEDIA_TYPE`.

## Trait-based DI

Injecting a trait — `Arc<dyn Upstream>` for a service the tool calls out to —
keeps the concrete provider module-private: a test app swaps in a stub with
`override_dyn::<dyn Upstream>(…)`, which every consumer then injects,
the tool host and any service built at boot alike. Same hexagonal pattern as the rest of the
framework: the tool depends on the trait, the impl lives behind the module,
the access graph rejects accidental coupling at boot.
