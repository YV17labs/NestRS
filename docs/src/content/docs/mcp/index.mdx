MCP (Model Context Protocol) is the spec language models use to call tools.
In the [**Publish**](/publish/) workspace, the assistant lives in
[`assistant`](/publish/) on port **3003**.

A NestRS MCP server is a struct with a `#[mcp]` decorator: DI handles its
dependencies, `#[tool]` defines each tool, and the server self-mounts on the
HTTP transport at the path you choose. Same DI, same access graph, same
ambient ability — your tools live next to your controllers, not in a sidecar.

That ambient ability covers **every** MCP capability, not tools alone. A
prompt fetch, a resource read, a completion, a `tasks/*` call: each runs inside
the caller's request scope, with the caller's ability installed and the
operation's transaction around it. A handler writes no check on any of them.

`nest-rs-mcp` builds on [rmcp](https://docs.rs/rmcp) 3.x — the framework wraps
it so a server is an `#[injectable]` struct that self-mounts on the HTTP
transport, with [schemars](https://docs.rs/schemars) deriving the tool input
schemas the client reads.

## Install

```bash frame="terminal"
cargo add nest-rs --features mcp
```

The `mcp` feature pulls the HTTP transport the endpoint mounts on and the guard
surface that gates it: the transport runs the global pool and the endpoint's
guards at every `/mcp` request, so `/mcp` is gated by them instead of staying
deny-all.
None of that is a line you write. Add `authz` when a tool carries
`#[authorize]`, or `seaorm`, which implies it; the decorator names the feature
when it is missing.

`rmcp` is not a dependency either, and it is not an import: `#[tools]` emits
the SDK's own macros inside generated code that carries its own scope. That keeps
the SDK at the exact major `nest-rs` was built against — two majors in one graph
put two `ServerHandler` traits in scope and every generated method mismatches.
A host that needs the raw SDK reaches it through `nest_rs::mcp::rmcp`.

## The smallest possible tool

The fastest way to see the shape: one tool, one string in, one string out.

```rust title="crates/features/src/hello/mcp/tool.rs"
use nest_rs::mcp::{McpError, Parameters, input, mcp, tools};

#[input]
pub struct HelloParams {
    pub name: String,
}

#[mcp]
#[derive(Clone, Default)]
pub struct HelloTool;

#[tools]
impl HelloTool {
    #[tool(description = "Say hello to someone by name.")]
    #[public]
    async fn hello(&self, Parameters(params): Parameters<HelloParams>) -> Result<String, McpError> {
        Ok(format!("Hello, {}!", params.name))
    }
}
```

Every operation declares its access posture, and one of the two forms is
**required** — `#[public]` here because a greeting gates nothing. An operation
nobody thought about does not compile, rather than shipping ungated to a model.
[Authorization](/mcp/authorization/) covers the other form.

That's a complete MCP server — but a bare `#[mcp]` endpoint is **closed by
default**. Its request runs the global guard pool
(`App::builder().use_guards_global(...)`) and the
[endpoint guards](/security/authorization/endpoint-guards/) the app's modules
declare for it, either alone when the other is missing, and with neither it is
**deny-all** — every request answers `401`, so a schema-added tool can never
leak unauthenticated. The boot says so once, on `nest_rs::layers`:

```text frame="terminal"
WARN nest_rs::layers: a gated endpoint runs no guard at its request; it denies every request path="/mcp" kind="mcp"
```

The feature lists its tool like any provider:

```rust title="crates/features/src/hello/module.rs"
use nest_rs::core::module;

use crate::hello::tool::HelloTool;

#[module(providers = [HelloTool])]
pub struct HelloModule;
```

A *deliberately* public endpoint has to say so, where the app is composed:

```rust title="apps/assistant/src/module.rs"
use nest_rs::core::{Posture, module};
use nest_rs::http::HttpModule;
use nest_rs::mcp::{McpModule, McpOptions};

use features::hello::HelloModule;

#[module(imports = [
    HttpModule::for_root(None),
    McpModule::for_root(McpOptions { posture: Posture::Public, ..Default::default() }),
    HelloModule,
])]
pub struct AssistantModule;
```

A public `/mcp` runs no guard at its request, the global pool's included, so the
opening belongs where the app is composed, never in a feature crate another app
might import — and a module declaring guards for the endpoint beside it fails
the boot rather than seeing them dropped. The opening is made at one import: a
second `McpModule::for_root` opening the endpoint fails the boot naming both,
even when the two agree. `#[mcp]` mounts the tool on the existing HTTP transport —
same port, same CORS, no second server. An MCP client pointed at
`http://localhost:3003/mcp` sees one tool called `hello` and can invoke it. (To
authenticate instead of opening it, see [Authorization](/mcp/authorization/).)

Two decorators, one per item shape:

- **`#[mcp]` on the struct** registers it as a discoverable provider that mounts
  a streamable-HTTP endpoint on the HTTP transport, at `/mcp`. An optional
  `path` serves a different URL instead — write it whole, the way a client
  config carries it.
- **`#[tools]` on the impl** declares the operations. Every `#[tool]` and
  `#[prompt]` method is mounted, and the endpoint's advertised capabilities are
  derived from the roles present — you cannot serve a tool you forgot to
  declare. An operation declares the same request layers a route does:
  `#[use_guards(...)]`, `#[authorize(...)]` / `#[public]`,
  `#[use_exception_filters(...)]`, `#[use_interceptors(...)]`, a pipe on its
  arguments and a `Scoped<T>` parameter — see
  [Layers around an operation](#layers-around-an-operation). An operation
  answers a `Result`, known by its type: it fails with whatever error it
  holds — an `McpError`, a domain error — answered by that type, an alias
  such as `type Ledgered<T> = Result<T, LedgerError>` serves as well as the
  spelled one, and a `String` is refused at the return type. Two readings go
  by the spelling: a *masked* operation spells its `Result<…>`, since the mask
  reads `Json<T>` off it, and rmcp derives a tool's output schema only from a
  return spelled `Result<Json<T>, …>`.
- **The description is `#[tool(description = "…")]`** — the sentence the model
  reads to pick this tool, so it is a value the decorator compiles in rather
  than commentary. Write a doc comment instead and it is used as a fallback, so
  the prose is never written twice; write **neither and it does not compile**.
  A blank one is none: `description = "  "`, and a doc line or a stated value
  the compiler evaluates — `include_str!` of an empty file, a `concat!` of
  spaces, a constant — fails the build with the same sentence.

The struct can take `#[inject]` fields like any other provider — `HelloTool` has
none, real servers usually do.

Note what the file does *not* name: no `rmcp`, no `ServerHandler`, no router, no
`get_info`. Those are rmcp's, and the expansion keeps them in generated code.

## Run it

```bash
$ nestrs run dev assistant
```

```text frame="terminal"
INFO nest_rs::routes: mounted endpoint kind="mcp" path="/mcp"
INFO nest_rs::app: app ready transports="HttpTransport" addresses="0.0.0.0:3003"
```

Point an MCP-aware client at `http://localhost:3003/mcp`. With Claude Code, add
it over the streamable-HTTP transport:

```bash frame="terminal"
$ claude mcp add --transport http hello http://localhost:3003/mcp
```

Or explore the tool surface with the MCP Inspector — no client config needed:

```bash frame="terminal"
$ npx @modelcontextprotocol/inspector
```

Now use it. Ask the model — in Claude Code, "say hello to Ada" — and it calls
the `hello` tool with `{ "name": "Ada" }`; the tool answers `Hello, Ada!`. That
round trip — client → `/mcp` → your `#[tool]` method → response — is the whole
surface. You have a running assistant, discovered and wired like any other
provider.

## Multiple tools on one server

Each `#[tool]` method becomes its own callable. Share state through `&self` —
`#[inject]` once, every tool reuses it.

```rust title="crates/features/src/weather/mcp/tool.rs"
#[mcp(path = "/mcp/weather")]
#[derive(Clone)]
pub struct WeatherTool {
    #[inject]
    svc: Arc<dyn WeatherService>,
}

#[tools]
impl WeatherTool {
    #[tool(description = "Return the current temperature for a city.")]
    #[public]
    async fn current_temperature(
        &self,
        Parameters(p): Parameters<CityParams>,
    ) -> Result<String, McpError> {
        let t = self.svc.current(&p.city).await.opaque()?;
        Ok(format!("{t:.1}°C"))
    }

    #[tool(description = "Return the forecast for a city, N days out.")]
    #[public]
    async fn forecast(
        &self,
        Parameters(p): Parameters<ForecastParams>,
    ) -> Result<String, McpError> {
        let f = self.svc.forecast(&p.city, p.days).await.opaque()?;
        Ok(f.summary())
    }
}
```

The client now sees two tools — `current_temperature` and `forecast` — both
sharing the injected `WeatherService`. The `description` is what the model
reads to decide when to call each.

## A validated tool

Tool inputs are deserialized to a typed struct, so the schema the client reads
is already typed. Arguments that do not decode are refused before the body runs
as a tool error the model can correct — `failed to deserialize parameters:
invalid type: a string, expected f64` — naming where and what kind and never the
value, which would otherwise land in the model's transcript. `Parameters` is the
framework's own for that reason, with rmcp's shape and schema. A prompt's
arguments are refused in the same words, as JSON-RPC's `invalid_params` under
`data: { "code": "INVALID_ARGUMENT" }`.

For extra checks beyond shape — ranges, enums, mutual exclusion — add
`validate(...)` attributes: `#[input]` already carries the `validator` derive,
so no extra import and no extra manifest line.

```rust title="crates/features/src/weather/coords.rs"
use nest_rs::mcp::input;

#[derive(Debug)]
#[input]
pub struct Coords {
    #[validate(range(min = -90.0, max = 90.0))]
    pub latitude: f64,

    #[validate(range(min = -180.0, max = 180.0))]
    pub longitude: f64,
}
```

Wrap the arguments in `Valid<T>` and the check runs before the body — the same
[pipe](/fundamentals/pipes/) binding GraphQL, WebSockets and queue handlers use:

```rust title="crates/features/src/weather/mcp/tool.rs (abridged)"
#[tool(description = "Return the current weather at the given GPS coordinates (Open-Meteo).")]
#[public]
async fn current_weather(
    &self,
    Parameters(params): Parameters<Valid<Coords>>,
) -> Result<String, McpError> {
    let params = params.into_inner();
    let report = self.svc
        .current(params.latitude, params.longitude)
        .await
        .opaque()?;

    Ok(report.summary())
}
```

`JsonSchema` derives the schema sent to the client — from `Coords`, not from the
carrier, so a client never sees `Valid` — and a rejection answers
`invalid_params` carrying the field errors, which is the one MCP error a model
can act on:

```json
{"code":-32602,"message":"validation failed",
 "data":{"latitude":[{"code":"range"}]}}
```

`Piped<P, T>` runs any [pipe](/fundamentals/pipes/) in the same slot when the
argument needs transforming rather than validating.

## Layers around an operation

Every request a client sends is an operation of its own — its span, its line,
its unit of work — run on the same pipeline as a route. A tool call and a
prompt fetch run the layers their host and their method bind, then the app's,
each family once: the guards' `check`, the posture's gate, the exception
filters, the interceptors, then the pipes, the `Scoped<T>` parameters, the body
and the mask. A layer reads the operation through `McpView`:

```rust title="crates/features/src/billing/mcp/tool.rs"
#[mcp(path = "/mcp/billing")]
#[use_interceptors(ToolMetrics)]
#[derive(Clone)]
pub struct BillingTool {
    #[inject]
    svc: Arc<BillingService>,
}

#[tools]
impl BillingTool {
    #[tool(description = "Charge the caller's account for one report.")]
    #[public]
    #[use_exception_filters(LedgerConflictFilter)]
    async fn charge(&self, basket: Scoped<Basket>) -> Result<String, LedgerError> {
        self.svc.charge(&basket).await
    }
}
```

`cx.switch_to::<McpView>()` answers the JSON-RPC method (`method()`), the
router serving it (`kind()`), the tool or prompt it names (`name()`) and the
host declaring it (`host()`). `charge` fails with the domain's own
`LedgerError`: `LedgerConflictFilter` reads it as that type and may answer a
problem — a `409` is `invalid_request` with `data.code: "CONFLICT"` — and an
error no filter answers is rendered by its type: a `ToProblem` error says its
problem, any other is answered opaquely, its chain filed at `error`. A filter
answers what the client reads, never whether the operation failed: its unit of
work rolls back either way.

`Scoped<T>` resolves an `#[injectable(scope = request)]` provider from the
`/mcp` request's scope, once the guards and the gate admitted the caller. It is
checked at boot like an `#[inject]` field: a provider no imported module
offers fails the boot rather than the first call. A host writing rmcp's handler
by hand reads `nest_rs::core::current_request_scope()` instead.

The app's own interceptors (`use_interceptors_global`, a module's
`#[interceptor]`) run around every tool call and prompt fetch too, outermost,
after the guards. An `#[interceptor(stage = unit)]` serving MCP runs once
around every request — a listing, a handshake, a tool call alike, one naming
no declared tool included — before rmcp decodes it; `Layer::serves` reads the unit, `nest_rs::mcp::unit::OPERATION`.
Every operation's layers are composed at boot, so one that no module provides,
or two `#[meta]` values of one type on one operation, fail the boot.

`#[mcp]` and `#[tools]` sit on a concrete type: each operation's site is a
`static`, so a generic host does not compile.

## Failing without leaking

A tool body talks to a **language model**, and an error's `Display` is handed to
it verbatim: a `DbErr` carries schema, column names and sometimes row values.
So a failure the model has no business reading goes through `opaque`:

```rust title="crates/features/src/weather/mcp/tool.rs"
let rows = self.svc.list().await.opaque()?;
```

The real error is logged at `error` on `nest_rs::mcp`, inside rmcp's own
per-operation span; the model gets the opaque answer, one JSON-RPC internal
error whoever answered it — a constant `internal error`, and the class every
edge names it by under `data`:

```json
{ "code": -32603, "message": "internal error", "data": { "code": "INTERNAL" } }
```

Returning the
error itself does the same — an operation answering a `Result<T, E>` answers
an `E` that says no problem opaquely, and files it — while keeping it typed for an
[exception filter](#layers-around-an-operation). A *deliberate* error is the
opposite case — `McpError::invalid_params(...)` exists to be read, so return it
directly and never route it through `opaque`.

A tool that **panics** is answered the same way: rmcp runs it on a task of its
own, so the panic is contained where the operation is dispatched, the client
gets that opaque answer instead of waiting out its own timeout, the
`mcp.operation` line files `outcome="panic"`, and the panic's text goes to
`nest_rs::mcp` at `error` — never to the model.

What the client named is never handed back either. rmcp refuses a prompt no
host declares, a method no host serves, a task its `TaskManager` does not hold
and a request its transport turns away — an `MCP-Protocol-Version` it does not
know, an `Mcp-Method` or `Mcp-Name` header the body contradicts — in sentences
quoting the name, the id or the header. The endpoint answers each by kind:
`prompt not found`, still listing the prompts under `available_prompts`;
`unknown task`; JSON-RPC's own words for the error's code, such as `Method not
found`, its id and code kept; or, for a refusal that is no JSON-RPC error, the
status's problem document. A refusal rmcp words without quoting the request —
`Not Acceptable: Client must accept both application/json and
text/event-stream`, `Not Found: Session not found`, the `_meta` keys the
specification requires — keeps its sentence, as the `detail` or the message.

## Trait-based DI

Injecting `Arc<dyn WeatherService>` keeps the concrete provider
module-private — a test app swaps in a stub with
`override_dyn::<dyn WeatherService>(…)`, which every consumer then injects,
the tool host and any service built at boot alike. Same hexagonal pattern as the rest of the
framework: the tool depends on the trait, the impl lives behind the module,
the access graph rejects accidental coupling at boot.
