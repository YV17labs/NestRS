Import one module and your REST API documents itself. `OpenApiModule` serves an
**OpenAPI 3.1** document at `GET /api-json` and a bundled, offline **Swagger UI**
at `GET /api` — composed from the route table and your `Json<T>` types. There is
no spec to hand-write, and it **cannot drift** from the code: change a handler,
the document changes with it.

`nest-rs-openapi` builds on [schemars](https://docs.rs/schemars) for the JSON
Schema derivation and bundles [Swagger UI](https://swagger.io/tools/swagger-ui/)
as the offline browser asset — the framework wires both behind the route table
so the spec composes itself.

## Install

```bash frame="terminal"
cargo add nest-rs --features openapi
```

## Wire it in

Add `OpenApiModule::for_root` to the app root, alongside the controllers it
should document:

```rust title="apps/api/src/module.rs (from the demo, abridged)"
use nest_rs::core::module;
// …
use nest_rs::openapi::OpenApiModule;
// …

#[module(
    imports = [
        // …
        OpenApiModule::for_root(None),
        // …
        UsersHttpModule,
        // … the rest of the HTTP modules
    ],
)]
pub struct ApiModule;
```

That's the whole opt-in. The module self-mounts both endpoints on the existing
`HttpTransport` — same port, same CORS, no second server. `None` reads
`<PREFIX>_OPENAPI__*` from the [`.env` cascade](/configuration/); pass an
`OpenApiConfig` to pin it in code instead.

## What you get

- **`GET /api-json`** — the OpenAPI 3.1 document, **composed from the route
  table** your app serves. Every `#[controller]` your app mounts contributes its
  operations; nothing is listed by hand.
- **`GET /api`** — a **bundled** Swagger UI. The assets ship inside the binary,
  so it works with no internet access and no CDN, and the page loads nothing
  from elsewhere: it carries its own `Content-Security-Policy` (scripts and
  requests from its own origin only, never framed), and Swagger UI's online
  validator, which would send the document's URL to swagger.io, is off.
- **`GET /api-json/v{n}`** — one document per API version, and only under
  `<PREFIX>_HTTP__VERSIONING=header` or `media_type`. OpenAPI 3.1 keys operations
  by path, so two versions selected by a header cannot both be described at
  `/posts`. Under the default `uri` strategy the version is already in the path
  and `/api-json` describes every version at once. See
  [Versioning](/http/versioning/).
- **Schemas for free.** Request and response bodies are derived from your
  `Json<T>` payload types via [`schemars`](https://docs.rs/schemars). An entity
  declared with `#[expose]` already produces its JSON Schema — the same type
  feeds the handler, the GraphQL schema, and this document, so the three stay in
  sync by construction. See [Database](/database/).

<Aside type="note">
  Because the document is composed from what the binary actually mounts, a worker
  that serves no HTTP routes produces no spec — and an app only documents the
  controllers it imports. Discovery is module-gated, like every other transport.
</Aside>

## Run it

```bash frame="terminal"
$ curl -s http://localhost:3000/api-json | jq '.openapi, .info.title, (.paths | keys)'
"3.1.2"
"nestrs API"
[
  "/users",
  "/users/{id}"
]
```

Open [`http://localhost:3000/api`](http://localhost:3000/api) for the interactive
Swagger UI — try a request straight from the browser.

## Describe an operation

The document is complete without annotations. `#[api(...)]` adds what the
signature cannot say — a summary, a description, the group it sits in:

```rust title="crates/features/src/users/http/controller.rs (from the demo)"
#[post("/")]
#[authorize(Create, UserEntity)]
#[api(
    summary = "Create a user in the caller's org",
    description = "Requires a bearer JWT (obtain one from `POST /login` on the auth app). The \
                   user's org is taken from the caller's token, never the body."
)]
async fn create(&self, auth: Ctx<Claims>, body: Valid<Json<CreateUser>>) -> Result<Json<User>> {
    let user = self
        .svc
        .create_in_org(body.into_inner(), auth.org_id)
        .await?;
    Ok(Json(User::from(&user)))
}
```

`#[api]` takes eight keys — `summary`, `description`, `tags(...)`,
`response = Type`, `multipart = Type`, `response_content_type = "type/subtype"`,
`error(status = Type)` and `deprecated = "YYYY-MM-DD"` — and refuses any other
at compile time. Path, method, parameters, request schema and success status
come from the handler signature. [OpenAPI operations](/openapi/operations/)
covers each of them.

## Schemas from `#[expose]`

An entity decorated with `#[expose]` produces a wire DTO whose `JsonSchema`
ends up in `components.schemas` the moment a handler returns `Json<User>`.
The schema generator is **shared across every route**: payloads referenced from
multiple handlers de-duplicate, and a `User` returned from `GET /users/:id` is
the same `$ref` as the one returned from the `List` endpoint.

The same type powers the GraphQL output type, the wire DTO the handler returns,
and the JSON Schema in `/api-json` — change one column on the entity, all three
move together. No hand-written schema, no annotation, nothing to drift.

## Limits

The document composes from the route table, so everything in it is derived:

- the whole `info` block and `servers` — the transport's `global_prefix`, or
  `/` at the origin root;
- every operation under `paths`, with its path, query and header parameters;
- its request body, and the media type that body arrives as;
- a shared `components.schemas` holding every type an operation reaches and
  nothing else, an id keeping `format: uuid` and a timestamp `format: date-time`;
- a `bearerAuth` entry in `components.securitySchemes`, per-operation
  `security` on guarded routes, and `security: []` on a `#[public]` one;
- the error statuses an operation can actually produce — `400`, `401` with its
  `WWW-Authenticate` challenge, `403`, `404`, `409`, `413`, `429` with its
  `Retry-After`, and `500`, each where it applies — as RFC 9457
  `ProblemDetails`, beside any body `#[api(error(...))]` declares;
- the response headers the framework sends: `Location`, the `Link` to a
  paginated `#[crud]` list's next page, `Deprecation` on a deprecated route,
  and every `#[response_header]` with its value;
- `deprecated: true` on a route `#[api(deprecated = "…")]` marks.

`operationId` is derived too, as `<controller>_<handler>`, mapped onto what an
identifier can carry — `PostsController::list` publishes `posts_list`, and a raw
handler `r#type` publishes `…_r_type` rather than an id with a `#` in it.
Qualified by the controller because `#[crud]` names every resource's handlers
identically, and OpenAPI requires the id to be unique across the document: a
generator meeting two `list`s either errors or renames one, so a method goes
missing from the SDK. A versioned operation carries its version too
(`posts_list_v2`).

What the composer does not derive, it leaves to you:

- **`example` / `examples` on inputs and responses.** schemars derives the
  shape, and `#[schemars(example = …)]` on a field puts a sample in its schema;
  the document invents none.
- **A response header a handler sets itself** on a `Response` it builds. The
  route table knows the ones the framework and `#[response_header]` send, not
  what a handler body writes.
- **`externalDocs`**, the document-level link to further reading.
- **OpenAPI 3.2.** The document is 3.1.2, the 3.1 line's current patch. A 3.2
  document is valid with no other change, but the TypeScript client
  generators read it as 3.1 and silently drop what only 3.2 can say — a
  `QUERY` operation, a typed event stream — so the framework stays on the
  version every generator reads in full. An [`#[sse]`](/http/streaming/)
  route's events are therefore typed `string`.
- **Which version `/api-json` describes, when the deployment names no default.**
  It then aggregates every declared version and resolves a contested path to the
  highest one, naming the loser in a boot `warn`. Point a client at
  `/api-json/v{n}` when it needs one version's shapes exactly.

Don't hand-patch the document: it is composed at boot from the route table, so
an out-of-band edit is lost the next time the app starts and breaks the no-drift
invariant that makes the spec worth trusting. (Composed once, not per request —
serving it is a string write.)
