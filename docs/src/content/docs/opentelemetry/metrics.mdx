Metrics are the aggregate counterpart to [traces](/opentelemetry/traces/) —
reach for them when you need a number over time (signups per minute, job
duration percentiles, queue depth) rather than the story of one request.

`OpenTelemetryModule` provides `Arc<Metrics>`, the app's meter: import it in
the module whose provider injects it, and inject it like any other
dependency. Telemetry itself needs no import — `main`'s `OpenTelemetry::init()`
installs the meter the module hands out — so an app recording no metric of its
own imports the module nowhere. The module installs `Metrics` in its own
`register`, as `EventsModule` installs `EventBus`, so the access graph gates
neither way ([What is global](/fundamentals/module-boot/#what-is-global)): an app
in which nothing imports it fails the boot naming `OpenTelemetryModule`, and a
provider whose module skips the import reaches `Metrics` only when a module
importing it registered first — registered before, it fails the boot. The
import beside each injection is what puts the module first. In a suite, which
never runs `main`, `Metrics` record on a meter nothing exports.

## What every unit records on its own

Before an app records anything, the framework times each unit of work whose
edge's semantic conventions name a duration histogram for it, so a backend's
ready-made HTTP, messaging and MCP dashboards light up with nothing written:

| Unit | Histogram | Keyed by |
|---|---|---|
| `http.request` | `http.server.request.duration` | `http.request.method`, `url.scheme`, `http.route`, `http.response.status_code`, `error.type` |
| `queue.job` | `messaging.process.duration` | `messaging.system`, `messaging.operation.name`, `messaging.destination.name`, `error.type` |
| `mcp.operation` | `mcp.server.operation.duration` | `mcp.method.name`, `gen_ai.tool.name`, `gen_ai.prompt.name`, `gen_ai.operation.name`, `network.transport`, `network.protocol.name`, `rpc.response.status_code`, `error.type` |

One histogram is the rate, the errors and the latency at once: a backend counts
its points per second, splits them on `http.response.status_code` or
`error.type`, and reads its percentiles off the buckets each convention advises:
`[0.005, 0.01, … 10]` seconds for HTTP and messaging, up to 300 for an MCP
operation, a tool call running long.

- **Every unit is counted.** The durations come from the unit's span, under a
  filter of their own: a console filtered to `RUST_LOG=warn` and a sampler
  keeping one trace in a hundred count every request all the same, where a
  collector deriving metrics from spans counts the ones it was sent.
- **A duration ends with the answer.** It stops where the edge records the
  unit's outcome, the same instant as its line's `duration_ms`: a child span
  or work handed off past the answer keeps the span open, never the clock.
- **Every key is the server's.** `http.route` is the template, never the path;
  a method outside the HTTP conventions' known set is `_OTHER`; an MCP method
  only the client named — a custom one — reads `_OTHER` too, though the span
  keeps it as sent, and so does a tool or a prompt no host declares, on the
  span as on the duration. A client cannot mint a series.
- **A binary exporting no metric pays nothing.** The layer is installed only
  when the metrics export, and `OTEL_METRICS_EXPORTER=none` turns it off with
  them. The instruments are recorded under the instrumentation scope `nest-rs`
  and the framework's version.

GraphQL, WebSocket, scheduled and event units record no duration: no
convention names one for them, and their spans carry their timings.

Each statement the Postgres pool sends — a unit's `BEGIN` and `COMMIT`
included — and each command a Redis connection sends is timed the same way, in
`db.client.operation.duration`, keyed by the
database it ran on and what it did — the statement's operation, table and
summary, the Redis command — into the buckets the database conventions advise,
`[0.001, 0.005, … 10]` seconds ([Statements and commands](/opentelemetry/traces/#statements-and-commands)).

A package's unit declares its own with `unit!`'s `duration:`, keyed by fields
its span declares, and records in it the same way
([the operation log](/opentelemetry/operation-log/)).

## The process and its runtime

The same export carries what the process and its async runtime say of
themselves, read at each export and never between:

| Instrument | What it reads |
|---|---|
| `process.cpu.time` | CPU seconds, by `cpu.mode`: `user`, `system` — Unix |
| `process.uptime` | seconds since the process started, as `#[nest_rs::main]` marks it |
| `process.unix.file_descriptor.count` | descriptors held open — Unix |
| `process.memory.usage`, `process.memory.virtual` | resident and virtual bytes — Linux |
| `process.thread.count` | threads — Linux |
| `tokio.worker.count` | the runtime's worker threads |
| `tokio.task.count` | tasks alive on it |
| `tokio.global_queue.length` | tasks waiting in the queue every worker takes from |
| `tokio.worker.busy_time` | seconds the workers spent running tasks |

The `process.*` names are the OpenTelemetry process conventions'. No convention
names a tokio runtime, so its four follow the conventions' runtime metrics
(`dotnet.thread_pool.*`) under `tokio.`: a backend reads the runtime's
saturation as `rate(tokio.worker.busy_time) / tokio.worker.count`, Node's event
loop utilisation in Rust's words, and a growing `tokio.global_queue.length` as
work waiting for a worker. Memory and threads are read off `/proc`, so a macOS
development host exports neither; the scheduling latency tokio counts only
under `tokio_unstable` is not exported.

## The database pool

The Postgres pool `SeaOrmModule` opens reports its connections in the database
conventions' pool instruments, each keyed by
`db.client.connection.pool.name` — `server.address:server.port/db.namespace`,
as the conventions name a pool that has none of its own,
`db.internal:5432/publish`:

| Instrument | What it reads |
|---|---|
| `db.client.connection.count` | connections open, by `db.client.connection.state`: `idle`, `used` |
| `db.client.connection.max` | the most the pool opens, its `max_connections` |
| `db.client.connection.idle.min` | the fewest it keeps open, its `min_connections` |
| `db.client.connection.timeouts` | callers that gave up waiting for a connection |

A saturated pool reads as `used` at `max` while `timeouts` climbs. sqlx counts
no caller still waiting and times no acquire, so `pending_requests`,
`wait_time`, `create_time`, `use_time` and `idle.max` are not exported; a
unit's `BEGIN`, which waits for its connection, carries that wait in
`db.client.operation.duration`. The names are those of the conventions' 1.42
schema, the one the export declares. A Redis connection is one multiplexed
socket, not a pool, and reports none.

## A first counter

Ask `Metrics` for the instrument by name, then record on it. The first call
makes the instrument and every later one hands back the same, so asking at the
call site costs a lookup and needs no extra field.

```rust title="crates/features/src/users/metrics.rs"
use std::sync::Arc;

use nest_rs::core::injectable;
use nest_rs::opentelemetry::{Attribute, Metrics};

#[injectable]
pub struct SignupMetrics {
    #[inject]
    metrics: Arc<Metrics>,
}

impl SignupMetrics {
    pub fn record_signup(&self, source: &'static str) {
        self.metrics
            .counter("users.created")
            .add(1, &[Attribute::new("source", source)]);
    }
}
```

The instruments are the four synchronous kinds of the
[OpenTelemetry Metrics API](https://opentelemetry.io/docs/specs/otel/metrics/api/),
under their names:

| Instrument | Asked for with | Records | For |
|---|---|---|---|
| `Counter` | `metrics.counter(name)` | `add(u64, …)` | what only grows — signups, failed jobs |
| `UpDownCounter` | `metrics.up_down_counter(name)` | `add(i64, …)`, negative too | what is in flight — open sockets, queued jobs |
| `Histogram` | `metrics.histogram(name)` | `record(f64, …)` | what is measured per event — a latency, a size |
| `Gauge` | `metrics.gauge(name)` | `record(f64, …)` | what is sampled — a pool's idle connections |

Each is a cheap `Clone`, so a service that records on every request may also
keep one in a field.

## Units, descriptions and buckets

What an instrument declares — the unit its values are in, what it measures, a
histogram's bucket boundaries — is declared once, by the `_with` call that
makes it:

```rust title="crates/features/src/posts/metrics.rs"
use nest_rs::opentelemetry::Describe;

let latency = self.metrics.histogram_with(
    "posts.publish.latency",
    Describe::default()
        .with_unit("ms")
        .with_description("time to publish a post"),
    &[5.0, 25.0, 100.0, 500.0],
);
latency.record(elapsed_ms, &[]);
```

`counter_with`, `up_down_counter_with` and `gauge_with` take the same
`Describe`. A later call by the same name returns the instrument already made,
whatever it declares.

## Attributes

The second argument to `add` and `record` is a slice of `Attribute`s — the
metric's labels at the OTel/Prometheus boundary. A value is a `bool`, an `i64`,
an `f64` or a string:

```rust title="crates/features/src/users/metrics.rs"
use nest_rs::opentelemetry::Attribute;

self.metrics.counter("users.created").add(1, &[
    Attribute::new("org_id", org_id.to_string()),
    Attribute::new("source", "api"),
]);
```

Stick to a small, bounded cardinality on the label set — every distinct
attribute combination becomes a separate time series.

## Export

Metrics batch on a
[`PeriodicReader`](https://docs.rs/opentelemetry_sdk) and export through the
same OTLP endpoint as the traces (set `OTEL_EXPORTER_OTLP_ENDPOINT`, or
`OTEL_EXPORTER_OTLP_METRICS_ENDPOINT` for the metrics alone). Without an endpoint, or with
`OTEL_METRICS_EXPORTER=none`, instrument construction still works — `counter()` and friends return real handles, so
wiring compiles and runs — but the meter comes from a `NoopMeterProvider` and
every reading is **dropped**. The SDK says so once, at `debug`: `Meter was obtained
from a NoopMeterProvider. No metrics will be recorded.`, then how to set a provider. A test that needs to assert
on an increment has to hold its own counter; there is nothing to read back
here.

**The interval is 60 seconds by default, and that will look broken.** Traces and
logs reach a collector immediately; metrics wait for the reader's next flush. The
natural first check — record on a counter, hit the route, look at the collector — shows
spans and log records with **zero** metrics, for a full minute. Nothing is wrong;
shorten the interval for a local run:

```bash frame="terminal"
OTEL_METRIC_EXPORT_INTERVAL=5000 nestrs run dev api
```

or pin it in code, as with any other field:

```rust title="apps/api/src/main.rs"
let _otel = OpenTelemetry::init_with(OpenTelemetryConfig {
    metric_interval: Duration::from_secs(5),
    ..OpenTelemetryConfig::from_env()?
})?;
```

The variable is the specification's, in milliseconds, and wins over the pin.
Either is held to a second to an hour — a `PeriodicReader` on a zero period
is a tight export loop, and an hourly one reaches the collector after the
dashboards that read it — and `OpenTelemetry::init` fails with
`OpenTelemetryError::Config` outside that range, naming the variable or the
field. A value that is not a whole number of milliseconds fails it too,
naming the variable, where the SDK would keep its period in silence.

## Resource attributes

Every exported metric carries the service-level resource attributes built from
`OpenTelemetryConfig`, under what `OTEL_SERVICE_NAME` and
`OTEL_RESOURCE_ATTRIBUTES` set:

- `service.name` — the binary's package name, which `#[nest_rs::main]` reads
  off its manifest
- `service.version` — the binary's package version
- `deployment.environment.name` — none unless set
- `service.instance.id` — a fresh UUIDv7 per process by default, so restarts
  get distinct identities in the backend

These come from the
[`opentelemetry-semantic-conventions`](https://crates.io/crates/opentelemetry-semantic-conventions)
schema, so any backend that understands OTel semconv (Grafana Cloud, Honeycomb,
Datadog OTLP, …) keys on them out of the box.
