Everything a queue holds lives under one prefix, and every job is delivered **at
least once**: the common second delivery is answered without running, and a
handler is written so that running it twice is harmless. This page is the
contract behind that sentence: the keys, the guard that filters duplicates and
what it does not cover, what a crash, a Redis timeout and a shutdown do to a job
in flight, and what each capability the backend declares keeps beside the
queue.

The backend runs on [apalis-redis](https://docs.rs/apalis-redis/0.7.4) 0.7.4,
which fetches, schedules and acknowledges jobs. What a job attempt *is* — its
id, its retries, its trace — is the queue port's, and what this page adds to
apalis lives in keys of the framework's own, reached through apalis's calls and
never around them. A queue named `audio`, after one job completed, one
dead-lettered and one held back for an hour:

```text frame="terminal"
$ redis-cli --scan --pattern 'nestrs:queue:audio:*' | sort
nestrs:queue:audio:consumers
nestrs:queue:audio:data
nestrs:queue:audio:data::result
nestrs:queue:audio:dead
nestrs:queue:audio:done
nestrs:queue:audio:failed
nestrs:queue:audio:open:01a0de7d-ceb5-778a-bf40-ac44a74a55c8
nestrs:queue:audio:scheduled
nestrs:queue:audio:settled:01a0de7d-ceb3-73dd-8d85-847b2157a83e
nestrs:queue:audio:settled:01a0de7d-ceb4-75bd-aca2-7ebb6298cccd
```

## Where a queue lives

The queue's namespace is `nestrs:queue:<queue>`. apalis derives its own
structures from it; the framework adds its own beside them, under words apalis
does not use, each keyed by the job id a push returns.

| Key | Holds | Written by |
|---|---|---|
| `nestrs:queue:<queue>:active` | Job ids waiting to be fetched — the list an autoscaler reads | apalis |
| `nestrs:queue:<queue>:scheduled` | Jobs held back: a delayed push, a retry's next attempt, a job handed back | apalis |
| `nestrs:queue:<queue>:inflight:<worker>` | Jobs one replica has fetched and not yet settled | apalis |
| `nestrs:queue:<queue>:consumers` | Each replica's in-flight set, scored by its last heartbeat | apalis |
| `nestrs:queue:<queue>:data`, `…:dead`, `…:done`, `…:failed`, `…:signal` | Records, the ids of finished, dead-lettered and rescheduled jobs, and a wake-up list | apalis |
| `nestrs:queue:<queue>:open:<job_id>` | That the job was pushed and has not reached its outcome, and the unique key it holds | the framework |
| `nestrs:queue:<queue>:leases:<job_id>` | Which delivery runs the job right now | the framework |
| `nestrs:queue:<queue>:settled:<job_id>` | That the job reached its outcome, and which one | the framework |
| `nestrs:queue:<queue>:cancelled:<job_id>` | That a cancel promised the job never starts | the framework |
| `nestrs:queue:<queue>:checkpoints:<job_id>` | The progress the job saved | the framework |
| `nestrs:queue:<queue>:attempts:<job_id>` | How many attempts at the job have started, less those handed back without an answer — cut by a drain, or unread | the framework |
| `nestrs:queue:<queue>:deferred:<job_id>` | When a job a newer release sealed was first handed back unread, in Redis's milliseconds — cleared once a delivery reads it | the framework |
| `nestrs:queue:<queue>:unique:<key>` | The id of the job holding a unique key | the framework |
| `nestrs:queue:<queue>:throttle` | How many attempts of the queue's method started in the current window, less those handed back unread | the framework |

Nothing sits at the root of the keyspace, so a Redis user whose ACL reaches
`~nestrs:queue:*` and nothing else runs a queue end to end — the producer and the
worker alike. Most of what they send is Lua — apalis's scripts and the
framework's, sent as `EVALSHA` with a `SCRIPT LOAD` the first time Redis has not
cached one — and Redis checks the commands *inside* a script against the caller's
ACL as well. With the connection's `PING`, which proves it at boot, and the
`SELECT` of the database its URL names, a Redis user for a queue is this rule and
nothing more:

```text title="Redis ACL"
ACL SETUSER <user> on ><password> resetchannels ~nestrs:queue:* +ping +select +evalsha +script|load +get +set +del +exists +incr +decr +pexpire +pttl +time +hget +hset +hsetnx +hmget +hmset +hdel +lpush +rpush +lrange +ltrim +sadd +srem +spop +zadd +zrem +zscore +zrangebyscore +zremrangebyrank
```

An app that also rate-limits or fires scheduled jobs once gives the same user
[the rate limiter's](/rate-limiting/#redis-shipped) and
[the schedule's](/schedule/#the-keys) rules as well. The one check this rule
refuses is the 6.x one, which reads the queue's bare name at the root of the
keyspace: the worker says at `warn` that it could not look, and
[Upgrading queues from 6.x](/queue/upgrading/) runs it with a user that can.

The client library also sends `CLIENT SETINFO` on every connection and ignores
its refusal; no rule names it, because Redis 7.0 knows no such subcommand and
would refuse the whole rule. Redis 7.2 and later file that refusal in `ACL LOG` as
`client|setinfo`, and Redis 6.2 as `client`.

## At least once, and the guard

Delivery is **at least once**. Two replicas never fetch the same job from
`active`: the fetch claims ids in one atomic script. A job can still reach a
second delivery three ways — a replica **starting** sweeps up to ten times its
method's `concurrency` of its peers' in-flight jobs back onto the queue (apalis
sweeps with a cutoff of *now*, which matches the living too), a replica whose
heartbeat falls behind the orphan threshold has its jobs swept — by a peer, or
by its own periodic sweep, which reads its heartbeat like any other — and an
acknowledgement can be lost on its way to Redis.

So each delivery takes the job's **lease** before the attempt runs, and renews
it every third of its length while the attempt runs. When the job reaches its
outcome, the delivery writes the **settled** mark and drops the lease, in one
script. A second delivery then does one of two things, and neither runs the job:

- the lease is held elsewhere — the job goes back on the schedule until the
  lease would lapse, and is never acknowledged, so the guard can delay a job
  but not lose one;
- the job is settled — it is acknowledged the way the first delivery answered,
  completed or dead-lettered, without running.

A settled mark lasts an hour, or two orphan thresholds plus a lease when that
is longer, however it was written — past the latest a sweep could hand the job
to a second delivery, and no longer. A delivery after it lapsed runs the job
again. That is the case of a lost acknowledgement: apalis acknowledges a job
from its worker's own loop after the delivery answers, and drops what is still
queued when the worker stops, or what Redis refuses; the job then waits in that
replica's flight until a replica starts and sweeps it, which may be days later,
and runs once more if its mark is gone by then.

<Aside type="caution">
**Delivery is at least once, so a handler is idempotent.** The guard
answers the common second delivery — a sweep, a job filed twice — and nothing
past it: a delivery after the settled mark lapsed runs the job again, and a
replica cut off from Redis for longer than its lease, still running, can see
another replica take the job. A handler whose effects leave the process — an
email, a charge — keeps its own idempotency key; one that writes only through
its transaction is covered for retries, not for redeliveries.
</Aside>

## Replicas, heartbeats and crashes

Each method of each replica consumes under an id of its own — the host name
when the platform sets one, then a UUID v7 — so no two replicas share an
in-flight set. A replica proves it is alive every tenth of the orphan threshold,
and never more often than once a second, and a peer sweeps its jobs only once it
has been silent
for the whole threshold — ten missed proofs at the default.

A replica that crashes mid-attempt leaves its job in flight. The next replica
to start sweeps it back onto the queue at once and runs it once the dead
replica's lease lapses; with none starting, a running peer sweeps it after the
orphan threshold. **The attempt that died counts against the budget.** The
envelope only counts attempts that answered, so each delivery that takes the
lease also counts a start, in `…:attempts:<job_id>`, and the port runs the later
of the two: a job that takes its replica down every time — an abort, an OOM
kill, a hang until the pod is killed — runs `retries + 1` times, then is
dead-lettered without running, as
`job dead-lettered: retry budget spent by attempts that never returned`, its
`unfinished` field saying how many never did. A drain's hand-back takes its start
back, in the first call it makes once the window closes on the attempt — see
[Shutdown](#shutdown). The job runs again from the start of its body, so a crash
between a database commit and the settled mark writes twice — the transaction
bounds a retry, never a redelivery.

## When Redis is slow or gone

A command a worker sends answers or fails within
`NESTRS_REDIS__CONNECT_TIMEOUT_SECS`, ten seconds by default, so an outage fails
calls rather than holding them. A timeout says the answer did not arrive in time,
never that the command did not run — which is why two commands wait for their
answer however late it comes: apalis's **fetch**, and the **admission** that
takes a job's lease. Each claims something in the script it answers with — the
fetch, the jobs it hands this replica; the admission, the lease, a throttle start
and the attempt — so a wait cut at the budget would leave the claim held for
nobody: fetched jobs in a live replica's flight, never run and never swept. They
end when Redis answers, or when the socket learns Redis is gone rather than slow:
keepalive probes after the budget idle and, on Linux, `TCP_USER_TIMEOUT` at the
budget — each a second at the least. apalis's heartbeat and acknowledgements share the fetch's connection and
wait the same way — and its loop: apalis sends one call at a time, so a stall
that outlasts the orphan threshold holds the heartbeat as long, and the jobs the
replica holds in flight are swept back onto the queue while its fetch still
delivers the ones it claimed. That is a second delivery, which the guard answers,
and never a job left in flight. What a delivery does when a call fails:

| The call that failed | What happens to the job | The line, on `nest_rs::queue` |
|---|---|---|
| taking the lease | handed back for a second later; never run unguarded | `job lease not asked for; …`, `warn` |
| handing a job back | apalis files its stored record again, due at once — the attempt it was fetched at, or its next one when the filing landed after all — or a sweep does, when Redis refuses apalis too | `job not handed back; …`, `error` |
| renewing the lease | the attempt runs on, and the renewal is tried again | `job lease not renewed; retrying`, `warn` |
| writing the settled mark | the outcome stands; a second delivery could run the job again, and its unique key stays held until its records lapse | `job settled mark not written; …`, `warn` |
| dropping the lease, or giving back a start | the next delivery waits for the lease to lapse, and a start the attempt was to give back stays counted | `job lease not dropped; …`, `warn`, with `gives_back` |
| the acknowledgement | stays in the replica's flight until a replica sweeps it — a live replica's is never taken by the periodic sweep while its heartbeat keeps up — and is answered by its settled mark without running while the mark lasts, run again after | `job acknowledgement lost; …`, `error` |

A fetch that fails is retried at the next poll. When its connection failed
under it, Redis may have run it all the same, and the jobs it claimed then wait
in this replica's in-flight set until a replica starts and sweeps them back —
the `warn` says so. A heartbeat that fails is retried on its next tick, and a
scan of the schedule after a backoff doubling up to thirty seconds; each is said
at `warn`. A heartbeat that keeps failing, or waits behind a stall, past the
orphan threshold lets a sweep take the replica's jobs — a peer's, or its own —
the case the lease exists for.

A push, a cancel and a checkpoint's read or save fail within one budget of Redis
going silent too: none sends a second command after one that got no answer, so
the caller reads the connection's cause before the queue port's own net, twenty
seconds, gives up on the call — see
[When a push fails](/queue/producing-jobs/#when-a-push-fails).

**An attempt has no timeout of its own.** A handler that never returns holds its
permit and keeps its lease renewed, so its job is neither lost nor run elsewhere,
and its method runs one attempt fewer at a time until a shutdown interrupts it.
Bound a slow call inside the handler, with `tokio::time::timeout`, and return
the `Err` the retry budget decides on.

## Shutdown

A shutdown stops fetching at once. Running attempts get the shutdown window,
less a reserve, to finish where they run, and jobs the replica fetched but had
not started still start as permits free inside it. What still runs when the
window closes is interrupted — its `queue.job` line filed with
`outcome="cancelled"` — and its job handed back to the queue inside the
reserve, so the orchestrator's `SIGKILL` never lands on a job the worker still
holds. The window is 20 seconds by default, which leaves the shutdown hooks'
five and the telemetry flush's three inside Kubernetes' default 30-second grace
period; a window you raise needs the pod's grace period at least 8.5 seconds
above it — eight for those two, and the half second an app serving HTTP beside
the worker spends after its own window
([the way down](/fundamentals/lifecycle/#the-way-down)). A job
that reaches its permit after the window closed is handed back without
starting. A retry's next attempt is already on the schedule, so it holds
nothing up.

**The reserve is one Redis call long**: the connection's budget,
`NESTRS_REDIS__CONNECT_TIMEOUT_SECS` — ten seconds by default — or five seconds
when that is shorter, and never more than half the window. An interrupted
attempt gives its start back in the first call it makes, before it hands its
job back: left counted, that start would spend the retry budget of a job that
never failed, and a job with no retry left would be dead-lettered on its next
delivery without running. A Redis that answers within its budget takes the
give-back whatever happens next. A worker the drain still waits on once the
whole window has passed — Redis stalled past the reserve — is said at `error`
with how many deliveries it cut (`cut`), and left: each of those jobs stays in
flight until a replica sweeps it, its attempt spent unless the give-back reached
Redis.

## Delayed jobs

The Redis backend declares `Capability::DelayedPush`, so a push can hold a job
back:

```rust title="crates/features/src/audio/service.rs"
self.queue
    .push(
        AudioQueue,
        TranscodeCommand { file },
        PushOptions::default().with_delay(Duration::from_secs(60)),
    )
    .await?;
```

The job waits on `scheduled`, due on the second its delay ends — apalis
schedules on whole seconds, and the backend rounds up, so a job never runs
before its instant **as the pushing host's clock reads it**. The due second is
taken from the producer's clock and the move onto `active` from the promoting
worker's — apalis compares the schedule with the host it runs on, not with
Redis — so a worker whose clock runs ahead of the producer's by some seconds
runs a delayed job up to that much early, and a retry's backoff or a throttle's
hand-back is measured on the filing worker's clock the same way. Keep the hosts
on NTP; the throttle and the lease are counted on Redis's clock and need no
such care. Every worker scans the schedule once a second, moving up to
a hundred due jobs onto `active` each time — its method's `concurrency` when
that is more — and so does the producer that filed them, a hundred at a time,
for as long as it has delayed jobs of its own still ahead, so a due job reaches
the list an autoscaler reads even while no worker runs. A retry is the same filing: the port's backoff
decides when, and the next attempt waits on the schedule rather than in a
worker. What that means for a deployment scaled to zero is on
[Concurrency and scaling](/queue/scaling/#on-queue-depth-with-keda).

## Unique keys

A push under a unique key claims `…:unique:<key>` for its job in the same
script that reads it, and opens the job's record, before the job is filed —
so pushes racing for one key queue one job, and a push refused because the
key is held files nothing. The job lets go of the key in the step that settles
it, completed or dead-lettered, and a cancel lets go of it too.

The claim is taken for forty seconds — twice the queue port's twenty-second
net, which ends every call a push makes — and extended to the job's full keeping
once Redis confirms the filing. A push can fail after the claim. When Redis
answered the filing — refused it — the job is not on the queue, and the push
lets go of the key before it returns the error. When a push never learns
whether its job was queued — the claim or the filing got no answer, Redis did
not extend the claim, or the caller or the net dropped the push midway — the
claim lapses within those forty seconds, unless a worker admits the job first,
which keeps it. One `warn` says so, naming the job, the key and the step:

```text
WARN nest_rs::queue: unique key claimed without its job confirmed queued; the claim lapses within its hold unless a worker admits the job queue=audio job_id=01a0… unique_key="transcode-song.wav" step="filing unanswered" held_ms=40000 error="…"
```

Until then a retry is refused naming a job the caller never received, and
`cancel_unique` frees the key if that job never started. The direction this
errs in is at-least-once: a job that *was* queued, and that no worker admits
inside the hold, can be pushed again under its key.

## Cancels

A cancel never touches apalis's storage. It writes a tombstone beside the job,
`…:cancelled:<job_id>`, in one script that first checks the job is still
open and that no delivery holds its lease — so `true` is only ever answered
while no attempt runs, and an attempt can never start after it. The same
script closes what the job held: its open record, its unique key and its
checkpoint. The job stays where it waits; the delivery that eventually meets
the tombstone acknowledges it without running, and files
`job delivered after it was cancelled; acknowledged without running`.

## Throttles

A method's throttle is counted in `…:throttle` by the step that admits an
attempt, in the same script as the lease, so every replica counts against one
number and no two admissions race. An attempt over the limit is handed back to
the schedule for when the window ends, as it was fetched, and files
`job deferred to its throttle's next window` as detail — and shuts that
replica's fetch for the method until then, so the rest of the backlog waits on
`active` instead of being fetched, refused and filed back one poll after
another. The window's shape, and
what it allows at its edges, is on
[Concurrency and scaling](/queue/scaling/#throttling-starts).

## What a job keeps, and for how long

Every record the framework keeps for a job while it waits — its open record, its
unique key, its checkpoint, its count of attempts started, the instant it was
first handed back unread, a cancel's tombstone — lives **a week past the instant
the job is due**, renewed each time a delivery admits the job, files its next
attempt or hands it back. A job that is delivered stays well inside it; the bound is
for a job that never is.

A job can vanish without reaching an outcome a worker sees: one filed and then
lost outside the framework leaves its claim behind. That claim refuses pushes
under its key for at most a week past the job's due time, and `cancel_unique`
frees it sooner. A producer that stops between claiming a key and filing the
job leaves a claim of forty seconds, as above. The same week caps a job that waits: one
still waiting a week past its due time has been forgotten — its key is free,
its checkpoint gone, and a cancel's promise no longer outlives the tombstone
that kept it.

## Configuration

`RedisWorkerModule::for_root(RedisWorkerConfig { .. })`, or the environment:

| Variable | Default | What it bounds |
|---|---|---|
| `NESTRS_REDIS__WORKER__SHUTDOWN_TIMEOUT_SECS` | `20` | The drain window, hand-backs included — attempts get all of it but the reserve, one connection budget or five seconds, at most half; at least `1`, at most `3600` |
| `NESTRS_REDIS__WORKER__ORPHAN_AFTER_SECS` | `300` | How long a silent replica keeps its jobs; at least `5`, at most `86400` — a day |
| `NESTRS_REDIS__WORKER__LEASE_SECS` | `30` | How long a claim outlives its last renewal; at least `1`, and at most half the orphan threshold, so a crashed replica's lease has lapsed by the time a peer takes its jobs |
| `NESTRS_REDIS__WORKER__POLL_INTERVAL_MS` | `100` | How often a method asks for jobs while a permit is free — its ceiling, and its idle cost; at least `10`, and at most the orphan threshold, since the sweep of silent replicas runs on it |

A value out of its bounds fails the boot, whether the environment set it or
`for_root` pinned it, naming the variable — and a lease or a poll too long for
the orphan threshold names both. Every value accepted is one apalis handles:
its sweep converts the orphan threshold with an `unwrap`, which a threshold of
about 262,000 years would panic, and the ceiling of a day keeps it far from
that.

## Limits

- **Redis Cluster is unsupported.** apalis 0.7's scripts touch several of a
  queue's keys in one call — some of them read out of another key rather than
  declared — without a shared hash tag, which a cluster refuses. A primary with
  replicas, or a managed single-shard Redis, is the shape.
- **Redis 6.2 or later.** 7.0's Redis suite passed on 6.2.20, 7.0.15 and 8.6.3,
  and 6.2 is the oldest it ran on. Before 7.0, a worker a starting peer swept
  fetches nothing until its next heartbeat: apalis registers it again on an
  error text only Redis 7 writes.
- **A fetch per poll.** A method starts at most `concurrency` jobs per poll on
  one replica, and a busy replica holds up to `concurrency` jobs it has not
  started — see [Fetching on Redis](/queue/scaling/#fetching-on-redis).
- **A fetch claims 799 jobs at the most.** apalis passes a fetch's ids to
  Redis's Lua in one call, and a sweep ten fetches' worth; Lua takes at most
  7,999 values per call, and a sweep past that loses the jobs it has popped. A
  method whose `concurrency` exceeds 799 still runs that many at once, fetching
  799 per poll.
- **`failed` only grows.** apalis records there every job it reschedules — a
  retry, a hand-back — and nothing trims it.
- **apalis's own attempt cap binds only what 6.x filed.** apalis 0.7 keeps an
  attempt count of its own on every record, raised by each delivery, and kills
  a record answered with a failure once the count reaches the record's cap —
  five by default — with none of the port's events. A hand-back Redis refuses is
  answered that way, so the job is delivered again. Every record 7.0 files — a
  push, a delayed push, a retry, a hand-back — lifts the cap to `u32::MAX`
  deliveries, past any count a job reaches, so apalis's count never ends a job;
  a record a 6.x producer filed keeps the cap of five until a retry or a
  hand-back files it again. The cap is `u32::MAX` and not `usize::MAX` because
  apalis reads it into a `usize`, as wide as the host reading it: a record a
  64-bit replica filed with its own `usize::MAX` would not decode on a 32-bit
  one, and apalis's fetch would fail on every poll for the batch holding it.
- **A record apalis cannot decode holds back the jobs fetched beside it.**
  apalis-redis 0.7.4 claims a fetch's jobs in one script and decodes them
  afterwards, in the worker; at the first record it cannot read — written by
  hand, by a foreign producer, or by a release whose records apalis no longer
  reads — it drops the whole batch, already in the replica's flight. The worker
  never sees those jobs, so none reaches the port's dead-letter: they wait until
  a replica starts and sweeps them back, when the same record fails that
  replica's fetch in turn. The fetch is apalis's, private to it, so the worker
  names what happened instead — `queue fetch met a record apalis cannot decode;
  …`, at `error` — and the remedy is the operator's: remove the record from
  `…:data` and the id from the in-flight set holding it. A method of
  `concurrency` 1 fetches one record at a time and strands only the record.
- **A settle Redis refuses closes nothing.** The step that marks a job settled
  also lets go of its unique key and closes its open record; when Redis refuses
  it, the worker says so at `warn`, and until the job's records lapse a push under
  its key is refused and a cancel could answer `true` for a job that ran.
