import { Aside } from '@astrojs/starlight/components';

Background work shares the rest of the framework's shape. A queue
handler is a method on any `#[injectable]` provider, tagged
`#[process(queue = <Name>Queue, retries)]` inside a
`#[processor]` impl block. Importing `QueueModule` in the worker app
attaches the port's worker at boot, which discovers the reachable methods
and runs each with permits of its own. A producer-only app skips that
import and only pushes — same crate, same types, one less module.

A queue is named by a **type**, not a string. `#[queue(name = "...", job =
<Payload>)]` on a unit struct at the feature port declares the wire name
and the payload in one artifact both sides import, so a typo or a
mismatched payload is a compile error rather than a job that silently
never drains.

Read this section, then start from the working reference: the
[`worker`](/publish/) app in Publish — audio transcoding jobs, with the
`api` app as the producer.

The contract — `Queue`, `JobProducer`, `PushOptions`, the `#[processor]`
macro, what one attempt at a job is, and the `QueueWorker` that runs them —
ships in **`nest-rs-queue`**. The first-class storage, **Redis**, ships in
**`nest-rs-redis`**, written on Redis Streams: `RedisQueueModule` binds its
`RedisQueueProducer` and the consumer the worker runs jobs through. Both are
compilation units, not lines you write: the `redis-queue` feature below pulls
them together, and an app's manifest names neither.

## Install

```bash frame="terminal"
cargo add nest-rs --features redis-queue
```

One line in the feature crate's manifest: `redis-queue` implies `queue` and
`redis` — the Redis connection and the queue's binding over it, the macros, the
worker-context seam and the pipe fold `#[process]` expands to, together. `redis`
alone is the connection, and compiles no queue.

A job payload declares `serde` itself; `anyhow` and `tracing` come through
`nest_rs::core::anyhow` and `nest_rs::core::tracing`.
`nestrs g queue <feature>` writes the stanza for you.

## The queue's identity

One declaration, at the feature **port** — beside the payload, not inside
the `queue/` adapter. The producer is usually the port's own service, so
this is the artifact both sides reach for:

```rust title="crates/features/src/audio/command.rs (from the demo)"
use nest_rs::queue::{Queue, queue};
use serde::{Deserialize, Serialize};

#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct TranscodeCommand {
    pub file: String,
}

#[queue(name = "audio", job = TranscodeCommand)]
pub struct AudioQueue;

pub const AUDIO_QUEUE: &str = <AudioQueue as Queue>::NAME;
```

Re-export both from the feature's `mod.rs`. A marker that is not reachable
from the port leaves the untyped `push_json(name, payload, None)` escape hatch
as the only way to enqueue — which loses the check `Queue` exists to provide.

The name is 1 to 128 of `A-Z a-z 0-9 _ . -`, checked when the macro expands:
`:` separates the levels of a key, and whitespace would reach a log field.

## A first queue handler

A regular `#[injectable]` service with one decorated method. The
`#[processor]` attribute marks the impl block; `#[process]` marks the
method as a queue consumer.

```rust title="crates/features/src/audio/queue/processor.rs (from the demo, abridged)"
use std::sync::Arc;

use anyhow::Result;
use nest_rs::core::injectable;
use nest_rs::queue::processor;

use crate::audio::{AudioQueue, AudioService, TranscodeCommand};

#[injectable]
pub struct AudioProcessor {
    #[inject]
    svc: Arc<AudioService>,
}

#[processor]
impl AudioProcessor {
    #[process(queue = AudioQueue, retries = 3, concurrency = 4)]
    async fn transcode(&self, job: TranscodeCommand) -> Result<()> {
        self.svc.transcode(&job.file).await?;
        Ok(())
    }
}
```

The processor is thin: it owns no business logic of its own — it hands
`job.file` to `AudioService::transcode` and propagates the result. The
same `AudioService` is what an HTTP producer calls to enqueue, so a
single audited choke point describes everything the feature can do.
Adapters carry transport mechanics; the service carries intent.

- **`#[injectable]`** makes `AudioProcessor` a regular DI provider.
- **`#[processor]`** on the impl block orchestrates the per-method
  `#[process]` attributes and submits one queue consumer per decorated
  method.
- **`#[process(queue, retries, concurrency)]`** binds the method to a
  `Queue` **type**, gives it a retry budget, and lets `concurrency`
  attempts run side by side on each replica — see
  [How many at once](#how-many-at-once-and-how-fast). The job type is read from the
  method's first parameter after `&self`, and the macro asserts it is
  `AudioQueue::Job` — a handler consuming the wrong payload is a compile
  error naming both types. A queue is drained by one method: a second
  `#[process]` on the same queue fails the boot naming both.

The job argument also binds a [pipe](/fundamentals/pipes/):
`Piped<P, T>` / `Valid<T>` expose the wire payload `T`, run the pipe
after deserialization, and hand the handler the transformed value — a
rejection is a job error, so the queue's retry/failure policy applies.

## How many at once, and how fast

A `#[process]` method runs **one attempt at a time** per worker replica unless
it declares more — `concurrency = 4` lets four run side by side in each
replica — and throughput beyond that comes from running more replicas. A
`throttle(limit = 120, window = "1m")` caps how many attempts **start** per
window across every replica together, which is the key for a provider's rate
limit. Both, the pool they draw on, and scaling replicas on queue depth, are on
[Concurrency and scaling](/queue/scaling/).

<Aside type="caution">
**Delivery is at least once, so a handler is idempotent.** Two replicas never
receive the same job from the queue: each delivery holds a lease on its job,
renewed while the attempt runs, and every write it makes is fenced on that
lease. A job runs again only once a lease lapses — its replica crashed, froze,
or was cut off from Redis for longer than the lease — so a handler whose effects
leave the process keeps its own idempotency key. See
[Delivery on Redis](/queue/delivery/#at-least-once-and-the-fence).
</Aside>

## What a backend supports

Every backend owes three things, and none of them is a capability: the retry
budget and its backoff, which the port counts; one transaction per attempt,
which the worker's context owns; and each method's `concurrency`. Beyond them a
backend declares the capabilities it honours, and the port refuses a
declaration the backend lacks at the first site that sees both — the push for a
push option, the call for a cancel, the worker's boot for a `#[process]` key —
naming the backend.

| Capability | What declares it | Redis |
|---|---|---|
| `DelayedPush` | `PushOptions::with_delay` | yes — the job waits off the stream, due on Redis's clock |
| `UniquePush` | `PushOptions::with_unique` | yes — the key is claimed in the script that files the job |
| `Cancellation` | `cancel(&receipt)`, `cancel_unique(queue, key)` | yes — a waiting job is removed; a running one runs to its outcome |
| `Throttle` | `#[process(throttle(..))]` | yes — one fixed window per queue, across every replica |
| `Checkpoint` | a `Checkpoint<_>` parameter | yes — one field beside the job, gone with its outcome |

Redis is the one backend the framework ships; a driver you write declares its
own row — see [Writing a queue driver](/queue/writing-a-driver/).

## One attempt, one transaction

A job has **no caller** — system work, intentionally — so no ability is
installed and `Repo` reads are unscoped, which is correct for work with no
principal to scope to.

The executor is a **transaction per attempt**: it opens on the job's first
`Repo` call, commits when the method returns `Ok` and rolls back otherwise,
so an attempt that failed halfway leaves nothing for the retry to write
again. Add `transactional = false` to the decorator — `#[process(queue =
AudioQueue, transactional = false)]`, and the same word on `#[every]`,
`#[cron]` and `#[after]` — to run on the pool instead, which is right for a
job that brackets long work that is not the database's. Such a job owns its
own idempotency.

The transaction bounds what a **retry** repeats, never what a
**redelivery** does: a worker that dies between the commit and the job's
outcome leaves the job to its lease, and the next delivery runs it again — its
writes already landed. See
[Repo and the executor](/database/repo-and-executor/) and
[Retries and failure](/queue/retries-and-failure/).

## Several methods on the same provider

The pattern the framework is built for: one `#[injectable]` declares
the deps once, multiple decorated methods share them. Different queues,
same service. Three queues, so three `#[queue]` declarations at the port —
each pairing a wire name with the payload it carries:

```rust title="crates/features/src/audio/command.rs"
#[queue(name = "audio", job = TranscodeCommand)]
pub struct AudioQueue;

#[queue(name = "audio.preview", job = PreviewCommand)]
pub struct AudioPreviewQueue;

#[queue(name = "audio.cleanup", job = CleanupCommand)]
pub struct AudioCleanupQueue;
```

```rust title="crates/features/src/audio/queue/processor.rs"
#[injectable]
pub struct AudioProcessor {
    #[inject] audio_svc: Arc<AudioService>,
    #[inject] media_svc: Arc<MediaService>,
}

#[processor]
impl AudioProcessor {
    #[process(queue = AudioQueue, retries = 3)]
    async fn transcode(&self, job: TranscodeCommand) -> Result<()> {
        self.audio_svc.transcode(&job.file).await
    }

    #[process(queue = AudioPreviewQueue, retries = 1)]
    async fn preview(&self, job: PreviewCommand) -> Result<()> {
        self.media_svc.preview(&job.file).await
    }

    #[process(queue = AudioCleanupQueue)]
    async fn cleanup(&self, job: CleanupCommand) -> Result<()> {
        self.media_svc.cleanup(job.older_than).await
    }
}
```

`#[process(queue = AudioCleanupQueue)]` omits the optional `retries`
(default `0`).

Three inventory entries — `AudioProcessor::transcode`, `AudioProcessor::preview`,
`AudioProcessor::cleanup` — all pointing at the same `AudioProcessor` instance.
Same `Arc<AudioService>`, same `Arc<MediaService>`, three queues. Each
method still delegates: the processor is a router, never a place where
business logic accumulates.

<Aside type="caution">
A single `#[processor]` impl block per struct (multiple would conflict
at the discovery layer). Put every queue handler of a service in the
same block — same convention as `#[routes]` and `#[scheduled]`.
</Aside>

## Wire it in

Three modules, three roles:

- **`RedisModule::for_root(None)`** — opens the one Redis connection every
  Redis binding shares (`<PREFIX>_REDIS__URL`). Every app that touches Redis
  needs it.
- **`RedisQueueModule`** — binds the queue port over that connection: the
  producer, as `Arc<dyn JobProducer>`, and the consumer the worker runs jobs
  through. Every app that enqueues or runs jobs imports it.
- **`QueueModule::for_root(None)`** — from `nest_rs::queue`, attaches the
  port's `QueueWorker` transport. At boot it discovers the reachable
  `#[process]` methods, runs each over the bound consumer, and drains them
  with the app. A producer-only app does NOT import this.

```rust title="apps/worker/src/module.rs (from the demo, abridged)"
use nest_rs::config::ConfigModule;
use nest_rs::core::module;
// …
use nest_rs::queue::QueueModule;
use nest_rs::redis::{RedisModule, RedisQueueModule, RedisScheduleModule};
// …

use features::audio::AudioQueueModule;
// …

#[module(
    imports = [
        ConfigModule::for_root(),
        // …
        RedisModule::for_root(None),
        RedisQueueModule,
        QueueModule::for_root(None),
        // …
        AudioQueueModule,
        // …
    ],
)]
pub struct WorkerModule;
```

The demo's worker also opens the database — its notifications job writes a
row — runs the notifications purge on a schedule, and serves health probes on
HTTP. `AudioQueueModule` imports the
`AudioModule` port itself, so the app lists only the adapter — registration is
idempotent.

`main` is the universal skeleton:

```rust title="apps/worker/src/main.rs (from the demo)"
use anyhow::Result;
use nest_rs::config::Environment;
use nest_rs::core::App;

use worker::WorkerModule;

#[nest_rs::main]
async fn main() -> Result<()> {
    let _environment = Environment::init();

    App::builder()
        .module::<WorkerModule>()
        .build()
        .await?
        .run()
        .await
}
```
