Every queue event the framework emits targets `nest_rs::queue`. One
target, every worker-side log filterable by `RUST_LOG=nest_rs::queue=debug`,
one span wrapping each attempt so a trace backend groups its events. The
service-level logs your `#[process]` method emits keep their own target
(e.g. `features::audio`) — same convention as the rest of the framework.

## Targets and levels

| Target | What | Level |
|---|---|---|
| `nest_rs::queue` | Boot registration, per-attempt events, the reason a job failed, and what the Redis worker says about deliveries. | `debug` on job start, `warn` on a retryable failure, `error` on a dead-letter. |
| `nest_rs::operation` | One `queue.job` line per attempt — identity, `outcome`, `duration_ms`. Shared with every other edge. | `info`. |
| `nest_rs::app` | Boot: `attached module-contributed transport transport="RedisWorker"`. Emitted by the composition root, which attaches every transport — so the target is the app's, not the queue's. | `info`. |
| `features::<feature>` | Your service-level logs inside the `#[process]` method. | Your call. |

Hot paths respect `RUST_LOG=info`: `job started` sits at `debug`, so a
worker at `info` logs one `queue.job` line per attempt and, on failure, one
event saying why — no per-poll noise.

## The per-attempt span

The worker opens one span per attempt, `queue.job`, of kind `consumer`, and
exports it under OpenTelemetry's messaging name, `process <queue>`. The handler
runs inside it, so a trace backend files every event your service emits under
the attempt. Its attributes speak the messaging conventions:

| Attribute | Value |
|---|---|
| `messaging.system` | The backend's name — `redis`. |
| `messaging.operation.name`, `messaging.operation.type` | `process`. |
| `messaging.destination.name` | The queue, e.g. `audio`. |
| `messaging.message.id` | The job's id — the one its push returned, the same across its attempts and redeliveries. |
| `backend_id` | The backend's own id for the stored record — apalis's, on Redis. |
| `processor` | The method, e.g. `AudioProcessor::transcode`. |
| `attempt` | Which attempt this is, from `1`, counted by the queue port across retries. |
| `continued_trace` | `true` when the attempt continues the producer's `traceparent`, `false` when this job started a trace of its own — on every attempt of it, however the backend files retries. |
| `trace_id`, `span_id`, `parent_span_id` | This attempt's [W3C trace context](/fundamentals/correlation/). The parent is the span that enqueued the job; for a job that started a trace of its own, the first attempt has none and every later attempt's is the first attempt's span. |
| `actor_id` | Who the *enqueue* was served for. Absent when nobody was authenticated — a job pushed by a scheduled tick has none. |

A log line renders none of those: it carries the ids of the trace it ran in,
and the attempt's identity rides the `queue.job` line below. The trace crosses
a **process** boundary — the producer seals it into the job envelope and the
consumer continues from it — see [Correlation](/fundamentals/correlation/).

## What a job's life looks like

`job started` at `debug`, then whatever the handler logs, then one
`queue.job` line on `nest_rs::operation` — the same line every edge files for
a unit of work, carrying the job's identity, its `outcome` and its
`duration_ms`:

```text frame="terminal"
DEBUG nest_rs::queue: job started attempt=1 trace_id=01a0deaacf87732d9226abd2af0d5896 span_id=0da7f0208abbae0b
DEBUG features::audio: transcoded file="track-1787069801760.mp3" derived_key="transcoded/track-1787069801760.mp3" trace_id=01a0deaacf87732d9226abd2af0d5896 span_id=0da7f0208abbae0b
 INFO nest_rs::operation: queue.job queue=audio processor="AudioProcessor::transcode" job_id=01a0deaa-cf87-732d-9226-abd166aa514c backend_id="01M3FANKW8ER4N9CKF4KB2ZF7Y" attempt=1 outcome="ok" duration_ms=32.129 trace_id=01a0deaacf87732d9226abd2af0d5896 span_id=0da7f0208abbae0b
```

A failure adds one event on `nest_rs::queue` saying **why** — at `warn`
when the retry budget will re-run it, at `error` when the job
dead-letters — and the `queue.job` line reports `outcome="error"` (or
`outcome="panic"`) beside it. The two never restate each other: the
detail carries the cause, the line carries the timing and the identity.

`attempt` is how you correlate a retry: the same `job_id` runs again with
`attempt=2`, opening a fresh span and filing a fresh line — same `trace_id`,
new `span_id`:

```text frame="terminal"
 WARN nest_rs::queue: job failed; will retry within the budget error=transcode failed retry_after_ms=1143 trace_id=01a0deaacf9670f8a924efd95a2ec64b span_id=a83a4d58c89c3d5d
 INFO nest_rs::operation: queue.job queue=audio processor="AudioProcessor::transcode" job_id=01a0deaa-cf96-70f8-a924-efd8fbbe3d38 backend_id="01M3FANKWQCV095QBG19STWGT2" attempt=1 outcome="error" duration_ms=33.525 trace_id=01a0deaacf9670f8a924efd95a2ec64b span_id=a83a4d58c89c3d5d
 INFO nest_rs::operation: queue.job queue=audio processor="AudioProcessor::transcode" job_id=01a0deaa-cf96-70f8-a924-efd8fbbe3d38 backend_id="01M3FANKWQCV095QBG19STWGT2" attempt=2 outcome="error" duration_ms=31.659 trace_id=01a0deaacf9670f8a924efd95a2ec64b span_id=734f481aeb53cb7e
ERROR nest_rs::queue: job dead-lettered: retry budget spent error=transcode failed attempts=4 trace_id=01a0deaacf9670f8a924efd95a2ec64b span_id=a506bd5f6e799390
```

An attempt its worker stops — the drain window closed on it, or the worker was
torn down — is dropped where it waits and still files its line, with
`outcome="cancelled"` and the time it ran; what happens to the job next is the
worker's line to say, `job handed back to the queue` with `reason="shutdown"`
on Redis. An attempt whose process died answers nothing, so it files no line; on a
backend that counts the attempts it starts, the delivery that finds them past
the budget dead-letters the job without running it, as
`job dead-lettered: retry budget spent by attempts that never returned` at
`error` with `unfinished` counting them, beside a `queue.job` line at the next
attempt's number.

See [Retries and failure](/queue/retries-and-failure/) for the policy behind
`attempt`.

## What the Redis worker says

Beside each attempt, the Redis worker files a line when a job leaves a replica
without an outcome, when the delivery guard answers for it, and when apalis
itself reports trouble — all on `nest_rs::queue`, each carrying `queue` and
either `job_id` or `worker`:

| Message | Level | When |
|---|---|---|
| `queue worker started` / `queue worker stopped` | `info` | Once per method per replica, naming the id it consumes under. |
| `job handed back to the queue` | `info` | A job goes back without an outcome — `reason` is `shutdown`, `leased elsewhere` or `guard unavailable`. |
| `job delivered while another delivery runs it; handing it back` | `info` | A second delivery the lease sent back. |
| `job delivered again after it settled; acknowledged without running` | `info` | A redelivery the settled mark absorbed. |
| `job delivered after it was cancelled; acknowledged without running` | `info` | A delivery that met a cancel's tombstone. |
| `job filed for its next attempt`, `job deferred to its throttle's next window`, `job handed back for a consumer of a newer release` | `debug` | A retry on the schedule, an attempt over its throttle, and a job a newer release sealed — which the port says at `warn`, naming both versions. |
| `job lease not asked for; …`, `job lease not renewed; retrying`, `job settled mark not written; …` | `warn` | Redis refused a guard call — see [Delivery on Redis](/queue/delivery/#when-redis-is-slow-or-gone). |
| `queue fetch failed; …`, `queue worker heartbeat failed; …`, `scheduled jobs not moved onto the queue; …` | `warn` | One of apalis's own calls failed, and it makes it again; a fetch whose connection failed under it may have claimed jobs, which wait in flight until a replica starts. |
| `due jobs not moved onto the queue; retrying` | `warn` | Redis refused the worker's scan of the schedule; `retry_in_ms` says when it runs again. |
| `settled marks kept a week` / `settled marks not kept a week; …` | `debug` / `warn` | The worker kept — or Redis refused to keep — the marks of the jobs settled just before a drain or a lost acknowledgement; `reason` says which. |
| `job lease lost while its attempt runs; another delivery may run it too` | `error` | The attempt's lease lapsed under it. |
| `job not handed back; …` | `error` | Redis refused a hand-back: apalis files the job's stored record again, due at once, and it runs again. |
| `job acknowledgement lost; …` | `error` | A job stays in flight until a replica starts; the worker keeps the marks of the jobs it settled lately a week, so that delivery does not run it again. |
| `queue fetch met a record apalis cannot decode; …` | `error` | A fetch claimed a record apalis cannot read, and dropped its whole batch in flight — see [Delivery on Redis](/queue/delivery/#limits). |
| `queue workers did not stop within the shutdown window; …` | `error` | An attempt outlived the drain and its reserve. |

At boot, a key at a 6.x queue name holding something other than the structure
6.x kept there is said at `warn`, its `keys` naming each with what it holds —
`a key at a 6.x queue name holds what 6.x never kept there; …` — and left
alone. A producer files lines of its own on the same target, among them
`jobs wait under the 6.x key layout; …` once per queue at `warn` — see
[Upgrading queues from 6.x](/queue/upgrading/) — `unique key claimed without
its job confirmed queued; …` at `warn` when a push under a unique key never
learned whether its job was queued, its `step` saying where, `due jobs not moved
onto the queue; retrying` at `warn` when Redis refused its scan of the delayed
jobs it filed, and `queued job cancelled` at `info` when a cancel answered
`true`.

## What boot looks like

Each active processor logs one `attached` line (from the transport) and one
`registered queue processor` line carrying what it declared — its `retries`,
its `concurrency`, and its throttle when it has one. A `#[process]` method that
compiled in but whose provider isn't reachable from this app's module tree is
skipped with a `warn`:

```text frame="terminal"
 INFO nest_rs::app: attached module-contributed transport transport="RedisWorker"
 INFO nest_rs::queue: registered queue processor processor="AudioProcessor::transcode" queue="audio" retries=3 concurrency=4
 WARN nest_rs::queue: skipped #[process] method: no instance of the provider in
      this app's container processor=ReportJobs::weekly queue=reports
      origin="features::reports::queue::processor"
      hint="nothing is registered under that exact type. Common causes: its module
      is not imported by this app (import it, or delete the methods); it is bound
      only as `dyn Trait`; it is imported through a `for_root`; it is registered by
      hand under a key or a trait"
```

The skip line is `warn` — a linked-but-unimported handler is usually a
wiring mistake worth surfacing, and it confirms a shared `features`
crate isn't accidentally activating handlers this binary doesn't want.
See [Wiring the worker](/queue/wiring/) for the module-gating rule.

<Aside type="caution">
A legacy payload with no wire envelope logs `processed an unversioned
job payload` at `warn` (fields `queue`, `job_id`, `hint`) as it starts. It
still executes; drain the queue to clear pre-envelope jobs. A payload
tagged with an *unsupported* version fails the job instead of warning.
</Aside>

## Filtering recipes

```bash
RUST_LOG=info,nest_rs::queue=debug nestrs run dev worker
```

`info` everywhere, `debug` on the queue path: adds the `job started`
line per attempt, and each filing and deferral, on top of the `queue.job` line
and any failure detail.

```bash
RUST_LOG=nest_rs::queue=warn nestrs run dev worker
```

Strictly failures, skips, and unversioned warnings — useful for tailing
a healthy worker where the only thing you care about is "did anything go
wrong."
