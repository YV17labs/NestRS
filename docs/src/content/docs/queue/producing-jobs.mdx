Pushing a job is a one-line call — `queue.push(AudioQueue, job, None).await?`
— but *where* that line lives decides whether the feature stays auditable.
The rule is the same one that holds `Repo` calls behind a service:
controllers, resolvers, and gateways ask the service to enqueue. The
service names the queue; the transport adapter doesn't.

## The payload

A job is any `Serialize + DeserializeOwned + Clone + Send + Sync + 'static`
type — the marker `nest_rs::queue::Job` is auto-implemented for every
type that satisfies those bounds. No derive, no trait to write. The
convention is to keep payloads small: a reference to the work, not the
work itself.

```rust title="crates/features/src/audio/command.rs (from the demo)"
use nest_rs::queue::{Queue, queue};
use serde::{Deserialize, Serialize};

#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct TranscodeCommand {
    pub file: String,
}

#[queue(name = "audio", job = TranscodeCommand)]
pub struct AudioQueue;

pub const AUDIO_QUEUE: &str = <AudioQueue as Queue>::NAME;
```

**Plain `serde` derives, not `#[input]`** — the one place the wire-DTO
shorthand is the wrong tool. `#[input]` carries `deny_unknown_fields`, which is right at an edge a client
controls and wrong on a producer↔worker contract. A producer one deploy
ahead that adds a field would have every job it enqueues refused by the
older worker. And a decode failure aborts rather than retries, so the job
[dead-letters](/queue/retries-and-failure/) on its first attempt.
Adding a field to a payload has to be survivable, and that means accepting one
you do not know yet.

A queue payload is named for the boundary it crosses: an imperative
"do X" handled by one processor is a **`Command`** (`command.rs` at the
feature port); a published past-tense fact with potentially many
consumers is an **`Event`** (`event.rs`). The HTTP body that triggers
the enqueue is a *separate* `TranscodeDto` — each boundary speaks its
own vocabulary.

Producer and consumer agree on **both** facts by importing `AudioQueue`:
the wire name and the payload type travel together, so a renamed queue or
a changed payload breaks the build on whichever side did not follow. The
`#[queue]` marker sits at the port beside the payload, not in the
consumer-side `queue/` adapter — the producer is one directory up, and a
marker it cannot see is a marker it cannot use.

## The service is the choke point

A producer is any code that asks the service to enqueue. The HTTP
controller, the GraphQL resolver, the scheduled producer — all of them
delegate. They do **not** hold the producer and do **not** know the queue
name.

```rust title="crates/features/src/audio/service.rs (from the demo, abridged)"
use std::sync::Arc;

use nest_rs::core::injectable;
use nest_rs::queue::{JobProducer, JobProducerExt};

use super::command::{AudioQueue, TranscodeCommand};
use super::error::AudioError;

#[injectable]
pub struct AudioService {
    #[inject]
    queue: Arc<dyn JobProducer>,
}

impl AudioService {
    pub async fn enqueue_transcode(&self, file: String) -> Result<(), AudioError> {
        self.queue
            .push(AudioQueue, TranscodeCommand { file: file.clone() }, None)
            .await?;
        tracing::debug!(target: "features::audio", file, "enqueued transcode job");
        Ok(())
    }
}
```

`push` takes both the wire name and the accepted payload from the marker, so
enqueueing onto the wrong queue, or with the wrong payload, does not compile,
and answers with a receipt naming the queue and the job's id. `push` comes
from `JobProducerExt`, a blanket extension
over any producer — import the trait, and it is available on
`Arc<dyn JobProducer>` and on a backend's concrete producer alike. It is `async`
because Redis is async; that is the whole producer surface from a
feature's point of view. Inside the call, `nest-rs-redis` wraps your
payload in the wire envelope (`{ "v": 1, "payload": ... }`) so any other
backend can drain it, and seals your trace context into it so the job
runs under the trace that enqueued it. You never see either — see
[Correlation](/fundamentals/correlation/).

<Aside type="caution">
One escape hatch: `push_json(name, value)` takes a raw name and a JSON
payload — correct **only** for a queue this binary does not declare, drained
by another deployment whose `#[queue]` types it does not link. It opts out of
both the name check and the payload check, so it is never the default path.
</Aside>

<Aside type="tip">
`Arc<dyn nest_rs::queue::JobProducer>` is the form to inject: the feature names
no backend, so it compiles unchanged against a different driver.
`RedisQueueModule` binds **both** that name and the concrete
`nest_rs::redis::RedisQueueProducer` over the one connection `RedisModule`
opens, so the concrete type resolves too when a service genuinely needs it.
Same publisher surface either way — `push` is on the extension trait, not
the concrete type.
</Aside>

## Holding a job back

The third argument carries what a push declares besides its queue and its
payload. A delay holds the job until a duration has passed, or until an
instant:

```rust title="src/audio/service.rs"
self.queue
    .push(
        AudioQueue,
        TranscodeCommand { file },
        PushOptions::default().with_delay(Duration::from_secs(60)),
    )
    .await?;
```

A delay needs a backend declaring `Capability::DelayedPush`. The Redis backend
does; a backend that does not refuses the push with `QueueError::Unsupported`,
naming itself, before anything is filed — a delay is never dropped in silence.
On Redis the job waits on the queue's schedule and reaches the queue once due,
whether or not a worker runs — see [Delivery on Redis](/queue/delivery/#delayed-jobs).

## One job per key

A unique key keeps a queue from holding the same piece of work twice. While a
job pushed under a key is pending or running, a second push under that key is
refused with `QueueError::UniqueKeyHeld`, which names the job holding it, and
files nothing:

```rust title="src/billing/service.rs"
let pushed = self
    .queue
    .push(
        InvoiceQueue,
        InvoiceCommand { customer },
        PushOptions::default().with_unique(format!("invoice-{customer}")),
    )
    .await;
match pushed {
    Ok(receipt) => Ok(Some(receipt)),
    Err(QueueError::UniqueKeyHeld { holder, .. }) => {
        tracing::debug!(target: "features::billing", holder = %holder, "invoice already queued");
        Ok(None)
    }
    Err(error) => Err(error.into()),
}
```

The key is held from the push until the job reaches its outcome — it
completes, it dead-letters, or it is cancelled — and is free for the next push
from then on. It is scoped to the queue: the same key on two queues names two
jobs. `push_many` refuses a unique key, since a key names one job.

**At most once over pushes, never a lock.** A unique key keeps a sequence of
pushes from queueing one piece of work twice. It does not make two replicas or
two methods take turns at anything, and a job redelivered after its replica
died runs again under the key it already holds.

A unique key needs a backend declaring `Capability::UniquePush`. On Redis the
key is claimed in the same step that reads it, before the job is filed, so
pushes racing for one key queue one job; how long a key whose job vanished
holds out is on [Delivery on Redis](/queue/delivery/#what-a-job-keeps-and-for-how-long).

## Cancelling a job

The receipt a push returns names the job, and `cancel` takes it back while it
waits:

```rust title="src/audio/service.rs"
let receipt = self.queue.push(AudioQueue, job, None).await?;

if self.queue.cancel(&receipt).await? {
    tracing::info!(target: "features::audio", job_id = %receipt.id(), "transcode withdrawn");
}
```

`Ok(true)` is a promise: the job had not started, and now never will —
whether it waited on its queue, on the schedule its delay holds it on, or for
the next attempt a failed one left it. Cancelling is the job's outcome, so the
unique key it held is free again and its checkpoint is gone. `Ok(false)` says
the job already started — it then runs to its own outcome — already finished,
or was never known to the backend. A job is never stopped mid-attempt.

A receipt is data: it serializes as `{"queue": …, "id": …}`, so a caller that
cancels later, from another request or another process, keeps it wherever it
keeps state. `cancel_unique(AudioQueue, key)` cancels the job holding a unique
key instead, with the same answer.

Cancelling needs a backend declaring `Capability::Cancellation`. On Redis a
cancel leaves a tombstone beside the job rather than touching the queue's
storage, written only while no attempt holds the job, and the delivery that
meets it acknowledges the job without running it.

## The HTTP adapter

The controller is a thin transport. It accepts a `TranscodeDto` — the
REST body, a distinct type from the queue's `TranscodeCommand` — calls
the service, returns the wire response. No queue knowledge of its own.

Declare the DTO with `#[input]`: a `Json<T>` handler argument requires
`schemars::JsonSchema` (see [extractors](/http/extractors/)), and `#[input]`
derives it along with `Deserialize` and `Validate`. A hand-derived DTO needs
`#[derive(schemars::JsonSchema)]` and the `schemars` dependency to go with it.

```rust title="crates/features/src/audio/dtos/transcode_dto.rs (from the demo)"
use nest_rs::http::input;

#[input]
pub struct TranscodeDto {
    pub file: String,
}
```

```rust title="crates/features/src/audio/http/controller.rs (from the demo)"
use std::sync::Arc;

use nest_rs::http::{controller, routes};
use nest_rs::http::poem::http::StatusCode;
use nest_rs::http::poem::web::Json;
use nest_rs::http::poem::{Error, Result};

use crate::audio::{AudioService, TranscodeDto};

#[controller(path = "/audio")]
#[use_guards(AuthnGuard, AuthzGuard)]
pub struct AudioController {
    #[inject]
    svc: Arc<AudioService>,
}

#[routes]
impl AudioController {
    #[post("/transcode")]
    async fn transcode(&self, body: Json<TranscodeDto>) -> Result<Json<TranscodeDto>> {
        let job = body.0;
        self.svc
            .enqueue_transcode(job.file.clone())
            .await
            .map_err(|e| Error::from_string(e.to_string(), StatusCode::INTERNAL_SERVER_ERROR))?;
        Ok(Json(job))
    }
}
```

Swap this for a `#[resolver]` mutation, a `#[gateway]` message, or a
`#[scheduled]` method on a timer — the controller is the only file that
changes. The service stays the single audited entry point, every
transport hits it through `enqueue_transcode`.

## Why this rule

Three reasons the `push` call hides behind a service:

1. **One audit point per queue.** `AudioQueue` is named in exactly one
   place per side. A grep for `enqueue_transcode` shows every producer.
2. **Pre-flight logic survives a swap of transport.** If enqueueing
   needs an ability check, an idempotency key, a tracing field — the
   service holds it. Adding a second producer doesn't duplicate that.
3. **The consumer can change without touching producers.** Renaming the
   queue, splitting `audio` into `audio.fast` and `audio.slow`, moving
   from Redis to SQS — one file changes, every adapter follows. And
   because the name lives on the `#[queue]` type, a rename that misses a
   call site is a compile error rather than a queue nobody drains.

The same shape the rest of the framework uses for `Repo`, just on the
push side. The service is the contract; transports adapt.
