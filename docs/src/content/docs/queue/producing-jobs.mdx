Pushing a job is a one-line call — `queue.push(AudioQueue, job, None).await?`
— but *where* that line lives decides whether the feature stays auditable.
The rule is the same one that holds `Repo` calls behind a service:
controllers, resolvers, and gateways ask the service to enqueue. The
service names the queue; the transport adapter doesn't.

## The payload

A job is any `Serialize + DeserializeOwned + Clone + Send + Sync + Unpin + 'static`
type — the marker `nest_rs::queue::Job` is auto-implemented for every
type that satisfies those bounds. No derive, no trait to write. The
convention is to keep payloads small: a reference to the work, not the
work itself.

```rust title="crates/features/src/audio/command.rs (from the demo)"
use nest_rs::queue::{Queue, queue};
use serde::{Deserialize, Serialize};
use uuid::Uuid;

#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct TranscodeCommand {
    pub file: Uuid,
}

#[queue(name = "audio", job = TranscodeCommand)]
pub struct AudioQueue;

pub const AUDIO_QUEUE: &str = <AudioQueue as Queue>::NAME;
```

**Plain `serde` derives, not `#[input]`** — the one place the wire-DTO
shorthand is the wrong tool. `#[input]` carries `deny_unknown_fields`, which is right at an edge a client
controls and wrong on a producer↔worker contract. A producer one deploy
ahead that adds a field would have every job it enqueues refused by the
older worker. And a decode failure aborts rather than retries, so the job
[dead-letters](/queue/retries-and-failure/) on its first attempt.
Adding a field to a payload has to be survivable, and that means accepting one
you do not know yet.

A queue payload is named for the boundary it crosses: an imperative
"do X" handled by one processor is a **`Command`** (`command.rs` at the
feature port); a published past-tense fact with potentially many
consumers is an **`Event`** (`event.rs`). The HTTP body that triggers
the enqueue is a *separate* `TranscodeDto` — each boundary speaks its
own vocabulary.

Producer and consumer agree on **both** facts by importing `AudioQueue`:
the wire name and the payload type travel together, so a renamed queue or
a changed payload breaks the build on whichever side did not follow. The
`#[queue]` marker sits at the port beside the payload, not in the
consumer-side `queue/` adapter — the producer is one directory up, and a
marker it cannot see is a marker it cannot use.

## The service is the choke point

A producer is any code that asks the service to enqueue. The HTTP
controller, the GraphQL resolver, the scheduled producer — all of them
delegate. They do **not** hold the producer and do **not** know the queue
name.

```rust title="crates/features/src/audio/service.rs (from the demo, abridged)"
use std::sync::Arc;

use nest_rs::core::{error_message, injectable};
use nest_rs::queue::{JobProducer, JobProducerExt};
use uuid::Uuid;

use super::command::{AUDIO_QUEUE, AudioQueue, TranscodeCommand};
use super::error::AudioError;

#[injectable]
pub struct AudioService {
    #[inject]
    queue: Arc<dyn JobProducer>,
}

impl AudioService {
    pub async fn enqueue_transcode(&self, file: Uuid) -> Result<(), AudioError> {
        self.queue
            .push(AudioQueue, TranscodeCommand { file }, None)
            .await?;
        tracing::debug!(target: crate::audio::TARGET, queue = AUDIO_QUEUE, "enqueued transcode job");
        Ok(())
    }
}
```

`push` takes both the wire name and the accepted payload from the marker, so
enqueueing onto the wrong queue, or with the wrong payload, does not compile,
and answers with a `PushReceipt` naming the queue and the job's id. `push`
comes from `JobProducerExt`, a blanket extension over any producer — import the
trait, and it is available on `Arc<dyn JobProducer>` and on a backend's
concrete producer alike. `push_many` takes an iterator of jobs for one queue and
answers one receipt per job, in order. Both are `async` because the backend is.

The port does the rest before the backend sees the job: it checks the options,
mints the job's id — a UUID v7, the `job_id` every attempt at the job reports —
and seals your payload in the wire envelope with your trace context, your actor
and your tenant, so the job runs under the trace that enqueued it and for the
same tenant: `current_tenant_id()` answers in the processor what it answered
where you pushed. You never see either — see
[Correlation](/fundamentals/correlation/) and
[Multi-tenant SaaS](/security/multi-tenant-saas/).

<Aside type="caution">
One escape hatch: `push_json(name, value, None)` takes a raw name and a JSON
payload — correct **only** for a queue this binary does not declare, drained
by another deployment whose `#[queue]` types it does not link. It opts out of
both the name check and the payload check, so it is never the default path.
</Aside>

`Arc<dyn nest_rs::queue::JobProducer>` is the form to inject: the feature names
no backend, so it compiles unchanged against a different driver.
`RedisQueueModule` binds **both** that name and the concrete
`nest_rs::redis::RedisQueueProducer` over the connection `RedisModule` opens
for its instance ([a second Valkey](/queue/topologies/#a-second-valkey) has
one of its own), so the concrete type resolves too when a service genuinely needs it.

## When a push fails

A push is refused before anything is filed when its options cannot be honoured
— `QueueError::Unsupported` for an option the backend does not declare,
`QueueError::InvalidUniqueKey` for a key no backend could file,
`QueueError::InvalidOptions` for a delay ending after `9999-12-31T23:59:59.999Z`,
the last instant RFC 3339 writes (`Delay::LATEST_DUE`) — or when a unique key is
held. Past those, an error from the backend is a failure to
*answer*: the job may be queued and its reply lost, so a caller that retries such
a push can queue it twice unless it carries a unique key.

**No backend holds a push past eighteen seconds.** The port waits
`BACKEND_TIMEOUT` for the backend's answer to a push or a cancel, then gives up
on the call and fails it with `QueueError::Unanswered`, naming the queue and the
call — which, like any failure to answer, may still have filed the job. It is a
net under the backend, never its budget: on Redis each command a push sends
waits at most `<PREFIX>_REDIS__CONNECT_TIMEOUT_SECS`, ten seconds by default, so a
Redis that stopped answering fails the push at that budget, with its own cause,
well before the net. Eighteen seconds stays under the HTTP edge's request timeout,
so a push made inside a request fails with an error naming its queue while the
request can still answer. A backend that panics answering a push or a cancel
fails it the same way, as `QueueError::Panicked` naming the queue and the call —
the panic itself is filed once at `error` on `nest_rs::queue`, never handed to
your handler.

`push_many` hands the backend its jobs a hundred at a time (`ENQUEUE_BATCH`),
each call under the net, so the net holds a push of any size. It is not atomic.
When a call fails after the backend accepted earlier ones, the error is
`QueueError::PartiallyQueued { receipts, source }`: `receipts` names every job
of the accepted calls — queued, and to be left out of a retry or cancelled —
and `source` is the failure that stopped the push. The failing call's own jobs
may be queued too, and no receipt says which, so retrying those can queue one
twice. A push failing at its first call returns that failure alone.

## A push inside a transaction

A push written inside a transaction — a mutating request, a WebSocket message,
a job attempt, a listener's call — is written **into** that transaction. With
the `seaorm` and `queue` features, the job becomes a row of the outbox table,
`nestrs_outbox`, committed or rolled back with the request's own writes; once
the transaction commits, the outbox relay files it on the backend. A rollback
leaves no job behind, a crash after the commit loses none, and the receipt
names a job that exists exactly when the request's writes do. A `push_many`
there is one write, so it lands whole or not at all.

You write the push as anywhere else, and list nothing: `SeaOrmDatabaseModule`
keeps the outbox and attaches the relay. Your migrator lists the framework's
migration, which creates the table — `nestrs g queue` registers it, or
`nestrs g migration nestrs_outbox`, and the boot refuses without it, naming
that remedy:

```rust title="crates/migrations/src/migrator.rs (abridged)"
fn migrations() -> Vec<Box<dyn MigrationTrait>> {
    vec![
        // …
        Box::new(nest_rs::seaorm::queue::OutboxMigration),
    ]
}
```

A push on the pool — a safe request, a `transactional = false` job — is filed
at once, as is one in an app binding no database.

Two answers move from the push to the relay. A unique key another job holds is
checked once the transaction committed: the record is dropped, in one `info`
line on `nest_rs::queue` naming both jobs, and the caller saw `Ok`. A backend
that refuses delays the job without losing it: the relay retries each record on
the job retry backoff, says a failing pass at `warn`, and says once at `error`
when records waited past the stall warning. Delivery stays [at least
once](/queue/delivery/#filed-after-the-commit).

## Holding a job back

The third argument carries what a push declares besides its queue and its
payload. A delay holds the job for a `Duration`, or until a `SystemTime`:

```rust title="crates/features/src/audio/service.rs"
self.queue
    .push(
        AudioQueue,
        TranscodeCommand { file },
        PushOptions::default().with_delay(Duration::from_secs(60)),
    )
    .await?;
```

A delay needs a backend declaring `Capability::DelayedPush`. The Redis backend
does; a backend that does not refuses the push with `QueueError::Unsupported`,
naming itself, before anything is filed — a delay is never dropped in silence.
On Redis the job waits off the stream, due on Redis's clock, and a running
worker files it within a second of falling due — with none running, it waits —
see [Delivery on Redis](/queue/delivery/#delayed-jobs).

## One job per key

A unique key keeps a queue from holding the same piece of work twice. While a
job pushed under a key is pending or running, a second push under that key is
refused with `QueueError::UniqueKeyHeld`, which names the job holding it, and
files nothing:

```rust title="crates/features/src/audio/service.rs"
let pushed = self
    .queue
    .push(
        AudioQueue,
        TranscodeCommand { file },
        PushOptions::default().with_unique(format!("transcode-{file}")),
    )
    .await;
match pushed {
    Ok(receipt) => Ok(Some(receipt)),
    Err(QueueError::UniqueKeyHeld { holder, .. }) => {
        tracing::debug!(target: crate::audio::TARGET, holder = %holder, "transcode already queued");
        Ok(None)
    }
    Err(error) => Err(error.into()),
}
```

The key is held from the push until the job reaches its outcome — it
completes, it dead-letters, or it is cancelled — and is free for the next push
from then on. It is scoped to the queue: the same key on two queues names two
jobs. A key is 1 to 256 bytes with no control character, and `push_many`
refuses one, since a key names one job.

**At most once over pushes, never a lock.** A unique key keeps a sequence of
pushes from queueing one piece of work twice. It does not make two replicas or
two methods take turns at anything, and a job redelivered after its replica
died runs again under the key it already holds.

A unique key needs a backend declaring `Capability::UniquePush`. On Redis a
push is one script: it reads and claims the key in the step that files the job,
so pushes racing for one key queue one job, and a push lands whole or not at
all — a push that never learned its answer claimed the key with its job, or
claimed nothing. See [Delivery on Redis](/queue/delivery/#unique-keys).

## Cancelling a job

The receipt a push returns names the job, and `cancel` takes it back while it
waits:

```rust title="crates/features/src/audio/service.rs"
let receipt = self.queue.push(AudioQueue, job, None).await?;

if self.queue.cancel(&receipt).await? {
    tracing::info!(target: crate::audio::TARGET, job_id = %receipt.id(), "transcode withdrawn");
}
```

`Ok(true)` is a promise: the job had not started, and now never will —
whether it waited on its queue, on the schedule its delay holds it on, or for
the next attempt a failed one left it. Cancelling is the job's outcome, so the
unique key it held is free again and its checkpoint is gone. `Ok(false)` says
the job already started — it then runs to its own outcome — already finished,
or was never known to the backend. A job is never stopped mid-attempt.

A job still waiting in the outbox — its transaction committed, the relay not
yet done filing it — is cancelled there: the cancel deletes its record, waiting
a moment for a relay filing it at that instant, then asks the backend, and
either answers `true`.

A receipt is data: it serializes as `{"queue": …, "id": …}`, so a caller that
cancels later, from another request or another process, keeps it wherever it
keeps state. `cancel_unique(AudioQueue, key)` cancels the job holding a unique
key instead, with the same answer.

Cancelling needs a backend declaring `Capability::Cancellation`. On Redis a
cancel is one script: it removes a job still waiting — on the stream and not
yet handed over, or held back — with everything it held, and answers `false`
for one a delivery runs. See [Delivery on Redis](/queue/delivery/#cancels).

## The HTTP adapter

The controller is a thin transport. It accepts a `TranscodeDto` — the
REST body, a distinct type from the queue's `TranscodeCommand` — calls
the service, and answers `202`: the job is queued, not done, and the reply
echoes nothing the client sent. No queue knowledge of its own.

Declare the DTO with `#[input]`: a `Json<T>` handler argument requires
`schemars::JsonSchema` (see [extractors](/http/extractors/)), and `#[input]`
derives it along with `Deserialize` and `Validate`. A hand-derived DTO needs
`#[derive(schemars::JsonSchema)]` and the `schemars` dependency to go with it.

```rust title="crates/features/src/audio/dtos/transcode_dto.rs (from the demo, abridged)"
use nest_rs::http::input;
use uuid::Uuid;

#[input]
pub struct TranscodeDto {
    pub file: Uuid,
}
```

`file` is the key an upload minted, parsed as a UUID at the edge: a name the
client chose is a `400` before the service runs.

```rust title="crates/features/src/audio/http/controller.rs (from the demo, abridged)"
use std::sync::Arc;

use nest_rs::http::{
    Body, Header, HeaderValue, HttpError, Json, Query, Response, Result, SseEvent, SseStream,
    StatusCode, Valid, controller, routes,
};
use nest_rs::throttler::{Throttle, ThrottlerGuard};

use crate::audio::TranscodeGuard;
use crate::audio::{
    AudioService, DirectUploadDto, PresignedUrlDto, StreamResumeDto, TranscodeDto, TranscodeState,
};
use crate::authn::AuthnGuard;
use crate::authz::AuthzGuard;

#[controller(path = "/audio")]
#[use_guards(ThrottlerGuard, AuthnGuard, AuthzGuard, TranscodeGuard)]
pub struct AudioController {
    #[inject]
    svc: Arc<AudioService>,
}

#[routes]
impl AudioController {
    #[post("/transcode")]
    #[meta(Throttle::per_minute(20))]
    // … #[api(…)]
    #[http_code(202)]
    async fn transcode(&self, body: Valid<Json<TranscodeDto>>) -> Result<()> {
        self.svc.enqueue_transcode(body.into_inner().file).await?;
        Ok(())
    }
}
```

Swap this for a `#[resolver]` mutation, a `#[gateway]` message, or a
`#[scheduled]` method on a timer — the controller is the only file that
changes. The service stays the single audited entry point, every
transport hits it through `enqueue_transcode`.

## Why this rule

Three reasons the `push` call hides behind a service:

1. **One audit point per queue.** `AudioQueue` is named in exactly one
   place per side. A grep for `enqueue_transcode` shows every producer.
2. **Pre-flight logic survives a swap of transport.** If enqueueing
   needs an ability check, an idempotency key, a tracing field — the
   service holds it. Adding a second producer doesn't duplicate that.
3. **The consumer can change without touching producers.** Renaming the
   queue, splitting `audio` into `audio.fast` and `audio.slow`, moving
   from Redis to another backend — one file changes, every adapter follows. And
   because the name lives on the `#[queue]` type, a rename that misses a
   call site is a compile error rather than a queue nobody drains.

The same shape the rest of the framework uses for `Repo`, just on the
push side. The service is the contract; transports adapt.
