The same `features::audio` crate compiles into the API binary and the
worker binary. Only the worker drains the queue. That split is two
module imports, two `main`s, one shared features crate — the framework
decides which `#[process]` methods actually run by walking the access
graph from each app's root.

## Three modules, three roles

| Module | Role | Imported by |
|---|---|---|
| `RedisModule::for_root(cfg)` | Opens the **one** Redis connection every Redis binding shares — the queue's producer and consumer, the rate-limit store, the schedule's lock. | Every app that touches Redis. |
| `RedisQueueModule` | Binds the queue port over that connection: the producer, `Arc<dyn JobProducer>`, the portable handle a feature injects to enqueue, and the consumer the worker runs jobs through. A bare import reads `<PREFIX>_REDIS__QUEUE__*`; `for_root(RedisQueueConfig { lease })` pins the base — see [Delivery on Redis](/queue/delivery/#configuration). | Every app that enqueues or runs jobs. |
| `QueueModule::for_root(cfg)` | From `nest_rs::queue`: contributes the port's `QueueWorker` transport, which discovers the reachable `#[process]` methods at boot and runs each over the bound consumer; its own setting is the drain window, `<PREFIX>_QUEUE__SHUTDOWN_TIMEOUT_SECS`. | Worker apps only. |

`RedisModule::for_root(None)` reads `<PREFIX>_REDIS__URL` from the environment;
`RedisModule::for_root(RedisConfig { url, .. })` supplies that URL as the
**base** the environment overlays — so a deployment setting `<PREFIX>_REDIS__URL`
still wins, field by field ([the dual-path rule](/configuration/#the-dual-path-rule)).
One connection, one variable, named for the crate that parses it: a
throttler-only app sets the same `<PREFIX>_REDIS__URL`. See [fundamentals/modules](/fundamentals/modules/) for the
four boot phases that resolve the connection before any transport attaches.

<Aside type="note">
The connection is built in the **collect** phase as an async factory, and
every binding's factory declares that it runs after it — so `imports = [...]`
order is a readability choice, and by the time `QueueWorker::configure` runs
the connection is in the container. A worker app that forgot `RedisModule`
fails fast at boot with an error naming it — and so does one whose
`<PREFIX>_REDIS__URL` is unreachable: every connect attempt warns on
`nest_rs::redis`, and the boot gives up after `<PREFIX>_REDIS__CONNECT_TIMEOUT_SECS`
(10 s by default) naming the redacted endpoint. A container that cannot reach
its Redis crashes rather than parking forever between "not healthy" and "not
dead".
</Aside>

## The worker app

The worker imports the connection, the queue's Redis binding, the port's worker
and each feature's queue adapter. That's it — `AudioQueueModule` pulls in the
`AudioModule` port itself.

```rust title="apps/worker/src/module.rs (from the demo, abridged)"
use nest_rs::config::ConfigModule;
use nest_rs::core::module;
// …
use nest_rs::queue::QueueModule;
use nest_rs::redis::{RedisModule, RedisQueueModule, RedisScheduleModule};
// …

use features::audio::AudioQueueModule;
use features::notifications::{NotificationsQueueModule, NotificationsScheduleModule};

#[module(
    imports = [
        ConfigModule::for_root(),
        // …
        RedisModule::for_root(None),
        RedisQueueModule,
        QueueModule::for_root(None),
        // …
        AudioQueueModule,
        NotificationsQueueModule,
        // …
    ],
)]
pub struct WorkerModule;
```

The demo's worker also opens the database — the notifications job writes a
row — runs the notifications purge on a schedule, and serves its health probes
over HTTP; the excerpt keeps the queue's lines.

At boot:

1. `ConfigModule` reads env, materializes `RedisConfig` from
   `<PREFIX>_REDIS__URL`.
2. `RedisModule::for_root(None)` registers a factory that opens the
   `RedisConnection`.
3. `RedisQueueModule` registers factories — declared to run after the
   connection's — that bind `RedisQueueProducer` as `Arc<dyn JobProducer>` and
   the Redis consumer as the port's `BoundConsumer`, with its lease read from
   `<PREFIX>_REDIS__QUEUE__*`.
4. `QueueModule::for_root(None)` contributes the `QueueWorker` transport, with
   its drain window read from `<PREFIX>_QUEUE__*`.
5. `AudioQueueModule` brings `AudioProcessor` (the `#[processor]` host) and
   its `#[process]` methods into the reachable set.
6. `QueueWorker::configure` discovers `inventory::iter::<ProcessMethod>()`,
   keeps only the methods whose provider is reachable, refuses what the
   backend cannot honour, and logs each one. It then prepares the consumer,
   which creates each queue's consumer group and loads the scripts. `serve`
   runs each method with permits of its own until the drain.

## The producer-only app

A producer-only binary imports `RedisModule::for_root(...)` and
`RedisQueueModule`, and skips `QueueModule` entirely. It gets
`Arc<dyn JobProducer>` to push with — and no worker, no discovered
inventory, no read of any queue.

```rust title="apps/api/src/module.rs (from the demo, abridged)"
use nest_rs::config::ConfigModule;
use nest_rs::core::module;
use nest_rs::http::{HttpConfig, HttpModule};
use nest_rs::redis::{RedisModule, RedisQueueModule, RedisScheduleModule};
use nest_rs::schedule::ScheduleModule;
use nest_rs::seaorm::{SeaOrmDatabaseModule, SeaOrmHealthModule, SeaOrmModule};

use features::audio::{AudioHttpModule, AudioScheduleModule};

#[module(
    imports = [
        ConfigModule::for_root(),
        SeaOrmModule::for_root(None),
        SeaOrmDatabaseModule,
        RedisModule::for_root(None),
        RedisQueueModule,
        ScheduleModule,
        RedisScheduleModule,
        HttpModule::for_root(HttpConfig {
            port: 3002,
            compression: true,
            ..Default::default()
        }),
        AudioHttpModule,
        AudioScheduleModule,
    ],
)]
pub struct ApiModule;
```

That `apps/api` is exactly this shape: producer-only. Its HTTP
controller and scheduled timer both end in `AudioService::enqueue_transcode`,
which pushes through the bound `JobProducer` onto Redis. No worker
runs in this process — that's the worker binary's job. `RedisScheduleModule`
is the schedule's binding, not a worker's: the occurrence lock the timer
claims through, because the API's replicas fire that enqueue once per
occurrence between them rather than once each.

## Module-gating across the shared crate

The worker depends on the shared `features` crate, so `AudioController`
and `AudioResolver` are **compiled in**. They are not **active**: the
worker doesn't import `AudioHttpModule` or `AudioGraphqlModule`, so
the access graph never marks those providers as reachable. Every
transport — `HttpTransport`, `QueueWorker`, `GraphqlTransport` — filters
its inventory through the `ReachableProviders` set the access graph
computes from the running app's root. Linked but unreachable ⇒ inert,
said once at boot — at `debug` for these, which live in a shared crate and
are another binary's to serve, and at `warn` for a host in the app's own
crate, whose module it forgot to import.

The same property cuts the other way: the API binary's
`AudioQueueModule` is **not imported**, so its `#[process]` methods
sit in the binary as dead code. No worker is spawned for `audio` in
the API. Even if you accidentally imported `QueueModule` in the
API, omitting `AudioQueueModule` would keep `AudioProcessor::transcode`
out of the reachable set — `QueueWorker::serve` would idle until
shutdown.

This is what makes splitting producer and consumer across deploys
cheap. The features crate is one library, the binaries are
compositions of it, and module-gating is the line that decides what
each binary *actually does* at runtime. See
[fundamentals/modules](/fundamentals/modules/) for the access graph
that enforces this — boot fails with `AccessGraphError` if a provider
injects something its module doesn't own or import transitively.

## What the wire looks like at boot

```text frame="terminal"
$ nestrs run dev worker
 INFO nest_rs::app: attached module-contributed transport transport="QueueWorker"
 INFO nest_rs::queue: registered queue processor processor="AudioProcessor::transcode" queue="audio" retries=3 concurrency=4
```

One `attached` line per transport, and one `registered` line per discovered
method that survived the reachability filter. The producer-only API's boot
opens the same connection, but logs no `attached transport=QueueWorker` and no
`registered queue processor` line — the worker side never wakes up.
