The same `features::audio` crate compiles into the API binary and the
worker binary. Only the worker drains the queue. That split is two
module imports, two `main`s, one shared features crate — the framework
decides which `#[process]` methods actually run by walking the access
graph from each app's root.

## Two modules, two roles

| Module | Role | Imported by |
|---|---|---|
| `RedisQueueModule::for_root(cfg)` | Seeds the shared `RedisQueueConnection` (the producer side). | Every app that talks to the queue. |
| `RedisWorkerModule` | Contributes the `RedisWorker` transport — drains `#[process]` methods at boot and spawns one worker each. | Worker apps only. |

`RedisQueueModule::for_root(None)` reads `NESTRS_QUEUE__URL` from the
environment; `RedisQueueModule::for_root(RedisQueueConfig { url, .. })` supplies
that URL as the **base** the environment overlays — so a deployment setting
`NESTRS_QUEUE__URL` still wins, field by field
([the dual-path rule](/configuration/#the-dual-path-rule)). See
[fundamentals/modules](/fundamentals/modules/) for the four boot
phases that resolve the connection before any transport attaches.

<Aside>
The connection is built in the **collect** phase as an async factory.
By the time `RedisWorker::configure` runs, `Arc<RedisQueueConnection>` is in
the container regardless of how modules were ordered in `imports = [...]`.
A worker app with no `RedisQueueConnection` seeded fails fast at boot with
a clear error — and so does one whose `NESTRS_QUEUE__URL` is unreachable:
every connect attempt warns on `nest_rs::queue`, and the boot gives up after
`NESTRS_QUEUE__CONNECT_TIMEOUT_SECS` (10 s by default) naming the redacted
endpoint. A container that cannot reach its queue crashes rather than parking
forever between "not healthy" and "not dead".
</Aside>

## The worker app

The worker imports both queue modules plus the feature's queue adapter.
That's it — `AudioQueueModule` pulls in the `AudioModule` port itself.

```rust title="apps/worker/src/module.rs"
use nest_rs::config::ConfigModule;
use nest_rs::core::module;
use nest_rs::redis::{RedisQueueModule, RedisWorkerModule};

use features::audio::AudioQueueModule;

#[module(imports = [
    ConfigModule::for_root(),
    RedisQueueModule::for_root(None),
    RedisWorkerModule,
    AudioQueueModule,
])]
pub struct RedisWorkerModule;
```

At boot:

1. `ConfigModule` reads env, materializes `RedisQueueConfig` from
   `NESTRS_QUEUE__URL`.
2. `RedisQueueModule::for_root(None)` registers a factory that calls
   `RedisQueueConnection::connect(url)`.
3. `RedisWorkerModule` contributes the `RedisWorker` transport.
4. `AudioQueueModule` brings `AudioProcessor` (the `#[processor]` host) and
   its `#[process]` methods into the reachable set.
5. `RedisWorker::configure` drains `inventory::iter::<ProcessMethod>()`,
   keeps only the methods whose provider is reachable, and logs each
   one. `serve` builds one apalis worker per method on a shared
   `Monitor`.

## The producer-only app

A producer-only binary imports `RedisQueueModule::for_root(...)` and skips
`RedisWorkerModule` entirely. It gets `Arc<RedisQueueConnection>` to push
with — and no worker spawn, no drained inventory, no apalis monitor.

```rust title="apps/api/src/module.rs (abridged)"
use nest_rs::config::ConfigModule;
use nest_rs::core::module;
use nest_rs::http::HttpModule;
use nest_rs::redis::RedisQueueModule;
use nest_rs::seaorm::SeaOrmDatabaseModule;

use features::audio::{AudioHttpModule, AudioScheduleModule};

#[module(imports = [
    ConfigModule::for_root(),
    HttpModule::for_root(None),
    SeaOrmDatabaseModule::for_root(None),
    RedisQueueModule::for_root(None),
    AudioHttpModule,
    AudioScheduleModule,
])]
pub struct ApiModule;
```

That `apps/api` is exactly this shape: producer-only. Its HTTP
controller and scheduled timer both call `AudioService::enqueue_transcode`,
which uses the seeded `RedisQueueConnection` to push onto Redis. No worker
runs in this process — that's the worker binary's job.

## Module-gating across the shared crate

The worker depends on the shared `features` crate, so `AudioController`
and `AudioResolver` are **compiled in**. They are not **active**: the
worker doesn't import `AudioHttpModule` or `AudioGraphqlModule`, so
the access graph never marks those providers as reachable. Every
transport — `HttpTransport`, `RedisWorker`, `GraphqlTransport` — filters
its inventory through the `ReachableProviders` set the access graph
computes from the running app's root. Linked but unreachable ⇒ inert,
with a boot `tracing::warn` if the discovery layer expected them to
appear.

The same property cuts the other way: the API binary's
`AudioQueueModule` is **not imported**, so its `#[process]` methods
sit in the binary as dead code. No worker is spawned for `audio` in
the API. Even if you accidentally imported `RedisWorkerModule` in the
API, omitting `AudioQueueModule` would keep `AudioProcessor::transcode`
out of the reachable set — `RedisWorker::serve` would idle until
shutdown.

This is what makes splitting producer and consumer across deploys
cheap. The features crate is one library, the binaries are
compositions of it, and module-gating is the line that decides what
each binary *actually does* at runtime. See
[fundamentals/modules](/fundamentals/modules/) for the access graph
that enforces this — boot fails with `AccessGraphError` if a provider
injects something its module doesn't own or import transitively.

## What the wire looks like at boot

```text frame="terminal"
$ nestrs run dev worker
 INFO nest_rs::app: attached module-contributed transport transport="RedisWorker"
 INFO nest_rs::queue: registered queue processor processor="AudioProcessor::transcode" queue="audio" retries=3
```

One `attached` line per transport, one `registered` line per
discovered method that survived the reachability filter. The
producer-only API's boot log has the same `RedisQueueConnection` factory
line, but no `attached transport=RedisWorker` and no `registered queue
processor` lines — the worker side never wakes up.
