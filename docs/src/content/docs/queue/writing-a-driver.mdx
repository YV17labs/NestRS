A queue driver connects the queue port to a storage — a broker, a stream, a
database table. The port owns what consuming a job *is*: the attempt, its
retry budget and backoff, the trace, each method's permits, the lease's
renewal, the drain. Its `QueueWorker` runs all of it on every backend, so a
driver only moves records and keeps leases. At the end of this page your
backend runs every `#[process]` method an app declares, and the port's
behaviour kit proves it keeps the contract.

Every excerpt below is lifted from `nest-rs-queue`'s in-memory test backend or
from the Redis binding, so each compiles and runs in the framework's suite.

## Install

```bash frame="terminal"
cargo add nest-rs --no-default-features --features queue
cargo add nest-rs --dev --no-default-features --features queue,testing
```

Your crate is `nestrs-<storage>`, and it depends on the umbrella alone, so
neither line links an HTTP stack. The [naming rule](/semver/#naming-a-package)
roots every name your driver owns at that crate — its target, its keys, its
`<PREFIX>_<STORAGE>__*` settings.

## The contract

<Steps>

1. **Declare the backend.** One `QueueBackend` constant names your storage — its
   OpenTelemetry `messaging.system` — and each optional capability it honours,
   one at a time, never `Capabilities::ALL`:

   ```rust title="from nest-rs-queue's test backend"
   pub(crate) static DELAYING: QueueBackend = QueueBackend::new(
       "memory",
       Capabilities::NONE
           .with(Capability::DelayedPush)
           .with(Capability::Checkpoint),
   );
   ```

   The retry budget, one transaction per attempt and a method's `concurrency`
   are not capabilities: the port keeps all three on every backend. Checkpoint:
   a method declaring `throttle(..)` on this backend fails the boot, naming the
   capability and the backend.

2. **File jobs.** Implement `JobProducer`. The port has refused every option
   your backend does not declare, minted each job's id and sealed each
   envelope; store the record as the bytes it gives you, keyed by
   `envelope.id()`, and never read inside it. Skip an envelope whose job your
   storage still holds — waiting, held back or running — and answer `Ok` for
   it, so a call sent again after its answer was lost files nothing twice:

   ```rust title="from nest-rs-queue's test backend, abridged"
   #[async_trait]
   impl JobProducer for Memory {
       fn backend(&self) -> &'static QueueBackend {
           self.inner.backend
       }

       async fn enqueue(
           &self,
           queue: &QueueName,
           envelopes: Vec<Envelope>,
           options: &PushOptions,
       ) -> Result<(), QueueError> {
           // …
           for envelope in envelopes {
               if state.queue(queue.as_str()).holds_job(envelope.id()) {
                   continue;
               }
               let job = Some(envelope.id().clone());
               let entry = state.entry(job, envelope.into_json().to_string().into_bytes());
               // …
           }
           // …
       }
   }
   ```

   A backend declaring `UniquePush` makes that check first: a held envelope's own
   job holds its key, which never refuses it. A backend declaring
   `Cancellation` implements `remove`, and `remove_unique` beside `UniquePush`.
   Checkpoint: a push answers a receipt naming the job.

   The skip is also what the outbox leans on: a job pushed inside a
   transaction reaches `enqueue` from the port's relay after the commit, and a
   relay that dies before deleting its record sends the same envelope again.
   Your backend owes the outbox nothing more.

3. **Hand jobs over under a lease.** Implement `JobConsumer`. The worker asks;
   your storage answers in the backend's own words:

   | Call | What it owes |
   |---|---|
   | `prepare` | Ready the storage for the methods, once, at boot, and say how long a call takes to answer at most — under `BACKEND_TIMEOUT`, or the boot refuses the backend, naming it. |
   | `receive` | At most `ask.max` deliveries, waiting at most `ask.wait` for the first — each **leased in the step that hands it over**, with its delivery count: 1 the first time, one more each time it is handed over again. |
   | `renew` | Extend each lease still yours, **without counting a delivery**; one `LeaseHold` per lease, in order. |
   | `settle` | End one delivery as its `Disposition` says, **in the step that checks the lease is still yours** — and answer `Lost`, writing nothing, when it is not. |
   | `maintain`, `close`, `checkpoint` | Optional: upkeep while nothing runs (a delayed record falling due), letting go at the end of the drain, and a checkpoint store for a backend declaring `Checkpoint`. |

   The fence on `settle` is the heart of it. A worker whose lease lapsed — frozen,
   or cut off from the storage — must write nothing once another delivery holds
   the job:

   ```rust title="from nest-rs-queue's test backend, abridged"
   async fn settle(
       &self,
       _method: &'static ProcessMethod,
       lease: &MemoryLease,
       disposition: Disposition<'_>,
   ) -> Result<LeaseHold, QueueError> {
       let mut state = self.memory.lock();
       if !state.queue(&lease.queue).holds(lease) {
           return Ok(LeaseHold::Lost);
       }
       // …
       match disposition {
           Disposition::Complete => {
               // …
           }
           Disposition::Retry { after, record, .. } | Disposition::Defer { after, record, .. } => {
               refile(&mut state, record, after);
           }
           Disposition::Requeue { record, .. } => refile(&mut state, record, Duration::ZERO),
           Disposition::DeadLetter { reason, record, .. } => {
               // …
           }
           other => panic!("a disposition the in-memory backend was not written for: {other:?}"),
       }
       // …
       Ok(LeaseHold::Held)
   }
   ```

   `Complete` and `DeadLetter` end the job: let every record of it go — its
   unique key and its checkpoint with it — and keep a dead letter with the
   value-free `reason`. `Retry`, `Defer` and `Requeue` file the record given,
   due once `after` passed, and a record filed again starts its delivery count
   over. A backend without `DelayedPush` is never handed a wait: the port waits
   in process. `Disposition` is non-exhaustive, and a variant added later goes
   only to a backend declaring the capability that names it. Checkpoint: a
   delivery the worker never settles comes back once its lease lapses, with its
   count one higher.

</Steps>

<Aside type="caution">
**Delivery is at least once, and no driver promises more.** A storage that loses
no job delivers some twice — a lease that lapsed under a frozen worker, an
acknowledgement lost — and a `#[process]` handler is idempotent.
</Aside>

## The binding

`<Vendor>QueueModule` binds the producer as `Arc<dyn JobProducer>` and the
consumer as `BoundConsumer`, each a **declaration** carrying `BACKEND_REMEDY`,
so a second backend imported beside yours fails the boot naming both:

```rust title="from nest-rs-redis's queue binding, abridged"
fn bind(builder: ContainerBuilder) -> ContainerBuilder {
    RedisConnection::<I>::netted(builder, "the queue port", BACKEND_TIMEOUT)
        // …
        .provide_declared_factory_after::<Arc<dyn JobProducer>, (RedisQueueProducer<I>,), _, _>(
            BACKEND_REMEDY,
            |container| async move {
                // …
            },
        )
        .provide_declared_factory_after::<
            BoundConsumer,
            (RedisConnection<I>, I::Of<RedisQueueConfig>),
            _,
            _,
        >(BACKEND_REMEDY, |container| async move {
            let conn = RedisConnection::<I>::of(&container, "RedisQueueModule")?;
            // …
            renewable::<I>(config.lease, conn.budget())?;
            Ok(BoundConsumer::new(RedisQueueConsumer::new(conn, config.lease)))
        })
}
```

The worker renews a lease a third of the way in, so a lease no renewal fits
in lapses while your storage still answers: refuse it at boot with
`nest_rs::queue::lease_fits_renewal(lease, answer_bound)`, naming the settings
that lengthen the one or shorten the other, as `renewable` does.

An app running jobs imports `QueueModule::for_root(None)` beside your module;
one only pushing does not. Checkpoint: the worker app's boot logs
`attached module-contributed transport transport="QueueWorker"`.

## Budget and net

The port waits `BACKEND_TIMEOUT` — eighteen seconds — for each call, its net,
then gives up on it. Your client's own budget must answer first, with its
cause, so the binding declares both, and the boot refuses a budget at or past
the net with `BudgetPastNetError`:

```rust title="from nest-rs-redis's connection"
pub(crate) fn netted(
    builder: nest_rs_core::ContainerBuilder,
    port: &'static str,
    net: Duration,
) -> nest_rs_core::ContainerBuilder {
    builder
        .provide_meta(Self::declared_budget())
        .provide_meta(nest_rs_core::Net::over::<Self>(port, net))
}
```

`declared_budget` reads the budget off the connection the app opened, and
`Net::over` names the port in the refusal. Bound each round trip inside that
budget yourself, so an outage reaches the caller as your error rather than
as the port's.

## When the backend fails

The port decides, and your backend returns its error rather than logging it,
so each failure is said once:

- **A push or a cancel** answers the caller your `Err` as it is, a call silent
  past the net as `QueueError::Unanswered`, and a call that panics as
  `QueueError::Panicked`, naming the queue and the call — the panic filed once
  at `error`. Answer your client's failure as an error, never an `unwrap`.
- **A consumer call** that fails, falls silent or panics counts as one that did
  not answer, and the worker makes it again under its backoff; a `settle` only
  while its lease holds, and `prepare` never — it fails the boot.
- **A checkpoint's read or save** that fails fails the attempt, retryably.

## TLS

A client your driver opens verifies its server, with nothing that turns
verification off. Read what it trusts and presents as
`nest_rs::config::ClientTls`, a field of your config read under your own
namespace — `<PREFIX>_<STORAGE>__TLS_CA_CERT`, `__TLS_CERT` and `__TLS_KEY`,
each with its `_FILE` spelling:

```rust title="from nest-rs-redis's config, abridged"
#[config(namespace = "redis")]
#[derive(Clone)]
pub struct RedisConfig {
    // …
    pub tls: ClientTls,
}
// …
    fn from_env(env: &ConfigService, base: Self) -> Result<Self> {
        let connect_timeout = CONNECT_TIMEOUT.read(env, base.connect_timeout)?.value;
        Ok(Self {
            url: resolve_url(env, base.url)?,
            connect_timeout,
            tls: ClientTls::from_env(env, base.tls)?,
        })
    }
```

Before dialling, `ClientTls::check` refuses material no handshake could use,
naming your variables and never quoting the PEM, and `refuse_beside_plaintext`
refuses material beside a URL that does not encrypt, where it would go unused.
Hand your client `authorities_pem()` — the system's authorities, read once,
unless the deployment names others — and `identity_pem()` when a certificate
is set.

## Proof at boot

The connection your driver opens is proved before the app serves, through
`nest_rs::core::prove`: attempt after attempt within the connect budget, on
`Backoff::RECONNECT`'s curve drawn from the process's own seed, so replicas
that lost the server together do not dial it again together:

```rust title="from nest-rs-redis's connection"
pub(crate) async fn proved<T, E, F, Fut>(
    instance: &RedisInstance,
    budget: Duration,
    endpoint: &str,
    seed: u64,
    attempt: F,
) -> Result<T, Unproved<E, RedisError>>
where
    F: FnMut(Duration) -> Fut,
    Fut: Future<Output = Result<T, Attempt<E, RedisError>>>,
    E: std::error::Error + 'static,
{
    prove(
        budget,
        Backoff::RECONNECT,
        seed,
        said(instance, endpoint, budget),
        attempt,
    )
    .await
}
```

Each attempt answers `Attempt::Refused` for what every attempt would meet —
credentials refused, a handshake `ClientTls::negotiation_failed` recognises —
which ends the boot at once with `ClientTls::remedy`'s sentence, and
`Attempt::Failed` for what may clear. `said` reports each retry on your own
target, naming the server by its endpoint, never by a URL carrying a
password.

## Health

Ship the connection's readiness check as a binding module attaching an
`IndicatorEntry` keyed `nestrs_<storage>` — see
[an indicator a module attaches](/health/indicators/#an-indicator-a-module-attaches).
It runs on the readiness and startup probes, never on liveness: an
orchestrator should not restart a pod because the broker blinked.

## Test it

Implement `KitBackend` — an app reaching your storage, the lease it holds
deliveries for, and three hooks on the storage — and let `queue_kit!` write
one test per case:

```rust title="from nest-rs-queue's suite, abridged"
impl KitBackend for MemoryKit {
    const IN_PROCESS: bool = true;

    fn app(&self) -> nest_rs_testing::TestAppBuilder {
        let producer: Arc<dyn JobProducer> = Arc::new(self.memory.clone());
        HeadlessApp::builder()
            .provide(BoundConsumer::new(self.memory.consumer()))
            .provide_dyn(producer)
    }

    fn lease(&self) -> Duration {
        LEASE
    }

    async fn purge(&self, queue: &QueueName) -> anyhow::Result<()> {
        // …
    }

    async fn lapse(&self, queue: &QueueName) -> anyhow::Result<()> {
        // …
    }

    async fn take(&self, queue: &QueueName) -> anyhow::Result<()> {
        // …
    }
}

/// The kit over a backend that files a record due later.
mod delaying {
    use super::MemoryKit;

    nest_rs_testing::queue_kit!(MemoryKit::delaying());
}
```

Your crate reaches the kit through the umbrella, as
`nest_rs::testing::queue_kit!` and `nest_rs::testing::queue::KitBackend`;
`app` starts from `nest_rs::testing::HeadlessApp::builder()`, since a driver's
suite serves no HTTP. `IN_PROCESS` is for a backend living in the test's own
process, whose leases run on paused time; a networked one leaves it `false`.
`purge` empties a queue, `lapse` makes every lease on it lapse with its holder
and count unchanged, and `take` hands every delivery to another holder that
lapses at once — what a frozen worker meets. Checkpoint: twelve tests pass,
among them a worker dying mid-attempt, a lease taken under a running attempt,
the stall limit, the drain and an envelope enqueued twice.

## What fails if you get it wrong

- **A settle that does not check its lease** lets two outcomes land for one job:
  the kit's case for a lease taken under a running attempt fails.
- **A renewal that counts a delivery** spends the stall limit on a job that
  answered every time: once its worker dies after a few renewals, the next
  delivery is past `STALL_LIMIT` and dead-letters it without running.
- **An enqueue filing an envelope whose job it still holds** runs that job
  twice: the kit's case for an envelope enqueued again fails.
- **A receive handing over more than it was asked** keeps no permit for the
  extra: the worker hands them back and says `queue backend handed over more
  deliveries than asked; …` at `error`.
- **A second backend imported** fails the boot, its message ending in
  `BACKEND_REMEDY`.
- **A capability declared and not honoured** passes the boot and fails the kit:
  a delayed push the backend files at once runs before its delay.
