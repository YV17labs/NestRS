import { Aside } from '@astrojs/starlight/components';

The throttler turns a unit of work into "at most N per window, per
caller". One `ThrottlerModule` import provides the in-memory counter (an
`InMemoryThrottler`, a fixed-window store); one
`#[use_guards(ThrottlerGuard)]` binds it wherever a guard binds; one
`#[meta(Throttle::per_minute(10))]` overrides the limit for a single
handler. Over the limit, an HTTP route answers `429 Too Many Requests`
with a `Retry-After` header, and the other edges answer through their own
error frame.

`ThrottlerGuard` checks **all four request-carrying edges**, and each keys
its bucket on the unit that edge addresses joined with the caller it can
see:

| Edge | Bucket |
|---|---|
| HTTP | the matched route's template as registered (`/users/{id}`, one bucket for every id; a surface's too, `/files/{*path}` for every file) + the client's network: its address in IPv4, its `/64` in IPv6 |
| GraphQL | the field name + the caller's actor — an operation carries no client address, but it runs inside the request's scope |
| MCP | the tool's or prompt's name + the caller's actor — the same, carried across the task rmcp spawns for the operation; a tool and a prompt sharing a name share its budget |
| WS | the event name + the connection — the peer that keyed the upgrade is gone by the time a message runs |

That is not a nicety: `/graphql` and `/mcp` run their guards in band, and a
WS message runs after the upgrade's chain returned, so **none of the three
units is reachable from an HTTP-scope binding**. Bind the guard globally *as well*
where those mounts are public, so the request carrying the document, the
session or the upgrade is metered per address too.

The actor is the principal the authentication guard resolved, so one caller
spending the window exhausts their own bucket and nobody else's. An anonymous
operation has none, and every anonymous caller then shares the field's or the
operation's bucket; the guard reports that once per process, at `warn`, as
`rate-limit keying degraded to a shared bucket`. The global binding is what
meters that traffic per address.

On an endpoint `McpAccess::Public` opens, no guard runs at the request, so no
throttler meters its sessions: `<PREFIX>_MCP__LEGACY_SESSION_MODE=false` or a
proxy's limit does.

`#[meta(Throttle::…)]` overrides the module default on every edge — beside a
route, a `#[query]`, a `#[subscribe_message]` or a `#[tool]`, or on its host
for all of them; a unit that pins none counts against `ThrottlerConfig`'s
limit.

Bind it **per route**, or per controller. The app's `GlobalGuards` works and reads
the same `#[meta(Throttle::…)]` — the guard pool runs post-routing, see
[the request lifecycle](/fundamentals/request-lifecycle/) — but it meters
*every* route the pool reaches at the module default, which is a wider
decision than rate limiting usually is.

**A rate limit opens nothing.** It identifies no one, so it covers no unit: a route, a
message or an operation under `ThrottlerGuard` alone says `#[public]` or fails the
boot, which names each. Beside an authentication guard, it needs nothing more.

## Install

```bash frame="terminal"
cargo add nest-rs --features throttler
```

One replica, one counter. Across replicas each process keeps its own, so four
pods let four times the configured rate through — the cross-process store is a
second feature on the same page:

```bash frame="terminal"
cargo add nest-rs --features redis-throttler
```

## Wire it in

The adapter whose controller binds the guard imports the port, as it imports
the module serving its edge:

```rust title="crates/features/src/posts/http/module.rs"
use nest_rs::core::module;
use nest_rs::throttler::ThrottlerModule;

use super::controller::PostsController;
use crate::posts::PostsModule;

#[module(
    imports = [PostsModule, ThrottlerModule],
    providers = [PostsController],
)]
pub struct PostsHttpModule;
```

That import is the whole wiring. It registers the shared store **and** the
`ThrottlerGuard` that reads it, both as global infrastructure — so the guard
resolves from any module that binds it, and nothing goes in a controller
module's `providers`. Listing `ThrottlerGuard` there as well is a duplicate
registration and fails the boot naming it. Several adapters importing it share
one store and one policy, and the app's root imports nothing for them.

A root whose `GlobalGuards` lists the guard binds it too, so it imports
`ThrottlerModule` itself: the pool stays armed whichever adapters the root lists.

The bare import reads `ThrottlerConfig` from `<PREFIX>_THROTTLER__*` over its
defaults (`60` requests per `60s` window), which apply when nothing is set.
`ThrottlerModule::for_root(ThrottlerConfig { .. })`, at the root, pins the limit
in code, superseding the adapters' bare imports —
the pinned value is the base `<PREFIX>_THROTTLER__*` overlays, field by field,
on the same dual-path rule the rest of the framework follows. The limit runs from
`1` to a billion requests per window and the window from a second to a day, and a
value outside either range fails the boot naming its variable.

```bash frame="terminal"
NESTRS_THROTTLER__LIMIT=120
NESTRS_THROTTLER__WINDOW_SECS=60
# Not a throttler setting — the transport's, shared with `ClientIp`.
NESTRS_HTTP__TRUSTED_PROXIES=10.0.0.1,10.0.0.2
```

## Guard a controller

```rust title="crates/features/src/posts/http/controller.rs"
use nest_rs::http::controller;
use nest_rs::throttler::ThrottlerGuard;

#[controller(path = "/posts")]
#[use_guards(AuthnGuard, ThrottlerGuard)]
pub struct PostsController { /* … */ }
```

Every route on this controller now goes through the throttler. The
default limit applies unless a handler overrides it. Each route's
[OpenAPI document](/openapi/) lists its `429` and the `Retry-After` it
carries, wherever the guard is bound — the controller, the route, an alias,
the global pool — `#[public]` routes included.

## Override per route

```rust title="crates/features/src/posts/http/controller.rs"
use nest_rs::http::{controller, routes};
use nest_rs::throttler::{Throttle, ThrottlerGuard};
use nest_rs::http::Json;

#[controller(path = "/posts")]
#[use_guards(AuthnGuard, ThrottlerGuard)]
pub struct PostsController { /* … */ }

#[routes]
impl PostsController {
    #[post("/")]
    #[meta(Throttle::per_minute(10))]
    async fn create(&self, /* … */) -> Result<Json<Post>> { /* … */ }

    #[get("/")]
    async fn list(&self, /* … */) -> Result<Json<Vec<Post>>> { /* … */ }
}
```

`#[meta]` attaches the limit to the route; the guard reads it back through
`cx.reflector()` at request time. `create` is capped at 10/min; `list`
inherits the module default. Forms:

| Form                                | Meaning                          |
|-------------------------------------|----------------------------------|
| `Throttle::per_second(n)`           | `n` requests per second          |
| `Throttle::per_minute(n)`           | `n` requests per minute          |
| `Throttle::new(n, Duration::from_secs(s))` | `n` requests per `s` seconds |

A window must count something: `Throttle::new` refuses one under a
millisecond — the Redis store's resolution — which in a `const` is a compile
error and in `#[meta]` fails the boot at the route. A zero window reset every
bucket on every hit, so the limiter let everything through at any limit.
`<PREFIX>_THROTTLER__WINDOW_SECS=0`, or a pinned `window: Duration::ZERO`, fails the
boot naming the variable for the same reason.

## What "per client" means

The client key is the **direct peer IP** by default — every request
coming from the same IP shares the same window. If the request arrives
through a reverse proxy you have listed in
`<PREFIX>_HTTP__TRUSTED_PROXIES`, the throttler reads the **rightmost** hop that
is not itself a trusted proxy — from `Forwarded` (RFC 7239), else
`X-Forwarded-For`, else `X-Real-IP` — and counts that as the client.

**Rightmost, not leftmost** — and the difference is the whole defence. A proxy
*appends* the address it received the request from to the right of the chain,
so the genuine client is the last hop your infrastructure wrote. A caller can
only *prepend*, and a prepended entry lands to the **left** of the genuine one:
it can neither mint a fresh bucket by rotating a value nor drain a victim's by
forging theirs. Keying on the leftmost hop is exactly the spoofable rule this
avoids — if you reproduce this keying anywhere else, reproduce it in this
direction.

The rest of the rule:

- A forwarding header from a peer that is **not** a listed proxy is
  **ignored** — a direct client cannot bypass its own bucket by setting one.
- A chain over several field lines is one list, in order: a proxy may add its
  own line after the caller's (RFC 7239 §4), and that line stays the rightmost.
  `X-Real-IP` names one hop, so its last line is the one read.
- A chain is read whole or not at all. A hop that is no address, bytes no text
  holds or a quote no quote closes make the header unreadable, and a node the
  proxy withheld (`unknown`) where the client stands names nobody: either way the
  request counts against the proxy's own bucket, whatever the other headers say,
  so no hop a caller wrote becomes its key. `X-Real-IP`, one hop in no order, is
  read only where neither chain names a client, and refused the same way there.
- An entry of `TRUSTED_PROXIES` that is no address or CIDR range, a `/0`, or a
  range with address bits set past its prefix (`10.0.0.1/8`), **aborts the boot**
  naming the variable and the entry's place in the list, never its value — never
  a silent skip — and so do ranges holding between them every address of a family
  a caller connects from (`0.0.0.0/1,128.0.0.0/1`, or
  `0.0.0.0/1,128.0.0.0/2,192.0.0.0/3`, short only of multicast and reserved
  space), a `/0` in all but name.
- A request with no peer addr (synthetic, in-process) is counted
  against a literal `"global"` bucket.

**The bucket is the client's network, not its exact address.** An IPv4 client
counts under its address (`/32`). An IPv6 client counts under its `/64`, the
link its host's addresses share (RFC 4291 §2.5.4): a host chooses the other 64
bits itself and rotates them (RFC 8981), so keyed on the address it would get a
fresh bucket with each one. An IPv4 client that a dual-stack listener reports as
`::ffff:203.0.113.7` counts as `203.0.113.7`. The cost is that every host on one
IPv6 link shares a bucket, the way every host behind one IPv4 NAT already does.

The list is `<PREFIX>_HTTP__TRUSTED_PROXIES`, on the transport, not on the
throttler: which proxies a deployment believes decides who *every* request is
attributed to — the [`ClientIp`](/http/extractors/) extractor's answer as much
as the rate-limit bucket's. One list, so the extractor and the bucket can never
attribute a request to different callers. No log line names that caller: the
refusal's line — `guard denied the request` on `nest_rs::throttler`, `reason =
"limit_exceeded"` — carries the route template the route declares and the
wait, never the path a client sent, and a client's address is personal data a
line does not hold.

<Aside type="caution">
Trust the proxy header **only** when the request arrived through a
proxy you control. Production behind an ingress: list its addresses, or the
range its pods move within. Direct exposure: leave `TRUSTED_PROXIES` empty.
</Aside>

## Run it

This is what an over-limit response looks like — the eleventh call
in a minute, against the default window:

```bash frame="terminal"
$ for i in {1..11}; do
    curl -s -o /dev/null -w "%{http_code} retry=%{header.retry-after}s\n" \
      -X POST http://localhost:3002/posts -H "Authorization: Bearer $TOKEN" -d '{...}'
  done
200 retry=s
200 retry=s
… (8 more 200s)
429 retry=47s
```

`Retry-After` is the time until the window resets — clients respecting
it back off cleanly and resume on the same window.

## Alternative stores — Redis, and anywhere else

The counter sits behind a **`ThrottlerStore`** trait. `InMemoryThrottler`
(fixed-window, process-local) ships with the module and covers a single
replica. Across replicas each process would keep its own counter, so an app on
four pods lets four times the configured rate through — which is why the
cross-process store ships too.

### Redis, shipped

Enable it at the top of this page, then:

```rust title="apps/api/src/module.rs"
use nest_rs::core::module;
use nest_rs::redis::RedisThrottlerModule;

use features::posts::PostsHttpModule;

#[module(imports = [
    PostsHttpModule,
    RedisThrottlerModule,
])]
pub struct ApiModule;
```

One line, at the root. `ThrottlerModule`, which the adapter imports, stays
exactly as it was: it owns the policy (`<PREFIX>_THROTTLER__*` — the limit and the window are the
throttler's whatever store counts them) and the `ThrottlerGuard` that applies it.
`RedisThrottlerModule` is a bare import that *declares* `RedisThrottler` as the
`dyn ThrottlerStore`, which supersedes the port's in-process default wherever
the two fall in the app's imports; it imports the `RedisModule` opening its
connection (`<PREFIX>_REDIS__URL`), and an app that also queues shares that one
`RedisConnection` with its producer. You add a line to move the counters off-process and remove none. A
second vendor binding beside it is a named boot failure, never a silent
last-one-wins.

**Redis never holds a client.** A bucket's subject — the route and the client's
address, the field and the actor — is personal data, and Redis keeps what it
counts where a replica, a backup or a `SCAN` reads it. So a store whose counters
leave the process counts each bucket under a pseudonym: the first 128 bits of an
HMAC-SHA256 of its subject, in hex (`nestrs:throttler:buckets:3f9c…`), keyed by
`<PREFIX>_THROTTLER__PSEUDONYM_KEY`. Set it to the same 32 bytes or more on every
replica, as a secret:

```bash frame="terminal"
NESTRS_THROTTLER__PSEUDONYM_KEY_FILE=/run/secrets/throttler-pseudonym-key   # openssl rand -base64 32
```

Without it the boot refuses, naming the store and the variable: replicas keyed
apart would each count their own buckets in the shared store. Changing it starts
every bucket afresh, which costs a window at most. A key under 32 bytes is
refused too, without being repeated — HMAC-SHA256's key is as strong as its
length up to the hash's size (RFC 2104 §3).

The counter is one Lua script — `INCR`, read the TTL with `PTTL`, set it with
`PEXPIRE` on the first hit — so it is atomic across replicas with no
check-then-act race. A window in its last millisecond, whose TTL Redis answers
`0`, has ended: the script deletes it with `PEXPIRE … 0`, so that hit opens the
next window, as it would in process. A backend failure
**denies**: a rate limiter that fails open is not a rate limiter. The store
answers Redis's error and the guard refuses the caller, as it does for any store
that cannot count (below). Each command is bounded by the connection's budget
(`<PREFIX>_REDIS__CONNECT_TIMEOUT_SECS`, 10 s by default), well inside the guard's
own bound — the boot refuses a budget at or past it — so an outage reaches the
guard's line as Redis's own error, with its cause.

The script is sent as `EVALSHA`, with a `SCRIPT LOAD` the first time Redis has not
cached it, and Redis checks the commands *inside* it against the caller's ACL as
well. With the connection's `PING`, which proves it at boot, and the `SELECT` of the
database its URL names, a Redis user for the rate limiter is this rule and nothing
more:

```text title="Redis ACL — rate limiter"
ACL SETUSER <user> reset on ><password> ~nestrs:throttler:* +ping +select +evalsha +script|load +incr +pttl +pexpire
```

Under Sentinel and on a Cluster, the rule is created on every node and takes
what its topology's connection adds — see
[ACL on Sentinel and Cluster](/queue/topologies/#acl-on-sentinel-and-cluster).

An app that also queues or fires scheduled jobs once gives the same user
[the queue's](/queue/delivery/#where-a-queue-lives) and
[the schedule's](/schedule/#the-keys) rules as well.

**The server runs `maxmemory-policy noeviction`.** A window carries an expiry, so
a `volatile-*` or `allkeys-*` policy may evict a full one once the server reaches
its `maxmemory`, and the next hit opens a fresh window: the client it denied gets
through. The boot cannot read the policy, so it is the deployment's to set, for
every binding the server holds — see [Eviction](/queue/topologies/#eviction).

### Your own store

Any store that can count a window implements `ThrottlerStore` and binds it the
way `RedisThrottlerModule` does: the contract, its binding, the net it answers
under and why its failure always denies are on
[Writing a rate-limit store](/rate-limiting/writing-a-store/).
