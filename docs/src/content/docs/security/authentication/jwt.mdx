JSON Web Tokens are the framework's default bearer credential.
`JwtStrategy<C>` is generic over the claims type — your app picks the
shape, the framework verifies the signature, checks expiry, and hands
the claims to the handler. Signing and verifying both run through
`JwtService`, configured once via `AuthnConfig` and injected wherever a
token is minted.

The implementation is a thin wrapper over
[`jsonwebtoken`](https://docs.rs/jsonwebtoken), which your code never names:
the algorithms are nestrs's own `Algorithm`, spelled as RFC 7518 spells
`alg` — `RS256`, `ES256`, `EdDSA` — so a release of the library reaches you
in a nestrs minor.

## The three-line setup

A resource-server app declares a type alias and a tiny module:

```rust title="crates/features/src/authn/strategy.rs (from the demo)"
use nest_rs::authn::JwtStrategy;

use super::Claims;

pub type AuthnStrategy = JwtStrategy<Claims>;

pub type AuthnGuard = nest_rs::authn::AuthnGuard<AuthnStrategy>;
```

```rust title="crates/features/src/authn/module.rs (from the demo)"
use nest_rs::core::module;

use super::strategy::{AuthnGuard, AuthnStrategy};

#[module(
    imports = [nest_rs::authn::AuthnModule],
    providers = [AuthnStrategy, AuthnGuard],
)]
pub struct AuthnModule;
```

`AuthnModule` reads `AuthnConfig` from the environment;
pass an `AuthnConfig` to pin it in code. The factory phase builds
`JwtService` once and registers it as global infrastructure —
controllers, login services, OAuth flows all inject the same instance.

One env var makes it work end to end — a shared HS256 secret (32 bytes
minimum; anything shorter fails the boot):

```bash frame="terminal"
export NESTRS_AUTHN__SECRET="$(openssl rand -hex 32)"
```

With that set, `JwtService` signs and verifies against the same
secret: `AuthnGuard` returns a 401 without a valid
`Authorization: Bearer` token and attaches the claims otherwise.
Every other knob is optional — the full env table and the
HS256-vs-EdDSA decision come [later on this page](#configuration).

## What `JwtStrategy` does

`JwtStrategy<C>` is an `#[injectable]` over an `Arc<JwtService>` and a
`PhantomData<C>`. On each request it:

1. Pulls `Authorization: Bearer <token>` out of the headers via
   `bearer_token`.
2. Calls `JwtService::verify::<C>(token)` to verify the signature,
   check `exp` / `nbf`, and deserialize the claims.
3. Returns `Ok(claims)` on success.

A missing header yields `AuthError::MissingCredentials`; a bad
signature yields `AuthError::InvalidSignature`; an expired token
yields `AuthError::Expired`. `AuthnGuard` maps every variant to a 401
with `WWW-Authenticate: Bearer`.

## Claims — your shape, your business rules

The framework's `JwtStrategy<C>` is generic. `C` is any
`DeserializeOwned + PrincipalIdentity + AmbientValue + Clone` type — usually a
struct with the standard `sub` plus whatever your app needs, which derives the
two traits. `exp` is the signer's, so the struct needs no field for it:

```rust title="crates/features/src/authn/claims.rs"
use nest_rs::authn::PrincipalIdentity;
use serde::{Deserialize, Serialize};
use uuid::Uuid;

#[derive(Clone, Debug, PartialEq, Eq, Serialize, Deserialize)]
#[serde(from = "String", into = "String")]
pub enum Subject {
    User(Uuid),
    Client(String),
}
// …

#[derive(Clone, Debug, Serialize, Deserialize, PrincipalIdentity)]
pub struct Claims {
    #[principal(actor)]
    pub sub: Subject,
    #[principal(tenant)]
    pub org_id: Uuid,
    pub roles: Vec<Role>,
}
```

`#[derive(PrincipalIdentity)]` reads each role off the field marked for it.
`#[principal(actor)]` is the audit identity: on a successful authentication
`AuthnGuard` records it as `actor_id` onto the request span, so every
downstream event — denials included — is attributable without threading the
identity through each call site. `#[principal(tenant)]` is the tenant the
caller acts within, made ambient for the request and every job it pushes
([Multi-tenant SaaS](/security/multi-tenant-saas/)), and `#[principal(scopes)]`
the token's `scope` claim ([Scopes](/security/authorization/scopes/)); both are
optional. An actor or a tenant is read as the text its value prints, so a
`Uuid`, a `String` or an enum with its `Display` all serve, and an `Option`
answers `None` when it holds none. The derive also implements `AmbientValue`,
which is what lets `AuthnGuard` attach the claims for the rest of the request —
every guard after it, and `Ambient<Claims>` in a handler on any edge, a resolver
below `/graphql` included, read them there. Claims marking no actor, or a role
the derive does not know, are a compile error naming the three roles it takes;
a role marked twice is refused at its second mark. A generic principal, or one
narrowing what it carries, writes the two impls by hand.

Every access token names its subject: RFC 9068 §2.2 requires `sub`, the user's
id, or the client's own when it acts on its own behalf (the
`client_credentials` grant). So `sub` is never optional, a token without one is
refused before any route, and `actor_id` always returns it — which is what an
[MCP session](/mcp/configuration/#a-session-belongs-to-the-principal-that-opened-it)
binds to. `Subject` keeps the two kinds apart: one string on the wire, read
back by its shape, a UUID being a user. The registry of your clients therefore
refuses a client id a UUID parses, so no client passes for a user (RFC 9068
§5): with `nest_rs::oauth::server`, a module-init hook of yours over
`OAuthServerConfig`, since the scheme reading a subject is yours
([OAuth 2.0](/security/authentication/oauth2/#the-registry-is-the-frameworks-the-policy-yours)).
A route writing a user's row reads `claims.sub.user_id()`, which a client
answers with `None`. `nestrs g auth` writes the enum, its conversions
and the struct with its derive.

The handler reads them back through `Ambient<Claims>`:

```rust title="crates/features/src/users/http/controller.rs"
async fn caller_org(&self, auth: Ambient<Claims>) -> Json<Uuid> {
    Json(auth.org_id)
}
```

A create needs no `Ambient<Claims>` to land in the caller's org: the `Create` grant
that pins `org_id` also fills it ([CRUD](/database/crud/#the-tenant-comes-from-the-grant)).

## Signing a token

A login or OAuth callback injects `Arc<JwtService>` and calls `sign`:

```rust title="crates/features/src/authn/service.rs"
let claims = Claims {
    sub: Subject::User(user.id),
    org_id: user.org_id,
    roles: user.roles.clone(),
};
let token = self.jwt.sign(&claims)?;
```

`sign` is `Result<String, SignError>`. A token this server cannot mint — a
verify-only service, EdDSA with no private key or a JWK Set, is the one you will
meet — is the server's failure, never the caller's: `?` in a route answers the
opaque `500` and files the chain at `error`, where a `401` would send a client off
for another credential, and a handler returning it on another edge answers as
opaquely. A handler has nothing to add. A service holds it as a `#[from]` variant
of its own error, and a token endpoint's `TokenError` already does. It does not convert into `AuthError`, whose every answer speaks of the
credential: a login handler `?`-ing both answers `nest_rs::http::Result`, into which
each converts on its own status.
`ttl_secs()` is the token's lifetime, `JwtOptions::expires_in` (default one
hour), so the issuer can return it alongside the token.

[RFC 9068 §2.2](https://datatracker.ietf.org/doc/html/rfc9068#section-2.2)
lists the claims every JWT access token carries, and `sign` writes the ones
only the signer knows: `iat`, the time it signs; `exp`, its lifetime after
that; `jti`, an identifier no other token shares; and the `aud` and `iss` you
configured. Your claims name the rest — `sub`, and the `client_id` of the
OAuth client the token is issued to — and a claim they already carry is kept
as written: an `exp` of their own outlives or undercuts the signer's.

`sub` is held by the type. `sign` and `sign_for` take a `PrincipalIdentity`, the
derive your claims already carry for the guard, and a type without it does not
compile. A claims type holding its subject under another name, or a `sub` that is
blank, is stamped its `#[principal(actor)]` as `sub`; one naming no subject at all,
its actor `None` or blank, mints nothing and answers the `SignError` above. So does
a `sub` that is no string, since
[RFC 7519 §4.1.2](https://datatracker.ietf.org/doc/html/rfc7519#section-4.1.2) makes
it one and a verifier reading one refuses anything else: an integer id is written as
its decimal string, which `#[principal(actor)]` on a field of another name does for
you. A test forging such a token, to prove your verifier refuses it, hands it to
[`TestApp::bearer`](/tutorial/testing/), which signs what it is given.

Every claim the specifications register is held the same way, the `SignError`
naming it: `iss`, `jti`, `client_id` and `acr` are strings; `exp`, `nbf`, `iat` and
`auth_time` are NumericDates, a JSON number of seconds since the epoch; `aud` is a
string or an array of them, `amr` an array of strings, and `scope` the list RFC 6749
§3.3 writes, scope tokens each separated by one space, or empty when the token grants
none. A registered claim your claims serialize as `null` is left out of the token.

`client_id`, which RFC 9068 §2.2 requires too, is your claims' to name: `sign`
supplies none, and a token whose claims name none goes out without it. The demo's
claims hold it as a `String`, so no literal leaves it out. A machine token names the
client that authenticated at `/token`; a user's, from `/login` or the social callback,
names the first-party client the sign-in serves, `<PREFIX>_SIGN_IN__CLIENT_ID`
(`publish-web` by default), which the boot refuses any registered client to hold. An
authorization-code grant by that client (RFC 6749 §4.1, with PKCE) would have it
identify itself, where the deployment names it here.

`sign_handshake`, for a flow's short-lived token, stamps the same but `exp`:
its claims name their lifetime with `expiry_in(secs)`, and claims naming none
are refused rather than given the access token's.

`sign` mints a token for this app itself: its `aud` is this app's own
audience, the one its verifier requires. An issuer minting a token another app
will verify names that app instead, with `sign_for`:

```rust title="crates/features/src/sign_in/service.rs"
let token = self.jwt.sign_for("https://api.example.com", &claims)?;
```

The resource becomes the token's `aud` and nothing else does, so only the app
serving it accepts the token — the one a client asked for in the
[RFC 8707](https://datatracker.ietf.org/doc/html/rfc8707) `resource` parameter
of its token request ([OAuth2](/security/authentication/oauth2/#the-request)).
A token for one resource replayed at another is refused there. `sign_for`
refuses a blank resource, and claims carrying an `aud` of their own.

## Verifying outside the guard

Most code reaches the claims through `Ambient<C>`. A path that needs to
verify an access token manually — say, a queue job carrying a signed envelope —
injects `Arc<JwtService>` and calls `verify`, which refuses a handshake token such as
the OAuth transaction cookie; that one takes `verify_handshake`:

```rust title="crates/features/src/authn/service.rs"
let claims: Claims = self.jwt.verify(token).await?;
```

`verify` is `async` because a JWK Set may have to be fetched first; against a
secret or a PEM key it never waits. The verification path runs `Validation::leeway`, checks `nbf`, and
applies RFC 7519 §4.1.3 to `aud` **always**: a token carrying an audience
this service is not named in is rejected whether or not
`AuthnConfig::audience` is set. Setting it adds the other direction — the
claim becomes mandatory, so a token omitting `aud` is rejected too. A token its
issuer bound to a key, carrying `cnf`, is refused as `AuthError::SenderConstrained`:
`verify` reads a bearer token, which proves no key
([Split deployment](/security/authentication/split-deployment/)).
Verification failures here log at `tracing::debug!` under `nest_rs::authn`,
carrying the typed decode reason — and an *expired* token logs nothing at all.
Both follow from "one event, said once": the single `warn` for an
authentication failure is the guard's, which has the strategy and the route to
name, so a second line from the service would double-count every denial.

## Configuration

`AuthnConfig` follows the framework-wide dual-path rule: every field is
settable from `<PREFIX>_AUTHN__*` env vars **or** from a pinned struct
passed to `AuthnModule::for_root(config)`.

| Field | Env var | Notes |
|-------|---------|-------|
| `secret` | `<PREFIX>_AUTHN__SECRET` | HS256 shared secret |
| `private_key` | `<PREFIX>_AUTHN__PRIVATE_KEY`, or a path in `<PREFIX>_AUTHN__PRIVATE_KEY_FILE` | EdDSA PEM, issuer only |
| `public_key` | `<PREFIX>_AUTHN__PUBLIC_KEY`, or a path in `<PREFIX>_AUTHN__PUBLIC_KEY_FILE` | EdDSA PEM, verifier needs it |
| `jwks_uri` | `<PREFIX>_AUTHN__JWKS_URI` | An external issuer's JWK Set, `https` only — verify-only, see [below](#verifying-another-issuers-tokens) |
| `algorithms` | `<PREFIX>_AUTHN__ALGORITHMS` | Comma-separated JOSE names (`EdDSA,RS256`), each a `nest_rs::authn::Algorithm` — `HS256`, `HS384`, `HS512`, `RS256`, `RS384`, `RS512`, `PS256`, `PS384`, `PS512`, `ES256`, `ES384` or `EdDSA`, case and all. Unset: HS256 for a secret, EdDSA for a PEM key, every asymmetric algorithm for a JWK Set. A secret or a PEM key takes exactly one, which must fit it |
| `tls` | `<PREFIX>_AUTHN__TLS_CA_CERT`, `<PREFIX>_AUTHN__TLS_CERT` and `<PREFIX>_AUTHN__TLS_KEY`, each or a path in its `_FILE` spelling | A `nest_rs::config::ClientTls`: the PEM authorities the JWK Set endpoint's certificate chains to, replacing the system's, and the client certificate presented to an endpoint that requires one. Without `jwks_uri`, fails the boot |
| `leeway` | `<PREFIX>_AUTHN__LEEWAY_SECS` | Clock skew, default 30 s, at most 300 s — RFC 7519 §4.1.4's "a few minutes" |
| `audience` | `<PREFIX>_AUTHN__AUDIENCE` | The `aud` this app requires — set makes it mandatory; unset still refuses a foreign `aud`. Stamped by `sign`, never by `sign_for`. Under `OAuthResourceModule`, unset is the resource |
| `issuer` | `<PREFIX>_AUTHN__ISSUER` | `iss` claim, stamped on every token this app mints — set makes it mandatory; unset means no issuer check (§4.1.1 states no rejection clause), but under `OAuthResourceModule` a token's `iss` must be one of its authorization servers |
| `expires_in` | `<PREFIX>_AUTHN__EXPIRES_IN_SECS` | Minted-token lifetime, default an hour, from 1 second to thirty days. Outside it — from the environment, a pinned `AuthnConfig` or a `JwtOptions` built in code — the boot fails naming the variable |
| `explicit_typing` | `<PREFIX>_AUTHN__EXPLICIT_TYPING` | RFC 9068 §2.1/§4 — stamp and require `typ: at+jwt`, default `true`. Turn off only for an issuer minting a plain `typ: JWT`, or no `typ` |
| `allow_any_audience` | `<PREFIX>_AUTHN__ALLOW_ANY_AUDIENCE` | Opt out of §4.1.3, default `false`. Refused beside `audience` and beside `OAuthResourceModule`; `warn`s once per boot |

`AuthnConfig::into_options` walks the four key fields and chooses a
mode:

- `private_key` + `public_key` → EdDSA (sign and verify). The two are proved
  one pair at boot: a signature the private key makes has to verify under the
  public key.
- `public_key` alone → EdDSA verify-only — a resource server with no
  private key cannot mint a token even if it wanted to.
- `secret` alone → HMAC HS256 (both sign and verify).
- `jwks_uri` alone → verify-only, against the keys an external issuer
  publishes.
- nothing → boot fails with `"no JWT key configured"`.

Each field is read on its own, like every other setting, and the combination
is then judged whole. A `secret` beside either key fails the boot — two signing
modes, and nothing says which one is meant — whether both come from the
environment, from `.env`, from code, or the environment beside code. A config
pinned in code stops `.env` being read for this namespace, so a `.env` value
never meets a pinned one. A `jwks_uri` beside a secret or a key fails the boot
the same way. A `private_key` without its `public_key` fails the
boot too, and so does key material that does not parse as EdDSA PEM, a
`jwks_uri` that is not `https`, and an `algorithms` entry that does not fit the
key. Each refusal names the settings that are set.

## HS256, EdDSA or a JWK Set — pick on deployment shape

**HS256** is fine when one binary both issues and verifies tokens.
Symmetric — anyone with the secret can mint a token. Convenient for
local development and single-process apps. Set
`<PREFIX>_AUTHN__SECRET`.

**EdDSA** is the production posture for split deployments. The issuer
holds the private PEM; every resource server holds the public PEM
only. Even a compromised resource server cannot mint a token. The
issuer sets both `PRIVATE_KEY` and `PUBLIC_KEY`; verifiers set only
`PUBLIC_KEY`.

See [Split deployment](/security/authentication/split-deployment/)
for the deployment pattern.

**A JWK Set** is the posture when someone else issues the tokens — an
identity provider you run beside the API or buy as a service. The resource
server holds no key at all: it reads the ones the issuer publishes, and picks
up a rotation on its own. Set `<PREFIX>_AUTHN__JWKS_URI`; the
[next section](#verifying-another-issuers-tokens) says what it checks.

```bash
# generate an EdDSA key pair
openssl genpkey -algorithm ed25519 -out jwt.pem
openssl pkey -in jwt.pem -pubout -out jwt.pub
```

<Aside type="caution">
A short `ttl` is the first defense against token replay. The
framework leaves the duration to your app — `JwtOptions::expires_in`
defaults to one hour. Pair short access tokens with a refresh-token
endpoint when the UX demands long sessions. See
[Threat model](/security/threat-model/) for what JWT does and does
not catch.
</Aside>

## Verifying another issuer's tokens

When an identity provider you do not run issues the tokens — better-auth,
Keycloak, Auth0, Cognito, Entra ID, Google, Firebase, Clerk, Zitadel — point
the resource server at the JWK Set
([RFC 7517](https://datatracker.ietf.org/doc/html/rfc7517)) it publishes, the
`jwks_uri` of its discovery document:

```bash frame="terminal"
export NESTRS_AUTHN__JWKS_URI='https://auth.example.com/.well-known/jwks.json'
export NESTRS_AUTHN__ISSUER='https://auth.example.com'
export NESTRS_AUTHN__AUDIENCE='https://api.example.com'
```

Nothing else changes: `JwtStrategy` verifies, the claims reach `Ambient<C>`,
`iss`, `aud` and `exp` are checked as above. The service holds no signing key,
so `sign` refuses, and so do `sign_handshake` and `verify_handshake`: an OAuth
flow's transaction cookie needs a key of this deployment's own. An issuer that stamps no `typ: at+jwt` on its access tokens
also needs `<PREFIX>_AUTHN__EXPLICIT_TYPING=false` — read one token's header to
know. [External identity provider](/security/authentication/external-identity-provider/)
walks the whole setup with better-auth.

**What a token may be signed with is the verifier's choice, never the
token's** ([RFC 8725 §3.1](https://datatracker.ietf.org/doc/html/rfc8725#section-3.1)).
Each key checks only an algorithm of its own type — an RSA key RS256 to RS512
and PS256 to PS512, an EC P-256 key ES256, P-384 ES384, Ed25519 EdDSA — and
only the `alg` it names when it names one. A key published with a `use` other
than `sig` is ignored. No `HS*` or `none` token is ever accepted against a
JWK Set, and such a token is refused before the set is fetched.
`<PREFIX>_AUTHN__ALGORITHMS` narrows the list to what your issuer signs with —
`EdDSA`, `RS256` — which also binds a key published without `alg` to that one
algorithm.

The token's `kid` picks the key. A token naming no `kid` is checked only when
exactly one key of the set fits its algorithm, never tried against each.

**The set is fetched when the first token needs it**, not at boot: an issuer
down while the API deploys does not crash-loop the API. Tokens arriving during
a fetch wait for that one fetch; a `kid` the set lacks earns one more, so a
rotation is picked up with the first token signed by the new key. The bounds
are constants of `nest_rs::authn`:

| Constant | Value | What it bounds |
|---|---|---|
| `JWKS_FETCH_TIMEOUT` | 5 s (3 s to connect) | one fetch, body included — a token waits on one at most |
| `JWKS_MAX_BYTES` | 128 KiB | the document read; a longer one is refused unread |
| `JWKS_REFRESH_FLOOR` | 30 s | the least time between two fetches, whatever asks — a flood of forged `kid`s costs the issuer one request per floor |
| `JWKS_DEFAULT_MAX_AGE` | 10 min | how long a set stays fresh when the answer states no `Cache-Control: max-age`; a stated one is honoured, net of `Age`, from the floor to `JWKS_MAX_AGE_CEILING` (1 h) |
| `JWKS_STALE_CEILING` | 1 h | how long past its freshness the last good set still verifies while every refresh fails |

A stale set keeps serving while it refreshes, and a refresh that fails is said
once at `warn` on `nest_rs::authn` while the last good set is kept. A set that
cannot be had — never fetched, past its stale ceiling, or failing while the
key a token names is looked for — answers `503` with `Retry-After`, on a
`#[public]` route too, never a `401`: the token was never checked. The
endpoint must be `https`, and its certificate is verified against the system's
authorities, or the ones `<PREFIX>_AUTHN__TLS_CA_CERT` names; an issuer that
requires a client certificate gets the one `<PREFIX>_AUTHN__TLS_CERT` and
`<PREFIX>_AUTHN__TLS_KEY` name, read at the start: a renewed file takes effect
at the next one, so rotate it with a rolling restart. A handshake that fails
answers that same opaque `503`, while the line the edge files for it — `guard
denied the request` on `nest_rs::authn`, at `warn` — names the setting that
fixes it in its `error` chain; the fetch follows no redirect.
