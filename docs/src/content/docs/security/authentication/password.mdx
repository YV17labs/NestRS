A password-login service does three things: store a hash on signup,
compare it on signin, and refuse a login without telling the attacker
whether the email exists. The framework ships three small helpers
that cover the cryptography and the timing-attack mitigation —
everything else (lockouts, registration policy, mailers) belongs to
your service.

The helpers wrap the [`argon2`](https://docs.rs/argon2) crate at a
**pinned** work factor — Argon2id, m = 19 MiB, t = 2, p = 1, the OWASP
Password Storage Cheat Sheet's recommendation — rather than riding the
crate's defaults, which an upstream release could lower without a line
changing here.

## Three functions

```rust title="crates/features/src/users/service.rs"
use nest_rs::authn::{hash_password, verify_password, burn_verify};

let hash: String = hash_password("hunter2")?;
let ok: bool = verify_password(&hash, "hunter2")?;
burn_verify("anything"); // runs a verify against a dummy hash
```

| Function | Returns | Use |
|----------|---------|-----|
| `hash_password(&str)` | `Result<String, PasswordError>` | Store this string on signup |
| `verify_password(&hash, &str)` | `Result<bool, PasswordError>` | Compare on signin |
| `burn_verify(&str)` | `()` | Run on the miss path so timing matches |

`hash_password` draws a fresh 16-byte salt from the system CSPRNG on every
call — the PHC specification's recommended length — so you never reuse a
salt and never store one separately. The returned string encodes the
PHC-format hash, salt, and parameters in one self-describing column, and
`verify_password` reads the parameters back out of it: moving the pinned
work factor never invalidates a credential already stored.

## Signup — hash then store

```rust title="crates/features/src/users/service.rs (from the demo, abridged)"
use nest_rs::authn::{AuthError, CredentialError, burn_verify, hash_password, verify_password};
// …

pub(crate) fn prepare_new_user(
    input: CreateUser,
    org_id: Uuid,
    password: Option<&str>,
) -> Result<entity::ActiveModel, ServiceError> {
    input.validate()?;
    let password_hash = match password {
        Some(plain) => Some(
            hash_password(plain)
                .map_err(|e| ServiceError::internal(format!("password hashing failed: {e}")))?,
        ),
        None => None,
    };
    Ok(active_for_new_user(input, org_id, password_hash))
}
```

Validation runs first, so a malformed signup never pays for a hash. A failed
hash is `ServiceError::internal` — a `500` whose detail stays in the trace
while the wire carries a constant message.

## Signin — burn on every miss path

The naïve signin path leaks existence: an absent email returns in
microseconds, a present one takes ~50ms to hash and compare. An
attacker probes the timing and enumerates the user base.

`burn_verify` runs a real Argon2 verify against a static dummy hash so
every miss path takes the same wall-clock time as a real verify:

```rust title="crates/features/src/users/service.rs (from the demo)"
pub(crate) fn verify_credentials(
    email: &str,
    user: Option<entity::Model>,
    password: &str,
) -> Result<entity::Model, CredentialError> {
    let Some(user) = user else {
        burn_verify(password);
        tracing::warn!(target: crate::users::TARGET, identity = %redact_email(email), reason = "unknown_email", "login failed");
        return Err(CredentialError);
    };

    let Some(ref hash) = user.password_hash else {
        burn_verify(password);
        tracing::warn!(target: crate::users::TARGET, identity = %redact_email(email), reason = "no_password_set", "login failed");
        return Err(CredentialError);
    };

    match verify_password(hash, password) {
        Ok(true) => Ok(user),
        Ok(false) => {
            tracing::warn!(target: crate::users::TARGET, identity = %redact_email(email), reason = "bad_password", "login failed");
            Err(CredentialError)
        }
        Err(e) => {
            tracing::error!(target: crate::users::TARGET, identity = %redact_email(email), error = %error_message(&e), reason = "unverifiable_hash", "login failed");
            Err(CredentialError)
        }
    }
}
```

Four things in that snippet are the rule rather than the style, and each
was a defect before it was a habit:

- **`verify_password` is matched, never `unwrap_or(false)`.** A stored
  hash that cannot be parsed is not a wrong password — folding the two
  loses the `error` event and reports a broken record as an ordinary
  miss.
- **The target is `features::users`, not `nest_rs::authn`.** A span
  target names the crate that *emitted* the event; app code writing a
  framework target makes the event unattributable.
- **The email is redacted.** It is a `warn`+ security event, so the raw
  address would be PII in exactly the log an incident query reads.
- **Every line carries a `reason`.** Three identical `"login failed"`
  warns tell an operator nothing about which path fired.

Three miss paths, three calls — none distinguishable from the wire:

- No user with that email → `burn_verify`, return `CredentialError`.
- User found but no `password_hash` (OAuth-only account) →
  `burn_verify`, return `CredentialError`.
- Hash exists, password wrong → `verify_password` already ran (real
  Argon2 work), return `CredentialError`.

The dummy hash is computed once and cached in a `OnceLock` so the
first burn pays the hash cost and every subsequent burn reuses it.

<Aside type="caution">
`burn_verify` runs an Argon2 verify but throws away the result — the
goal is wall-clock time, not the boolean. A profiler will still see
the call. Treat the constant-time property as a wire-side property,
not a per-call constant-time guarantee against a side-channel-capable
local attacker.
</Aside>

## `CredentialError` — opaque by design

Every failure path returns the same `CredentialError`, whose
`Display` is the fixed string `"invalid credentials"`. Wrong email,
wrong password, no password set, DB unreachable — all the same on the
wire:

```rust title="nest_rs::authn::CredentialError"
#[derive(Debug, Clone, thiserror::Error)]
#[error("invalid credentials")]
pub struct CredentialError;
```

A login endpoint turns it into 401. A *token endpoint* serving the
password grant wraps it in `TokenError::InvalidGrant` instead — RFC 6749
§5.2 assigns rejected resource-owner credentials to `invalid_grant` (400)
and reserves `invalid_client` (401) for a failure of the client's own
authentication. The two are not interchangeable, and the status differs,
so pick by which endpoint you are serving. The `tracing::warn!` calls in
`verify_credentials` capture the actual reason for operators — they
never reach the client.

## `PasswordError` — hashing-level failures

`hash_password` and `verify_password` return `PasswordError`:

| Variant | Meaning |
|---------|---------|
| `HashFailed(cause)` | Argon2 refused to hash (rare — usually an OOM or RNG failure); `cause` says which |
| `InvalidHash(cause)` | The stored string is not a hash Argon2id can run — it did not parse as PHC, or names an algorithm, version or parameters the hasher refuses (schema drift or corruption); `cause` says which. Only a mismatch is `Ok(false)` |

A login service collapses both into `CredentialError` so the wire
stays uniform; only the stored-hash-corrupt case logs distinctly.

## What the helpers do not cover

- **Lockouts and rate-limiting.** Pair signin with
  [`ThrottlerGuard`](/rate-limiting/) at the controller level.
- **Password policy.** Validate the input with
  [`validator`](/fundamentals/pipes/) before calling `hash_password`.
- **Account-lookup queries.** The service decides what to load, the
  helpers only hash.
- **Refresh tokens, session rotation.** Live in your token-issuer's
  domain — the auth crate stays storage-agnostic.
