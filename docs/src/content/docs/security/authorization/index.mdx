Authorization answers *what the caller may do*. You write one
`AbilityFactory` per app that compiles the caller's principal into an
`Ability` — the per-request capability set. The framework reads that
ability from three places: the query pre-filter on every read, the
by-id binding when a route loads a row, and the response mask after
the handler returns. Each is a line on the unit: its `#[authorize]` or
`#[public(Action, Subject)]` names what it reads, and a unit naming nothing has
the ability withheld from its reads, so what it did not declare fails closed.

The engine is ability-based — grants, conditional rules, fields — but
backed by one shared `Predicate` AST so the SQL filter and the
in-memory check can never disagree row by row.

## Install

```bash frame="terminal"
cargo add nest-rs --features authz
```

`seaorm` turns it on too. Every edge's `#[authorize]` expands into this crate,
so a decorator carrying it in a build without `authz` is a compile error that
names the feature.

## One factory, one ability per request

`AbilityFactory` is a tiny trait you implement once. The framework
calls `define` per request, after the authn guard attached the
principal. The guard attaches the resulting `Ability`, so it is ambient
for the rest of the request, where the data layer reads it.

A minimal policy is one statement — "members read their org's users":

```rust title="crates/features/src/authz/ability.rs (from the demo)"
use nest_rs::authz::{AbilityBuilder, AbilityFactory, Action};
use nest_rs::core::injectable;

#[injectable]
pub struct AuthzAbility;

impl AbilityFactory for AuthzAbility {
    type Actor = Claims;

    fn define(&self, actor: &Claims, ab: &mut AbilityBuilder) {
        ab.can(Action::Read, user::Entity)
            .when(|p| p.eq(user::Column::OrgId, actor.org_id));
    }
}
```

That one line lands the class-level gate, the SQL pre-filter
(`WHERE org_id = $caller_org_id`), and the response-side check on
every loaded row. The next step is a role matrix — same builder,
branched on the principal:

```rust title="crates/features/src/authz/ability.rs"
fn define(&self, actor: &Claims, ab: &mut AbilityBuilder) {
    if actor.is_admin() {
        ab.can(Action::Manage, user::Entity)
            .when(|p| p.eq(user::Column::OrgId, actor.org_id));
        ab.can(Action::Manage, org::Entity);
    } else {
        ab.can(Action::Read, user::Entity)
            .when(|p| p.eq(user::Column::OrgId, actor.org_id))
            .fields([user::Column::Id, user::Column::Name]);
        ab.can(Action::Create, user::Entity)
            .when(|p| p.eq(user::Column::OrgId, actor.org_id));
        ab.can(Action::Read, org::Entity)
            .when(|p| p.eq(org::Column::Id, actor.org_id));
    }
}
```

A `RuleSpec` commits on drop — `ab.can(...).when(...).fields(...)` is
one statement, no terminal `.add()` call. See
[Policies](/security/authorization/policies/) for the full builder API.

The trait has a second, defaulted branch — `define_visitor` — that the
guard calls instead of `define` when what `#[public(Action, Subject)]` opens is reached with
no credential. It grants nothing until you write into it; see
[Public reads](/security/authorization/public-reads/).

## Mount it on the controller

The `AuthzModule` provides `AuthzGuard` — a **project type alias** for
`AbilityGuard<AuthzAbility>` defined in `features/authz/guard.rs`, **not**
exported from `nest_rs::authz`. Import `AuthzGuard` from your feature crate, or
use `AbilityGuard<YourAbility>` directly from `nest_rs::authz`. Bind it
after `AuthnGuard`:

```rust title="crates/features/src/users/http/controller.rs (from the demo)"
#[controller(path = "/users")]
#[use_guards(AuthnGuard, AuthzGuard)]
pub struct UsersController {
    #[inject]
    svc: Arc<UsersService>,
}
```

Order matters: `AuthnGuard` attaches the principal; `AuthzGuard` reads
it and builds the `Ability`. The route's `#[authorize]` class gate runs
right after them, before any interceptor or filter the route declares, so
nothing the route binds answers a caller the gate refuses. A handler whose
posture names what it reads sees an ambient `Ability` it does not have to thread.

## One class gate on every edge

`#[authorize(Action, Entity)]` means one thing wherever it is written — a
route, a GraphQL operation, a WebSocket message, an MCP tool — because every
decorator emits the same function, `nest_rs::authz::class_gate::<Action,
Entity>`, run on the unit right after its guards:

- no ability guard in the unit's chain or at its request: the boot refuses, naming
  the site and the guard to bind;
- no ability reached the unit all the same — a guard answering for one attached
  none: refused opaquely, and one `error` on `nest_rs::authz` names the site and the
  remedy;
- the caller is anonymous and the site is not `#[public]`: `401`, whatever
  the visitor's rules grant — a grant written for
  [public reads](/security/authorization/public-reads/) never satisfies an
  `#[authorize]`;
- no grant on the class: `403`, `forbidden`;
- a denial no `when` narrows — `cannot(Create, E)` beside `can(Manage, E)` —
  matches every row, so the action is refused here, and so is a site gated on
  `Manage`, which means every action: `403`, `forbidden`, the same answer
  whatever the token carries, since no scope lifts a denial;
- a grant the token's scopes withhold: `403` naming the scopes to ask for
  ([Scopes](/security/authorization/scopes/)).

A grant or a denial a `when` narrows passes the gate: the rows decide it, in
the query pre-filter and on the loaded row. A `when` that holds for every row
by its shape — `p.all([])`, a disjunction holding one — narrows nothing, and
its denial is refused here like one with no `when`.

Each refusal files one `warn`, `authorization denied`, with its `reason`, and
reads the same on every edge, each answering in its own form. The gate is no
feature of an edge: a package's decorator emits it for its own posture as the
framework's do.

The subject need not be a table. A capability — may transcode, may export —
is a [subject `#[subject]` declares](/security/authorization/policies/#subjects-no-table-holds):
`#[authorize(Manage, Transcoding)]` runs this same gate, scope challenge
included, and arms no mask, since there is no row to mask.

## Three places the framework reads it

1. **`Repo::scoped(Action)` — the query pre-filter.**
   `condition_for::<E>(action)` lowers the grants matching this
   action+entity into a `sea_orm::Condition`, joined into every query.
   No matching grant ⇒ `1 = 0` ⇒ the query returns nothing. See
   [Row-level filtering](/security/authorization/row-level-filtering/).
2. **`#[authorize(A, bind = S)]` — the by-id loader.**
   `Service::access(id)` loads the row **unscoped**, then re-checks
   the same primary key filtered by `condition_for(action)` — the
   decision is made in SQL, by the same predicate the list path
   joins. Missing row ⇒ 404, present but denied ⇒ 403. See
   [By-id binding](/security/authorization/by-id-binding/).
3. **The response shaper `#[authorize(A, S)]` or `#[public(A, S)]` arms.** After a 2xx, the
   shaper reads each row of the body back into `S::Model`, judges it
   as `Ability::mask_many` does, and keeps only the exposed columns its
   grants permit. See [Response masking](/security/authorization/response-masking/).

## Reading the ambient ability

A query of a service's own starts from `Repo::scoped`, which joins the
`Condition` for it ([a custom query](/security/authorization/row-level-filtering/#when-you-really-do-need-a-custom-query)).
A service method or any code a masked unit reaches — a dataloader batch
included — reads the ability directly:

```rust title="crates/features/src/users/service.rs"
use nest_rs::authz::current_ability;
use nest_rs::authz::Action;

if let Some(ab) = current_ability() {
    if !ab.can::<user::Entity>(Action::Update, &model) {
        return Err(ServiceError::forbidden("not permitted"));
    }
}
```

`can` decides on the model alone: synchronous, no query. What the
model cannot show — a relation (`p.related(…)`) above all — grants
nothing there, and a denial resting on it refuses.
So a relation-gated `Update` grant answers `false` on a row you read for
`Read`. When such a rule decides, ask SQL: `Repo::can` re-checks the
row's primary key under the action's own condition, one indexed query.

```rust title="crates/features/src/users/service.rs"
use nest_rs::seaorm::Repo;
use nest_rs::authz::Action;

if !Repo::<user::Entity>::can(Action::Update, &model).await? {
    return Err(ServiceError::forbidden("not permitted"));
}
```

On an entity declared `soft_delete`, a deleted row answers `false` for
every action but `Create` and `Delete`, as every `Repo` read leaves it out;
`Delete` stays `true` where the grant holds, since the hard purge reaches it.

A row a route bound through `#[authorize(Update, bind = S)]` was already
authorized for `Update` in SQL, and needs neither check.

`current_ability()` returns `None` outside a request (worker job, cron
tick, init or shutdown hook). That work runs **unscoped** by design — system
work should not be filtered by a caller's ability. See
[Threat model](/security/threat-model/) for what that buys and what
it does not.

It returns `None` as well on a unit no mask shapes, every `#[sse]` stream among
them, and for a visitor anywhere but a unit naming what it reads: the ability is
withheld there, so a `Repo` read fails closed. A check of your own that must hold
on such a unit asks `Repo::can`, which refuses there, rather than skipping on `None`.

## What an `Ability` exposes

```rust title="nest_rs::authz::Ability"
ability.can_class(Action::Read, TypeId::of::<user::Entity>())
ability.condition_for::<user::Entity>(Action::Read)
ability.can::<user::Entity>(Action::Update, &model)
Repo::<user::Entity>::can(Action::Update, &model).await?
ability.mask::<user::Entity>(Action::Read, &model)
ability.mask_many::<user::Entity>(Action::Read, models.iter())
ability.permitted_fields::<user::Entity>(Action::Read, &model)
```

Each method targets one layer of enforcement — the framework picks
which one to call where, but the surface is documented because your
own services may reach for `can` directly when they cannot fit through
`Repo` or a bound subject. `Repo::can` is the one that reads the database: it
answers what `Ability::can` cannot see on the model.

`Action::Manage` is the wildcard: a grant on `Manage` matches every
other action. A grant on `Action::Read` does not imply `Update`. Asked of a
site, `Manage` means every action at once: `can_class` and `can` hold each of
the four, `condition_for` conjoins their conditions, and `mask` and
`permitted_fields` read `Read`'s
([Policies](/security/authorization/policies/#actions)).

<Aside type="caution">
A handler **without** the authz module imported has no request
`Ability`, and every path fails closed rather than open: an
`#[authorize]` gate refuses the boot, and a `Repo` read on the request-scoped
executor renders `1 = 0` — zero rows, plus a `warn` naming the entity and
action. The access graph catches the missing import at boot, and a route
that no guard identifying a caller covers and is not `#[public]` refuses the boot. Match every new
controller with the transport's authz module, and write a
[negative-path test](/testing/negative-path/) that pins the 403.
</Aside>

  you hand tokens to third-party clients (MCP, in particular).

  — how GraphQL, WS, and MCP build the ambient ability at their request
  (explanation — useful once you add a second transport, not before).
