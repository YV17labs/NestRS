HTTP handlers are not the only place a request reaches your code.
GraphQL operations multiplex over a single `POST /graphql`. WebSocket
messages multiplex over a single connection upgrade. MCP tool calls
multiplex over their own JSON-RPC. For each, the framework ships an
authz bridge that re-establishes the ambient `Ability` at the right
dispatch point. Your `AuthzAbility` factory stays the single source of
truth across every transport.

The bridges live in:

- `nest_rs::authz` — the guard itself, under any transport feature
- `nest_rs::authz::http` — feature `http`, the HTTP extractors and shaper
- `nest_rs::authz::graphql` — feature `graphql`
- `nest_rs::authz::mcp` — feature `mcp`

None carries a data context: every edge runs its units of work through the
`dyn UnitOfWork` that `SeaOrmDatabaseModule` binds, so a bridge only has the
ability to scope.

GraphQL, WS and MCP each get a one-import `Authz<Transport>Module` in
`crates/features/src/authz/`. Each wraps the framework bridge for its transport
and registers it against the access graph, so an app imports the module and
lists nothing else (see [MCP](#mcp--same-shape-as-http) below). **HTTP has no
such module**: the guard those bridges re-run is `AbilityGuard`, which answers
every transport, so `AuthzModule` provides it directly.

You do not write them: `nestrs g auth` writes `authz/module.rs` and
`authz/guard.rs`, and
`nestrs g graphql|ws|mcp` writes that transport's bridge alongside the adapter
and wires it into the app. The blocks below are what those generators produce —
read them to understand the wiring, copy them only into a workspace that was not
scaffolded.

## The bridges

| Bridge | Provides | What it bridges |
|--------|----------|------------------|
| `AuthzModule` | `AuthzGuard` (`AbilityGuard<AuthzAbility>`) | The HTTP request — guard runs on `&mut Request`, attaches `Arc<Ability>` |
| `AuthzGraphqlModule` | `AuthzGraphqlBridge` (`dyn OperationGuard`) | Re-runs the HTTP guard chain on `/graphql` and scopes the operation, the dataloader batches it triggers included |
| `AuthzWsModule` | nothing of its own: `AuthzModule` and `WsModule` | Brings the guards a gateway's upgrade runs; the ability they attach crosses the connection into each message — which is what the per-message `#[authorize]` gate and reply mask read |
| `AuthzMcpModule` | `AuthzMcpBridge` (`McpAbilityBridge<AuthnGuard, AuthzGuard>`) as `dyn McpOperationGuard` | Re-runs the HTTP guard chain on the MCP endpoint and installs the ability *inside* each tool dispatch |

A controller imports the matching module along with its feature
module. The transports transitively bring every layer the feature
needs.

```rust title="apps/api/src/module.rs"
#[module(
    imports = [
        SeaOrmModule::for_root(None),
        SeaOrmDatabaseModule,
        AuthnModule,
        AuthzModule,
        AuthzGraphqlModule,
        AuthzWsModule,
        UsersHttpModule,
        UsersGraphqlModule,
        UsersWsModule,
    ],
)]
pub struct ApiModule;
```

## HTTP — the direct case

HTTP is the simplest because guards run on the actual request before
the handler:

```rust title="crates/features/src/users/http/controller.rs"
#[controller(path = "/users")]
#[use_guards(AuthnGuard, AuthzGuard)]
pub struct UsersController { /* ... */ }
```

`AbilityGuard` reads the `Claims` an `AuthnGuard` attached, calls
`AuthzAbility::define(&actor, &mut builder)`, and attaches the `Ability`
with `cx.attach`. Once the guards pass it is ambient for the rest of the
request, so `Repo::scoped` sees it in the handler and in a streaming body
the route returns — on a route a response mask shapes. A route no mask
shapes, every `#[sse]` stream included, reads nothing scoped: the ability
is withheld there, so a read fails closed rather than answering what a
mask would have narrowed.

## GraphQL — in-band guards over a shared dispatch

A GraphQL `POST /graphql` is one HTTP request that multiplexes many
operations, so per-operation auth cannot run as plain HTTP guards. What
you write is unchanged in spirit: import `AuthzGraphqlModule`, bind
`AuthzGuard` on the resolver, and declare each operation's posture:

```rust title="crates/features/src/users/graphql/resolver.rs"
#[resolver]
#[use_guards(AuthzGuard)]
pub struct UsersResolver { /* ... */ }

#[operations]
impl UsersResolver { /* #[authorize(Action, Entity)] or #[public] per op */ }
```

`AuthzGuard` is the app's `AbilityGuard<AuthzAbility>` alias, and it is what
`#[use_guards]` binds: its `check` refuses an operation no ability reaches,
and it declares `GuardFor<GraphqlView>`, the bound `#[resolver]` emits. An
`AuthnGuard` does **not** belong in that list — it checks HTTP requests only,
so on a resolver it would run nothing; the bridge below already authenticated
the request in band.

The module those three providers live in is app code, like the rest of
`authz/`: **`nestrs g graphql <feature>` writes it** into
`crates/features/src/authz/graphql/` the first time a resource gets a
GraphQL adapter, and imports it from that adapter's `module.rs`. The
four files are the ones sketched below —
[`demo/crates/features/src/authz/graphql/`](https://github.com/YV17labs/NestRS/tree/main/demo/crates/features/src/authz/graphql)
is the same thing under version control.

That's the whole resolver-side surface. HTTP guards run `check_http` on
the request *before* the handler; they *are* the auth chain. GraphQL instead runs
authn/ability **in-band** per operation, seeds the ability into per-operation
context, and forwards the principal with `forward_principal!(Claims)`.

That forward binds nothing and gates on nothing, because it cannot fire without
the chain that feeds it: it copies `Claims` from the ambient context only when
the authn guard has attached them, and that guard is reachable only through the module
that declares it. Omit the authz module and the chain never runs, so there is
nothing to copy — the schema is anonymous because it was never authenticated,
not because a guard was left out of a list.

### Under the hood: the operation bridge

The seeding is done by `GraphqlAbilityBridge`, registered as the
`dyn GraphqlOperationGuard`:

```rust title="nest_rs::authz::graphql::GraphqlAbilityBridge"
use nest_rs::http::{Request, Response};

#[injectable]
pub struct GraphqlAbilityBridge<A: Guard, G: Guard> {
    #[inject] auth: Arc<A>,
    #[inject] ability: Arc<G>,
}

impl<A: Guard, G: Guard> GraphqlOperationGuard for GraphqlAbilityBridge<A, G> {
    fn before<'a>(&'a self, req: &'a mut Request) -> BoxFuture<'a, Result<(), Response>> { /* ... */ }
    fn covers(&self) -> &[TypeId] { /* A and G */ }
}
```

`before` runs the same HTTP guard chain (`AuthnGuard`, then
`AbilityGuard`) on the GraphQL request — nestrs's own `Request`, the one a
route's guards read. `/graphql` is **in band**
(`Posture::InBand`) — one endpoint, posture declared per operation — so a
caller with no credential is admitted here and takes the ability guard's
*visitor* branch, while a bearer that does not verify is refused with
`401 invalid_token`. The line is held one step later, by the operation's own
posture: `#[authorize(...)]` refuses an ability with no principal behind it
(`UNAUTHENTICATED`), whatever `define_visitor` granted, and only `#[public]`
operations read those grants. What the chain attached — the principal and the
resulting ability — is ambient for every operation the request carries.

**The bridge joins the global guard pool, never replaces it.** The endpoint runs
every guard the app lists in `use_guards_global(...)` at the request, bridge or
not, so an API-key or IP allow-list guard gates `/graphql` as it gates every
route. `covers()` names the guards the bridge runs itself: the bridge runs where
the pool lists the first of them, and the pool skips them, so an `AuthnGuard`
listed in both runs once.

A dataloader batch carries what its request carries, so relations that
fan out across batches run under the same ability, on the pool — scoped
without the resolver threading anything, and with nothing more to
register.

## WebSockets — per-message scope

A WS connection is one HTTP upgrade; messages arrive over a long-
lived socket and dispatch into separate handlers. Each message needs
its own ambient ability:

```rust title="crates/features/src/authz/ws/module.rs (from the demo)"
#[module(imports = [AuthzModule, WsModule])]
pub struct AuthzWsModule;
```

The ability the upgrade's guards attach crosses the connection into every
message and connection hook, and the gateway runs each as a unit of work of its
own — a transaction opened on its first query, committed unless the reply is
an error frame — with no shared state across messages.

Unlike GraphQL, WS has **no bridge** — a gateway's upgrade is `Gated`, so it
already carried the real chain and there is nothing to re-run in band. It reuses the HTTP `Guard` trait directly. The gateway struct binds the real guards; because the
upgrade is an HTTP `GET`, they run once on it, and the access graph
validates them like any HTTP binding (omit `AuthzWsModule` ⇒ the
guards are unreachable ⇒ boot fails). An optional per-message check
binds a real `Guard` beside the message:

```rust title="crates/features/src/chat/ws/gateway.rs"
#[gateway(path = "/ws")]
#[use_guards(AuthnGuard, AuthzGuard)]
pub struct ChatGateway { /* ... */ }

#[messages]
impl ChatGateway {
    #[subscribe_message("users.list")]
    #[authorize(Read, users::Entity)]
    async fn list(&self) -> Result<Vec<User>, ServiceError> {
        Ok(self.svc.list().await?.iter().map(User::from).collect())
    }
}
```

`AuthnGuard` + `AuthzGuard` run at the upgrade — those are real HTTP
guards on a real `GET`, so they declare `GuardFor<HttpView>`, not
`GuardFor<WsView>`; `#[gateway]` emits that bound, and `GuardFor<WsView>` is
what a guard bound beside a `#[subscribe_message]` owes instead. The upgrade has
returned before any message handler runs, so the connection carries the
ability, and the gateway opens each message's unit of work, around each
message.

**Above that, a message declares its posture like an operation on any
other transport**, and it is mandatory: `#[authorize(Action, Entity)]` or
`#[public]`, or it does not compile. `#[authorize]` emits the class gate
(`nest_rs::authz::class_gate`, every edge's) before the payload is deserialized and
the reply mask afterwards — so a handler answering with entity rows
writes **no masking call**. It fails closed when no ambient ability is
present, which is exactly the state of a gateway whose app imported
`AuthzModule` instead of `AuthzWsModule`.

The mask acts on the serialized reply, so a withheld column is absent
from the frame rather than an error — HTTP's behaviour, not GraphQL's,
because an envelope promises no schema. See
[WebSockets / Messages](/websockets/messages/) for the full contract.

An optional per-message `#[use_guards(...)]` still adds event-level
checks; such a guard runs `Guard::check` and must declare
`GuardFor<WsView>` — see [WebSockets / Guards](/websockets/guards/).

## MCP — same shape as HTTP

`AuthzMcpModule` registers `AuthzMcpBridge`
(`McpAbilityBridge<AuthnGuard, AuthzGuard>`) as `dyn McpOperationGuard` — on each
MCP HTTP request it runs the same `A` then `G` chain
controllers use (the same authenticate-then-authorize step the GraphQL
bridge runs), and what it attached — the caller's `Ability` — is ambient for the tool
call. Either
leg's denial is returned **as raised**, so a `401`, a `403` and a throttler's
`429` + `Retry-After` all reach the client intact. Import `AuthzMcpModule`
beside the feature module, the same shape as the other transports.

```rust title="nest_rs::authz::mcp::McpAbilityBridge"
#[injectable]
pub struct McpAbilityBridge<A: Guard, G: Guard> {
    #[inject] auth: Arc<A>,
    #[inject] ability: Arc<G>,
}
```

What the request's guards attached is captured with the request and installed
*inside* rmcp's spawned dispatch, where the request is long gone — the same
rule as on `/graphql`, so "who scopes the operation" has one answer on both
transports. Each operation is a unit of work of its own, opened through the
bound `dyn UnitOfWork`: it commits when the operation answers `Ok` without a
tool error in band (`isError: true`), and rolls back otherwise.

**The global guard pool always runs** at the request (`use_guards_global(...)`),
the bridge inside it exactly as on `/graphql` — so a global `ThrottlerGuard`
rate-limits tool calls, and a guard listed in both runs once. With no pool the
bridge runs alone; with neither, `/mcp` stays deny-all. `/mcp` carries no
`Posture::InBand` (its requests read `Gated`), so a pooled `AuthnGuard` still
refuses an anonymous tool call.

What that endpoint runs is `check_http` — it holds a request, not an operation.
A pooled guard's `check` runs in the **per-operation chain**, which folds
the pool too, so a global guard overriding `check` gates every tool call even
when the bridge already authenticated the caller who sent it.

The pool's runner is the MCP edge's own, so it reaches `/mcp` in every app that
serves it: the boot line reads `mode="global_guard_pool"` when a pool gates the
endpoint, and `no operation guard registered — mcp endpoint is deny-all
mode="deny_all"` with neither pool nor bridge — fail-closed.

## Public handlers — opt out per transport

A handler is "public" by **not** binding the transport's authz
module's guard. The whole module import then becomes optional — the
app lists `AuthzModule` only if other handlers need it.

```rust title="crates/features/src/users/http/controller.rs"
#[get("/health")]
#[public]
async fn health(&self) -> &'static str { "ok" }
```

`#[public]` makes `AuthnGuard` non-rejecting (anonymous requests pass
through with no claims). The `AbilityGuard` then builds an empty
`Ability` for the visitor; the row-level filter returns nothing
unless `AbilityFactory` granted the visitor branch explicitly. See
[Authorization](/security/authorization/) for the visitor-rule
pattern.

<Aside type="note">
Cross-transport rule: **same `AuthzAbility` everywhere**. The bridge
re-establishes the ambient ability at each transport's dispatch
point, but the factory that builds it stays the single source of
truth. Splitting policy across transports is the drift the framework
prevents — keep all rules in `crates/features/src/authz/ability.rs`.
</Aside>
