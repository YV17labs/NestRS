A policy is a function from a principal to an `Ability`. The function
runs per request — `AbilityFactory::define` is called once after
authn, and the guard attaches the returned `Ability`, ambient for the
rest of the request. This page covers the builder API: subjects, actions,
conditional rules, restricted fields, denials.

Predicates compile through a single `Predicate` AST that lowers to
[SeaORM](https://docs.rs/sea-orm)'s `Condition` for the SQL filter
and matches in-memory for the by-id check and the response mask.
One AST, two interpreters — the rows the query returns and the rows
the response check accepts cannot diverge.

## A minimal policy

```rust title="crates/features/src/authz/ability.rs (from the demo)"
use nest_rs::authz::{AbilityBuilder, AbilityFactory, Action};
use nest_rs::core::injectable;

#[injectable]
pub struct AuthzAbility;

impl AbilityFactory for AuthzAbility {
    type Actor = Claims;

    fn define(&self, actor: &Claims, ab: &mut AbilityBuilder) {
        ab.can(Action::Read, user::Entity)
            .when(|p| p.eq(user::Column::OrgId, actor.org_id));
    }
}
```

That is the whole surface for "members read their org's users". Three
things land at once: the class-level gate (can a member read users?),
the SQL pre-filter (`WHERE org_id = $caller_org_id`), and the
response-side check on every loaded row.

## Subjects

A subject is any type that implements `nest_rs::authz::Subject`. The
crate ships a blanket impl for every `sea_orm::EntityTrait`:

```rust title="nest_rs::authz::Subject"
pub trait Subject: 'static {}
impl<E: sea_orm::EntityTrait> Subject for E {}
```

So a SeaORM entity (`user::Entity`, `org::Entity`) is the canonical
subject — the bridge isolates the ORM coupling to one impl block.
Introducing a second data layer moves one impl, not the engine. A
capability no table holds is the other kind, which `#[subject]` declares
([below](#subjects-no-table-holds)).

`Subject` is used as a type-system guardrail in a posture's
`#[authorize(A, S)]` and `#[public(A, S)]` and in the `condition_for::<E>` calls. Subjects are keyed by `TypeId`
under the hood; `Action::Manage` on a subject acts as a wildcard for
every other action on that same subject.

### Subjects no table holds

Some decisions are about a capability, not rows: may this caller transcode
audio, export the org's reports, trigger a reindex? Declare the capability
with `#[subject]` on a unit struct, beside the feature that owns it:

```rust title="crates/features/src/audio/transcoding.rs"
use nest_rs::authz::subject;

#[subject]
pub struct Transcoding;
```

A rule grants it whole, with the scope a token must carry when the
capability is delegated:

```rust title="crates/features/src/authz/ability.rs"
if actor.is_admin() {
    ab.can(Action::Manage, Transcoding)
        .requires_scope(AUDIO_TRANSCODE);
}
```

and every operation that exercises it declares the posture on it —
`#[authorize(Manage, Transcoding)]` on an HTTP route, an `#[sse]` stream,
a GraphQL field, a WebSocket message or an MCP tool alike. It is the
same [class gate](/security/authorization/#one-class-gate-on-every-edge)
as on an entity, with the same refusals and the same RFC 6750 scope
challenge, and it arms **no mask**: the subject has no model, so the
reply goes out as written. A unit gated this way still withholds the
ability from its reads, on every edge, as every unit no mask shapes does.

The type system keeps the two kinds apart. `when` and `fields` narrow an
entity's rows and columns, so a subject no table holds refuses them; so
does `cannot`, because the class gate is that subject's one layer and a
grant you do not write is already the denial. Each is bounded on
`RowSubject`, which every entity is, and a capability is told why:

```text
error[E0277]: `Exporting` has no rows to deny or narrow: `cannot`, `when` and `fields` take a SeaORM entity
   = note: a capability `#[subject]` declares has no rows: a grant covers it
           whole, and a grant not written is its denial
```

Don't borrow an entity for a capability (`Manage` on `org::Entity` to mean
"may transcode"): a rule on the entity then grants or withholds the
capability by accident, and a grep for the capability finds nothing.

## Actions

Five variants, four typed markers:

```rust title="nest_rs::authz::Action"
pub enum Action { Read, Create, Update, Delete, Manage }
```

`Manage` is the action wildcard — a grant on `Manage` matches every
other action on the same subject. Each variant has a type marker
(`Read`, `Create`, `Update`, `Delete`, `Manage`) implementing
`ActionMarker`, so a posture can name an action as a type
(`#[authorize(Read, user::Entity)]`).

A grant on `Read` does not imply `Update`. A grant on `Manage` does.

```rust title="crates/features/src/authz/ability.rs"
ab.can(Action::Manage, org::Entity); // covers Read, Create, Update, Delete
```

A site gated on `Manage` asks for all of it: `#[authorize(Manage, E)]` passes only
where `Read`, `Create`, `Update` and `Delete` would each pass. So `cannot(Read, E)`
beside `can(Manage, E)` refuses a site gated on `Read` and a site gated on `Manage`,
and leaves the other three open; four separate grants pass it; `cannot(Manage, E)`
refuses all five. A caller barred from reading a thing does not manage it.

The rows follow the same reading: `condition_for::<E>(Action::Manage)` and
`Ability::can` hold a row to every action's rules. What such a site answers shows what
the caller may `Read`, and a write in its body reads the write's own action.

## Rules — grant, condition, fields

`AbilityBuilder` has two starters: `can` (grant) and `cannot`
(denial). Each returns a `RuleSpec` that commits on drop — bind it
to a variable only if you want to defer the commit:

```rust title="crates/features/src/authz/ability.rs"
ab.can(Action::Read, user::Entity)
    .when(|p| p.eq(user::Column::OrgId, actor.org_id))
    .fields([user::Column::Id, user::Column::Name]);
```

| Method | What it does |
|--------|--------------|
| `.can(action, subject)` | Begin a grant |
| `.cannot(action, subject)` | Begin a denial — a matching denial overrides a matching grant |
| `.when(\|p\| ...)` | Constrain the rule to rows matching the predicate |
| `.fields([col, ...])` | Restrict a grant to these columns: what a reply shows, and what a write sets |
| `.requires_scope(scope)` | Withhold a grant from a token without the scope ([Scopes](/security/authorization/scopes/)) |

Skip `.when` and the rule is unconditional. Skip `.fields` and every
field is permitted. A denial takes `.when` alone: it hides rows, never
columns, and holds whatever the token carries, so
`cannot(..).fields(..)` and `cannot(..).requires_scope(..)` do not
compile.

The closure handed to `when` receives a `PredicateBuilder<E>` typed
to the rule's entity, so column references are type-checked at compile
time. A rule scoped to `user::Entity` cannot accidentally reference
`org::Column::Id`.

## Predicates — the shared AST

```rust title="nest_rs::authz::Predicate"
pub enum Predicate<E: EntityTrait> {
    Always,
    Deny,                           // a rejected relation: fails the build
    Eq(E::Column, Value),
    In(E::Column, Vec<Value>),
    Cmp(E::Column, CmpOp, Value),   // Ne / Lt / Lte / Gt / Gte
    IsNull(E::Column, bool),        // IS NULL / IS NOT NULL
    And(Vec<Predicate<E>>),
    Or(Vec<Predicate<E>>),
    Not(Box<Predicate<E>>),
    Related(RelatedPredicate),      // condition on a related entity
}
```

`PredicateBuilder` exposes the constructors:

```rust title="crates/features/src/authz/ability.rs"
if let Some(user_id) = actor.sub.user_id() {
    ab.can(Action::Read, user::Entity).when(|p| {
        p.all([
            p.eq(user::Column::OrgId, actor.org_id),
            p.any([
                p.eq(user::Column::Role, "admin"),
                p.eq(user::Column::Id, user_id),
            ]),
        ])
    });
}
```

| Builder method | Variant | Use |
|---------------|---------|-----|
| `p.eq(col, value)` | `Eq` | Column equals value |
| `p.ne(col, value)` | `Cmp` | Column differs from value |
| `p.lt / p.lte / p.gt / p.gte(col, value)` | `Cmp` | Ordered comparison |
| `p.is_null(col)` / `p.is_not_null(col)` | `IsNull` | Nullness test |
| `p.is_in(col, [v, ...])` | `In` | Column in list |
| `p.all([...])` | `And` | Every part matches |
| `p.any([...])` | `Or` | At least one part matches |
| `p.not(inner)` | `Not` | Negation |
| `p.related::<R, _>(rel, \|r\| ...)` | `Related` | Condition on a related entity — see below |

`Predicate::Always` is the default — a rule with no `.when` admits
every row. An empty `p.any([])` matches nothing (SQL `FALSE`); an
empty `p.all([])` matches every row (SQL `TRUE`). The same identities
hold for the SQL lowering and the in-memory check.

## Relational scoping

Some entities carry no tenant column of their own — a `message`
belongs to a conversation, and the conversation carries the `org_id`.
`p.related` scopes `E` by a condition on a related entity `R`, reached
through a variant of `E`'s SeaORM `Relation` enum; the closure builds
the sub-condition with `R`'s own typed columns:

```rust title="crates/features/src/authz/ability.rs"
// `message` has no `org_id`; its tenant is the parent conversation's.
ab.can(Action::Read, message::Entity).when(|p| {
    p.related::<conversation::Entity, _>(
        message::Relation::Conversation,
        |c| c.eq(conversation::Column::OrgId, org_id),
    )
});
```

The SQL lowering is a semi-join: `belongs_to` / `has_one` becomes an
uncorrelated `IN (subquery)`, `has_many` a correlated `EXISTS`. A
relation's custom `on_condition` is folded into the subquery, in parentheses
of its own, so the scope is never widened past the join, nor past what the
`on_condition` says.

Three checks close the gaps a rule's text could open. A rule failing one files
one `error` on `nest_rs::authz` and fails `AbilityBuilder::build`, so the guard
answers `500` rather than install a silently-wrong filter:

- the relation must point at `R` (its target table is checked);
- the relation must be single-column — a tenant key is one column by
  design; denormalize it onto the child rather than scoping through a
  composite key;
- what the rule writes as text must stay where the scope writes it: the
  relation's `on_condition`, read alone, closes every parenthesis, string and
  identifier it opens and holds no comment, as a raw fragment in `Repo`'s
  `filter` must, and no value it compares is an enum whose type name holds a
  `"`. Its `reason` field says which.

One consequence for the read-back path: the in-memory check cannot
traverse the relation without loading the parent, so row visibility
for a relational rule is decided **in SQL** everywhere — including
the by-id binding and create paths, which re-check against the same
lowered condition (see
[By-id binding](/security/authorization/by-id-binding/)). `Ability::can`
grants nothing on a relation, and `Repo::can` decides it in SQL. A pushed
value went through no SQL read, so a relational grant admits none of it
([What the mask cannot see](/security/authorization/response-masking/#what-the-mask-cannot-see)).

## Field grants

`.fields([cols])` restricts the response mask to a set of columns. A
rule without `.fields` permits every field. The masker unions the
permitted fields across every matching grant — so an admin grant
with no `.fields` clears the field restriction even if a narrower
grant existed.

```rust title="crates/features/src/authz/ability.rs"
ab.can(Action::Read, user::Entity)
    .when(|p| p.eq(user::Column::OrgId, actor.org_id))
    .fields([user::Column::Id, user::Column::Name]);
```

A member reads `id` and `name`; the masker drops every other column
from the response — including columns the wire DTO exposes that the
member should not see.

A grant names a column, not a spelling of it: `.fields([post::Column::Headline])`
keeps `headline` on the wire whatever `#[sea_orm(column_name = …)]` calls it in the
table.

### What a write may set

On a grant a write reads — `Update`, `Create`, or `Manage`, which covers both —
`.fields` is the list of columns that write may set:

```rust title="crates/features/src/authz/ability.rs"
ab.can(Action::Update, post::Entity)
    .when(|p| p.eq(post::Column::AuthorId, author))
    .fields([post::Column::Id, post::Column::Title, post::Column::Body]);
```

The author may rewrite a post and never its `status`. A write setting a column no
grant permits answers `403`, `FORBIDDEN`, before a hook runs or a statement leaves:
a `#[crud]` operation names the input's field, as its client spells it, and a
service's `?` on `ServiceError` names the column in `detail`.

```json
{ "type": "about:blank", "title": "Forbidden", "status": 403, "code": "FORBIDDEN",
  "errors": { "status": [{ "code": "forbidden" }] } }
```

An input you write by hand names its fields through `CreateModel::field_for` and
`UpdateModel::field_for`, as it does on a unique conflict.

The write costs no extra round trip: the grants go in the statement's own `WHERE`, or
the re-check of a create, so a relational rule is decided exactly, and atomically with
the write.

Skip `.fields` and a write sets what it likes, in the statement it always sent.
With it, a few things are never held against the caller:

- **The key.** It addresses the row. `.when` is what holds it.
- **What the server fills.** What `before_save` stamps, what a `Create` grant pins,
  what a default seeds, and a soft delete's `deleted_at`.
- **A null on a create.** An input lowers a member the client left out to one, so
  it writes nothing the caller chose.
- **A column a replacement carries back.** `#[crud]`'s update is a `PUT`, whose input
  carries every writable field, so a client narrowed to `title` still sends `body`.
  Left as it stands, it is no write: it stays out of the statement, and so leaves
  what another writer put there since.

That last one holds only for a column the caller may read. Comparing one it may not
would tell it what the row holds, so such a column counts as written whatever its
value, and the input refuses the same way every time. A caller who may not read
`body` cannot use a `PUT` carrying it: give that caller a route of its own, or take
`body` out of `input(update)`.

As with a reply, a row's columns are the union of the grants it meets, so two grants
conjoin per column:

```rust title="crates/features/src/authz/ability.rs"
ab.can(Action::Update, post::Entity)
    .when(|p| p.eq(post::Column::AuthorId, author))
    .fields([post::Column::Title]);
ab.can(Action::Update, post::Entity)
    .when(|p| p.eq(post::Column::OrgId, actor.org_id))
    .fields([post::Column::Status]);
```

A write of `title` alone needs a post by the author; one of `title` and `status`, a
post by the author in the org. A row its grants do not permit each column on is outside
the caller's scope, as any other: `DbErr::RecordNotUpdated`, a `404`.

<Aside type="caution">
A write's reply still shows that write's own grant: `.fields([Title])` on `Update`
answers `{ "title": … }`. List `Id` to read the key back. `Read`'s list does not
narrow it, so a write with no list of its own answers every exposed column. On GraphQL
a selection naming a column the grant withholds is refused, so the field's savepoint
rolls the write back.
</Aside>

A job holds no ability, so no column is withheld from it, and `with_ability` narrows
it to a principal's. A service setting a server-decided column under a narrowed grant
adds the column to the grant, or moves it to `before_save`: there is no other way past
the list.

## A real match-on-role example

The exemplar in `crates/features/src/authz/ability.rs`:

```rust title="crates/features/src/authz/ability.rs (from the demo, abridged)"
impl AbilityFactory for AuthzAbility {
    type Actor = Claims;

    fn define(&self, actor: &Claims, ab: &mut AbilityBuilder) {
        if actor.is_admin() {
            ab.can(Action::Read, user::Entity)
                .when(|p| p.eq(user::Column::OrgId, actor.org_id));
            ab.can(Action::Manage, user::Entity)
                .when(|p| p.eq(user::Column::OrgId, actor.org_id));
            ab.can(Action::Manage, org::Entity);
            ab.can(Action::Manage, Transcoding)
                .requires_scope(constants::AUDIO_TRANSCODE);
            // …
        } else {
            ab.can(Action::Read, user::Entity)
                .when(|p| p.eq(user::Column::OrgId, actor.org_id))
                .fields([user::Column::Id, user::Column::Name]);
            ab.can(Action::Create, user::Entity)
                .when(|p| p.eq(user::Column::OrgId, actor.org_id));
            ab.can(Action::Read, org::Entity)
                .when(|p| p.eq(org::Column::Id, actor.org_id));
            // …
        }
        // …
    }
}
```

What this buys:

- **Admin** reads and manages every user in their org; reads and
  manages every org unconditionally; may transcode audio when the token
  carries `audio:transcode` (a [subject no table
  holds](#subjects-no-table-holds)).
- **Member** reads users in their org but only `id` and `name`; can
  create users in their org; reads their own org only.
- **No role at all** (or unknown role) falls into the member branch
  — the test `empty_roles_behave_as_a_non_admin_member` pins this so
  a degraded token cannot silently grant admin powers.

## Denials override grants

A `cannot` rule that matches a row overrides every matching grant on
the same action+subject. Use it sparingly — the common case is a
narrow grant, not a broad grant clawed back.

```rust title="crates/features/src/authz/ability.rs"
ab.can(Action::Read, user::Entity);
ab.cannot(Action::Read, user::Entity)
    .when(|p| p.eq(user::Column::Status, "banned"));
```

The SQL pre-filter for `Read` becomes
`(OR of grant conditions) AND NOT (OR of deny conditions)`. The
in-memory check refuses if any denial matches even when grants do.

A denial with no `.when` — or with one that holds for every row by its
shape, such as `p.all([])` — matches every row, so the class gate refuses
the action outright, on every edge, before a handler, a query or an entity
hook runs:

```rust title="crates/features/src/authz/ability.rs"
ab.can(Action::Manage, user::Entity)
    .when(|p| p.eq(user::Column::OrgId, actor.org_id));
ab.cannot(Action::Create, user::Entity);
```

This caller reads, updates and deletes the users of their org, and a
`POST /users` answers a plain `403` — the same answer whatever the
token's scopes, since no scope lifts a denial.

<Aside type="note">
The framework's authz engine is **ability-based**, but a rule's evaluation
is independent of every other rule's. There is no inheritance, no
precedence between non-denial rules — every matching grant
contributes to the union. Keep rules orthogonal: rules that have to be
evaluated in order belong in one stronger predicate, not in a longer
chain.
</Aside>

## Where the policy lives

Always in `crates/features/src/authz/ability.rs`. The factory is the
**single source of truth** for the app's authorization rules — HTTP,
GraphQL, WS, and MCP transports all build the same `AuthzAbility`.
Spreading policy across handlers is the drift the framework prevents.
