If you sell one deployment to many tenants, one leaked row is a breach.
This page states what the framework isolates for you, names the exact
places that bypass it, and gives you a checklist to audit before you
trust it. The guarantees are strong; the escape hatches are real and
deliberate — you should know both.

Isolation starts where every request enters: bind the two guards on the
controller, and the caller's org scope flows through every layer below.

```rust title="crates/features/src/users/http/controller.rs (from the demo)"
#[controller(path = "/users")]
#[use_guards(AuthnGuard, AuthzGuard)]
pub struct UsersController {
    #[inject]
    svc: Arc<UsersService>,
}
```

## The guarantee

Once the authz modules are imported, the caller's ambient `Ability` is
non-optional. It does three things on every request, without a
per-handler opt-in:

- **Pre-filters every read.** `Repo` joins the ability's predicate into
  the SQL `WHERE`, so a member querying posts gets `org_id =
  $caller_org_id` appended.
- **Gates every by-id write.** A denied-but-existing row updates zero
  rows and returns `403`, not the row.
- **Masks every response field.** Fields the caller cannot read are
  stripped from the body before it leaves the process.

One predicate AST is interpreted twice — as SQL and in memory — so the
rows a query returns and the rows the masker keeps cannot diverge. The
mechanics live on one canonical page:
[Row-level filtering](/security/authorization/row-level-filtering/).
This page does not re-derive them; it covers what happens at the edges
of that guarantee.

## The escape hatches

The framework does not pretend the choke point is inescapable. Two
paths reach the database around the ambient scope. Each exists for a
reason, and each is a place a reviewer must look.

### 1. `Repo::conn()` and injected `Arc<DatabaseConnection>`

`Repo::conn()` is `pub`. It hands you the ambient executor for a custom
query. A `find()` against it that skips `scope_for` runs **unfiltered**:

```rust title="crates/features/src/posts/service.rs"
// Escape hatch: an unfiltered read across every tenant. A review trigger.
let every_post = posts::Entity::find()
    .all(&Repo::<posts::Entity>::conn()?)
    .await?;
```

An injected `Arc<DatabaseConnection>` goes one step further — it has no
executor and no ability at all, the sanctioned bypass for a truly
contextless path such as a one-shot command run outside every unit of work:

```rust title="crates/features/src/sessions/reaper.rs"
#[injectable]
pub struct SessionReaper {
    #[inject]
    db: Arc<DatabaseConnection>, // no executor, no ability — fully unscoped
}
```

Both are deliberate seams for system-level work, not the default path.
Feature code that reaches for either owes a comment saying why the scope
does not apply, and a reviewer who confirms it.

### 2. Worker and queue jobs run for a tenant, never under an ability

A `#[processor]` runs with **no ambient ability** — and, by default, in one
transaction per attempt. A job is system work with no caller to scope, so the
row filter is a no-op there: nothing a job reads or writes is filtered for you.

What a job keeps is the tenant it was pushed for. Your claims name it once,
off the verified token:

```rust title="crates/features/src/authn/claims.rs (from the demo, abridged)"
impl nest_rs::authn::PrincipalIdentity for Claims {
    // …
    fn tenant_id(&self) -> Option<String> {
        Some(self.org_id.to_string())
    }
    // …
}
```

The authentication guard makes that tenant ambient for the request. Every job
the request pushes seals it into its envelope beside the actor, and the worker
restores it, so `nest_rs::core::current_tenant_id()` answers in a processor
what it answered in the request that pushed the job. The ambient tenant comes
from a verified principal or a sealed envelope and nothing else — never a
header — and a record whose `tenant_id` names no tenant is dead-lettered
rather than run for none. An envelope is as trusted as
[whoever can write the queue's keys](/queue/delivery/#where-a-queue-lives), so
the Redis rules that allow it are part of your tenant isolation.

A job's own facts still travel in its payload. The demo's publish notification
belongs to the org of the post that was published — a fact the post names, in
an org the publish was already scoped to — so its payload carries it, declared
at the feature port beside the queue:

```rust title="crates/features/src/notifications/command.rs (from the demo)"
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct NotifyCommand {
    pub org_id: Uuid,
    pub message: String,
}

#[queue(name = "notifications", job = NotifyCommand)]
pub struct NotifyQueue;
```

The processor reaches no data itself; it hands the job to its service:

```rust title="crates/features/src/notifications/queue/processor.rs (from the demo)"
#[processor]
impl NotificationsProcessor {
    #[process(queue = NotifyQueue, retries = 3)]
    async fn notify(&self, job: NotifyCommand) -> Result<()> {
        self.svc.persist(job).await?;
        Ok(())
    }
}
```

The service writes the row under the payload's org, through `Repo`:

```rust title="crates/features/src/notifications/service.rs (from the demo, abridged)"
pub async fn persist(&self, command: NotifyCommand) -> Result<(), ServiceError> {
    let active = entity::ActiveModel {
        id: Set(Uuid::now_v7()),
        org_id: Set(command.org_id),
        message: Set(command.message),
        created_at: Set(chrono::Utc::now().fixed_offset()),
    };
    let conn = Repo::<Notifications>::conn()?;
    let model = Repo::<Notifications>::insert_unscoped(active, &conn).await?;
    // …
    Ok(())
}
```

A read a job makes filters on its tenant itself. `Repo::<E>::scoped(Action::Read)`
in a job filters nothing, since no ability exists there, so the service adds
`.filter(Column::OrgId.eq(tenant))` with the tenant `current_tenant_id()`
answers — and refuses when it answers `None`. Treat every `#[processor]` as its
own boundary: a service method a job calls that loads by id with no tenant
predicate is the bug to grep for.

## Review checklist

Run this before a tenant-facing release. Each step is one `grep` or one
read:

1. **Grep for `Repo::conn()`** in feature code. Confirm each call site
   is a sanctioned unfiltered read, not a forgotten scope.
2. **Grep for `Arc<DatabaseConnection>`** outside the framework crates.
   Each injection should be a contextless path (a one-shot command), never
   a request handler or a lifecycle hook, which runs in a unit of work.
3. **Confirm every `#[processor]` re-scopes.** Trace the tenant —
   `current_tenant_id()`, or the id a tick puts in the payload — into the
   service's query. A load-by-id with no `org_id` predicate is the bug.
4. **Confirm every controller carries `#[use_guards(AuthnGuard,
   AuthzGuard)]`.** A missing binding fails closed to empty results, but
   a [negative-path test](/testing/negative-path/) pins it.

<Aside type="caution">
The most probable failure is not a missing guard — the framework makes
that loud. It is a logic bug in your `AbilityFactory` — a wrong `org_id` scope, a grant
on the wrong subject — which is exactly why the policy is one file and one
pure function. Pin the matrix with [policy tests](/testing/policy/) against
`Ability::can` and `Ability::condition_for`, and the whole tenant boundary
is covered by microsecond unit tests.
</Aside>

## Limits

**No database-side backstop exists in 7.0.** The framework sets no
database session or transaction setting, so a Postgres Row-Level Security
policy keyed on one has nothing to read. Setting one yourself per connection
leaks: a pooled connection keeps its session setting after the request and
serves the next tenant that checks it out. Closing the gap takes the framework
setting the tenant inside every transaction it opens — local to that
transaction — on every path that reads, the pool's included. Until it does,
the application-layer filter above is the only control, and the checklist is
how you hold it.

**A job pushed outside a request runs for no tenant.** A scheduled tick, a
boot task or `main` has no verified principal, so what it pushes carries none:
a tick fanning work out per tenant names each tenant in the job's payload, and
the service filters on that.

Isolation of rows and fields is the framework's job. Everything a
production tenant boundary also depends on remains yours: key management,
token revocation, TLS, and DDoS defense at the edge. The
[Threat model](/security/threat-model/) lists what each layer catches
and where the responsibility falls back on your deployment. Read it
before you go live.
