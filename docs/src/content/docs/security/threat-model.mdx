The security layers nestrs ships cover a specific slice. They catch
the bug classes that ship most often in business apps — forgotten
filters, leaked fields, missing auth — and they catch them
structurally, not by review. They do **not** cover everything a real
production deployment must think about. This page lists what each
layer covers, what it does not, and where the responsibility falls
back on you.

## What each layer catches

| Layer | Catches | Does not catch |
|-------|---------|----------------|
| [`AuthnGuard` + `JwtStrategy`](/security/authentication/jwt/) | Missing, malformed, expired, unsigned-incorrectly tokens; against a JWK Set, a token naming an algorithm its key was not published for (`HS*`, `none`, another key type) | Stolen-but-unexpired tokens, replay before expiry, key compromise; a key an issuer withdrew from its JWK Set, until the set is refreshed — within about an hour while the issuer answers, an hour more while it does not |
| [`OAuthClient`](/security/authentication/oauth2/) | CSRF (state cookie), a cookie planted from a sibling subdomain (`__Host-`), code-interception (PKCE), SSRF on token exchange (no redirects) | Phishing the provider, malicious provider, callback URL takeover |
| [`hash_password` + `burn_verify`](/security/authentication/password/) | Timing-based account enumeration via login | Slow GPU farms cracking dumped hashes, weak passwords, password reuse |
| [`AbilityGuard`](/security/authorization/) | Missing or malformed `Ability` (500), unauthenticated GraphQL/WS (403) | Logic bugs in your `AbilityFactory` itself |
| [`Repo::scoped`](/security/authorization/row-level-filtering/) | Scope leakage on every read — handler cannot forget the filter | Custom queries that ignore `Scope<E, A>` |
| [`Bind<A, S>`](/security/authorization/by-id-binding/) | Cross-tenant by-id reads (403) and missing rows (404) | Handlers that fetch by id outside `Bind` and skip `access` |
| [`Authorize` shaper](/security/authorization/response-masking/) | Leak of unexposed columns, field-restricted grants | A handler returning a hand-built `serde_json::Value` shape that does not match `Model` (500) |
| [`ThrottlerGuard`](/rate-limiting/) | Brute-force login, naïve enumeration scrapes | DDoS at network or HTTP layer (use a CDN / edge throttler) |
| [Connection deadlines](/http/configuration/#connection-deadlines) | A client holding connections it does not use: a head sent a byte at a time, a TLS handshake never finished, an idle socket, a peer that stops reading | Many clients each staying inside the deadlines (the connection cap holds them back; a CDN sheds them) |

## What the framework dials

Every URL a framework client dials follows one plaintext rule: plaintext
where the protocol's own URL declares it, refused where the governing
standard requires TLS. The rule is held where the client is built, so a
call site cannot open a door the configuration kept shut.

| Client | Where its URL comes from | Plaintext |
|--------|--------------------------|-----------|
| Postgres pool and `EphemeralDatabase` | `<PREFIX>_SEAORM__URL` | only with `sslmode=disable` written in the URL; any other mode short of `verify-full` is refused |
| Redis, all three topologies | `<PREFIX>_REDIS__URL` | only a `redis://` URL; a `#insecure` fragment is refused |
| Storage | `<PREFIX>_STORAGE__ENDPOINT` | only with `<PREFIX>_STORAGE__ALLOW_HTTP=true`, which the development profile alone turns on |
| JWK Set | `<PREFIX>_AUTHN__JWKS_URI` | refused when the module is built, and by the client on every fetch |
| OAuth token and userinfo endpoints | `<PREFIX>_OAUTH__CLIENT__TOKEN_URL`, `USERINFO_URL` | refused when the client is built (RFC 6749 §3.2), and by the client on every call |
| `OAuthClient::fetch` | a provider's code, at run time | refused before the call (RFC 6750 §5.3), and by the client whatever path reaches it |
| OAuth authorize and redirect URLs | `<PREFIX>_OAUTH__CLIENT__AUTH_URL`, `REDIRECT_URL`; followed by the browser, never dialled | the authorize URL never (RFC 6749 §3.1); the redirect only on a loopback address (RFC 8252 §7.3) |
| GitHub and Google sign-in | the providers' own constants | none: every endpoint is `https` |
| OTLP exporter | `<PREFIX>_OPENTELEMETRY__OTLP_ENDPOINT` | an `http://` endpoint declares it, as OTLP/HTTP allows; TLS material set beside it is refused |

A provider package building a URL at run time inherits the same rule: the
OAuth client speaks `https` alone, so a URL that slipped past every check
still never leaves the process in plaintext with a token on it.

## Every client the framework opens verifies TLS

An encrypted connection the framework opens checks the server's
certificate, every time: it chains to an authority the system's store
holds, or to the ones a `TLS_CA_CERT` setting names in place of them,
and it names the host dialled. No setting, URL parameter or code path
turns the check off — the framework's lints refuse the libraries' own
switches in its code — and each client below has a test that dials a
server whose certificate a private authority signed and sees it refused
before any request, login or credential crosses.

| Client | Trusts | Private authority |
|--------|--------|-------------------|
| Postgres pool, `connect_from_env`, `EphemeralDatabase` | the system's store, `verify-full` by default | the file `sslrootcert` names in `<PREFIX>_SEAORM__URL` |
| Redis, all three topologies | the system's store, for a `rediss://` URL | `<PREFIX>_REDIS__TLS_CA_CERT` |
| Storage | the system's store, for an `https://` endpoint | `<PREFIX>_STORAGE__TLS_CA_CERT` |
| JWK Set | the system's store | `<PREFIX>_AUTHN__TLS_CA_CERT` |
| OAuth client | the system's store | `<PREFIX>_OAUTH__CLIENT__TLS_CA_CERT` |
| GitHub and Google sign-in | the system's store | none: both serve publicly trusted certificates |
| OTLP exporter | the system's store, for an `https://` endpoint | `<PREFIX>_OPENTELEMETRY__TLS_CA_CERT` |

A refused certificate fails the call or the boot — never a fallback to
an unverified connection — and Redis, the JWK Set and the OAuth client
say which setting fixes it.

## What the framework does **not** do

These are out of scope on purpose. They matter, they belong in your
deployment, and they are not part of the framework's surface.

### Token theft and replay before expiry

A stolen JWT remains valid until `exp`. The framework's mitigation is
**short access tokens** (default 1 hour, configurable via
`JwtOptions::expires_in`) paired with a refresh-token endpoint your
app exposes. Verification is stateless by design — no shared revocation
store on the hot path, so a resource server needs nothing but the public
key. Server-side revocation is a `revoked_tokens` table your `Strategy`
consults on verify, read through the same `Repo` as everything else.

### CSRF

The framework's posture is **bearer tokens**, which are immune to
CSRF by construction (the browser does not auto-attach an
`Authorization` header). No nestrs credential rides a cookie, so the
framework ships no CSRF middleware. The one cookie it writes is the
OAuth transaction, read on the provider's `GET` callback and held by
the `state` comparison (RFC 6749 §10.12), PKCE and its binding to one
provider; its `__Host-` prefix keeps a sibling subdomain from planting
it. Cookie-based sessions are not supported as a first-party
credential. If you bridge to one (an SSR layer that forwards cookies),
add CSRF protection at the bridge — `Sec-Fetch-Site` and `Origin`
checks, OWASP's Fetch Metadata defence, are the current standard.

### Key management

EdDSA splits the issuer's private key from every verifier's public
key — see [Split deployment](/security/authentication/split-deployment/).
Rotation, HSM integration, and secret-store wiring are not the
framework's job. Treat `<PREFIX>_AUTHN__PRIVATE_KEY` as you would
treat any production secret: load it from a real secret store, never
commit it, rotate on a schedule. Against an external issuer's JWK Set
(`<PREFIX>_AUTHN__JWKS_URI`), rotation is the issuer's: a token signed by a
new key earns one refetch of the set, and a withdrawn key stops verifying once
the set is refreshed — see the
[bounds](/security/authentication/jwt/#verifying-another-issuers-tokens).

### TLS

TLS terminates either at your edge — the common production shape: CDN,
ingress, load balancer — or at the app itself, via
[`HttpConfig`](/http/configuration/). The transport serves whichever you
configure and does not assume an edge it cannot see, so pick one and pin
it in your deployment checklist.

### Network-level DDoS

The throttler is a per-handler guard, not a network defense. A real
deployment fronts the app with a CDN, WAF, or rate-limiter that
sheds load before the request reaches the process.

### Cryptographic primitives

The framework wraps [`jsonwebtoken`](https://docs.rs/jsonwebtoken),
[`argon2`](https://docs.rs/argon2),
and [`oauth2`](https://docs.rs/oauth2). The
cryptographic correctness comes from those crates. The framework's
job is to wire them correctly — call `hash_password` instead of
storing plaintext, `verify_password` instead of comparing strings,
`JwtService::verify` instead of decoding manually.

## Defense in depth — what to layer

For a production app:

1. **Bearer tokens with short TTL** + refresh.
2. **EdDSA split** between split deployments.
3. **Authz guards bound on every controller** (negative-path tests
   catch the missing one).
4. **Exposure is opt-in — no `#[expose]` on server-only columns.**
   A column crosses the wire only when its field carries `#[expose]`,
   so a forgotten or newly-migrated column is hidden, not leaked. The
   masker is the second line for columns you *do* expose but restrict,
   covering them only when the field rule is `.fields([...])`.
5. **CDN / WAF** in front for DDoS and bot defense.
6. **Real secret store** for `<PREFIX>_AUTHN__PRIVATE_KEY`, OAuth secrets, DB
   credentials.
7. **TLS terminated** at the edge or at the app (`HttpConfig`).
8. **Logging at the right level.** `nest_rs::authn` and `nest_rs::orm`
   emit `warn`+ on denials and security events — pipe them to your
   SIEM, do not silence them.

<Aside type="caution">
The framework's authz engine is **ability-based** and runs in-process.
A bug in your `AbilityFactory` (forgot to scope `org_id`, granted
`Action::Manage` on the wrong subject) is the framework's most
likely failure mode. Pin the matrix with unit tests against
`Ability::condition_for` and `Ability::can` — the
`crates/features/src/authz/ability.rs` exemplar's test module shows
the pattern.
</Aside>
