You start Postgres and apply the post table's migration, and the data layer
`blog` imports comes alive. By the end of this page, the
five CRUD routes mount, `POST /posts` persists into Postgres inside a
transaction, a failing handler rolls back automatically, and the e2e
baseline you add in [Test it end to end](/tutorial/testing/) has a real
database to point at.

## The data layer in one import

One import activates the SeaORM data layer, and `nestrs g resource` wrote it
into `blog`'s root on page 2: `SeaOrmDatabaseModule` binds the unit of work each
request and each job runs in, over the pool `SeaOrmModule` opens from
`<PREFIX>_SEAORM__URL`, which it imports. Every route `#[crud]`
generates runs its `Repo` call inside one — the transaction a `POST` commits
in — so an app importing `PostsHttpModule` without the binding never boots: the
access graph refuses it, naming the line to add, before a request could reach
the table. The configuration uses the framework's dual-path rule — import the
module bare and let env vars supply it, or pin a value with its `for_root`.

The data layer crates are
[**`nest-rs-database`**](https://github.com/YV17labs/NestRS/tree/main/crates/nest-rs-database)
(the store-agnostic seam) and
[**`nest-rs-seaorm`**](https://github.com/YV17labs/NestRS/tree/main/crates/nest-rs-seaorm)
(the SeaORM implementation, on top of [SeaORM](https://www.sea-ql.org/SeaORM/)).

No manifest line moves: the workspace's `nest-rs` already carries `seaorm`,
and `http` beside it turns on the hooks the HTTP data layer needs when a
controller reaches the database through `Repo`.

## A migration for the post table

`nestrs new` ships a `migrations` crate holding every SeaORM migration, plus
the `migrate` binary the `nestrs run db …` verbs drive. `nestrs g resource`
wrote the `post` table's migration into it on page 2, from the column list
that wrote the entity, and registered it in **both** `lib.rs` and
`migrator.rs` — the pair people forget by hand. `migrator.rs` is regenerated
from `lib.rs`'s list, so the two can never disagree:

<FileTree>
- crates/migrations/
  - src/
    - lib.rs
    - migrator.rs
    - m20260609_000000_create_posts.rs
    - bin/
      - migrate.rs
</FileTree>

It creates the columns `Post` declares, the key and the three timestamps
`timestamps` and `soft_delete` read included, each in the builder and as a
variant of the enum, which `DeriveIden` writes into the DDL:

```rust title="crates/migrations/src/m20260609_000000_create_posts.rs"
use sea_orm_migration::prelude::*;

#[derive(DeriveMigrationName)]
pub struct Migration;

#[async_trait::async_trait]
impl MigrationTrait for Migration {
    async fn up(&self, manager: &SchemaManager) -> Result<(), DbErr> {
        manager
            .create_table(
                Table::create()
                    .table(Post::Table)
                    .if_not_exists()
                    .col(ColumnDef::new(Post::Id).uuid().not_null().primary_key())
                    .col(ColumnDef::new(Post::Title).string().not_null())
                    .col(ColumnDef::new(Post::Body).text().not_null())
                    .col(
                        ColumnDef::new(Post::CreatedAt)
                            .timestamp_with_time_zone()
                            .not_null()
                            .default(Expr::current_timestamp()),
                    )
                    .col(
                        ColumnDef::new(Post::UpdatedAt)
                            .timestamp_with_time_zone()
                            .not_null()
                            .default(Expr::current_timestamp()),
                    )
                    .col(
                        ColumnDef::new(Post::DeletedAt)
                            .timestamp_with_time_zone()
                            .null(),
                    )
                    .to_owned(),
            )
            .await
    }

    async fn down(&self, manager: &SchemaManager) -> Result<(), DbErr> {
        manager
            .drop_table(Table::drop().table(Post::Table).to_owned())
            .await
    }
}

// `DeriveIden` snake-cases these into SQL: this enum writes the
// `post` table and its columns. Rename it if your entity's
// `#[sea_orm(table_name = "…")]` says otherwise — the two must agree.
#[derive(DeriveIden)]
enum Post {
    Table,
    Id,
    Title,
    Body,
    CreatedAt,
    UpdatedAt,
    DeletedAt,
}
```

The file name carries the day you ran `nestrs g resource`; yours differs from
the one above. A later change to the table takes a migration of its own,
named for what it does — `nestrs g migration add_status_to_posts` writes one
for you to fill — since the database that applied this one never runs it
again. The reference workspace lists other migrations (`org`, `user`, …) for
`api`. Your tutorial migrator only needs `post` until you extend the
workspace.

## Run Postgres

`nestrs new` scaffolds a `compose.yml` with Postgres, Valkey and an S3 object
store, and the committed `.env.development` and `.env.test` already point
`<PREFIX>_SEAORM__URL` at it — never `.env`, which production reads too, so a
deployment cannot fall back to a plaintext local URL. The credentials
are the **workspace** name, not the app's — a workspace scaffolded with
`nestrs new hello` gets `postgres://hello:hello@localhost:5432/hello?sslmode=disable`, whatever
its apps are called. Bring the services up once:

```bash frame="terminal"
$ docker compose up -d
✔ Container hello-postgres-1         Started
✔ Container hello-redis-1            Started
✔ Container hello-storage-1          Healthy
✔ Container hello-storage-buckets-1  Started

$ nestrs run db up
INFO sea_orm_migration::migrator::exec: Applying migration 'm20260609_000000_create_posts'
INFO sea_orm_migration::migrator::exec: Migration 'm20260609_000000_create_posts' has been applied
```

`blog` reaches Postgres alone; the store and Valkey wait for a feature that
needs them.

`nestrs run db up` runs `Migrator::up` against `<PREFIX>_SEAORM__URL`. The
binary resolves it through `connect_from_env`, which reads the same `.env`
cascade the apps do — a tool and its app can never end up pointed at different
databases. `db.just` declares the development profile for every `db` recipe,
as `nestrs run dev` does for the app.

## Transactions wrap mutating routes automatically

Every request runs in the unit of work `SeaOrmDatabaseModule` binds, which reads
the HTTP method and installs the right executor before the handler runs:

| HTTP method | Ambient executor |
|-------------|------------------|
| `GET` / `HEAD` / `OPTIONS` / `TRACE` | Pool — no transaction, each statement commits on its own |
| `POST` / `PATCH` / `PUT` / `DELETE` | Transaction, opened on the first statement — committed on 2xx/3xx, rolled back otherwise |

The contract you write code against: on a mutating method, every success
commits and every error response unwinds. A safe method has nothing to
unwind — a `GET` that writes keeps its write, whatever it answers. No
`tx.begin()` / `tx.commit()` in the service.

## Run the binary

```bash frame="terminal"
$ nestrs run dev blog
INFO nest_rs::app: app starting app="blog" version="0.1.0" framework="7.0.0"
INFO nest_rs::orm: connecting to database endpoint=localhost:5432 max_connections=10
INFO nest_rs::app: app ready transports="http" addresses="0.0.0.0:3001"
```

`connecting to database` names Postgres by host and port, never by its URL,
which carries the credentials. The boot dials one connection before the pool
opens: credentials Postgres refuses stop it at once, and a server still
starting is retried within the connect budget, one `warn` per attempt.

The route table — the `nest_rs::routes` target prints every mount — shows
the full CRUD surface of one `#[crud]` block, before you wrote a single
handler body, beside the greeting and the development token route:

```text frame="terminal"
INFO nest_rs::routes: mounted host="DevTokenController" method="dev_token" verb="POST" path="/auth/dev-token"
INFO nest_rs::routes: mounted host="PostsController" method="list" verb="GET" path="/posts"
INFO nest_rs::routes: mounted host="PostsController" method="create" verb="POST" path="/posts"
INFO nest_rs::routes: mounted host="PostsController" method="get" verb="GET" path="/posts/{id}"
INFO nest_rs::routes: mounted host="PostsController" method="update" verb="PUT" path="/posts/{id}"
INFO nest_rs::routes: mounted host="PostsController" method="delete" verb="DELETE" path="/posts/{id}"
```

Every route is behind the guards `nestrs g resource` bound, which you read on the
previous page, so an anonymous call stops at the door:

```bash frame="terminal"
$ curl -s -o /dev/null -w '%{http_code}\n' http://localhost:3001/posts
401
```

```text frame="terminal"
WARN nest_rs::authn: guard denied the request guard="AuthnGuard<JwtStrategy<Claims>>" unit="http.request" host="PostsController" method="list" verb="GET" path="/posts" status=401 reason="missing_credentials" error="missing credentials" trace_id=01a190f2f5e277bda79f735006bdcc6b span_id=0b5f30d871801957
```

One denial, one line, filed by the edge on the target of the guard that
decided it. It names the route by the `host`, `method`, `verb` and `path` of
its `mounted` line above, so a filter on any of them finds both. It carries the
request's `trace_id`, and no `actor_id` — nobody was authenticated, which is
the whole story of a `401`. Drop
`#[use_guards(...)]` from the controller and the boot refuses instead,
naming every route no guard covers: a route runs a guard, or says
`#[public]`.

A call needs a bearer token. The auth adapter `nestrs g resource` wrote serves
one route that mints them —
signed with the `<PREFIX>_AUTHN__SECRET` it drew into `.env.local`, issued by
`blog` to itself (its origin, which `apps/blog/.env` names as both issuer and
audience), and refusing to boot anywhere but development and test:

```bash frame="terminal"
$ TOKEN=$(curl -s -X POST http://localhost:3001/auth/dev-token \
    -H 'Content-Type: application/json' -d '{}' | jq -r .access_token)
```

Pass `{"roles": ["admin"]}` for an admin token, or a `sub` to pin the subject.
The real login is yours to write — what counts as a credential and where users
live are domain decisions, and [Add a login route](/security/add-login/) is the
pattern. Delete `crates/features/src/authn/http/` the day you write it.

```bash frame="terminal"
$ curl -s -X POST http://localhost:3001/posts -H "Authorization: Bearer $TOKEN" \
    -H 'Content-Type: application/json' -d '{"title":"Hello","body":"World"}'
{"id":"019f9bd5-725d-7ee2-8031-b45d3aa4cc7a","title":"Hello","body":"World","created_at":"2026-…","updated_at":"2026-…"}

$ curl -s http://localhost:3001/posts -H "Authorization: Bearer $TOKEN"
[{"id":"019f9bd5-725d-7ee2-8031-b45d3aa4cc7a","title":"Hello","body":"World","created_at":"2026-…","updated_at":"2026-…"}]
```

**No row crosses the data layer without an ability.** `Repo` ANDs
`Ability::condition_for` into every read and every by-id write, and a request
with no ability at all is filtered to nothing rather than granted everything —
fail-closed, deliberately. Drop the `ab.can(Action::Manage, post::Entity)` you
added on the previous page and the same two calls answer `403` with an empty
table behind them.

Create a second post with the same title — there is no unique constraint
on `title`, so both rows persist. Transaction rollback on a `5xx` is what
the e2e suite in [Test it end to end](/tutorial/testing/) locks down when
you add richer failure paths; for now, trust the unit-of-work contract
above.

<Aside type="tip">
Set `RUST_LOG=nest_rs::orm=trace` to watch `Repo`'s own events, such as
`instance check` on a by-id load. Each line carries the request's `trace_id`.
</Aside>

## What you have now

- Postgres running beside `blog`, and the data layer `g resource` wired —
  the five CRUD routes mount.
- The `post` table's migration, applied through `nestrs run db up`.
- `POST /posts` persisting into Postgres inside an automatic
  transaction, scoped by the caller's ability.

<Aside type="note">
`blog` grants one blanket rule, so row-level filtering and response masking are
present but not yet *doing* anything. [Authenticate and
authorize](/tutorial/security/) replaces it with per-caller conditions and field
grants — the layers you saw enforced on [See the security
payoff](/tutorial/checkpoint/).
</Aside>
