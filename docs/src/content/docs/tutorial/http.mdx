You write the service that owns the entity, the controller that declares
the CRUD routes, and the HTTP module that ties them together. By the end
of this page, the boot refuses, naming the one line the data layer still
needs. The next page, [Persist through Postgres](/tutorial/database/),
adds it: the five routes of one empty `#[crud]` impl mount, and the first
`curl` returns a post.

## The service

A service is the entity's single DB gateway. Every read and write goes
through `Repo<Posts>`; controllers, resolvers, gateways never touch
SeaORM directly. The HTTP layer in this section drives a service that
implements `CrudService` — that trait is what the `#[crud(...)]` macro
on the controller expands against.

The service crate here is
[**`nest-rs-seaorm`**](https://github.com/YV17labs/NestRS/tree/main/crates/nest-rs-seaorm) —
it provides `CrudService`, `Repo`, `ServiceError`, and the SeaORM
integration. SeaORM stays the source of truth for the column types and
the active-model semantics.

```rust title="crates/features/src/posts/service.rs"
use nest_rs::core::injectable;
use nest_rs::seaorm::{Creatable, CrudService, Deletable, Updatable};

use super::entity::{CreatePost, Entity as Posts, UpdatePost};

#[injectable]
pub struct PostsService;

impl CrudService for PostsService {
    type Entity = Posts;
}

impl Creatable for PostsService {
    type Create = CreatePost;
}

impl Updatable for PostsService {
    type Update = UpdatePost;
}

impl Deletable for PostsService {}
```

`#[injectable]` marks the struct as a provider — the container builds
it once and shares it as `Arc<PostsService>`. `CrudService` carries the
**read** half — it names the entity, and every resource implements it.
Writes are **opt-in traits**: `Creatable` (`type Create`), `Updatable`
(`type Update`), and `Deletable` — a resource implements each only when
it genuinely offers that operation. A read-only projection implements
`CrudService` alone and declares no write trait. No custom methods yet:
the read half plus these three write impls give a bare CRUD feature its
full surface.

Every `Repo::<Posts>` call runs on the ambient executor — the pool on safe
routes, the transaction on mutating routes. You don't pass it in; the
data layer installs it before the handler runs
([Persist through Postgres](/tutorial/database/) makes that concrete).

Register the service in the port module:

```rust title="crates/features/src/posts/module.rs"
use nest_rs::core::module;

use super::service::PostsService;

#[module(providers = [PostsService])]
pub struct PostsModule;
```

## The controller

A controller is a struct with `#[controller(path = ...)]` and a
`#[crud(service = svc)]` impl block naming the field that holds the
service. The macro generates every CRUD verb — `list`, `get`, `create`,
`update`, `delete` — and reads every type they name off that service: the
entity off `CrudService`, the bodies off `Creatable` and `Updatable`, and
the answer off the entity's `#[expose(name = "Post")]`. Each verb reads its
trait, so a resource missing one — a `create` with no `Creatable` impl — is
a build break, not a silent no-op; `ops = [list, get]` lists the verbs a
read-only resource has. You don't write handler bodies unless you need
domain logic the trait doesn't cover.

```rust title="crates/features/src/posts/http/controller.rs"
use std::sync::Arc;

use nest_rs::http::{controller, crud};

use crate::authn::AuthnGuard;
use crate::authz::AuthzGuard;
use crate::posts::PostsService;

#[controller(path = "/posts")]
#[use_guards(AuthnGuard, AuthzGuard)]
pub struct PostsController {
    #[inject]
    svc: Arc<PostsService>,
}

#[crud(service = svc)]
impl PostsController {}
```

## Every read is filtered by its caller, starting here

From this line on, no row crosses the data layer without someone to answer for
it. `Repo` ANDs the caller's ambient [`Ability`](/security/authorization/) into
every read and every by-id write; nothing but `AuthzGuard` installs one, so a
request with no ability reads **nothing** rather than everything. That is the framework's central claim doing its work: row-level filtering
you never write a `WHERE` for. The price is that it starts now rather than
later — there is no "skip auth for now" switch: even a public read runs under
an ability, the one your `AbilityFactory`'s `define_visitor` grants an
anonymous caller.

`AuthnGuard` and `AuthzGuard` are **your** types, not framework ones: the
framework is generic over the principal and the policy, so each workspace writes
them once. Generate them:

```bash
nestrs g auth
```

That writes `crates/features/src/{authn,authz}/`, adds the modules to the app,
draws two random `<PREFIX>_AUTHN__SECRET`s — yours into the git-ignored
`.env.local`, the test suites' into `.env.test` — and gives you
`POST /auth/dev-token`, the route the next page gets its bearer token from —
behind the framework's `DevelopmentOnlyGuard`, which refuses the boot anywhere
but development and test, so the file holds only the handler building your
`Claims`. The committed `.env`, which every environment reads, holds no
secret: a deployment sets its own.
Then grant the ability — the policy starts empty, so `Post` needs a rule:

```rust title="crates/features/src/authz/ability.rs" {2, 8}
use nest_rs::authz::{AbilityBuilder, AbilityFactory, Action};
use crate::posts as post;

impl AbilityFactory for AuthzAbility {
    type Actor = Claims;

    fn define(&self, _actor: &Claims, ab: &mut AbilityBuilder) {
        ab.can(Action::Manage, post::Entity);
    }
}
```

`Manage` is every action on `Post`, unconditionally — the smallest rule that
lets the tutorial move. [Authenticate and authorize](/tutorial/security/)
narrows it down to what a given caller may actually touch.

## The HTTP module

The feature's HTTP adapter is a separate module. It imports the port
(`PostsModule`), `AuthzModule`, which is what makes the ability guard
reachable — omit it and the access graph fails the boot by name — and
`HttpModule`, the server its controller is served on, so an app importing the
adapter serves it.

```rust title="crates/features/src/posts/http/module.rs"
use nest_rs::core::module;
use nest_rs::http::HttpModule;

use super::controller::PostsController;
use crate::authz::AuthzModule;
use crate::posts::PostsModule;

#[module(
    imports = [PostsModule, AuthzModule, HttpModule],
    providers = [PostsController],
)]
pub struct PostsHttpModule;
```

```rust title="crates/features/src/posts/http/mod.rs"
mod controller;
mod module;

pub use controller::PostsController;
pub use module::PostsHttpModule;
```

Add the adapter to the feature root:

```rust title="crates/features/src/posts/mod.rs"
mod entity;
mod module;
mod service;

pub mod http;

pub use entity::*;
pub use module::PostsModule;
pub use service::PostsService;

pub use http::{PostsController, PostsHttpModule};
```

## Wire it in

The app root imports the feature's HTTP adapter beside the greeting one the
scaffold wired on page 1.

```rust title="apps/blog/src/module.rs"
use nest_rs::core::module;

use features::blog::BlogHttpModule;
use features::posts::PostsHttpModule;

#[module(imports = [
    BlogHttpModule,
    PostsHttpModule,
])]
pub struct BlogModule;
```

`BlogHttpModule` is the scaffold's greeting on `/`. Drop the import and delete
`crates/features/src/blog/` whenever you want — it exists so page 1 had
something to prove.

`PostsHttpModule` imports `AuthzModule`, and `AuthzModule` imports
`AuthnModule`, so the root lists the edges it serves and nothing they bring:
the access graph checks each import where it is used.

No manifest line moves: `apps/blog/Cargo.toml` has depended on `features`
since `nestrs new`.

The port `3005` is what the reference workspace pins — yours may differ
if other apps already occupy it when you ran `nestrs new blog`.

## Run it

```bash frame="terminal"
$ nestrs run dev blog
Error: unmet dependency: `PostsController` (in module `PostsHttpModule`) depends on `dyn UnitOfWork`, which no module this app imports provides. Import exactly one unit-of-work binding: `nest_rs::seaorm::SeaOrmDatabaseModule` runs every edge's units of work over SeaORM's executor.
```

The boot stops before a route mounts, and that is the framework doing its
job. Every route `#[crud]` generates runs its `Repo` call inside a unit of
work — the transaction a `POST` commits in — and nothing in this app binds
one yet. The declaration alone says so, so the boot names the line to add
rather than answering `500` to the first request that reaches the table.

## What you have now

- A `PostsService` that owns the entity through `Repo<Posts>`.
- A `PostsController` with the full CRUD surface `#[crud]` generated,
  behind `AuthnGuard` + `AuthzGuard`.
- An `AuthzAbility` granting `Manage` on `Post`.
- A `PostsHttpModule` imported by the app, and a boot naming the one
  binding still missing.
