You ship one feature — **`posts`** — into the [**Publish**](/publish/) story's
**`blog`** app: entity, service, a `PostsController` behind the guards,
validation, Postgres, and an e2e test. Each page leaves you with code that
compiles and a command you can run.

**Pages 1–7 build your `blog`. Pages 8 to 10 read the reference `api`, and
apply what it shows to `blog`.** That is a deliberate switch, and worth knowing
before you reach it: `blog`'s `Post`
has an id, a title and a body — no tenant column, no relation — because a small
domain is what makes pages 2 to 7 short. Per-caller row filtering and an
auto-resolved GraphQL relation both need a domain that has those things, so
pages 8 and 10 walk through the feature that does (`api`'s `users`) rather than
first sending you to add a column you have no use for. Each leads back to your
own `blog`: page 9 narrows its policy, page 10 adds a GraphQL resolver to `posts`.

## What you end up with

`hello` for the quick-start binary, `apps/blog/` for the tutorial app, a
`posts/` feature over HTTP and then GraphQL, its table's migration, and the
auth adapter `nestrs g resource` writes with it on page 2 — a DB-backed route
is guarded from its first request.

Two `curl`s against the running binary, carrying the development token
`POST /auth/dev-token` mints on
[Persist through Postgres](/tutorial/database/). The bearer is not optional:
`Repo` filters every read by the caller's ability, so the guards go on with
the database, not later.

```bash frame="terminal"
$ curl -s -X POST http://localhost:3001/posts -H "Authorization: Bearer $TOKEN" \
    -H 'Content-Type: application/json' \
    -d '{"title":"Hello","body":"World"}'
{"id":"018f…","title":"Hello","body":"World","created_at":"2026-…","updated_at":"2026-…"}

$ curl -s http://localhost:3001/posts/018f… -H "Authorization: Bearer $TOKEN"
{"id":"018f…","title":"Hello","body":"World","created_at":"2026-…","updated_at":"2026-…"}
```

And a passing e2e suite:

```bash frame="terminal"
$ nestrs run test e2e
         PASS [   …] blog::e2e posts::posts_round_trip
```

## What you should know going in

- A **workspace** scaffolded per [Getting started](/getting-started/) —
  the [`nestrs` CLI](/cli/) installed and `nestrs run dev hello` serving
  `Hello World` from `crates/features/src/hello/`.
- **Rust 1.97+**, and enough of [Fundamentals](/fundamentals/),
  [Configuration](/configuration/), and [HTTP](/http/) that module,
  provider, and controller are familiar terms.
- **Docker** available — the database and testing pages need Postgres
  (`docker compose up -d`, the services `nestrs new` scaffolded); earlier
  pages run without one.
- Page 1 adds `apps/blog/` with `nestrs new blog`; everything after that
  happens in `blog`, not `hello`, and every command runs from the workspace
  root.

<Aside type="note">
If you cloned **this** repository to explore Publish, scaffold `hello` and
`blog` in a separate workspace — they are not hosted here.
</Aside>
