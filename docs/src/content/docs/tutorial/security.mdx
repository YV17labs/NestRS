</Aside>

This is the feature behind [See the security payoff](/tutorial/checkpoint/)
— now you read how it is built. Your `blog` already carries the same two
guards from [Expose over HTTP](/tutorial/http/), with one blanket `Manage`
rule standing in for a real policy. Here that policy gets teeth: the framework
filters every read by the caller's organisation, gates every by-id load against
their ability, and masks the response before it leaves the process. By the end
of this page, a cross-tenant `GET /users/{id}` returns `403`, a plain user sees
only their org, and the `email` column disappears from a non-admin listing.

## Two layers, two guards

Authentication and authorization are different jobs handled by different
crates. The reference feature wires both:

- **`AuthnGuard`** lives in
  [**`nest-rs-authn`**](https://github.com/YV17labs/NestRS/tree/main/crates/nest-rs-authn).
  A `Strategy` turns the request into a principal — for a resource
  server, that's `JwtStrategy<Claims>` verifying a `Bearer` token.
- **`AuthzGuard`** lives in
  [**`nest-rs-authz`**](https://github.com/YV17labs/NestRS/tree/main/crates/nest-rs-authz).
  It seeds the ambient `Ability` from the principal and an `AbilityFactory`.

Two crates, one binding on the controller. The reference feature
re-exports both under `crates/features/src/authn/` and `authz/`; the
tutorial reuses those aliases.

## The principal

A resource server pins a single alias once. The reference feature's
`Claims` carries an org id and a role set — exactly what authz reads
back.

```rust title="crates/features/src/authn/strategy.rs (from the demo)"
use nest_rs::authn::JwtStrategy;

use super::Claims;

pub type AuthnStrategy = JwtStrategy<Claims>;

pub type AuthnGuard = nest_rs::authn::AuthnGuard<AuthnStrategy>;
```

`JwtStrategy<Claims>` is provided by `nest-rs-authn`. On a missing or
expired token it returns `401` automatically — the controller never
sees the request.

Both aliases, their modules, and the `Claims` above are what
[`nestrs g auth`](/cli/#generate-features-and-adapters) writes. They are app
code by necessity — the framework is generic over the principal and the policy,
so it cannot ship a `Claims` or an `AuthzAbility` for you.

## The policy

`AuthzAbility` is the single source of truth for *what each role may do*.
Admins manage their org's users; plain users read a scoped, redacted
view. The reference policy fits in one method:

```rust title="crates/features/src/authz/ability.rs (from the demo, abridged)"
use nest_rs::authz::{AbilityBuilder, AbilityFactory, Action};
use nest_rs::core::injectable;

// …
use crate::Claims;
// …
use crate::users as user;

#[injectable]
pub struct AuthzAbility;

impl AbilityFactory for AuthzAbility {
    type Actor = Claims;

    fn define(&self, actor: &Claims, ab: &mut AbilityBuilder) {
        if actor.is_admin() {
            // …
            ab.can(Action::Manage, user::Entity)
                .when(|p| p.eq(user::Column::OrgId, actor.org_id));
            // …
        } else {
            ab.can(Action::Read, user::Entity)
                .when(|p| p.eq(user::Column::OrgId, actor.org_id))
                .fields([user::Column::Id, user::Column::Name]);
            ab.can(Action::Create, user::Entity)
                .when(|p| p.eq(user::Column::OrgId, actor.org_id));
            // …
        }
        // …
    }
}
```

Two patterns to read here:

- **`.when(|p| p.eq(Column::OrgId, actor.org_id))`** is the row-level
  rule — every read and every by-id write the caller issues filters by
  that condition. Cross-tenant access becomes structurally impossible.
- **`.fields([...])`** is the field-level rule — when a plain user
  reads a `User`, only the listed columns survive the response masker;
  `email` is dropped before the body leaves the process.

## Bind the guards on the controller

The controller gains one attribute: the guard chain on the struct. Every
operation `#[crud]` generates declares its own posture, the create included.

```rust title="crates/features/src/users/http/controller.rs (from the demo, abridged)" {5-6, 10}
use std::sync::Arc;

use nest_rs::http::{controller, crud};

use crate::authn::AuthnGuard;
use crate::authz::AuthzGuard;
use crate::users::UsersService;

#[controller(path = "/users")]
#[use_guards(AuthnGuard, AuthzGuard)]
pub struct UsersController {
    #[inject]
    svc: Arc<UsersService>,
}

#[crud(
    service = UsersService,
    // … api(get(…), create(…))
)]
impl UsersController {}
```

| Piece | Job |
|-------|-----|
| `#[use_guards(AuthnGuard, AuthzGuard)]` | Run authn then authz on every route in the controller |
| `#[crud]`'s generated `get` | Declares `#[authorize(Read, UserEntity)]`: parse the `{id}`, load the row through the service, `404` if absent, `403` if the ability refuses it |
| `#[crud]`'s generated `create` | Declares `#[authorize(Create, UserEntity)]`, fills the columns the caller's `Create` grant pins, re-checks the fresh row against it, and answers `201` with its `Location` |

The org id comes from the caller's grant, never from the body. `CreateUser`
has no `org_id`, and the rule `p.eq(Column::OrgId, actor.org_id)` that
filters reads also decides the column on a create: `Creatable::create` fills
what the grant pins and the input left unset, then checks the row in SQL. There
is no placeholder to fill in, no hand-written create, and no way to spoof the
tenant.

## Import the authz module

The HTTP adapter imports the authz module, as `blog`'s `PostsHttpModule` has
since `nestrs g resource` wrote it:

```rust title="crates/features/src/users/http/module.rs (from the demo)" {4, 8}
use nest_rs::core::module;

use super::controller::UsersController;
use crate::authz::AuthzModule;
use crate::users::UsersModule;

#[module(
    imports = [UsersModule, AuthzModule],
    providers = [UsersController],
)]
pub struct UsersHttpModule;
```

`AuthzModule` carries the `AuthzGuard` provider and the response
masker. Forgetting the import is caught at boot by the access graph —
the binary fails to start with a clear "missing guard" error rather
than running silently unprotected.

The app root — `api`, not `blog` — lists the adapter, and nothing it brings:
`AuthzModule` reaches it through `UsersHttpModule`, and `AuthnModule` through
`AuthzModule`, where the access graph checks each import. Its one provider,
[`GlobalGuards`](/fundamentals/guards/#the-three-scopes), puts the two guards
in the app-wide pool every route runs first; `blog` declares none, its
controllers binding theirs.

```rust title="apps/api/src/module.rs (from the demo, abridged)"
use nest_rs::core::module;
use nest_rs::guards::GlobalGuards;
// …
use nest_rs::seaorm::SeaOrmDatabaseModule;
// …
use features::authn::AuthnGuard;
use features::authz::AuthzGuard;
// …
use features::users::{UsersGraphqlModule, UsersHttpModule};

#[module(
    imports = [
        // …
        SeaOrmDatabaseModule,
        // …
        UsersHttpModule,
        // …
    ],
    providers = [GlobalGuards<(AuthnGuard, AuthzGuard)>],
)]
pub struct ApiModule;
```

## What changed at runtime

Three behaviours land without writing them in the handler.

**Row-level filter on every read.** A plain user issuing
`GET /users` gets `WHERE org_id = $caller_org_id` appended to the
SQL — the `Repo::scoped(Action::Read)` `CrudService::list` uses joins
the ambient ability's `condition_for(Read)`.

**By-id load checks access.** The generated `get` parses the `{id}`
path segment, loads the row through the service, runs the ability check
— as a route of yours does when it declares
`#[authorize(Read, bind = UsersService)]` and takes the row as an
`Authorized<Read, UserEntity>`. Three failure shapes:

| Caller's view | Status |
|---------------|--------|
| The row doesn't exist | `404` |
| The row exists but the ability refuses it | `403` |
| The `{id}` segment isn't a valid UUID | `400` |

`403` (rather than `404`) on a denied-but-existing row discloses that the
row exists — the standard REST trade-off, chosen here so a client can
tell "not yours" from "not there". Collapse the `403` into a `404` when
existence itself is confidential: see [by-id
binding](/security/authorization/by-id-binding/). A `500` would mean the ambient ability
didn't install; that's a wiring bug.

**Response masking on every body.** The masker runs after the handler
returns. It reconstructs the full `User` model from the body, walks
`Ability::mask`, and drops any column outside the caller's
`.fields([...])` grant. A plain user's listing returns:

```json
[{ "id": "018f…", "name": "Bob" }]
```

— no `email`, even though the handler returned a `Json<User>` that
included it. Forgetting per-handler redaction is structurally
impossible.

## See it for yourself

A short check from the reference e2e:

```bash frame="terminal"
$ curl -i -H 'Authorization: Bearer <plain-user-token-for-org-A>' \
    http://localhost:3002/users/<user-in-org-B>
HTTP/1.1 403 Forbidden

$ curl -s -H 'Authorization: Bearer <plain-user-token>' \
    http://localhost:3002/users
[{"id":"018f…","name":"Bob"}]
```

The email is gone, the cross-tenant load is refused, and the handler
never had to know.

## Now narrow your own `blog`

Step 4 left `posts` on one blanket rule — `Action::Manage` for everybody.
Rewriting `define` in `crates/features/src/authz/ability.rs` turns it into a
policy, using only the columns `blog` already has:

```rust title="crates/features/src/authz/ability.rs" {21-25}
use nest_rs::authz::{AbilityBuilder, AbilityFactory, Action};
use nest_rs::core::injectable;

use crate::authn::Claims;
use crate::posts as post;

#[injectable]
pub struct AuthzAbility;

impl AbilityFactory for AuthzAbility {
    type Actor = Claims;

    /// Every rule this app grants, keyed off the authenticated actor. Nothing
    /// is granted until you add a `can` here — reads return 403 and no row
    /// crosses the data layer.
    ///
    /// `nestrs g resource <name>` prints the grant to paste for the resource it
    /// just generated, with `_ab` renamed `ab`; narrow it to a user's own rows
    /// with `.when(|p| p.eq(Column::AuthorId, user_id))` under
    /// `if let Some(user_id) = actor.sub.user_id()` — a client owns none.
    fn define(&self, actor: &Claims, ab: &mut AbilityBuilder) {
        ab.can(Action::Read, post::Entity);
        if actor.is_admin() {
            ab.can(Action::Manage, post::Entity);
        }
    }

    /// What an *unauthenticated* caller may do, on what `#[public(Action, Entity)]`
    /// opens. Empty on purpose: nothing is public until you say so here, and a
    /// route naming its read still serves no row without a grant — a
    /// `can(Action::Read, …)` narrowed by `.when(…)` to the rows meant for
    /// anyone.
    ///
    /// Such a route reached with a valid token uses `define` instead — this branch
    /// answers only for the visitor.
    fn define_visitor(&self, _ab: &mut AbilityBuilder) {}
}
```

Anyone signed in may read; only an admin may write. The suite you finished on
page 7 signs its tokens as a plain user, so its writes now answer `403`: sign
them as an admin, and pin the refusal a plain user gets — the policy is as
much the feature as its routes:

```rust title="apps/blog/tests/e2e/posts.rs" {9, 12, 19, 50, 68-78}
use nest_rs::http::StatusCode;
use serde_json::json;
use uuid::Uuid;

use features::authn::{Claims, Role, Subject};

use crate::boot;

fn bearer(app: &nest_rs::testing::TestApp, role: Role) -> String {
    app.bearer(&Claims {
        sub: Subject::User(Uuid::now_v7()),
        roles: vec![role],
    })
}

#[tokio::test]
async fn posts_round_trip() {
    let app = boot().await;
    let bearer = bearer(&app, Role::Admin);

    let created = app
        .http()
        .post("/posts")
        .header("authorization", &bearer)
        .body_json(&json!({ "title": "Title 1", "body": "Body 1" }))
        .send()
        .await;
    created.assert_status(StatusCode::CREATED);
    let created = created.json().await;
    let id = created.value().object().get("id").string().to_owned();

    let read = app
        .http()
        .get(format!("/posts/{id}"))
        .header("authorization", &bearer)
        .send()
        .await;
    read.assert_status_is_ok();
    let read = read.json().await;
    let fields = read.value().object();
    assert_eq!(fields.get("title").string(), "Title 1");
    assert_eq!(fields.get("body").string(), "Body 1");
}

#[tokio::test]
async fn create_with_empty_title_returns_400() {
    let app = boot().await;
    app.http()
        .post("/posts")
        .header("authorization", bearer(&app, Role::Admin))
        .body_json(&json!({ "title": "", "body": "Body 1" }))
        .send()
        .await
        .assert_status(StatusCode::BAD_REQUEST);
}

#[tokio::test]
async fn create_without_a_token_returns_401() {
    let app = boot().await;
    app.http()
        .post("/posts")
        .body_json(&json!({ "title": "Title 1", "body": "Body 1" }))
        .send()
        .await
        .assert_status(StatusCode::UNAUTHORIZED);
}

#[tokio::test]
async fn a_plain_user_cannot_create_a_post() {
    let app = boot().await;
    app.http()
        .post("/posts")
        .header("authorization", bearer(&app, Role::User))
        .body_json(&json!({ "title": "Title 1", "body": "Body 1" }))
        .send()
        .await
        .assert_status(StatusCode::FORBIDDEN);
}
```

Restart, mint a plain token and a `{"roles":["admin"]}` one from
`POST /auth/dev-token`, and `POST /posts` answers `201` for the second and
`403` for the first — with no check in the handler. That is the same mechanism
this page just walked through, at the size your domain is.

## What the reference feature has

- A `UsersController` guarded by `AuthnGuard` + `AuthzGuard` — every
  route requires a valid JWT and a matching ability.
- An `AuthzAbility` policy that scopes reads to the caller's org and
  masks the email column for plain users.
- A by-id route that loads through the service — `403` on a denied
  row, `404` on a missing one, both without manual checks.
