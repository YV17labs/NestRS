A WebSocket upgrade is an HTTP `GET`, so a gateway **self-mounts** on the
existing `HttpTransport` — same port, same CORS, same TLS, no second
server. Every frame rides one JSON envelope, `{ "event": "...", "data":
... }`, and each `#[subscribe_message("event")]` method handles one
event. List the gateway in `#[module(providers = [...])]` and you have
real-time wired in.

Read this section, then start from the working reference: the
[`live`](/publish/) app in Publish — a chat gateway plus org-scoped
notifications, running the exact shapes below.

`nest-rs-ws` speaks the protocol through
[tokio-tungstenite](https://docs.rs/tokio-tungstenite), over the connection the
HTTP transport's own server hands across once it answers the handshake. It
hides the handshake, the read/write split, the outbox writer task, the
connection registry, and the dispatch plumbing behind one decorator.

In the [**Publish**](/publish/) workspace, live comments and notifications
run in [`live`](/publish/) on port **3004**.

## Install

```bash frame="terminal"
cargo add nest-rs --features ws
```

`#[input]` on a typed payload carries its `serde` derives and routes them back
through the framework, and `nest_rs::ws::tracing` is the gateway's logger — so
the manifest stops at one line. `nestrs g ws <feature>` writes it. Add `authz`
when a message carries `#[authorize]`, or `seaorm`, which implies it; the
decorator names the feature when it is missing.

## A one-event gateway

The smallest possible gateway: one event, one reply.

```rust title="crates/features/src/chat/ws/gateway.rs"
use nest_rs::ws::{gateway, messages};

#[gateway(path = "/ws")]
#[derive(Default)]
pub struct PingGateway;

#[messages]
impl PingGateway {
    #[subscribe_message("ping")]
    #[public]
    async fn ping(&self) -> &'static str {
        "pong"
    }
}
```

`#[gateway(path = "/ws")]` mounts on the HTTP transport at `/ws`.
`#[messages]` turns the impl block into a dispatcher: the read loop
parses each frame's envelope, matches the event, deserializes `data`,
calls the handler, and serializes the return into a reply frame on the
same event name.

Each message runs through the same [pipeline](/fundamentals/interceptors/) a
route does, as a unit of its own: the app's interceptors and exception filters
wrap it, and so do the ones the gateway and the message bind — see
[Messages](/websockets/messages/#interceptors-filters-and-pipes).

Wire it in like any other provider:

```rust title="apps/api/src/module.rs"
use nest_rs::core::module;
use nest_rs::http::{HttpConfig, HttpModule};
use nest_rs::ws::WsModule;

use features::chat::PingGateway;

#[module(
    imports = [
        HttpModule::for_root(HttpConfig { port: 3004, ..Default::default() }),
        WsModule,
    ],
    providers = [PingGateway],
)]
pub struct LiveModule;
```

`HttpModule` for the transport, `WsModule` for the connection registry
(`WsServer`). The gateway itself is listed in `providers` — no
`.transport(...)` call, no second port.

`WsModule` is **not optional** for a default-namespace gateway: every
`WsClient` a handler touches reads that registry. A gateway declares the
dependency, so leaving it out fails the boot through the access graph, naming
both the missing type and the module that provides it:

```text frame="terminal"
Error: module access violation: `PingGateway` (in module `LiveModule`) depends on
`WsServer`, but `LiveModule` imports no module that provides it. `WsServer` is
provided by `WsModule` — add `WsModule` to `#[module(imports = [...])]` …
```

Import it in whichever module lists the gateway — `nestrs g ws` writes it into
the generated adapter module. `WsModule` owns the
[`namespace`](/websockets/namespaces/)d registries too, so the import is the
same one step whichever registry a gateway uses.

## Run it

```bash
nestrs run dev live
```

```text frame="terminal"
2026-06-08T10:23:14Z  INFO nest_rs::routes: mounted endpoint kind="ws" path="/ws"
```

Drive it from any WebSocket client. With
[`websocat`](https://github.com/vi/websocat):

```bash frame="terminal"
$ websocat ws://localhost:3004/ws
{"event":"ping","data":null}
{"event":"ping","data":"pong"}
```

The envelope you send is `{event, data}`; the server's reply rides the
same shape on the same event name. From here, every other concern is a
matter of adding one decorator.

A socket can live for hours, so the **message** is the unit of work: each one
opens its own `ws.message` span under the trace and the actor the upgrade
established — see [Correlation](/fundamentals/correlation/).

The whole conversation is legible from the console — the `101` that opened the
socket, the connection, then a line per message, all under the upgrade's trace:

```text frame="terminal"
INFO nest_rs::operation: http.request method=GET route="/ws" status=101 bytes=0 duration_ms=1.265 trace_id=01a015e0074575729557467b3d9e2317 span_id=0aa87fe2893b32d0
INFO nest_rs::operation: ws.connect conn_id=0 outcome="ok" duration_ms=0.093 trace_id=01a015e0074575729557467b3d9e2317 span_id=0aa87fe2893b32d0
INFO nest_rs::operation: ws.message event="message" conn_id=0 outcome="ok" duration_ms=0.045 trace_id=01a015e0074575729557467b3d9e2317 span_id=3398a131c2baa84a
INFO nest_rs::operation: ws.message event="_OTHER" conn_id=0 outcome="error" duration_ms=0.011 trace_id=01a015e0074575729557467b3d9e2317 span_id=2a3f10371aa5cbc8
```

The last message named an event no handler serves. Its line says `_OTHER`
rather than the event it sent, as its span does: a name only the client used is
its own data, and no line the framework files repeats it. The client still gets
`{"event":"nope","data":{"error":"unknown event"}}`, answered on the event it
sent.

Same `trace_id` throughout, a fresh `span_id` per message — because a connection
inherits identity, never resources: it takes the upgrade's trace and actor, and
opens its own request scope per message. Your own handler's events carry the
message's ids without naming them; see [Logs](/opentelemetry/logs/).

## What bounds a socket

`WsModule::for_root(WsConfig { .. })` pins these, and `<PREFIX>_WS__*` overlays
each field:

| Variable | Default | What it bounds |
|---|---|---|
| `<PREFIX>_WS__MAX_CONNECTION_SECS` | `14400` (4 h) | a socket's lifetime, so a credential checked at the upgrade expires with it; whole seconds from `1` to `86400`, `0` ⇒ unlimited |
| `<PREFIX>_WS__MAX_MESSAGE_BYTES` | `65536` (64 KiB) | one inbound frame, refused before it is buffered |
| `<PREFIX>_WS__MESSAGE_TIMEOUT_SECS` | `20` | one message — its guards, pipes and handler — counted once its envelope is decoded; whole seconds from `1` to `3600`, `0` ⇒ none |
| `<PREFIX>_WS__CONNECT_TIMEOUT_SECS` | `20` | the `#[on_connect]` hook, on the message timeout's range |
| `<PREFIX>_WS__DISCONNECT_TIMEOUT_SECS` | `20` | the `#[on_disconnect]` hook, on the message timeout's range |

A socket answers one message at a time, so a handler that never returns would
hold its socket until the connection's lifetime ran out. Past the message
timeout its work is dropped and rolled back, the client gets an error frame on
the message's event, and the socket goes on serving the next one:

```json
{"event":"report","data":{"error":"the message was not answered in time","errors":{"code":"UNAVAILABLE","reason":"timeout"}}}
```

The `ws.message` line files `error`, and one `warn` on `nest_rs::ws` names the
event and the timeout with `reason="timeout"`. The default is the HTTP request
timeout's, inside the 20-second shutdown window; a timeout past
`<PREFIX>_HTTP__SHUTDOWN_TIMEOUT_SECS`, or `0`, is said once per gateway and
unit at boot, since a unit admitted just before a stop could then be cut
unanswered. A handler that legitimately runs longer raises the timeout and the
window together.

A statement the database cancelled at its own bound answers the same `code`,
`UNAVAILABLE`, which is what a client branches on, retrying the message. Only the
gateway's own deadline adds `reason: "timeout"`: the cancelled statement is the
service's answer, rendered as every [problem](/websockets/messages/) is, with
its `retryAfterSeconds` when the bound gives one.

The connection hooks are bounded the same way, each by its own timeout: past
it, the hook's work is dropped and rolled back, its `ws.connect` or
`ws.disconnect` line files `error`, and one `warn` names the unit. A connect hook
cut there leaves the socket set up halfway, so it closes unserved, as one that
panicked does; a disconnect hook cut there lets the close go on.

## When the server refuses a handshake

A gateway's handshake is a `GET`. Any other method is answered by the route
table before anything else runs: `405`, with `Allow: GET, HEAD`. Then the
browser-origin check and the gateway's `#[use_guards]` run, so a refused caller
learns nothing about the handshake. A handshake the server cannot accept is
answered before any socket opens, with a problem document saying what it lacks
(RFC 6455 §4.2.1) and never quoting what was sent:

| The handshake | Status |
|---|---|
| Sent as a `HEAD`, which the route table answers as its `GET` without the content | `400` |
| An `Upgrade` listing no `websocket`, a `Connection` listing no `upgrade`, or a `Sec-WebSocket-Key` that is not 16 bytes in base64 | `400` |
| A `Sec-WebSocket-Version` other than `13` | `426`, with `Sec-WebSocket-Version: 13` |
| Over a connection that cannot switch protocols — HTTP/1.0, or an in-process test client | `426` |

`Upgrade` and `Connection` are lists, read as RFC 9110 reads them:
`Upgrade: h2c, websocket` asks for a WebSocket, and the browser-origin check
reads it the same way.

## When the server closes a socket

The server closes a socket with the RFC 6455 code for the cause, and a reason,
so a client can tell a deliberate close from the `1006` a network fault leaves:

| Cause | Code | What the client does |
|---|---|---|
| The shutdown signal, after the message it is answering | `1001 Going Away` | reconnects, to a replica still serving |
| `<PREFIX>_WS__MAX_CONNECTION_SECS` elapsed | `1001 Going Away` | re-upgrades, and is authenticated again |
| The client stopped reading and its outbox filled | `1008 Policy Violation` | drains faster, or is shed again |
| The client took nothing for `<PREFIX>_HTTP__SEND_TIMEOUT_SECS` (60 s) | none can reach it — it reads `1006` | reconnects |
| A message past `<PREFIX>_WS__MAX_MESSAGE_BYTES` | `1009 Message Too Big` | sends smaller messages |
| A read failed on broken framing | `1011 Internal Error` | reconnects |
| `#[on_connect]` panicked, or outlasted `<PREFIX>_WS__CONNECT_TIMEOUT_SECS` | `1011 Internal Error` | reconnects |

A handler that panics does not close the socket: its `ws.message` line files
`panic`, the client gets the opaque error frame — `internal error`, under
`code: "INTERNAL"` — and the panic's text goes to `nest_rs::ws` at `error`. A message still running when the shutdown
window closes is dropped with its socket, and files `cancelled`.

## Version the socket

`#[gateway(path = "/ws", version = "1")]` serves at `/v1/ws`. It is the same
`version` argument `#[controller]` takes, resolved through the same
`version_path`, because a gateway's mount is an address the client selects —
[the edges where it is not](/http/versioning/) refuse the argument with a named
compile error rather than accept a version nothing could apply.

A gateway owns its mount, so the version is part of that ownership: `version =
"1"` and `version = "2"` on one path are two mounts that both boot with their own
message tables, while two gateways sharing a path *and* a version still fail boot
naming both.

Only the URI form selects a gateway. `<PREFIX>_HTTP__VERSIONING=header` rewrites
controller paths in front of routing and never learns a self-mount's prefixes, so
a versioned gateway stays at `/v1/ws` under every strategy — which is just as
well, since a browser cannot set headers on a `WebSocket` handshake.
